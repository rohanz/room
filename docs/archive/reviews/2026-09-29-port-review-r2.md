## Findings

1. **must-fix — The publication ceiling can permanently wedge an accepted publication and prevent privacy narrowing.** `packages/roomd/src/publisher.ts:110`, `packages/roomd/src/publisher.ts:214`, `packages/roomd/src/publisher.ts:225`; ceiling at `packages/roomd/src/policy.ts:87`.

   The initial plan accepts up to 4,096 disk facts, but subsequent prepares count incoming facts **plus** existing manifest entries **plus** existing overlays, base-text records and room-wide map counts. This is neither a consistent per-path admission bound nor a count of actual mutations. An accepted state can exceed the limit for every subsequent operation, including deletion of that state. Counts also include other participants' base-text records, so unrelated room growth can deny this publisher service.

   **Reproduction:** `/tmp/astra2-probe.mts`, using the real `startRoomd`, a temporary committed repository, local-room mode, a memory provider, and disabled watcher callbacks for deterministic explicit reconciles. Create **2,050 untracked files containing one byte each**, then reconcile:

   - First reconcile: `complete: true`, level `full`, 2,050 shared manifest entries and 2,050 text overlays.
   - Second identical reconcile: `publication path limit exceeded during atomic apply`; `complete: false`; all old entries/text remain. Existing entry+overlay count alone is 4,100.
   - Apply `policyFromLevel('intent')` and drain the queue: `publication path limit exceeded during policy narrowing`; head still says `full`, and every old content hash, size and text remains replicated.
   - Delete all 2,050 disk files and reconcile again: still incomplete, with the same 2,050 shared entries/text. The old-count guard prevents even an empty desired state from clearing them.

   Output is in `/tmp/astra2-probe-local.log`. This is a naturally reachable publication, not an injected oversized map. The added `publication-reconcile.test.ts` oversized-narrowing test checks only `complete: false`; it does not check withdrawal or recovery.

   **Semantics/visibility:** overflow is visible in the daemon log, and readers conservatively see `coverage: none / starting`. Refusing to certify an oversized scan does not itself falsely certify absence as base (§4). However, marking incomplete is not a substitute for the synchronous withdrawal required by manifest §5.1 and D1/invariant 16. The policy is already changed locally while old authorized hashes/text remain in the shared document. A permanent `starting` state also gives the user no actionable path-limit explanation. The new permanent capacity limit is not specified in §4.5/§5.3, and its effective threshold varies with prior state and other people.

   **Fix:** make admission account consistently for the maximum later update/withdrawal cost, and guarantee an atomic withdrawal/reset path for any state already admitted. Narrowing must remove forbidden text and content metadata even when ordinary publication is over budget. Scope accounting to actual affected operations; do not charge another participant's unrelated stored base texts as this participant's update. If a capacity ceiling remains, specify it, expose a distinct actionable incomplete reason, and test initial overflow, repeat publication at the boundary, policy narrowing, full revert, and recovery after reducing the path set. Preserve the single atomic publication transaction.

2. **must-fix — Uncertain claims are kept, but their advertised retry never reanchors them after the HEAD transition succeeds.** `packages/roomd/src/index.ts:989`, `packages/roomd/src/index.ts:758`, `packages/roomd/src/index.ts:789`; budget at `packages/roomd/src/reanchor.ts:35`.

   On budget exhaustion or an oversized/unreadable file, `reanchorOwnClaims` only calls `publisher.markDirty()`. The transition then commits the new HEAD and advances `appliedHead`/refs. Its dirty retry calls `reconcileGitChanges`, whose `pollHead` returns early because HEAD/refs/fence have not changed. The subsequent publisher reconcile has no claim-validation step. The uncertain IDs and their original anchors are not retained as pending work or represented as uncertainty in the shared claim.

   **Reproduction:** the second part of `/tmp/astra2-probe.mts` commits a 245,004-byte file (`old\n` plus 35,000 `filler\n` lines), adds 20 claims on the first line, then commits replacement of `old` by `new`. All claimed blocks are absent, and the worktree is clean. The actual transition releases 7 claims and logs `claim reanchor uncertain for 13 claim(s); keeping them and retrying`. The manifest is **complete**, with 13 stale claims still present. Three further explicit reconciles leave all 13 claims; an instrumented `reanchorOwnClaims` was called **once total**. This uses a file below the normal size cap, so merely special-casing oversized files does not solve it.

   `/tmp/astra2-reanchor-compare.mts` also compares the real helper extracted from `8f70442` with the fixed helper on the same inputs: **before: 20 releases; after: 7 releases, 13 uncertain**. The new helper's bounded CPU behavior is useful; the production retry integration is incomplete.

   This can keep a claim that should be released indefinitely. It does not currently spin forever reanchoring—the retry skips that work altogether. Simply rerunning the same full ordered claim list under the same total budget would introduce starvation as well: early unchanged claims can consume the budget on every retry, and a permanently oversized file never becomes decidable under that rule. Manifest §5.4 says complete publication must not certify the new transition with old claim coordinates.

   **Fix:** retain a fenced pending claim-validation set with the original identity/anchor and resumable work, retry it independently of further HEAD changes, and remove completed claims from that budget. Represent persistent uncertainty explicitly and define recovery for permanently unreadable/oversized claims; do not blindly release an uncertain claim. Guard claim changes and file inputs at the eventual apply. Add an end-to-end test where budget exhaustion happens during a real clean HEAD transition and subsequent retries eventually validate every eligible claim, plus a permanently unreadable case that cannot silently masquerade as a normal validated claim.

3. **must-fix — Moving the final stat gate into a yielding loop allows an already-checked file to change before a publication is certified complete.** `packages/roomd/src/publisher.ts:233`, `packages/roomd/src/publisher.ts:241`, `packages/roomd/src/publisher.ts:260`.

   `validatePrepared` yields between groups of paths, but `valid`/`apply` now check only input-object identity, stop state and fence. Ordinary disk events do not replace that input object: `scheduleDisk` merely queues a batch (`index.ts:1172`). A file checked early in `validatePrepared` can be changed by a callback on a later yield, and no final check notices. This removes the synchronous filesystem revalidation required by manifest §5.3, rather than preserving it under a bound.

   **Reproduction:** `/tmp/astra2-gate-probe.mts` prepares 96 files. At the first `lstat` of `gate-000.txt`, it schedules a `setImmediate` write to that same file, increasing its size before a later validation batch. Actual results:

   ```text
   valid: true
   applied: true
   changed: true
   disk: 'after with different size\n'
   published: 'before\n'
   complete: true
   ```

   The fixture disables watcher callbacks to isolate the validation contract; even a normal delivered callback only queues `scheduleDisk`, not a generation change. This is not a same-size/mtime trick. The newly added validation test mutates the **last, not-yet-checked** file and therefore misses this regression. Before the fix, the stat loop and transaction had no intervening event-loop yield in which this callback could run.

   **Fix:** retain an immediate synchronous filesystem gate over a properly bounded accepted publication, or introduce a proven generation/stability mechanism that invalidates prepared data for changes during the yielding pass. Do not certify `complete` solely because the policy object is unchanged. Test a mutation of the first already-validated path at a later batch boundary, alongside the existing last-path test. Both ordinary publication and the HEAD-transition call to `validatePrepared` need the guarantee.

4. **should-fix — Whole-region merge fallback can throw instead of returning its exact alternatives because it spreads file-sized arrays into function arguments.** `packages/room-mcp/src/merge.ts:111`, `packages/web/src/merged.ts:92`, `packages/web/src/merged.ts:100`.

   The new `diff3WithinBudget` correctly prevents the reported repetitive-line LCS explosion. When it selects a large region, however, MCP calls `rendered.push(marker, ...a, marker, ...o, ..., ...b, marker)`. The web fold similarly spreads complete `ok`/conflict arrays into `push`. These hit the JavaScript argument-count limit well below the 512 KiB publication cap.

   **Reproduction:** `/tmp/astra2-merge-probe.mts` calls the real functions with `base = 'x\n'.repeat(n)`, `a = base + 'a\n'`, and `b = 'b\n' + base`. A temporary Git executable returning 128 forces the real MCP fallback.

   - MCP at **50,000 lines / about 100 KB per input**: `RangeError: Maximum call stack size exceeded` (also at 80,000 lines).
   - Web `classifyThreeWay` at **150,000 lines / about 300 KB per input**: the same error.
   - The 4,000-line control returns exact MCP alternatives; the web control returns both alternatives. MCP's `split('\n')` alternatives preserve trailing empty strings, and joining each alternative reconstructs its original input. The common-prefix/suffix slicing in the web bound is also conservative; the demonstrated defect is rendering/folding capacity, not dropped fallback slice text. The web view is line-oriented and already normalizes final-newline distinctions.

   **Fix:** append arrays by iteration or safe bounded chunks, including the web `ok` path. Keep exact MCP strings/alternatives and web line provenance. Add under-byte-cap, high-line-count regressions for both functions that assert a returned result, no exception, and exact alternatives. The existing 4,000-line test cannot cover this limit. The spread idiom predates the fix; the new bound still routes valid large inputs into it, so the fallback's promised completeness is not established.

5. **must-fix — The stall audit still has synchronous snapshot fan-out and unbounded file-processing phases outside the repaired loops.** Primary: `packages/room-mcp/src/conflict-set.ts:202`, `packages/room-mcp/src/conflict-set.ts:223`, `packages/shared/src/manifest.ts:73`. Further sites below.

   `withdrawUnauthorizedContracts`, called synchronously from manifest/graph/participant/claim observers, takes a full snapshot for **each contract slot**. Each snapshot copies every manifest entry and calls `toString()` on every overlay. It needs authorization/provenance, not a fresh full text copy per slot. The new `fileTurn` and pair-path budget do not run here, and the graph index's `snapshotPath` change does not affect it.

   **Measured real-function probe:** `/tmp/astra2-stall-probe.mts` supplies 1,000 one-byte overlays and 1,000 contract slots for one peer, then calls the actual cleanup method. It makes **1,001,000 `Y.Text.toString()` calls**, takes **159 ms**, and never services the scheduled immediate during the call. Its quadratic shape is the evidence; the timing is an observation, not a portable threshold. This cleanup is synchronous before ordinary reconciliation can reach any of the new yields.

   The remaining audit also found these concrete unbounded phases (source review, not timed reproductions):

   - `tools/combined-tree.ts:174`: the path-safety/submodule pass runs over every path with synchronous filesystem checks and `localWorkerBaseline` **per participant per path**, without a yield. `localWorkerBaseline` (`worker-registry.ts:121`) reconstructs/reads a durable registry snapshot. The later merge and materialization yields do not cover this earlier pass. The next remote-gap pass at `combined-tree.ts:203` can likewise traverse held/deleted fast paths using only resolved promises, with no event-loop yield.
   - `bridge.ts:308` and `bridge.ts:366`: projection plans/hashes all facts and compares/applies all entries synchronously. Its source includes **B..C committed differences**, so the source daemon's 4,096-path cap does not bound the projection. `composeFacts` at `bridge.ts:394` also parses/plans entire candidate sets without yielding. This is manifest projection work, not the excluded worker-carry `hash-object` path.
   - `roomd/src/index.ts:920`: `snapshotOwnClaims` now reads the old Git text of **every** owned claim path even when a claim already has its digest. `gitShowMany` (`roomd/src/git.ts:152`, `:157`) collects uncapped blob output, concatenates it, and decodes all files synchronously. The `sizeCap` check at `index.ts:930` happens **after** those reads; the fallback `claimDigest` at `:928` can also hash an uncapped old text before that check. Similarly, publication requests a complete old base blob for a small replacement without bounding that old blob's size (`publisher.ts:190`). A per-current-file disk cap does not bound old Git blobs or aggregate base-text decoding/publication.
   - Local reader/preview paths still read arbitrary disk file sizes synchronously: `tools/files.ts:61` and `tools/combined-tree.ts:117`. Diff/merge work budgets bound the algorithms' searches, but not uncapped input reads, line tokenization, or output construction. `disk-scan.ts:107` also retains a stat-then-uncapped-`readFileSync` race if a file grows between the size check and read; its later stat rejects the result only after the large synchronous read.

   **Fix:** use metadata-only authority reads or one cached immutable participant view per cleanup; do not copy text for each slot. Bound/index the synchronous revocation work while preserving immediate D1 withdrawal. Yield at the top of **all** many-file preparation loops, and hoist stable registry/baseline lookups out of per-path loops. Bound projection atomic work with the same recoverable design as finding 1. Check old blob sizes using metadata before reading, stream/batch with byte limits and yields, and use descriptor-bounded or asynchronous disk reads. Add focused responsiveness/operation-count tests for these phases. The patch's new tests cover merge candidates, policy planning, graph single-file snapshots and merged-file writes; they do not cover these paths.
