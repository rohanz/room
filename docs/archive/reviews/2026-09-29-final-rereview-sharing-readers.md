## New must-fix

### N1 — Redaction replicates a guessing oracle for the withdrawn signature

**Owner area:** sharing / derived contract slots. **Locations:** `packages/room-mcp/src/conflict-set.ts:80`, `:87`, `:520`. Introduced by `ecc698c`'s new `redacted` identity array.

A provider first shares `call(a,b)` and creates a contract notice, then narrows its declared area away from `api.py`. The manifest becomes hashless held and the slot's visible signature is removed, but every redacted identity retains the original `factId`. That value is the **unsalted SHA-256 of `[symbol, before/after signature detail, change kind]`**. A newly joined peer can compute candidate signatures and match the stored digest. This is derived content evidence in a replicated field, violating D1/manifest invariant 16 after withdrawal.

**Probe:** real ConflictSet, a real Git base and readable provider/consumer manifests; after narrowing B to `declared` with no prefixes and clearing its overlay, the wildcard held a `redacted[0].factId` exactly equal to `hash(JSON.stringify(['call', 'call(a) → call(a,b)', 'signature']))`. Encoding the document and applying it to a fresh RoomDoc preserved that digest. The signature text was absent from the redacted slot, so merely checking for the literal text would miss the leak. Rohanz explicitly confirmed during this review that D1 includes this derived digest.

**Fix direction:** preserve monotonic notice identity using opaque episode state that is not an unsalted digest of restricted content. Keep any content-comparison evidence private or use the lead-approved keyed/opaque design, with a fresh-reader narrowing test. Address the previous N2 history-loss cases at the same time; deleting all history to remove the digest would restore the notification-loss bug.

### N2 — A head-only exclusion is withdrawn, then republished with fresh provenance

**Owner area:** sharing / graph publication. **Locations:** `packages/room-mcp/src/graph-index.ts:124`, `:131–135`, `:302–307`, `:496–513`. Introduced by `ecc698c`'s provenance-only publication path.

An unchanged tracked `api.py` is present in the base graph and has no manifest entry. It is already ignored by the publisher, but unchanged files need no exclusion digest. Editing it makes it an excluded changed path. Publication changes only `manifestHead.excluded` and its revisions: the manifest remains empty. The synchronous withdrawal removes the graph path correctly. However, `publicationKey()` omits exclusions, so the new same-key branch republishes after `whenIdle()` without scheduling a source refresh. Withdrawal changed only the replicated snapshot; `publishedCache` still contains the old path/edges. The new provenance key forces that cached content back into a **ready graph stamped with the current manifest revision**, exposing the excluded path by name again.

**Probe:** real temporary Git checkout and GraphIndex; `readDisk` + `plan` with `api.py` ignored first produced a changed excluded path and no named entry, and the production `publishManifest` applied it. Immediately after publication, `graphs[B].paths` omitted `api.py`; after the scheduled publication, it contained `api.py` again with `status:'ready'` and `sourceRev === manifestHead.rev`. `minPublishMs:0` made the probe quick; the same new-provenance publication is merely delayed by the normal production interval. This violates manifest invariant 7 and the graph reader's exclusion boundary, even though the returned cached content is the old base rather than the new private edit.

**Fix direction:** treat exclusions (and other authorization inputs, including salt validity) as cache invalidations, refresh/remove affected cached paths before stamping provenance, and fence the final publish against those inputs. Add the no-entry→excluded transition to the regression test; the checked-in shared-entry→excluded test generates a manifest-map event and therefore misses this path.
