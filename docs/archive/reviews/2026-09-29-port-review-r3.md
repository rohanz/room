## Findings

1. **must-fix — A subsequent unrelated HEAD or ref transition discards pending claim validation and certifies stale claims.** `packages/roomd/src/index.ts:775`, `:782`, `:793`, `:812`; changed-path filter at `:971`.

   The pending set is merged into a newly captured snapshot, but `reanchorOwnClaims(..., true)` then filters that snapshot to paths changed between the *last applied* HEAD and the new HEAD. Pending claims concern an earlier, still-unvalidated transition; an unrelated new commit does not make them validated. On a refs-only transition, `claimSnapshot` is empty and the merge requires `current` to exist, so every pending claim is lost even before the filter. The assignment at line 812 replaces the old pending set with the empty result, and the transaction publishes `complete: true`.

   **Reproduction:** `/tmp/astra3-claims.mts`, `nexthead` case, uses the real daemon and the round-2 245,004-byte/20-claim fixture. After replacing `old` with `new` and committing: 12 claims remain, pending=12, complete=false. Commit only `unrelated.txt`, then reconcile: **12 claims remain, pending=undefined, complete=true**. All twelve claimed blocks are still absent. `/tmp/astra3-refs.mts` configures an origin/upstream and advances `refs/remotes/origin/main` to the already-applied HEAD: the same **12 / undefined / true** result, without a worktree or HEAD change. Logs: `/tmp/astra3-claims.log`, `/tmp/astra3-refs.log`.

   **Fix:** carry pending originals independently of the current HEAD's changed-path optimization. Revalidate their union with newly affected claims against the new target, or retain the unprocessed pending IDs; do not clear an ID merely because it was filtered out. On refs-only transitions, retain/revalidate the pending set rather than starting with an empty claim snapshot. Keep complete=false until every still-current pending identity has a decision. Add both transition sequences as daemon regressions.

2. **must-fix — Pending validation rotates whole claims but cannot resume an individually expensive claim.** `packages/roomd/src/index.ts:1060`, `:1067`; `packages/roomd/src/reanchor.ts:40`, `:87`; missing original text at `packages/roomd/src/index.ts:941`.

   Each retry starts `reanchorClaims` with fresh work counters and a fresh candidate scan. Rotation prevents one claim from denying *other* claims a turn, but supplies no progress for that claim itself. A claim with `claimedHash` on a clean file normally has no old overlay, and the new old-blob optimization deliberately skips reading its old text. It therefore takes the digest-only candidate scan, which can exceed the same budget on every retry even for an ordinary file below 512 KiB.

   **Reproduction:** `/tmp/astra3-claims.mts`, `wide` case: the same 245,004-byte file, one claim covering lines **1–2000**, with the correct digest. Commit replacement of only the first `old` line by `new`. The block is absent and the file is clean/readable. Initial transition and five independent reconciles all report **claims=1, pending=1, complete=false** and log another uncertain retry. Every invocation restarts at candidate zero; this is deterministic non-progress, not a slow eventual scan. Increasing the number of retries cannot resolve it.

   **Fix:** retain resumable per-claim search state, fenced to the original claim and the target file identity, including candidate position/match count and any prepared line/filter data. Alternatively retain enough bounded original-anchor data to guarantee completion within the per-claim budget, with a resumable fallback when it does not. Reset only when the guarded inputs change. Do not release a readable claim merely for exceeding the CPU budget. Add an end-to-end wide-claim completion test, alongside a permanently uncertain claim followed by a cheap claim to verify fairness.

3. **must-fix — The retry's final Git await comes after its fence/input checks, permitting an unfenced claim mutation.** `packages/roomd/src/index.ts:1061`, `:1074`.

   JavaScript evaluates `stopped`, `fence`, and `inputs` before `await gitHead(...)` in the compound condition. A lease loss, replacement policy/input object, or stop during that await is not rechecked. The following file-identity and claim-identity gates do not check authority, and `removeClaim`/`moveClaim` mutate the shared document directly.

   **Reproduction:** `/tmp/astra3-claims.mts`, `lease` case. Starting from the twelve real pending claims, wrap `reanchorOwnClaims` to schedule a `setImmediate` changing the daemon's standalone fence after it returns. That callback runs during the final real Git subprocess await. `retryPendingClaims(oldHead, oldFence)` still releases a claim: **claims 12→11 and pending 12→11 under `new-fence`**. The claim and disk inputs were unchanged. This exercises the daemon fence getter used by the production lease callback; no claim-validation result was fabricated.

   **Fix:** await the final HEAD read first, then perform all synchronous checks together immediately before mutation: stopped, fence, input identity, pending-set/target identity, HEAD result, file identity, and claim identity. Apply nothing if any changed. Add lease loss and policy/input replacement during the last Git await; retain the existing claim-change check.

4. **must-fix — Lead policy narrowing leaves projected worker content metadata replicated until an asynchronous bridge pass.** `packages/room-mcp/src/session.ts:495`, `:581`; `packages/room-mcp/src/bridge.ts:363`, `:398`, `:407`.

   The production PolicyStore callback calls only the lead daemon's `applyInputs`, which withdraws the lead's own incarnation. It does not synchronously sanitize this lead's projected worker incarnations. The bridge schedules/serializes a later projection, and its new preparation loop now yields even while enumerating entries to delete for intent. Its policy-identity check prevents an old *prepared* projection from landing, but does not withdraw the already-published projection.

   **Reproduction:** `/tmp/astra3-bridge.mts` uses a real daemon, real durable `PolicyStore.open({ onChange: p => applySessionPolicy(daemon, p) })`, and the real `Bridge.projectWorker` to publish a worker modification. After **awaiting** `store.setRequested('intent')`, the store and lead are at intent, but the worker head remains full and its entry retains `hash`, `size: 4`, and `baseHash`. Only after awaiting `projectWorker` do those fields disappear. `/tmp/astra3-bridge.log` records all three states. The existing new bridge tests assert only after `await bridge.sync()`, so they do not establish immediate withdrawal.

   **Binding clarification:** in answer to room question `m_mumxfzskavp1hk`, rohanz ruled that manifest §12 projection lag is accepted for additive freshness only; projected hash/baseHash/size/text withdrawal must happen synchronously in the lead's PolicyStore callback. This is a defect against that ruling, including the pre-existing scheduling gap, not a request to remove the yielding prepare.

   **Fix:** add a fenced synchronous revocation path for all projections owned by the lead, called by narrowing policy changes. Strip newly forbidden content metadata/text and update projection authority/coverage in the same callback, before queuing additive recomputation. Do not touch another lead's projections. Test immediately when the policy mutation resolves and while an old bridge prepare is suspended; later completion must not resurrect the stripped data.

5. **must-fix — The remaining stall paths still read uncapped file text synchronously and repeat whole-participant snapshots.** Primary: `packages/room-mcp/src/hooks-bridge.ts:112`, `:128`; `packages/room-mcp/src/tools/context.ts:180`, `:189`. Further sites below.

Instrumenting the real file read records **40 reads / 83,886,080 bytes / scheduled immediate not serviced**, about 49 ms here. Missing peer publication makes mapping conservative but does not prevent those reads. Larger files and more claims grow that work without a byte or claim-work bound. The same uncapped helper remains in `tools/state.ts:114–116` for claim/scope text and in `conflict-set.ts:308` for projected worker reads; the latter hashes the result afterward.

   **Additional audit evidence:**

   - `conflict-set.ts:295` still takes a full source snapshot for each projected file read. `/tmp/astra3-projected-stall.mts` resolves 1,000 projected held entries from a 1,000-overlay worker source through the actual `ConflictSet.read`: **1,000,000 Y.Text conversions**. Unlike the hook probe, an immediate *does* run in this async sequence; the evidence here is quadratic copying, not a claim of a single uninterrupted 319 ms stall. The newly cached `withdrawUnauthorizedContracts` is a different path and is fixed.
   - `tools/collect.ts:370–383` loops through all copy preflights and copies synchronously, including whole-file `readFileSync(...).equals(...)`; `:412–420` rereads all merged destinations synchronously before writing. The latter can also read an arbitrarily grown file after the earlier bounded preview. This is collection, not carry's hash-object checks. A small replacement of a large old file still sends the old text into synchronous splitting/patch/fallback construction. The publisher's new `gitShowManyCapped` does not cover these reader routes.
   - Remaining synchronous many-path preparation includes `disk-scan.ts:46–53` (whole inventory split/enumeration/set/sort), `git.ts:191–197` (whole batch-check concatenate/decode/split), and `manifest-publish.ts:71–78` (room-wide incarnation-key enumeration/filtering). Make hook preparation asynchronous with final fence/state checks and retain conservative whole-file warnings when text exceeds a bound. Add operation-count and event-loop-turn regressions for hook writes and projected reads, not just the already-fixed cleanup method.

6. **should-fix — Async local reads do not revalidate containment after the open yields.** `packages/room-mcp/src/tools/disk-text.ts:8`, `:17`; callers at `packages/room-mcp/src/tools/files.ts:58–61`, `packages/room-mcp/src/tools/combined-tree.ts:115–118`.

   Containment is resolved before `await fs.promises.open`. `O_NOFOLLOW` protects the leaf where supported, but not an ancestor that changes during the new async interval. There is no post-open containment/descriptor identity check before returning bytes.

   **Reproduction:** `/tmp/astra3-disk-race.mts` calls the real own-disk `room_read` for `nested/data.txt`. The open seam yields one immediate, renames `nested` aside, and replaces it with a link to an outside temporary directory before doing the real open. The tool successfully renders **`1| OUTSIDE DATA`**. All files are reviewer-created temporary fixtures. The existing between-files worker-root-swap regression still passes; it detects a later file, not this same-file interval.

   **Binding clarification:** rohanz's answer to `m_mumxj87crwyvkc` retains the documented local ancestor-swap limitation in `repo-path.ts`. A cheap post-open revalidation is **should-fix**, not must-fix. Windows' lack of `O_NOFOLLOW` is accepted and is not an additional finding.

   **Fix:** carry the captured root/original path into the read boundary, re-resolve containment after open, compare descriptor `dev`/`ino` against the current path's lstat, and refuse mismatch before returning content. Preserve contained-link policy and the hard read limit. This narrows the new async window; do not claim it supplies unavailable directory-relative open guarantees.
