# SQLite state: implementation and release plan

Date: 2026-11-06. Status: proposed implementation plan for rohanz's agent; no implementation or runtime qualification is claimed. Source baseline: `735607ae4fc4cff6294ae29d23464d6a769288e2`.

The [reviewed SQLite spec](../specs/2026-11-05-sqlite-state.md) is normative. The [local plumbing decisions](../specs/2026-11-05-local-plumbing-plan.md) fix the scope, runtime floor, NFS rule and stopped-writer window. This plan recommends changing connection ownership now that the standalone daemon exists; the amendments below require maintainer acceptance before implementing that part. All other spec invariants remain requirements. The [spec review](../reviews/2026-11-05-spec-review-sqlite-state.md) supplies failure scenarios, not evidence that the implementation passes them.

## Outcome and boundaries

Convert worker lifecycle and collection admission together: reservations, tags/adoptions, shared-checkout links, worker payloads, runs/reports/exits, semantic operation/run-writer/destination leases, review holds, archive/cleanup intent, scoped blockers/evidence and change invalidation. Preserve the lifecycle state machines and independent Git/process/sharing authorities. SQLite makes related facts atomic; it does not make an external effect transactional.

Keep ports, publisher leases, choice/sharing files, idle-release journals/counter, hook bridge/receipts/cursors, preview metadata/OS helpers, credentials, Y.Doc transport/snapshots, patch bytes, logs and Git resources outside SQL. Hooks and both hook manifests remain unchanged by this batch; `plugins/room/hooks.json` must stay byte-for-byte identical. Do not convert other JSON families for consistency alone.

Release in four slices. The first three remain useful, supported legacy-storage releases; only slice 4 enables conversion. Do not release partially converted worker/hold/lease domains. That final atomic boundary is intentionally larger than a worker assignment. Worker assignments below are implementation parallelism, not independent cutovers.

## Runtime evidence checked for this plan

On 2026-11-06, `node --version` in this worktree returned **v22.14.0**. It is below the selected floor and is not acceptance evidence for SQLite or either host launch. No live Room database was opened.

The constructor's `timeout` arrived in 22.16.0; the planned adapter can use it at the chosen floor. Use `exec`, bound `prepare/get/all/run`, explicit transactions and `close`; avoid APIs available only on newer major lines. Configure foreign keys, disabled extensions and `trusted_schema=OFF` explicitly. [22.22.3 release notes](https://nodejs.org/en/blog/release/v22.22.3) record SQLite 3.51.3. Pin the checked current patch and distribution digest in implementation evidence; recheck security-current 22.x at release time.

Retain the official **22.22.3 / SQLite 3.51.3 minimum**, qualify minimum and current patched official 22.x, and refuse unqualified vendor/major combinations. Keep catchable bootstrap preflight in the MCP even though it will not open the production DB: the maintainer already selected that launch requirement. Preflight may open disposable probes only. The daemon and offline command independently preflight their own actual executables; a previously running daemon might use a different runtime. `ensureLocalDaemon` currently launches `process.execPath`, but adopting an existing daemon does not prove its runtime.

Before importing application storage code, report executable realpath/Node version, catch `import('node:sqlite')`, query SQLite version and probe the selected filesystem/journal mode in private scratch. Keep stderr bounded and MCP stdout clean. No writable legacy open/import happens first. Probe time is at most 10 s; failure means restart/setup guidance, no fallback/reset. Audit all emitted entry bundles for import ordering.

## Ownership recommendation

**Use the existing per-clone daemon as the only online SQLite owner. MCPs use typed authenticated local RPC and never open `state.sqlite`, including for snapshots. Keep deliberate offline migration as a separate command.** Put storage primitives in a small `packages/local-state/` workspace used by relay and the offline command, with types/client transport importable without loading SQLite. Do not introduce a relay → room-mcp dependency or move host/Git orchestration into relay. New filenames in this plan are proposed; existing function names identify the integration seams.

| Design | Benefit | Cost / failure boundary |
| --- | --- | --- |
| Spec: connection per MCP plus elected maintenance MCP | Fits today's synchronous `WorkerRegistry` reads; fewer RPC interfaces. | Every opener, synchronous snapshot constructor, callback and MCP shutdown must participate in connection drain. Maintenance adds another election. Many clients can pin readers; SQL sync I/O blocks each host-facing process. |
| Recommended: daemon-owned connections | Reuses clone authority and lifetime; one place for close/checkpoint/pressure/version checks; removes maintenance election and direct-open bypasses. | Requires async consumers, a bounded RPC contract, durable retry results, control-only use by team sessions and a larger daemon failure domain. Daemon death makes lifecycle authority unavailable until verified restart. |

The daemon already exists in `packages/relay/src/daemon.ts`: `startLocalDaemon`, `ensureLocalDaemon`, `WriterIdleClock` and save-first `close`; `private-state.ts` supplies POSIX/Windows privacy. Reuse these. Current `setDraining`/`stopLocalDaemon` and `/daemon/stop` cover transport acceptance, connected writers and snapshot persistence. They do **not** register whole worker operations, fence JSON writers, drain detached Git helpers or close SQL connections. `daemon-cutover.json` proves neither SQL activation nor exclusion of old binaries. `inspectDaemonCutover` is bounded read-only inventory, not the storage barrier.

This removes **per-MCP production connections/prepared statements and their close acknowledgements**, the **dedicated maintenance-MCP ownership file/election/recovery**, and **checkpoint scheduling/ownership distributed among MCPs**. One daemon owns the maintenance connection and schedule instead. It cannot remove durable bootstrap ownership/generations, MCP/helper registrations and whole-operation tickets, semantic leases, seq checks, exact process probes, external-effect intent/acknowledgement, private evidence or the operator's old-binary inventory: callers still execute effects outside SQL, and a daemon socket cannot prove those effects have ended. WAL pressure, checkpoint bounds and close-before-DDL remain required even with one online owner.

Use one bounded DB worker thread inside the daemon from the outset. It owns the online data connection and a separate explicit maintenance connection; neither escapes the adapter. This protects relay transport/health from synchronous SQL stalls in a now shared process. It does not promise a hard fsync deadline. Measure queue delay, commit/checkpoint time and hook latency anyway. A stalled thread refuses further growth rather than spawning an unbounded pool; do not terminate it merely because a write timed out. On thread failure retain relay memory, refuse storage-dependent effects and resolve committed operation IDs before reopening authority.

The offline command owns `migration.lock`, generation, staging, backup, import, DDL and publication. The online daemon runs **no DDL**, even on an empty clone: initializing an empty schema is the same explicit maintenance operation with an empty source manifest. Before first activation, the compatibility release can continue legacy operation after initialization of its legacy gate. After activation, missing DB/marker is always an error. No permanent runtime backend selector, dual write or JSON fallback.

### Contracts to agree before dependent work

1. **Storage gate:** `StorageGate.register/admit/finish/drain/status` with canonical common-dir/HEAD validation, private instance identity, build ranges, monotonically increasing generation and unique operation ticket. Preserve the spec's file guard and durable external gate/registration records. Admission and drain transition serialize on the same short guard. A draining successor generation records which predecessor tickets may finish; it cannot invalidate their acknowledgement paths. Cap at 256 processes/4,096 tickets; scan at most 200 per yielded pass. No constructor, snapshot or timer bypass.
2. **LocalState client:** asynchronous bounded `snapshot/query`, typed mutation commands, `changes(after)`, and operation-result lookup. Each request carries protocol/schema version, clone/DB ID, daemon nonce, generation, authenticated instance, admission ticket and per-call token. A mutation includes operation ID, input digest, expected seq and required lease token/generation. Return revision, durable result or a typed refusal (`maintenance`, `incompatible`, `blocked`, `busy`, `pressure`, `unavailable`, `uncertain`). No arbitrary SQL, filesystem path or callback RPC. Proposed initial queue bound: 128 queued commands, paginated reads of at most 200 records/4 MiB, 1 MiB per payload; overflow refuses before effects. Reserve a bounded control/acknowledgement path so saturation cannot prevent drain completion.
3. **Result identity:** RPC response loss is not mutation failure. Add `operation_results` keyed by generation/instance/call/command ID with input digest and committed result, atomically with the mutation. An exact retry returns the result; conflicting input refuses. Retain unacknowledged/ambiguous results without expiry; acknowledge explicitly, then prune acknowledged results in bounded batches when seven days old or the 10,000 acknowledged-entry limit is reached. Pressure from unresolved results refuses growth, never deletes them. A completed ticket can never execute again; a result pruned after acknowledgement yields “result unavailable,” never blind reexecution. Existing external-effect intent remains in the versioned worker payload. This small additional table has a demonstrated RPC recovery purpose; no task/log copies.
4. **Registry facade:** named lifecycle commands replace `update(id, callback)` over the wire. Async snapshots return consistent worker/run/report/exit/reservation/blocker facts and a revision; `statusOf` and host/log enrichment can remain MCP-side. A display snapshot/cache is never effect authority. Every consequential command validates fresh authoritative rows, expected seq, blockers and lanes. No transaction spans Git, process probes, network, filesystem effects or awaits. `sourceToken` becomes DB ID/generation/entity revision rather than file stats. A synchronous callback that cannot await uses an explicitly supplied snapshot with conservative unknown behavior, never opens storage.
5. **Lanes and effects:** admission → destination → shared-owner → worker → run-writer → short transaction; sort multiple keys, release in reverse. Publisher acquisition/verification precedes admission. Distinct same-MCP calls have distinct tokens; nested discard→stop reuses the outer token and cannot release it. Lease holder is the actual effect-owning MCP/helper identity, **not the daemon**, so disconnect/daemon restart does not free a live caller's lane. Probe identity outside SQL; takeover compares the exact observed token/generation in a transaction. Alive/unreadable is busy. Preserve 30 s destination wait and 1 s async jitter whole-transaction retry; local SQL busy timeout is zero.
6. **Availability and identity:** authenticated storage attachment is independent of Y.Doc room membership and counts as a writer for the existing five-minute idle clock. Team-only MCPs can use clone storage without joining/publishing a local room or inheriting team credentials into the daemon. Viewers never use storage or keep it alive. Repository binding may establish a control connection, but worker run authority still requires validated nonce/run/checkout admission; binding alone grants none. Reject cross-clone/foreign-machine DB identities. On daemon reconnect discard cached authority and revalidate nonce/generation/results; no silent new call ID after an uncertain result.

### Offline handoff and drain

The CLI, e.g. `room-state.mjs migrate --common-dir <canonical>`, first does runtime/filesystem preflight and the operator inventory. Then acquire `migration.lock` (existing full-identity, verified-dead recovery; 30 s ownership wait), publish a new draining generation under the gate guard, and stop new admissions. Never wait while holding the gate guard, SQL transaction or a lifecycle/preview lane. MCPs stop new timers/watchers, finish existing operations through their final Git/file/network acknowledgement and lease release, hand independently running callbacks/helpers their own tickets, then unregister. A daemon keeps serving admitted acknowledgements and diagnostics while draining; it does not manufacture completion when a socket closes.

After all tickets and registered helpers are reconciled, close both daemon SQL connections and acknowledge that fact. Disconnect writers, save transport snapshots and use the authenticated nonce-specific daemon stop; verify birth-identity exit. A failed save leaves the storage gate closed even though today's daemon reopens transport repair admission. The CLI then takes the **same existing `AuthorityLock`** in maintenance mode without serving a relay. Daemon startup must check the gate under that authority before opening storage: a racing starter refuses maintenance and releases authority. No second online-storage ownership file/election is needed. Migration order is migration ownership → short gate transition → lock-free drain/daemon stop → maintenance authority → canonical legacy exclusions → bounded SQL transactions. Ordinary operations cannot acquire migration ownership. Test the interval between daemon exit and CLI authority acquisition explicitly.

Only the verified offline owner may open the repository DB/staging DB now. Recheck generation/token at every irreversible publication. Use the spec's `staging → db-complete → active` transitions, stable assignments, digest revalidation, closed/checkpointed publication and matching activation identity. Keep 120 s drain and ten-minute import-attempt bounds; timeout leaves maintenance closed. Startup observing maintenance refuses within 10 s, independently of the daemon launcher's present 60 s progress cap. SQL-to-SQL upgrades use the identical ownership handoff, WAL-aware backup and close-before-DDL proof. On completion release authority/ownership; the next bound client starts the daemon, which verifies active DB/gate/version without DDL.

An active paused/unknown MCP, helper, migrator or owner blocks conversion. A definitively dead caller still needs intent/effect reconciliation or an explicit blocker before its ticket is resolved. Gate records cannot exclude an unmodified binary that ignores them. Retain the complete inventory/operator confirmation and prevent old host/reconnect loops, as the spec requires. Pair daemon and SQL maintenance in one human window when both are ready; an already completed daemon cutover does not waive the later SQL window or invent retrospective gate participation.

### Filesystem policy

Follow the maintainer's NFS addendum over the earlier blanket network refusal. Detect every repository open: macOS/Linux statfs plus mount information, Windows UNC and mapped-drive resolution. Proven native local filesystems use WAL; known network filesystems use DELETE only after locking, durability, single-host ownership and privacy qualification. Unknown, synchronized or foreign-machine paths refuse writable activation. A same-clone daemon cannot fence a different machine; DELETE alone is not permission for multi-host access.

Use zero SQLite busy timeout in WAL with async transaction retry. For qualified DELETE mode set an explicit bounded busy timeout, initially zero as well, with the same 1 s async retry budget; this avoids blocking the DB worker waiting for another connection. Verify the actual mode, FULL and foreign keys. Probe DELETE semantics instead of demanding WAL on network scratch. A moved WAL DB must be drained and converted with all connections closed at a provably safe location before network use; never open it in WAL on NFS to discover that conversion is needed. If that cannot be proven, refuse with relocation/recovery guidance. No automatic online journal-mode conversion. Qualifying network write support is a release support decision below; refusing unqualified network paths satisfies the maintainer's “DELETE or refuse” decision.
