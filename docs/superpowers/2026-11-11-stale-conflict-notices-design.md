# Stale conflict notices: design gate

**Status:** current stage 1 is registration plus exact-worker retirement endings only. Managed IDs now bind every private worker dependency’s workerId; unbound, unknown-holder, non-worker and non-capable paths keep baseline IDs/TTL. This supersedes earlier claims of byte-identical IDs for capable worker conflicts; bodies and posting decisions remain baseline. Evaluated completion was built, reviewed and set aside by the user after three unsafe cases: loss of a grouped member, stale negative graph evidence, and a queued completion surviving a sibling’s transition to unknown. The full evaluated version is preserved at `7da5c1f0`; it is not the current implementation or a release-ready proposal. All file/slot evaluation, clean/withdrawal and update-supersession endings are removed. Historical analysis below remains pinned evidence; persistence and projection are deferred.

Date: 2026-11-11. Baseline: `5456cd72` (worker startup tree).

**Original gate decision (resolved by review and stage-1 authorization): stop before production changes.** The proposed rule cannot safely apply to every existing notice from the state available to its reader. In particular, a local relay restart retains addressed notices but deliberately omits `conflicts`; a projected worker receives notices in its workers room while the slots exist only in its team room. An empty local slot map can therefore mean either a withdrawn conflict or a still-open conflict whose producer state is unavailable. A set difference cannot distinguish these cases. This is a verified failure of the brief's premise, not a conclusion that adding message fields is the only possible solution.

Read: the brief, `2fc29da4`, its withdrawal `b1accea8`, the three review reports and the associated notice repros. No inferred subject resolution, permanent notice expiry, protocol change or runtime change is proposed here.

Also checked the ledger/repository-room design specs and the 2026-10-03 / 2026-11-09 decisions against current code. The spec explicitly separates team slots from projected owner notices and makes slot publication and notice posting separate operations. Historical slot key/fact rules have since changed (notably stable per-path claim renewal and grouped peer/possible episodes); current constructors and tests govern this analysis.

## 1. Which ids derive from slots?

References below are repository-relative source locations; line numbers refer to the startup tree.

| Form | Available inputs and limitations |
| --- | --- |
| `noticeId(key, epoch, episode)` | The key and all identity inputs are in the replicated slot map. `unknown` preserves `settled`, so it must continue producing the last known conflict/possibility. A current slot's identity can be computed without participant or claim inference. |
| Non-contract `:clean` | Derived from owner, other, path, `clearedFrom`, epoch. Contract `:clean` uses the per-slot id plus suffix. Keep clean tombstones: repeated clean/unknown evaluations preserve the same clearing identity. |
| Grouped possible `:possible` / `:clean` | Derived from owner, other, path, `possibleEpisode`, and **all** group slots. The opener's disappearance must not end the group while a joined slot is still possible. Replay chooses a surviving open slot, including one whose current status is unknown but settled state is possible. No body claim is authoritative. |
| Per-peer `:peer:<episode>:<state>` | Derived from all pair slots, latest `peerEpisode`, sorted open/cleared paths and epochs (`postPeerNotice`, lines 195–223). However, the latest replay id is not the entire currently owed set under existing behavior; see below. |
| `:holder` | Derived from another owner's exact edit-in-claim slot, addressed to `slot.other`, not `slot.owner` (lines 302–310). A reader scanning only its owned slots misses these. For projection this holder copy goes to the team room while the owner copy goes to the workers room. |
| `:landed` | **Not slot-derived.** `releaseLandedWorkerClaims` hashes the released claim ids, after proving local disk equality using trusted registry/run facts, then removes those claims (lines 951–998). It is an event reporting completed cleanup. Leave it on ordinary receipts/TTL. |
| `:degraded` | **Not fully slot-derived.** Hashes a contract key plus a carried baseline SHA from local registry state (lines 1041–1048). The SHA is not recorded in the slot. Leave the coverage diagnostic on ordinary receipts/TTL; do not guess a baseline from unrelated fields. |

`postNotice` additionally checks the slot fence/current object and a worker view (`edit-in-claim` notices for the owner's non-running worker are suppressed). These are publication guards, not pure slot identity. A refactor must distinguish identity derivation from authority and live posting decisions.

There is also a behavioral incompatibility with an exact replay-id set: `supersededConflictNotices` explicitly retains an earlier `notify` when a later update only clears some files and has priority `fyi` (`packages/shared/src/messages.ts:43–70`). The remaining file still conflicts. Replay now produces the later fyi id only. Filtering every earlier id outside that set discards the still-owed notification the existing rule intentionally preserves. This needs an explicit design decision or additional retained episode evidence, rather than treating all older pair ids as stale.

## 2. Are subjects reliably removed at the producer?

No; removal is not one universal `drop` operation today.

- `ConflictSlots.drop` simply deletes the slot (line 115).
- `ConflictSet.run` drops slots whose other participant is no longer a neighbour, after obtaining a usable own snapshot and lease fence (lines 714–737). A worker holder tombstone is excluded by `participantsView` unless fresh awareness rescues it. This is a producer observation, with the existing delayed reconciliation/manifest availability limits.
- Worker retirement (`RoomDoc.retireWorker`, `packages/shared/src/doc.ts:224–241`) deletes slots **owned by** the retired name when that worker still owns the name. It does not delete other owners' slots **about** that name. Those depend on their live ConflictSet reconcilers. A stopped owner's slots can outlive a retired subject.
- Participant expiry likewise deletes only owned slots (`packages/shared/src/expiry.ts:76–93`). Ordinary disconnect/lease end intentionally retains coordination; offline does not mean work disappeared.
- Claim release usually settles a slot clean, preserving clearing identity (`ConflictSet.claims`, final loop), rather than dropping it. The production edit-in-claim key is stable per path, with its representative claim stored in `subject`. Renewing the claim can keep the same semantic epoch/episode. Inferring termination from temporary absence of the representative repeats review round two's bug.
- Finished own-worker claim/overlap slots are explicitly dropped at the start of `claims`, independent of retirement.
- A new owner lease does not universally delete all old slots: an unchanged evaluation re-fences a slot and preserves epoch/episode (`settle`; existing test “re-fences an unchanged slot for a new owner epoch”). Until a usable reconciliation completes, old owned slots may remain. Re-fencing itself must not be mistaken for ending a still-open conflict.
- `Bridge.dropProjection` removes participant/manifest projection state, but no conflict slots (lines 308–314). Projected-set retirement/authority cleanup needs explicit ownership if a revised design extends here.

Fixing stale slots requires authoritative producer/lifecycle transitions that distinguish retained offline work, renewal, real retirement and name reuse. A reader cannot repair these transitions by guessing subjects from messages. Deleting a slot on every holder change would also change the existing unchanged-fact takeover behavior.

## 3. Does dropping a told conflict send a clearing notice?

Today `drop` is silent. Neither direct drop, retirement nor expiry synthesizes `CONFLICT cleared`. A successful evaluation from conflict/possible to clean posts the corresponding fyi clearing notice and retains its slot tombstone for replay. This distinction must stay: withdrawing a subject or text authority is not proof that two versions now merge cleanly. A recipient already told CONFLICT gets no new clear solely because its slot was dropped.

## 4. Ledger, hub trim and mixed versions

A ledger-side reversible filter could affect delivery/wakes without changing the wire format; existing old readers would retain today's behavior and existing old hubs could continue storing/counting the messages until receipt, TTL or cap eviction. This would leave stale messages consuming caps (`trim`, `packages/shared/src/delivery.ts:148–183`), so it would not eliminate inbox-pressure losses of other mail. It must be reported as delivery relevance only, not authoritative storage cleanup.

The current hub cannot safely apply an absence-based permanent outcome. Local persisted snapshots omit slots, and a notice post and slot update are distinct operations/transports. Initial sync is not a barrier proving later slot absence is authoritative. Permanent expiry could poison an id that unchanged-fact replay deliberately reuses. Old servers/relays also cannot supply new provenance or readiness guarantees. Do not add a `conflictsReady` switch as though it solves these ordering issues.

`memorySnapshot` (`packages/shared/src/memory.ts:15–32,56–65`) copies only `MEMORY_TYPES`/`MEMORY_PREFIXES`; `conflicts` is in neither. It retains bus, mail, outcomes and claims. `packages/relay/src/memory.ts:105` uses it for durable local memory. Thus after a supported restart a live notice and its open claim can survive while the entire slot map is absent. New snapshot retention alone cannot repair already written snapshots or old relays within the compatibility window.

No negotiated or message-format change is needed merely to keep old behavior. A future design might publish a durable authoritative notice inventory/termination record through existing extensible replicated state, with a completeness/incarnation marker and conservative treatment of old snapshots. That is a new producer/persistence contract to design, not the asserted existing slot-only rule. This report does not claim older validators accept new message fields.

## 5. Projected workers and two rooms

`ConflictSet(team, owner, workers)` constructs its `ConflictSlots` over `team.room` but uses `workers.post` for owner notices and `team.post` for holder notices (constructor, lines 400–427; `reconcileProjectedConflicts`, final lines). `Bridge.projectOnce` invokes that reconciliation per projected worker. The worker is joined to its local workers room, not the team room. Its ledger consequently has no copy of those team slots; neither bridge observation nor `dropProjection` mirrors them into local `conflicts`.

Therefore the worker can have a valid, still-open, owner-addressed `cf:` notice and an empty slot map at the same instant even without a restart. A lead joined to both rooms cannot make the worker's autonomous reader or later takeover session see the other room's state merely by computing a local set. A global union in the lead's ledger would not fix worker delivery, would need room/source identity, and would lose its authority when the lead is absent.

Mirroring raw team slots into the workers room is not a routine refactor: it needs source/incarnation identity, deletion/restart rules, ordering with notice publication and local slot ownership, and a sharing-boundary review (remote peer details and paths are team-derived state). A separate minimal notice inventory may be preferable. Both require a revised design decision from the lead before implementation.

## Evidence and next decision

The minimum safe next decision is whether to expand this task into a durable producer/inventory and cross-room design, including a conservative legacy path and retained notification urgency, or keep current delivery until that design is agreed. The exact proposed filter is unsafe; no approximation has been implemented.

Validation results and any lead decision will be appended before collection. Runtime source, message format, bundle, hooks and changelog remain unchanged.

## Causes of stale delivery

| Cause | What actually ends or changes | Where the notice is left behind | Ownership of a fix |
| --- | --- | --- | --- |
| A slot is explicitly dropped | Producer deletes the derived slot | `drop` writes no terminal outcome; bus/mail still offer the old id | Producer bug: terminate the registered delivery obligation in the same lifecycle transition |
| Worker collected/discarded/retired | Retirement removes its own coordination and owned slots; another owner may be stopped | Inbound slots about that worker can survive; both owned and inbound messages have no episode termination | Worker lifecycle plus conflict producer; preserve `workerOwnsName`/incarnation guard |
| Claim released | Producer eventually settles clean, or removes finished-worker slots | Original exact/group notice may still be owed alongside a clear; released representative alone cannot identify episode end | Conflict producer; evaluate semantic renewal/group membership before ending an episode |
| Peer leaves or loses grant | A usable producer reconciliation drops the pair/contract slots | Stopped owners cannot perform this pass; dropping still leaves original notice | Existing expiry/retirement/grant authorities plus registered notice lifecycle; an ordinary disconnect retains work |
| Name reused by new session | Holder fence changes; unchanged facts can be re-fenced and reused | New holder reads earlier addressed mail; stale slots can persist before reconciliation | Explicit name-incarnation policy and durable ownership, rather than blanket drop on fence mismatch |
| Relay restarts | Snapshot deliberately preserves durable coordination/mail, excludes live derived slots | Old addressed notices survive without their derivation | Persistence gap; cannot interpret absent reconstructed state as termination |
| Worker projected into team room | Slot authority is team; delivery target is workers room | The destination never has the source slots, even with both rooms synced | Bridge producer must maintain destination-side durable obligations and endings |
| Peer conflict partially clears | Latest per-peer notice becomes fyi, while one file remains open | Earlier notify remains intentionally owed | Correct existing behavior; preserve its urgency until receipt or complete episode termination |

These causes cannot all be repaired by adding one reader predicate. Some are intentional retention policies, some are missing producer termination, and two are missing source-state contracts.

## Recommended design: durable producer outbox, explicit endings

Recommend a **producer-owned durable outbox per delivery room**, using a new internal replicated map and existing terminal outcomes; leave message bodies, hub protocol and schema version unchanged. This is a design proposal, not an approved or implemented API. Confirm its state-ownership/fencing contract before coding.

This outbox records production/replay/termination intent only. The existing ledger remains the sole delivery arbiter and `seen:<recipient>` remains the sole receipt; the outbox never records “shown” or manufactures a receipt. The current ledger spec assigns outcome writers to trim/retirement. Allowing producer-owned exact-id expiry is an explicit ownership change to review, not an existing authorization inferred from access to the Y.Doc. Alternatively the hub can consume explicit ending intents, but old hubs would then provide only old behavior until updated.

1. A complete producer evaluation registers each notice obligation in the same source transaction that advances its slot/group/peer episode. Store exact id, recipient, owning producer incarnation, semantic episode identity, destination/source room identity, state (pending/current/ended), delivery body for crash replay, urgency and any retained owed predecessor ids. No message parser or reverse hash lookup chooses subjects. Store the minimal dependencies needed to end an obligation at an authoritative lifecycle transition (worker id, actual episode/group), rather than a representative body claim. Bound entries/bytes; never silently evict a current obligation to assert it ended.
2. Register **before posting**; retry through the normal idempotent post path. A failed post leaves durable work to retry. End obligations at the producer's coherent evaluation/drop, authoritative worker retirement/participant expiry, or explicit episode termination. Write existing `expired` outcomes for exact registered ids in the delivery room, atomically with the local outbox ending when possible. `drop` remains silent: an outcome ends owed delivery, it does not invent a clear. A completed clean evaluation creates the existing clearing obligation before ending its predecessors. Do not end an id and then reuse it: actual episode termination/reopening gets a new persistent incarnation/episode token, including merge episodes whose counters currently reset if every slot is dropped.
3. Semantic renewal is decided by the completed producer pass. Replacing a claim does not terminate a stable unchanged overlap; an approximate group lives until its last member ends. Current/unknown evidence keeps the last settled episode. Missing manifest, missing worker view or temporarily missing representative claim never writes an ending outcome. Worker retirement may end only dependencies registered for that exact worker id and guarded by current name ownership; it must not end a same-tag successor's obligations.
4. Preserve current urgency: when a peer's later update only clears files, retain the earlier unreceipted notify obligation **and** the current fyi obligation. On a subsequent equally urgent update, the producer can end replaced undelivered predecessors just as today's supersession rule does. On complete clear, end old conflict obligations and keep one fyi clear. Store these ids instead of attempting to reconstruct their historic hash inputs from the latest slots.
5. Snapshot the outbox as protected coordination state with explicit byte/count bounds. A restart can replay pending/current obligations and terminal outcomes without needing manifests or slots to have been rebuilt. A takeover uses replicated outbox records only after obtaining its normal name authority, re-evaluates retained conflicts, and can finish previously recorded endings. A changed lease fence alone is not episode termination. Legacy snapshots without the outbox remain **unknown**, so their untracked old messages retain ordinary TTL; no completeness flag retrospectively asserts their absence is meaningful.
6. For projection, the lead owns a durable source intent and a minimal destination outbox record under its fenced projection identity. Destination record must be durable before owner notice posting. Source termination is a durable **ending intent** retried into the workers room, so a crash between two room writes cannot resurrect or strand a registered message indefinitely after recovery. No cross-room transaction exists: while the lead/bridge is unavailable, the last committed destination state remains owed until replay/TTL; this is an explicit availability limit, not inferred clearance. A newer incarnation must fence late publishers/endings from a previous lead/worker. Mirror obligations/ending ids, not remote raw conflict slots or unrelated paths. Holder-directed obligations remain in the team outbox.
7. Existing old readers/hubs already honor exact `outcomes` (`owed` and `Hub.post` duplicate checks). Old relays can continue operating without a negotiated change, but omit the new root from snapshots. Therefore the new producer must not advertise durable replay guarantees through an old relay; either retain conservative TTL on that deployment or have a new session republish its durable local/source intent after restart. A genuinely old writer creates **untracked** messages that remain on today's behavior. New producers must handle old slot formats conservatively. New internal state survives only where the authoritative persistence implementation retains it; this is a rollout constraint, not evidence that every old relay suddenly supports the feature.

The first release should scope the guarantee to **registered new obligations on updated persistence**, leave untracked historical messages on TTL, and document that an old bridge/old writer continues old behavior. If eliminating all 168 pre-existing notices immediately is mandatory, this proposal cannot prove that safe for legacy snapshots/projections: the human may choose an explicit reviewed inbox cleanup, or require a broader compatibility/persistence rollout. Do not silently classify old ids as registered.

Estimated size: medium to large, roughly 6–10 production modules plus focused tests: `conflict-set`, a dedicated outbox/lifecycle helper, shared persistence/outcome support, retirement/expiry integration, bridge handoff/recovery, takeover authority wiring, and compatibility fixtures. Expect several hundred lines of runtime code and a comparable regression suite, rather than a small ledger predicate. Sharing/authority and bounded storage should be reviewed before implementation. The lead owns final estimates and release scope.

### Alternatives rejected or deferred

| Alternative | Authority and ending | Restart / takeover / projection | Partial-clear and compatibility | Size / reason |
| --- | --- | --- | --- | --- |
| Exact current replay-id filter | Reader interprets slot absence as ended | Loses live state at restart; destination lacks projected slots; new holder inherits ambiguity | Drops earlier notify after partial-clear fyi; old clients retain old behavior | Small, **rejected as unsound** by the evidence above |
| Same filter plus persist/mirror slots | Reader still decides absence, but in more complete maps | New snapshots improve; old snapshots/relays and cross-room ordering remain incomplete; ownership collisions need a source namespace | Still cannot derive retained notify history from latest state | Medium; a completeness/incarnation protocol and predecessor retention would turn this into a new inventory design anyway |
| Only write outcomes from current `drop` | Producer is authoritative for that local transition | Fixes witnessed new drops, but slots absent after restart cannot enumerate ids; bridge outcome must reach the right room; inbound retirement still unhandled | Must preserve groups/notify predecessors and new episode ids; old readers honor outcomes | Small to medium partial fix, **insufficient as complete task**; useful building block after registration exists |
| Infer claim/worker from message text, claim id or hash | Reader guesses subject, trim makes irreversible ending | Repeats the reviewed renewal, grouped-claim and holder/view bugs; weak across restart/name reuse | No safe legacy provenance; no amount of TTL/readiness flags orders the updates | Rejected; withdrawn mechanism must not return |
| Put subject/incarnation in every message | Message carries provenance; producer still must publish authoritative episode ending | Easier association, but not enough by itself to solve omission or cross-room end delivery | Older validators reject unknown fields, requiring negotiated version rollout; predecessor urgency still explicit | Larger protocol/release change; **not proved unavoidable** because an outbox can use internal replicated state and existing outcomes |
| Keep current TTL | Existing receipts/trim remain authoritative | Works through current persistence and all supported old versions; stale delivery remains | Preserves current urgency and compatibility | Zero runtime change; safest interim until a producer/persistence design is approved |

No compatible design can promise durable additional state on an unmodified old relay that intentionally omits that state from disk. The honest compatibility claim is continued operation with conservative old behavior there, not full new-feature parity across every 0.17.0 deployment.
