## Goal

One local record per worker, written before each side effect, decides every local capability: which
directory Room may read, collect or delete, which process it may signal, and which conversation a follow-up
resumes. The Y.Doc only shows workers. The same layer holds participant-name and worktree-publisher
exclusivity. Out of scope: the collection journal (audit item 6). A kill after the first write into the lead's
checkout still leaves a partial apply, so **this does not make collection crash-safe**.

## Invariants

1. Every worker has one registry record, keyed `w_<ULID>`, whose intent is on disk before any worktree, ref or process exists.
2. A local action on a worker uses only the registry's facts, and only when the capability table (§1) grants it. Replicated data never authorizes a local action.
3. Every local file has one writer instance, identified by an instance token (session ID, pid, start time, nonce). Every create, replace and release of a lease runs under that lease's guard.
4. A lease is recovered only when its holder is `dead`. An `unknown` holder is kept until a human overrides it.
5. Status is the total function `statusOf` of durable facts. No decision reads a stored status or the CRDT.
6. Room never relaunches, signals or refuses a run without durable local evidence bound to that run.
7. A tag names at most one worker per common dir, from reservation until every room's retirement cleanup is done.
8. In each room, a worker's replicated records have one writer, fenced by its holder incarnation, and readers accept only the current incarnation.
9. Name ownership across clones and machines is a hub lease with an epoch (R1a; hub §2.3, §4); within one clone, the O_EXCL lease and process identity decide it.
10. A session's presence, name lease and publisher attachment end within a bounded time once its host session has finished, even when its MCP process lives on (§18, D5/H1). The 30-minute idle lease does not end a session that holds scope or claims, leads a non-terminal worker, or is inside a `room_wait`. For a shared app-server session, the eight-hour H1 cap releases its claims and clears its scope first; it never applies to an interactive CLI session.
11. Only the holder of a worktree's publisher lease writes base facts (`git`) and posts `pushed` for that worktree (§16, D5).

## Data model

### Local files (R5), under `<git common dir>/room/`

```

room/registry/collect/<h(worktree)>.json CollectLease         §11
room/registry/patches/<id>.patch        discard recovery patch, stable name (§10)
room/registry/migration.json            MigrationMap          under migration.lock (§Migration)
room/registry/retired/<id>.json         retired records, deleted after 7 days
room/registry/quarantine/               unparsable files, reported once
room/names/<h(roomKey, name)>.json      NameLease             R1a, SF4 (§15)

room/sessions/<sid>/session.json        SessionRecord         writer: SessionStart hook (§17)
room/sessions/<sid>/runtime.json        model/effort          writer: that session's hooks (§17); the rest of the directory is the ledger's

```

`h()` is sha256 over NUL-joined parts; `worktree` is a realpath; `roomKey` is reporooms' `shared/src/rooms.ts`.
Plain files are written temp, fsync, rename, fsync-dir (`git-dirs.ts:writeRecordSync` gains the fsyncs).

### Leases (`room-mcp/src/leases.ts`, replacing `owned-file.ts`)

```ts
interface ProcessIdentity { pid: number; startTime: string; executable: string }  // worker-process.ts:probeProcess
interface InstanceToken extends ProcessIdentity { sessionId: string; nonce: string }
type Liveness = 'alive' | 'dead' | 'unknown'
function liveness(t: ProcessIdentity): Liveness
function createExclusive(file: string, content: object): boolean  // write temp, link(temp, file), unlink temp; EEXIST → false
function withGuard<T>(file: string, fn: () => T): T               // holds `${file}.guard` (createExclusive; a dead guard holder is recovered)
function replace(file: string, expect: (c) => boolean, next: object): boolean // under the guard: re-read, check, temp + rename
function compareAndRelease(file: string, token: InstanceToken): boolean       // under the guard: re-read, same nonce → unlink
function recover(file: string, orphan: (c) => boolean): boolean               // under the guard: holder dead and orphan(c) → unlink
```

Takeover (`replace`), release and recovery are serialized by the same guard (MF12). A holder that re-read its
token outside the guard cannot unlink a successor's lease. Every periodic ownership check compares the full
token, nonce included, not only the session ID.

`liveness(t)` is `dead` when the pid is absent or its start time or executable differs, `alive` when all
three match, and `unknown` when the pid exists but its identity is unreadable (Windows, where `probeProcess`
returns `{}` at `worker-process.ts:206`, or a denied read). `unknown` counts as live. `room_state` names the
override: `room_join takeover=true` for a name, `room_collect tag=X discard=true force=true` for a worker. Full
identity is available on macOS and Linux (SF3).

## Behaviour per path

New modules: `worker-registry.ts`, `worker-status.ts` (`statusOf`, adapter, `completionMessage`), `leases.ts`,
`name-lease.ts` (names, publisher, `boundSession`). `Rooms` keeps sessions and routing only (Astra 13).

### 1. Local capabilities (the table manifest row 14 cites)

`WorkerRegistry.trusted(lead: { participant, room, dir }, tagOrName): Promise<TrustedWorker | undefined>`
resolves through the lead's own tag reservation, then the record, and validates the canonical worktree
asynchronously. A remote view, a CRDT `dir` or presence never yields a `TrustedWorker` (Leave 2).

| Capability | Granted when | Used by |
|---|---|---|
| Read the worktree | the record is not retired, `dir` passes `isOwnedWorkerWorktree` on each call, and it is read through a realpath root | `room_read` of a disconnected worker, previews, collect |
| Collect as a delta | `capabilities.collect === 'delta'`: `base` (and `carriedBase`) resolve locally | `room_collect` apply |
| Collect by copy | `collect !== 'none'` | `room_collect mode=copy` |
| Signal | `capabilities.signal`, and `liveness` of the target is `alive` and equal to `runs[n].launch.process` or to an admitted `RunReport.chain` entry for run `n` | stop, discard, shutdown |
| Resume | `capabilities.resume`, `hostSessionId` set, status resumable (§8) | `room_send` to a finished worker |
| Delete the worktree | owned (`decideDiscard`), with a discard plan recorded (§10) | discard, retirement cleanup |

### 2. Open and reconcile

`WorkerRegistry.open(commonDir)` runs once per MCP process. It runs migration first if
`migration.json.done` is not true. `reconcile()` runs at open, every 30 s, after every operation, and on the
`fs.watch` of `registry/` and `runs/`. Per record it:
1. Recovers orphaned leases (§3).
2. Settles launch outcomes and exit observations (§3, §5).
3. Finishes recorded plans whose steps allow it (§10, §12).
4. Emits `onChange` for the projectors (§13).

### 3. Spawn (`room_spawn`, write-ahead)

1. **Validate, then admit under the capacity guard (N3).** `withGuard(registry/capacity)` spans counting
   `occupancy()` (records whose status is `starting`, `running`, `unknown` or `ambiguous`, from every process)
   and writing the intent record of step 3. Resume holds the same guard from its count to appending run
   `n+1` (§8). This replaces `Rooms.launching`/`reserveWorkerLaunch`, which counted one process only.
2. **Reserve the tag.** `createExclusive(tags/<tag>.json, {id, holder, at})`. On EEXIST the reservation is:
   - **Bound** if record `id` exists and is not `abandoned`, and is not `retired` with every `cleanup` done and
     no `keptWorktree`. A retired-but-kept worktree keeps its tag until it is discarded. The reply is "tag in
     use by <lead>'s worker <id>", "still being cleaned up in <room>" or "kept at <dir>".
   - **Reserving** if the record is absent and the holder is `alive` or `unknown`. The reply is "being spawned
     right now".
   - **Orphan** if the record is absent and the holder is `dead`. It is recovered under the guard. This is safe
     because the record is written before any resource exists (MF1).
3. **Write intent.** Acquire `workers/<id>.op` and write the record with `phase: 'intent'` and run 1:
   `{nonce, busFrontier, promptMsgIds: [], launcher, logStart: 0}`. `busFrontier` is the lead's highest hub
   seq at intent, which seeds the ledger's frontier. For Claude, `hostSessionId` is pre-generated.
   The worker's name is reserved in its room (§15).
4. **Prepare, journaled** (MF2). `prepareWorktree` calls `onStep(step, facts)`, and the registry persists
   each step before its mutation: `PrepJournal = { step, worktreeExisted, branchExisted, previousCarryRefs:
   Record<ref, sha | null>, untrackedTree?, created, branchCreated }`, steps `plan → worktree → branch →
   carry-commit → carry-refs → untracked → prepared`. `plan` records the pre-existing facts before any git
   command. Recovery of `preparing` undoes, in reverse, only what the journal says this spawn did (worktree,
   branch, carry refs restored to `previousCarryRefs`), then writes `abandoned`. This is
   `cleanupPreparedWorktree` driven by the journal. The carry-record ownership checks
   (`worker-git.ts:202–218`) go: a `room/<tag>` branch or worktree unknown to the registry is refused as
   "unmanaged; discard it by tag first".
5. **Launch, tri-state** (MF3).
   - `defaultSpawner` gets env `ROOM_WORKER_ID`, `ROOM_WORKER_RUN`, `ROOM_LAUNCH_NONCE` and `ROOM_REGISTRY`,
     and sends stdout to the log file, not a pipe (F1).
   - **Claude argv (D4, F5).** `workerCommand` (`worker-config.ts:110`) today builds `claude
     [--dangerously-load-development-channels <ch>] -p [--resume <id>] <prompt> --permission-mode
     acceptEdits --allowedTools … [--model] [--effort] [--name] [--session-id <id>] [--max-budget-usd]`,
     with no `--output-format`; its stdout already goes to the log file (`worker-process.ts:77` pipes only
     Codex). Every Claude run, fresh and resume, gains `--output-format stream-json --verbose`, so the log
     is one JSON event per line and §8 can read acceptance from it. Its two readers change with it:
     `followUpAnswer` (`registry.ts:65`, which returns the last plain line for Claude) takes the `result`
     text of the run's final `result` event, else the last `assistant` text; `workerLogTail`
     (`worker-process.ts:43`) renders assistant text and the `result` line instead of raw JSON.
   - **Never:** a synchronous `spawn()` throw, or an `'error'` event before `'spawn'`, records `launch = never`
     with the error.
   - **Launched:** right after `spawn()` returns, the registry writes `launch = { launched, pid }`. On
     `'spawn'` it probes and adds `process`. An identity that is unreadable or already gone leaves `process`
     absent: the run is launched but not signalable until an admitted report supplies its chain.
   - **Ambiguous:** a record with no `launch` whose launcher instance is `dead` becomes ambiguous at
     reconcile. Nothing but the launch handoff (§4) upgrades it: there is no cwd scan and no time comparison.
   - **Handoff (MF3).** Only the launched child has `ROOM_LAUNCH_NONCE`, so its admission (§4) is launch
     evidence. Admission therefore accepts phase `prepared` as well as `active`. When reconcile finds a run
     writer for a run whose `launch` is absent or `ambiguous`, it records `launched` with the process from the
     writer's chain and advances `prepared` to `active`.
   - Room never relaunches an ambiguous run. Its status is `ambiguous` (§6), and the lead or human chooses
     resume (§8) or discard. Its `promptMsgIds` stay unreceipted.
6. Write `phase: 'active'`, release the op lease, and keep the tag reservation until §12.

`launchWorkerProcess` takes a `LaunchHost` (`setHandle`, `watch`, `aborted`) instead of `Rooms`.

### 4. The worker side: admission and reports (MF8)

At join, a process with `ROOM_WORKER_ID` is admitted as the worker only if all of these hold:
- the record exists at `ROOM_REGISTRY`;
- its phase is `prepared` or `active`;
- `ROOM_WORKER_RUN` is the newest run, and that run's `nonce` equals `ROOM_LAUNCH_NONCE`;
- `dir` matches its worktree root;
- it obtains the run's writer token **atomically**: `createExclusive(runs/<id>/<n>.writer, myToken)`, or,
  when the existing writer is `dead` with the same host session (an MCP restarted inside the run),
  `replace` under the guard. Two concurrent MCPs cannot both become the writer (MF8).

A refused process, including a stale one in a kept worktree, joins as nobody and tells its agent "this
worker run was collected, discarded or superseded". Report writes run under the writer file's guard after a
full-token compare, and they are monotonic merges: `joinedAt`, `chain` and `hostSessionId` are set once, and
`done` is added once and never removed, even by a restarted instance.

The worker's daemon reads `base`, `carriedBase` and `carriedUntracked` from the record, not from the CRDT
(F2). It publishes `base = C` in its workers room (R3a). In a team room it joined itself, it publishes the
lead's current team-room base and diffs its full tree against it (R3c).

`room_done` merges `done` into the run report and posts the completion message (§7), with no Y.Doc status
write. Admission replaces the stale-generation guard at `tools/workers.ts:57–63`.

### 5. Exit observation (MF6)

The launcher's child `'close'` callback writes `runs/<id>/<n>.exit.json` (`witnessed: true`) at once,
without an op lease (one writer), before dropping the handle or waking waiters. Reconcile writes
`witnessed: false` only when the process, the exit file and the launcher are all gone, so no callback can
still arrive. A witnessed file replaces an unwitnessed one, never the reverse, and polling never invents an
exit code.

### 6. Status: `statusOf(record, runs, reports, exits, liveness)`, total (MF4)

Run `n` is the newest run, but a resume run with `launch = never` is skipped, and its status is that of
`n-1` with the note "follow-up not delivered". The first matching row wins.

| # | Facts | Status | Note |
|---|---|---|---|
| 1 | phase `retired` | `retired` | not projected |
| 2 | phase `abandoned` | `abandoned` | not projected |
| 3 | phase `collecting`/`discarding`/`retiring` | `collecting` | `interrupted` shown if set |
| 4 | run `n` `ambiguous` | `ambiguous` | "launch may or may not have started; resume or discard" |
| 5 | fresh run `n` `never` | `failed` | "never started: <error>" |
| 6 | run `n` `imported` | `imported` | "a 0.16 worker; Room cannot check whether its process still runs" |
| 7 | phase `intent`/`preparing`/`prepared` with no launch fact, or run `n` has no `launch` and its launcher is `alive`/`unknown` | `starting` | |
| 8 | launched; process `alive`, or no exit file and the launcher is `alive` | `running` | "stopping" if `stop` is for run `n`; after 60 s with no run writer: "has not joined the room: its host's Room plugin may be older than 0.17 (host X)" |
| 9 | launched; process `unknown` and no exit file | `unknown` | "cannot verify pid P" |
| 10 | report for run `n` has `done` | `done` | the report wins over any exit code; a nonzero code is noted ("exited 137 after reporting") |
| 11 | `stop` recorded for run `n` | `stopped` | stop reason |
| 12 | witnessed exit 0, and an earlier run has a `done` report | `done` | `followUp` = `followUpAnswer(log, logStart)` |
| 13 | witnessed exit 0, no report at all | `failed` | "exited without room_done" |
| 14 | witnessed exit nonzero or signal | `failed` | code or signal, log tail; for Claude, the final `result` event's error (a missing resumed session: §8) |
| 15 | unwitnessed exit, resume run, earlier `done` report | `done` | "follow-up outcome unknown: ended while no session of yours was running" |
| 16 | unwitnessed exit, otherwise | `failed` | "stopped while no session of yours was running" |
| 17 | launched, process `dead`, no exit file | `running` | "exit being recorded"; the next reconcile writes it (§5) |

Launch facts (rows 4–6) outrank `starting` (MF4), so `prepared` with an ambiguous or `never` launch is never
reported as starting. Rows 12 and 15 are all that remains of 0.16.31: a follow-up is a turn, and the task's report stands. There is
no `resumedDone` code path and no edge write.

**Adapter to the kept `workerRealState`/`decide*` (MF5).**
`realStateInput(record, status, run)` maps `WorkerStatus2` onto the old `WorkerStatus`:

| `WorkerStatus2` | old `WorkerStatus` | finished / dismissed |
|---|---|---|
| `starting`, `running`, `unknown`, `ambiguous` | `running` | false / false |
| `done` | `done` | true / false |
| `failed` | `failed` | true / false |
| `stopped`, `imported` | `dismissed` | true / true (so an explicit collect takes it; collect-all skips it) |

`collecting`, `retired` and `abandoned` never reach `decide*`. The adapter also supplies `exitCode`,
`finishedAt`, `dismissedAt` (`stop.at`), `pid`/`processStartTime` only under the signal capability (else
`pid: 0`, which probes `not-ours`), and `hostSessionId` only under the resume capability. `decideCollect`
takes the capability (`copy` refuses apply) and returns `skip-status` for `ambiguous`.
`worker-state.test.ts` gains the mapping as tests.

### 7. Completion message (SF1, the ledger's contract)

There is one ID, `wk:<workerId>:<run>`, and one builder, `completionMessage(record, run, status, report?)` in
`shared/src/worker-messages.ts`. It gives `done`, or an `interrupt` note for a witnessed failure.
- **The worker's `room_done`** posts it, then sets `report.posted`.
- **The projector** posts it for a terminal run `n` only if neither `report.posted` nor `runs[n].posted`
  exists, then sets `runs[n].posted`.
- **Durable fact, not bus absence (SF1).** A trimmed bus or a pruned receipt never causes a repost. Only a
  crash between a post and its `posted` write can repeat it, once, and the ledger's `owed()` dedupes that by ID.

### 8. Resume (message to a finished worker)

`room_send` to a worker name resolves it through `trusted()`, not `s.room.workerOf`. `WorkerRegistry.resume`:
1. Take the op lease. The worker needs the resume capability and a status of `done`, `failed`, `ambiguous`,
   `imported`, or `stopped` with reason `lead-session-ended`, or `message-delivered-*`.
2. Run `decideResume` and `waitForPreviousExit` unchanged. For `ambiguous`, waiting requires that no process
   matching the run's evidence is alive.
3. Under the capacity guard (§3.1), count occupancy, then append run `n+1` with a new nonce, `busFrontier`
   and `promptMsgIds` (the follow-up plus the worker's other owed addressed messages, per the ledger), and
   clear `stop`. This is the write-ahead point.
4. Launch it tri-state (§3.5).

The registry writes no receipt, because a recorded launch is not host acceptance. The ledger commits
`via: 'prompt'` receipts from the admitted worker MCP's first Room call. If the run makes no Room call, the
projector commits them only on log evidence from `logStart`:
- **Codex:** a `turn.started` for thread `hostSessionId`.
- **Claude (D4, live check on Claude Code 2.1.283, 2026-09-28):** an `assistant` event whose `session_id
  === hostSessionId` in the run's stream-json log (§3.5). `system/*` events (`system/hook_started`,
  `system/init`) are not evidence: an accepted resume emits them *before* any model output, the same
  reason a SessionStart select is not evidence (ledger §Resume). The exit code alone is not evidence.

Otherwise the IDs stay owed. The reply stays "resumed <tag>'s retained conversation with your message".

**A missing Claude session (D4).** `claude -p --resume <missing-id> <prompt> --output-format stream-json
--verbose` exits 1, prints "No conversation found with session ID: <id>" on stderr and emits one `result`
event with `subtype: "error_during_execution"`, `is_error: true` and `num_turns: 0`, and no `assistant`
event. So no receipt is written, and row 14 applies with the detail "its retained conversation <id> no
longer exists; the message stays owed". An accepted resume exits 0, keeps `session_id` equal to
`hostSessionId` on every event (Claude forks only with `--fork-session`, which Room never passes), and
ends with a `result` of `subtype: "success"`.

### 9. Stop (dismiss, lead shutdown)

Take the op lease and write `stop` before signalling. Signal only under the signal capability, keeping
`decideStop`, `stopWorkerWithEscalation` and `terminateWorktreeProcesses`. An unconfirmed stop keeps `stop`
and reports "left running". Row 8 then shows "stopping". `persistWorkerStopReason` and the carry record's
stop fields are deleted.

### 10. Discard (MF7)

1. **Preflight, nothing written.** Check ownership, nested workers (`record.lead.participant` chains), and
   ignored artifacts against `force`. A refusal returns here, as today (`collect.ts:137,164`).
2. **Commit the plan.** Write `phase: 'discarding'` and `discard = { force, children: [ids], steps: {},
   patch?: { path: patches/<id>.patch, sha256 } }`.
3. **Steps, each recorded done:** `children`, `stop` (§9), `patch`, `cleanup`, `prune`. `saveDiscardPatch`
   builds and verifies the patch in scratch, records `patch = {path, sha256}`, and only then links it into
   `patches/<id>.patch` (MF7). A replay keeps a file whose hash matches. A mismatched file is quarantined, and
   a missing or mismatched one is rebuilt, its identity recorded before publication. Patches expire after 7
   days.
4. **Refusal after commit** (for example, a new ignored artifact without `force`) sets
   `interrupted: { op: 'discard', detail }` and restores `active`. It is not retried automatically.
5. **Recovery.** A `discarding` record whose op-lease holder is `dead` continues from its recorded steps,
   under the recorded `force` only, then retires (§12).

### 11. Collect (registry part only; Leave 1)

1. Take `collect/<h(lead worktree)>`, replacing `collectQueues`. Another process waits up to 30 s, then
   refuses.
2. Per worker: take the op lease and gate with the capability and `decideCollect`.
3. Write `phase: 'collecting'` before the first checkout write; the future journal keys on it.
4. On success, retire (§12). On failure, restore `active`. A `collecting` record with a `dead` lease holder
   returns to `active` with `interrupted` ("files may be partially applied"), shown in `room_state` and in
   the next `room_collect`.

### 12. Retirement, keyed by worker ID (MF13)

1. Write `phase: 'retiring'` with `cleanup[room] = 'pending'` for each room the worker joined or was
   projected into. From here no projector writes the worker (§13, N2).
2. In each room, that room's projector runs `retireWorker(id)` in one transaction. It is a compare-and-delete:
   W's flat participant keys, claims, scope, manifest, graph, colors, conflict slots and `seen:` are deleted
   only if `${W}\0holder`.workerId === id (for a team projection: `projectedFrom === id`). It also deletes
   `workerViews[id]` and appends the archive entry once, keyed by ID. A newer worker's name is never touched.
3. An offline room stays `pending`, and it is retried on reconnect.
4. When every room is `done`, the record goes to `phase: 'retired'` in `retired/`, and the tag is released by
   compare-and-release, unless `keptWorktree` holds it until a discard.

Auto-retirement keeps `decideRetire`'s rules, including keeping a done worker that has a host session until
an explicit collect or discard (`registry.ts:227`).

### 13. Rooms and writers per spawn mode (MF14, R3b)

| Record, per room | `mode: 'here'` (joins the lead's room) | `mode: 'local'`, workers room | `mode: 'local'`, team room |
|---|---|---|---|
| Who is in the room | the worker's own session | the worker's own session | nobody (its daemon is absent) |
| W's identity and `holder` fields (flat) | the worker session (holder: its own session, `workerId`) | the worker session | the lead's bridge (holder fence = lead session, `workerId`) |
| W's `git.base` (reporooms) | the worker daemon: the lead's team-room base in a team room (R3c), `C` in a local room | the worker daemon: `C` | the bridge: the lead's current team-room base, with the worker's full tree diffed against it (R3c) |
| `manifest[W]`, `manifestHead[W]` | the worker daemon, fenced by its own session | the worker daemon | the bridge: projected, `projectedFrom: id`, lead fence (manifest §5.5) |
| `coordination[lead]` | none (the worker is present itself) | none | the bridge |
| `workerViews[id]` | the lead's session in that room | the lead's workers-room session | the bridge |
| Conflict slots for W (reporooms §B5) | the worker's session | the worker's session | the bridge: slot keys owned by W, fenced by the lead's holder; notices go to W in the workers room |
| Retirement cleanup (§12) | the lead's session in that room | the lead's workers-room session, after the worker's daemon stops | the bridge |

The input for every lead-side writer is level-triggered:

```ts
projectable(lead: string, roomKey: string): { write: ProjectableWorker[]; retire: string[] }
// write:  records led by `lead` in that role with phase ∉ {retiring, retired, abandoned}
// retire: ids in phase `retiring` whose cleanup[roomKey] is 'pending' (done rooms are excluded) (N2)
onChange(listener: () => void): () => void
interface ProjectableWorker { id; tag; name; mode; view: WorkerView; base?; carriedBase?; carriedUntracked? }
```

For the team room's bridge, `projectable` returns only `mode: 'local'` workers. `project(set)` runs on start,
on reconnect and on each `onChange`, and only while the projector's holder and lease token are current (§15):
- it writes `write`;
- it runs `retireWorker(id)` for each ID in `retire`, then marks that room's cleanup `done`;
- it deletes views and projections whose ID is in neither list, or that carry an older incarnation of this
  lead.

It never writes a `retiring` record, so projection cannot undo retirement (N2).

**Read-side fence (MF11).** Readers accept a manifest, projection or `workerViews` entry only when its fence
is the current holder: `holder.sessionId` for a participant's own records, `liveHolder(projectedBy)`
(reporooms) for projections and views. Otherwise it reads "updating" or "stale". The manifest spec extends the
fence to every path entry, deletion and absence certificate through its publication incarnation, so a loser's
entry never passes under a winner's head. Completion messages are addressed facts, and the ledger delivers
them regardless.

### 15. Participant-name lease (R1, R1a, MF11, MF12)

This replaces `reserveAutoName` (`session.ts:312`). The candidate loop (bare name, `+<host>`, `+<host>-N`)
stays.

**Acquire** `room/names/<h(roomKey, name)>.json` (`NameLease`) with `createExclusive`. On EEXIST:

| Case | Result |
|---|---|
| holder `dead` | recover under the guard, then take the lease |
| same `sessionId`, holder `alive` (MCP reconnect or restart in one host session) | take over by rewriting the lease with the new instance token (compare-and-swap under the guard). The predecessor's next check sees a different nonce and stands down (MF12) |
| worker taking over its lead's reservation for `ROOM_WORKER_ID` | allowed when admitted (§4) |
| other `sessionId`, holder `alive`/`unknown` | taken: try the next candidate; an explicit tag is refused, and `takeover=true` overrides for an `unknown` holder only |

**Across clones and machines (R1a; amended for the hub).** After the local lease, the session sends
`acquire` to the room's hub (hub §2.3) with its `holder` fields. The hub grants the name with a new epoch and
writes `holder`, or answers `held`: then the session releases its local lease by compare-and-release and tries
the next candidate (an explicit tag is refused). The same session re-acquiring (an MCP restart) supersedes its
own grant; a worker takes over its lead's reservation by presenting the lead's epoch (`supersedes`). The local
relay ends a lease whose holder process is `dead` at once; the server waits out the 45 s TTL. There is no 90 s
grace, presence check or `machine` hash.

**Guarantee: one holder at a time, as seen by the hub.** A session keeps the name while it renews every 15 s
(hub §4.2). It measures validity from the send time of its last acknowledged renew, so it gives the name up
no later than the hub re-grants it (hub §4.3). It also compares its local name-lease token, nonce included
(MF12), on every tick and tool call. On a lapsed lease, `stale` or `lease-lost` it pauses coordination (hub
§7), stops its daemon's publication, withdraws (`publisher: false`) and detaches from the publisher lease
(§16); on reconnect it re-acquires, or releases its local lease and replies "another session now holds
<name>; rejoin to take a new name".

Writes it made under the lapsed lease carry the old fence, so readers reject them. The new holder's writes
and the hub's expiry replace them. Nothing depends on first-sync ordering.

### 16. Publisher lease (SF4, MF12)

`room/publishers/<h(worktree)>.json` belongs to one MCP instance, which publishes that worktree in every room
it attaches (a lead's team and workers-room sessions share one process).
- **Attach and detach.** Attaching adds `attachments[roomKey] = participant` through `replace`. Detaching
  (on leave, or on losing the name in that room, §15) withdraws that room first, then removes the entry. The
  last detach runs `compareAndRelease`.
- **Other processes.** A second process gets `publisher: false` (manifest §5.7). It takes over only from a
  `dead` holder, or when the lease file is absent because its holder released it (on leave, the idle
  lease of §18, or exit): the next reconcile tick of any attached-but-not-publishing session in the
  worktree tries `createExclusive`, and one wins. This replaces `choosePublisher`/`publishUnder`.
- **Base facts (D5, F4).** The lease is also the worktree's base-facts lease. Only its holder's daemon
  runs the full HEAD transition, writes the `git` record and posts `pushed` (reporooms §B2, §B4). Another
  session in the same checkout never does: its daemon polls HEAD only to re-anchor its own claims. With
  seventeen sessions in one checkout, a commit now gives one `git` update and at most one `pushed`, not
  seventeen notices.

### 18. Presence end and the idle lease (D5, F4)

A session's presence must end within a bounded time once its host session has finished, even when its MCP
process lives on. **Ending presence** means, in every room the session is in: remove its awareness state
and close the provider; stop its daemon; detach from the publisher lease (§16); release its hub lease
(`release`, hub §2.3, sent before the provider closes) and its local name lease by compare-and-release (§15). It deletes nothing from the doc: its records, claims, scope and owed mail stay,
shown offline, and age toward the reporooms expiry. A publisher whose checkout has another fresh session
naming it as publisher (manifest §5.7) withdraws first, in §16's handover order, so that session can
publish; otherwise its last manifest stays, shown offline with its age, as after an exit.

**The signal, per host.**

| Host session | End signal | Bound |
|---|---|---|
| Claude, interactive or `-p` | The MCP is a stdio child of the `claude` process. Stdin EOF means the host exited: the MCP ends presence and exits. Backstop: the 30 s reconcile tick finds `liveness` of the bound `session.json` `hostPid` `dead` | seconds; ≤ 30 s |
| Codex under `codex` or `codex exec` | the same: stdio child, stdin EOF, `hostPid` backstop | ≤ 30 s |
| Codex under a shared `codex app-server` (the broker's `codex-rescue` threads, IDE sessions) | the idle lease below. The MCP's stdin stays open while the app-server lives, and the app-server's pid says nothing about one thread | N + one tick |

**What Codex exposes, and why it is not the rule.** The locally installed Codex (codex-cli 0.157.1;
protocol generated on 2026-09-28 with `codex app-server generate-json-schema`, v2) has server notifications
`thread/status/changed` (status `notLoaded`, `idle`, `systemError`, or `active` with `activeFlags`),
`thread/closed`, `turn/started` and `turn/completed`. They go to the app-server's client, here the Claude
plugin's broker, not to the MCP servers the app-server starts; and an MCP server does not know which thread
it serves (open question 1, ledger Q2). Codex 0.157.1 also has `sessionEnd` and `stop` hook events, but
`plugins/room/hooks.json` is frozen (a change un-trusts every Codex user's hooks, AGENTS.md), so Room
cannot add one. The current Codex app-server docs page could not be read from this session (web access was
not granted), so nothing here rests on it. **The idle lease is the rule.** If a later Codex lets the MCP
learn its thread and observe `thread/closed` or `notLoaded` (for example through the shared daemon's
`codex app-server proxy`), that becomes a faster end signal, and the idle lease stays as the backstop.

**The idle lease (sessions under a shared app-server).**
- **Activity** is a Room tool call handled for this session, or a hook contact on its arbitration
  endpoint for its bound session (a before-edit or SessionStart select; ledger). An unbound MCP cannot be
  reached by hooks (ledger), so for it only Room calls count. A live host process is not activity.
- **`idleMin`** is measured on the MCP's monotonic clock since its last activity and published in its
  presence on every heartbeat (reporooms, participants view). Views show it from 10 minutes: "ben (idle
  25 min)".
- **Leave** when all hold: `idleMin ≥ N`, with **N = 30 minutes**; the session holds no scope and no
  claims in any of its rooms; `projectable(me)` has no `write` entries (it leads no non-terminal
  worker); and no `room_wait` is in progress. It then ends presence as above.
- **Return.** The session's next activity rejoins as at start: the name candidate loop (usually the same
  name, which it released), a fresh daemon and a full scan. That reply begins "[room] rejoined
  <room> as <name> after N min idle". Owed messages were kept under the name and are delivered then.
- **Why 30 minutes.** The finished `codex-rescue` threads of 2026-09-26/27 sat for two days; 30 minutes
  bounds that to one idle lease. A thread still working quietly with no scope or claims is either alone
  or not coordinating; its return costs one rejoin line and a scan.

**Held scope and claims: H1, decided by the human on 2026-09-28.** A shared app-server session holding
scope or claims stays present and shows its own idle duration. At eight hours of inactivity on that MCP's
monotonic clock, it releases only claims owned by its participant and posts one broadcast `note` from that
participant naming the released paths/ranges. The lead's extension of H1 clears the same session's scope
at that boundary, including when it held scope but no claims. The next idle-lease tick can then end
presence. An interactive CLI session never releases claims or scope solely for quiet time. Activity resets
the eight-hour measure. No timestamp from another machine is compared with this clock.

`WorkerRegistry.reconcileIdleClaims` is callable by the wave-4 presence loop or a rehearsal with injected
`monotonicMs`, `RoomDoc`, and `postNotice(id, text)`. It writes a durable pending record under
`room/sessions/<sid>/idle-claims/` containing the claim IDs/names and scope fact, removes those claims
through `RoomDoc.removeClaim` and the scope through `clearScope`, posts with deterministic ID
`idle-claims:<sessionId>:<idleEpoch>`, then marks the record done. Replay of a pending record repeats the
removal safely and posts the same ID; the ledger's idempotent `post(..., {id})` covers a crash after post
but before done. A completed record emits no second notice. The clock and activity epoch are per session.

**A human at a quiet terminal.** An interactive Claude or Codex CLI session has an exact end signal, so
the idle lease does not apply to it: while its host process lives it stays present, and after 10 quiet
minutes it shows "ben (idle 25 min)", or "ben (idle 3 h; holds 2 claims)" when it holds claims. Its claims
and scope are never dropped for being quiet. Under a shared app-server (an IDE), a quiet session that
holds scope or claims shows the same line and stays until H1's eight-hour release; one that holds neither
leaves after 30 minutes and comes back on its next Room call.

## Migration (R6a: local state only, once per clone; MF9, MF10)

`open()` runs migration under `createExclusive(migration.lock)`, recovered only if its holder is `dead`.
`migration.json` holds `{ v, sources: { <sourceKey>: { id, state: 'assigned' | 'imported' } }, done }`. For
each source, in order (MF10):
1. **Map first.** Durably write `sources[key] = { id, state: 'assigned' }`.
2. **Import.** Create the tag reservation and the record under that ID. Both are idempotent for that ID.
3. **Mark.** Write `state: 'imported'`.

A restart reuses assigned IDs, so no source is minted twice. `done: true` is written last. Deleting
`room/registry/` by hand is unsupported; re-migration then imports only the local evidence that remains.

**Sources.**

| Kind | Evidence | Imported as |
|---|---|---|
| **active** | worktree `<lead>/.room/workers/<tag>` (nested included) passing `isOwnedWorkerWorktree`, branch `room/<tag>`, no retired snapshot entry keeping it | phase `active`, one run with `launch: imported` (row 6) |
| **retired-kept** | as active, but the old snapshot's `retiredWorkers` has `keptWorktree` = this dir | phase `retired`, `cleanup` done, `keptWorktree` set: the tag stays bound (§3.2) until a discard |
| **unmanaged** | a `room/<tag>` worktree or branch that fails ownership | not a record. `room_state` lists it once and a discard by tag removes it |

**Capabilities, each requiring local evidence bound to the worker (MF9/MF10).**
- **Delta collect:** `<common>/room-carry/<tag>.json` with a `base` (and `carriedBase`) whose commits exist.
  Otherwise the worker is copy-only.
- **Resume:** the worker worktree's own `room-session.json`, with `worker_id` equal to the old ID and a host
  that matches. A snapshot's `hostSessionId` never counts.
- **Signal:** never, because 0.16 recorded no such evidence. A 0.16 process that is still running is left
  alone. An explicit collect warns "a 0.16 process may still be writing here", and a discard needs
  `force=true`.

The old local snapshot's `workers` entry (`relay/src/memory.ts` file, decoded read-only) is replicated data. It
supplies only display fields: `task`, `summary` as `legacy.said` (never as a report), `host`, `model` and
`startedAt`. The carry record stays on disk, renamed `.migrated`, until that worker retires, so its metadata
is never lost before retirement. The old lock folders are ignored, and their dead-pid files are deleted.
Records are keyed with `repoRoomOf` room keys (reporooms item 1).

**Mixed installs (reporooms §B12).**
- **New lead, 0.16 worker.** A 0.17 relay is a new generation, so a 0.16 worker never reaches it and is not
  refused. It never takes a run writer, so row 8 shows the "has not joined" detail. When it exits, rows
  13 and 14 apply. Nothing is signalled on the strength of room text (N1).
- **Old lead, 0.17 worker.** The worker exits non-zero at once, with the lead-side update text, on a legacy
  `ROOM_WORKER_ID` (`lead/tag#gen`) or a legacy-form `ROOM_ROOM`. Otherwise it uses `record.room` verbatim.

| Kill -9 of the lead at… | Durable state | Next reconcile |
|---|---|---|
| after the tag reservation, before the record | a tag with a dead holder, no record | orphan, recovered |
| during preparation | `preparing` with the journal | reverse the recorded steps, then `abandoned` |
| between `spawn()` and `launch` written | no `launch`, dead launcher, phase `prepared` | `ambiguous` unless the child takes the run writer (§3.5 handoff) |
| after launch | `launched`, pid ± identity | the worker runs on (F1 fixed). Exits become unwitnessed (§5), reports arrive (§4) |
| during discard | the plan and its steps | continue under the recorded `force` (§10) |
| during collect | `collecting` | `active` with `interrupted` (possible partial apply; Leave 1) |
| during retirement | `retiring` with a `cleanup` map | continue per room, compare-and-delete |
| after H1's pending idle-release record, before claim/scope removal or notice | pending claim names/IDs and scope fact | remove only this session's still-owned claims and scope; post the same deterministic notice ID, then mark done |
| after H1's notice, before its done record | pending idle release | repeat the deterministic ID; ledger de-duplicates; mark done |

A worker kill -9, a restarted worker MCP, a partition and two sessions in one checkout are covered by §5,
§4, §15 and §16. A corrupt file goes to `quarantine/` and is reported. Its tag stays reserved until a
copy-only `room_collect tag=X discard=true`, which uses the canonical path and the ownership checks.

## Rollout order and size

All of it ships in schema 2 (0.17):
1. `leases.ts`, `boundSession()` and the hook records (first: the ledger needs the binding).
2. The store, reconcile, `statusOf`, the adapter and migration.
3. The write paths and the worker report.
4. Readers and projectors (needs reporooms and manifest).
5. Name and publisher leases, publisher-only base facts and the presence end (§16, §18; needs reporooms).
   The stream-json Claude argv and its log readers (§3.5, §8) go with the ledger's resume step.

About 2,100 lines added and 1,350 deleted.

## Risks

- `link` atomicity can fail on network filesystems. Leases refuse to start if a probe link fails.
- Stale views while the lead is away are shown "as of", and completion still arrives through the ledger.
- On Windows, a reused pid can keep a lease reserved until a human overrides it.

## Open questions

1. **Codex app-server binding.** Does `x-codex-turn-metadata` carry the thread ID? The survey shows only
   `workspaces` (`workspace.ts:36`), and this is the same question as the ledger's Q2. Check the current docs.
   D5 adds a second reason: with the thread ID, the MCP could also learn when its thread closes. The
   codex-cli 0.157.1 protocol has `thread/status/changed` and `thread/closed`, but only for the
   app-server's client (§18); whether an MCP server can observe them is unverified.
2. **Claude `/clear` and hook ancestry.** Does SessionStart fire on `/clear` with a new `session_id`, and
   does the hook's ancestor chain contain the MCP's parent? Verify against the current hooks docs and a live
   run.
3. **Collect wait.** For a second process, is 30 s followed by refusal right, or should it queue without a
   bound?
4. **Which room a Codex thread in a clone joins (D5; verify in the wave-0 rehearsal).** The threads of F4
   worked in `/tmp` clones but joined the *main* checkout's local room. They were started on 2026-09-26/27,
   possibly on bundles older than 0.16.24. The rehearsal starts a `codex-rescue` thread through the shared
   app-server in clone X, records the bundle version, and checks that a thread whose turn metadata names X
   binds to X's room (`roomKey` from X's common dir), not the app-server's cwd. If it does not, binding by
   turn metadata (open question 1) is a precondition for §17's app-server row.
   **Answered 2026-09-28 (wave-0 rehearsal §4, corrected):** not a Room bug. The thread's workspace was the
   broker's `--cwd` (the lead's checkout); the prompt only set a per-command workdir. With `--cwd <clone>`,
   Room joins that clone's room, so this path needs no turn-metadata binding. The lingering MCPs are the
   broker never unsubscribing finished threads; §18's idle lease still covers them.
5. **Resolved by the human on 2026-09-28 (H1):** a finished app-server session holding scope or claims is
   shown idle; after eight hours on its own monotonic idle clock, its claims are released automatically
   with one notice naming them. The lead additionally clears its scope then, so presence can end on the
   next idle-lease tick. Activity resets the cap; interactive CLI sessions are exempt (§18).
