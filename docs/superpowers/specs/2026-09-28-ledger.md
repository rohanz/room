## Goal

The question "has participant P been shown message M" should have one answer, in one place: the
CRDT receipt map `seen:<P>` (R2). Every path that puts content in front of an agent follows one
rule:

> **Select only if unseen and not in flight; hand off; after a confirmed handoff, record the
> receipt.**

- There is one definition of what P is owed.
- Addressed messages stay owed until a receipt exists, even after they leave the bounded history.
- A wake-up (`codex queue`, the Claude inbox socket, a channel notification) carries no content
  and writes no receipt.
- One process arbitrates delivery for a host session: that session's MCP, fenced as the current
  holder of P. No local file decides "unseen".

## Invariants

1. **R2a, stated verbatim:** delivery is AT-LEAST-ONCE everywhere. A receipt is written only after a
   confirmed handoff. Duplicates are tolerated and minimised; loss is never acceptable.
2. The only replicated fact "P was shown M" is `seen:<P>[M.id]`. No local file, reservation or wake
   record is consulted to decide it.
3. The confirmed handoff is defined per path (table in [Handoff boundaries](#handoff-boundaries)).
   The handoff is to the host, not a model acknowledgement: Room cannot observe the model reading
   anything.
4. For each host session, one owner arbitrates in-flight delivery: its MCP. Reservations live in
   memory, expire, can be reclaimed, and are never receipts. One response carries the union of
   its selected ids, each at most once.
5. Every ledger operation is fenced. Select, wake, commit, prompt receipts and state snapshots run
   only while `participants[me].holder.sessionId === boundSession().id` (R1a; registry §12, §16).
   A process that fails the fence stops delivering.
6. `seen:<P>` has one writer at a time. While P's holder is live it is that holder's MCP. For a
   worker whose holder has ended, it is its projector (registry §14), fenced as projector. A
   `moot` receipt is never written: relevance is computed at read time.
7. `to` on any message means only the addressee participant. An addressed message (`m.to === P`)
   is owed until a receipt exists. It can also end with a
   recorded per-message terminal outcome: `expired`, `over-cap` or `recipient-retired`.
8. A broadcast is offered to session S only if its id was not in S's **frontier**, the set of bus
   ids S had observed when it first bound. Each broadcast is routed for S at most once. Addressed
   messages ignore the frontier.
9. The trim is a pure, idempotent function of doc state. Two trimmers in a partition converge
   after merge, and no trim-owned value is read-modify-written.
10. Owed delivery is bounded by count, bytes and age over `bus ∪ mail`, with admission at the
    sender and a terminal outcome for anything evicted.

## Data model

### Y.Doc (replicated; all of it is new at `schemaVersion: 2`, R6a)

| Root | Type | Key → value | Writer |
|---|---|---|---|
| `bus` | `Y.Array<Msg>` | bounded history | poster appends; the trim deletes |
| `seen:<P>` | `Y.Map<Receipt>` | msgId → `{s, via, at}` | invariant 6; also P's holder prunes (SF5) |
| `mail` | `Y.Map<Msg>` | msgId → addressed Msg that left `bus` | (1) the trim; (2) **migration**, a second writer that runs once per source (reporooms §Migration): `migrateRepo` on the server or relay, before admission; and later the release of an `unresolved` entry, in one transaction, by the fenced holder whose clone proves the legacy identity. | `outcomes` | `Y.Map<Outcome>` | msgId → `{to, from, outcome, at}` | the trim; `retireParticipant` |
| `archive` | `Y.Map<ArchivedMsg>` | msgId → `[type, from, at, areas, unfulfilled?]` | the trim. Replaces the read-modify-write `ledger` counts (`foldLedger`, `shared/src/ledger.ts:52`). Counts are derived at read time. |

export type Via = 'reply' | 'wait' | 'hook' | 'prompt' | 'agent'
export interface Receipt { s: string; via: Via; at: number } // s: holder session id (registry)

**Per participant, with session provenance (Leave 3).** The receipt map stays per participant; `s`
records which session got the message.
- Under R1/R1a and fencing, only the current holder selects or commits for P.
- A successor session B does not see what A was shown, but everything owed reaches B.
- `s` is never a filter.

### Message lookup (SF2)

`RoomDoc.message(id)` looks in `bus`, then in `mail`. A mail entry is deleted only when it is
receipted **and** its reply window has closed:
- it is neither a question nor a note, or
- it has been answered, or
- it is older than `REPLY_WINDOW` (14 days).

`holdingQuestion` (`registry.ts:302`), `room_send` inReplyTo validation (`messaging.ts:86,147`),
`unavailableQuestion`, `recipientNotice` and the resume path all use `message(id)`. Mail is bounded
(below), so the index is bounded. `trimBus`'s pinning of unanswered questions (`doc.ts:464`) is
deleted: questions move to `mail` like any addressed message.

### The trim (`shared/src/delivery.ts` `trim(doc, now)`, replacing `RoomDoc.trimBus`)

The trim is a function of `(doc, now)`. Each step is monotone: it only adds idempotent entries or
removes items.

1. **Which bus messages leave the bus.** Every message beyond the newest `BUS_KEEP` (2000), or
   beyond `BUS_BYTES` (1.5 MiB, serialized, counted from the newest), is handled in one
   transaction:
   - Write `archive.set(id, compact(m))`.
   - Write `mail.set(id, m)` when either condition holds:
     - it is **owed**: `m.to` is set, and there is no `seen:<m.to>[id]` and no `outcomes[id]`;
     - it is **reply-eligible**: an addressed question or note still inside its reply window,
       **receipted or not** (SF2).
   - Delete it from the bus.

   Yjs deletes are per item, so two trimmers deleting the same items converge. `set` of the same
   id with the same value converges.
2. Mail entries go when both are true: they are receipted, and they are outside the reply window
   (Message lookup).
3. **Bounds (MF6)**, all by the deterministic order `(at, id)`:
   - An owed message older than `OWED_TTL` (14 days) gets `outcomes.set(id, expired)` and is
     removed.
   - Each recipient's owed set (`bus ∪ mail`, unreceipted) is capped at 200 messages and 256 KiB.
   - All of `mail` is capped at 2,000 entries and 1.5 MiB.
   - Past a cap, evict in this order, writing `outcomes.set(id, over-cap)` for each owed eviction:
     1. receipted reply-eligible entries (they stop being answerable);
     2. owed `fyi` entries;
     3. owed `notify` entries;
     4. questions, last.
4. The archive keeps the newest 5,000 entries by `(at, id)`, within 512 KiB, plus unfulfilled
   releases (at most 200). `outcomes` keeps entries for 30 days, or at most 2,000 (256 KiB).

The clock (`now`) appears only in monotone expiry. A trimmer with a fast clock only expires
earlier, and the merge is the union of removals. Trim-leader election (`trimBusIfLeader`,
`roomd/src/index.ts:986`) stays only to limit churn; correctness does not depend on it.

**Aggregate snapshot budget (MF6).** The ledger's memory roots have one serialized budget:

`LEDGER_BUDGET = 4 MiB` = bus (1.5 MiB) + mail (1.5 MiB) + archive (512 KiB) + outcomes (256 KiB)
+ receipts (256 KiB).

- The remaining 1 MiB under the relay's `MAX_MEMORY_BYTES` (5 MiB, `relay/src/memory.ts:7`) is for
  the siblings' memory roots (`meta`, `participants`, `scopes`, `colors`, `retiredWorkers`,
  `workerViews`). Their specs own that share.
- **Receipts in a snapshot.** It keeps, in priority order:
  1. receipts for `mail` entries;
  2. receipts for addressed bus messages;
  3. receipts for broadcasts, newest first, until the 256 KiB is spent.

  A dropped broadcast receipt can only cause a repeat, and only for a session whose frontier does
  not already cover that broadcast.
- **`memorySnapshot` never exceeds the limit.** It measures the encoded update and, if it is over
  5 MiB, drops in this order:
  1. archive entries, oldest first;
  2. broadcast receipts;
  3. the oldest bus broadcasts.

  It never drops `mail`, `outcomes` or addressed receipts, which fit by construction. It logs
  what it dropped. Today `saveMemory` (`relay/src/memory.ts:36`) skips an oversized snapshot
  outright; that path becomes unreachable, and a test covers it.

**Deterministic ids (reporooms rev 2).** `RoomDoc.post(from, body, {id?})` accepts an id chosen by
the caller:
- epoch-based conflict notices (reporooms);
- `wk:<id>:<n>` completions (registry).

A post whose id already exists in `bus`, `mail`, `archive` or `outcomes` does nothing and returns
the existing record, so a retry after a crash cannot create a second copy. Two concurrent posts of
one id on partitioned replicas can both land on the bus; `owed()` dedupes by id, so it is still
delivered once.

**Admission (MF6).** Every addressed post goes through `admit(doc, m)` in `RoomDoc.post`:
1. Run `trim` (it is idempotent).
2. Check the recipient's owed caps and the mail and bus byte budgets.
3. The outcome is explicit:
   - `room_send` over a cap is refused with the reason: "X has 200 undelivered messages; wait
     until it reads them", or "the room's message store is full (N KiB owed to others)".
   - An automatic post (conflict, copy, relay, registry `done`) is never refused. The trim evicts
     by the order above and records `over-cap` outcomes, which senders see.
   - A single message over the server message cap, or over 64 KiB, is refused before posting.

**Outcomes are rendered (SF4).**
- The sender's `room_state` and `recipientNotice` (`messaging.ts:48`) list its own messages with
  an outcome: "m_x to P: expired undelivered after 14 days".
- A sender's owed-and-outcome view is computed from `outcomes`. No fold rewrites it.

**Receipt retention follows references (SF5).** P's holder prunes `seen:<P>` to ids present in
`bus ∪ mail ∪ outcomes`. `memorySnapshot` (`shared/src/memory.ts:24`) keeps exactly those receipts
instead of the newest 2,000, within the receipt budget above. It adds `mail`, `outcomes` and
`archive` to `MEMORY_TYPES`.

**There is no outbox** (MF4, MF11). The hook confirms delivery live (below). A receipt written while
the provider is offline lives in the local Y.Doc, and Yjs merges it on reconnect. If the MCP dies
first, the receipt is lost, and the message is delivered again: a duplicate, allowed by R2a.

## Behaviour per path

### The one selection function

```ts
// shared/src/delivery.ts (pure)
export function owed(doc: RoomDoc, me: Identity, cursor: Cursor, route: MessageRouteContext,
                     relevant: (m: Msg) => boolean): Msg[]
//   addressed: m in bus ∪ mail, m.to === me.name, (m.from !== me.name || m.fromKind === 'human')
//   broadcast: m in bus, !m.to, !cursor.frontier.has(m.id), !cursor.routed.has(m.id), messageForMe(me, m, route)
//   minus seen:<me>, minus outcomes, minus !relevant(m)
//   deduped by id (registry's deterministic ids, e.g. wk:<id>:<n>, may be pushed twice concurrently)
```

**`to` means the addressee participant, on every kind** (lead ruling, second pass):
- No message kind may use `to` for anything else. `owed()`, `messageForMe`
  (`messages.ts:92-93`), the trim's mail rule and admission all treat `to` as a participant name.
- A `pushed` message (reporooms §B4) is a broadcast with no `to`. It carries its commits as
  `fromSha`/`toSha`.
- A reporooms payload `{…, from, to, …}` must be renamed in the same change. Otherwise every
  `pushed` is addressed to a SHA that no participant holds, nobody receives it, and the trim files
  it as mail for that SHA.
- `delivery.test.ts` rejects any registered kind whose type declares a non-participant `to`.

**`relevant`** is computed at read time and never written:
- A `pushed` message whose `toSha` is an ancestor of my HEAD is not relevant.
- The ancestry check is cached by `(toSha, HEAD)`.
- A `toSha` missing locally is fetched once, as a team-room base is a remotely resolvable anchor
  (R3c). If it is still missing, the message is relevant: show rather than hide.
- It replaces `markIntegratedBaseNotices` (`roomd/src/index.ts:735-749`) and the branch-note
  `markSeen` (`join.ts:328`).
- Routing belongs to `MessageKinds` (Leave 2). Reporooms extends `MessageRouteContext` with
  `upstream` and manifest paths.

### Cursor: a causal frontier (SF1, MF2)

- **`frontier`** is the set of bus ids the session had observed at its first bind in this room,
  taken after the first sync. It is kept across MCP restarts inside one host session.
  - A broadcast inserted concurrently, which merges in later at an earlier array position, is not
    in the frontier, so it is still offered.
  - Addressed messages never consult the frontier.
- **Seeds:**
  - A spawned worker takes the registry's launch-intent frontier: the lead's bus ids at intent.
    This asks the registry to record `busFrontier: string[]` alongside, or instead of, `busMark`.
  - Anyone else takes the bus ids at first bind.
  - This is the same definition for every new participant or session, not a worker filter (lead,
    2026-09-28).
- **`routed`** holds broadcasts that `messageForMe` rejected. It is written when the routing
  decision is made, which is safe because nothing was delivered. A broadcast **selected** for
  delivery is never added to `routed`. It stays offered until its receipt exists, so a cancelled
  or crashed batch loses nothing (MF2).
- A filtered selection, such as `room_wait` choosing only the matching message, never marks any
  other message. Both sets are pruned to ids still on the bus.

### Arbitration and reservations (MF3)

`room-mcp/src/ledger.ts`, one `Ledger` per host session, covering all of the session's rooms:

```ts
class Ledger {
  select(room, filter?, batch): Msg[]   // fenced; owed() minus reserved minus batch; reserves into batch
  commit(batch, via): void              // fenced; one transaction per room: seen:<P>[id] = {s, via, at}
  release(batch): void                  // reservation ends; ids are selectable again
  notices(batch): Notice[]              // local synthetic items (sharing disclosure, startup notice)
}
// reservations: Map<id, {batch, until}>, in memory only, never persisted, never read as receipts
```

**How a batch works:**
- The tool wrapper (`tools/index.ts` `call`) opens one `ResponseBatch` per call.
- `room_wait` selects into it; the inbox prefix then selects into the same batch, which excludes
  ids already in it. So a response never shows an id twice.
- Concurrent calls and hooks exclude each other's reservations.
- Leases: a reply batch until its transport write settles (at most 60 s), a hook batch 10 s. Each
  batch arms its own expiry timer.
- An expired lease releases its ids. A late commit for an expired batch still writes, because it
  describes a real handoff. A duplicate that results is allowed.
- **Every `release`, whether explicit, by expiry or on a transport reject, and every `commit`
  calls `wakes.reconcile()` (MF8).** A message that was reserved, and so not wakeable, becomes
  wakeable again the moment its reservation ends. Nothing depends on a later bus event.

**`FlushedStdioTransport` (MF1).** `index.ts` replaces `StdioServerTransport` with a subclass whose
`send(message)` resolves in the `stdout.write(line, callback)` callback and rejects on an error.
The shipped transport resolves when `write()` returns true (review: the bundle,

### Before-edit and SessionStart hooks (MF4, MF10)

The hook never decides "unseen" from a file. It asks the MCP:

1. **Find the MCP.** Read `room/sessions/<sid(ev.session_id)>/mcp.json` and connect to
   `127.0.0.1:<port>` with the key, with a 700 ms budget.
2. **Select.** `select {sessionId}` → `{batch, items: [{id, line, priority}], notices, leaseMs}`. The
   MCP checks its fence and `boundSession().id === ev.session_id`, selects into a hook batch, and
   includes pending local notices.
3. **Hand off.** Print them with `process.stdout.write(json, callback)`.
4. **Confirm.** In the callback, `confirm {batch}`. The MCP commits `via:'hook'` receipts and records
   the notices in `notices.json`, then the hook exits.
   - A lost confirm (hook killed, 5 s timeout) lets the lease expire.
   - The items are delivered again: a duplicate, never a loss.
5. **If the MCP is unreachable, unbound or unfenced:**
   - When `state.json` is fresh (60 s) and `owedCount > 0`, the hook prints a content-free
     `[room] N messages pending; Room is reconnecting.`.
   - Otherwise it prints nothing. It never prints content from a file.

The rest of the hook is unchanged: claims, `near` and the company line from `state.json` and
`hook.json`, with no message content.

**SessionStart** (`session-start.mjs`) tries the same select with a 300 ms budget, flagged
`startup: true`. The MCP may not be running yet. If the select fails, the hook prints only the
company line. It makes no promise of a later count (MF8). A startup select delivers ordinary owed
items, but never counts as resume acceptance (Resume).

**Local notices** (MF10): the team sharing disclosure (`join.ts:65-82`) and the startup notice
(`index.ts:120`) become synthetic items with ids `n:<kind>:<sha(text)>`. They go through the same
select, handoff and confirm steps, and their receipts are in `notices.json`, written only by the
MCP after a confirmed handoff. A claimant that dies leaves nothing to suppress: its lease expires
and the notice is offered again. That replaces the pending/delivered fields, `consumeHookContext`
and both `acquireNoticeLock` copies.

### Resume prompt (MF1, MF3; registry §7)

The registry appends `runs[n+1] = {…, promptMsgIds}` before launch. `promptMsgIds` holds the
follow-up plus P's other owed addressed messages, from `owed()` in the lead's doc.

- **The handoff boundary is host acceptance, observed in the turn that carries the prompt.**
  - **What counts as evidence:** only a model action in run `n+1`, bound to `record.hostSessionId`:
    a Room tool call, or a before-edit (PreToolUse) select, from the process tagged
    `ROOM_WORKER_RUN=n+1`.
    - A headless `claude -p --resume` or `codex exec resume` run has exactly one user turn, the
      prompt. A tool call in that run is therefore inside the prompt-bearing turn.
    - Where the host reports a turn id (Codex hook `turn_id`, and turn metadata if Q2 confirms
      it), it must be the run's first turn.
  - **Never evidence (MF1):**
    - a SessionStart select, which runs before the prompt is processed, so authentication or
      session failures can still follow it;
    - MCP startup, auto-join or binding;
    - a recorded `process`.
  - At the first qualifying action, the **worker's own MCP** (the fenced holder of P) commits
    `promptMsgIds` as `via:'prompt'`, before it selects anything.
- **Reservation.** Until then, the worker's `Ledger` holds `promptMsgIds` as a `prompt` reservation,
  loaded from its run record through `ROOM_WORKER_ID`/`ROOM_WORKER_RUN`. The worker's inbox cannot
  show them before the receipt: there is one owner, the worker's MCP.
- **A run that ends without a Room call.** The projector (registry §14, fenced as projector,
  holder dead) commits the prompt receipts only on host evidence in the run log:
  - Codex: a `turn.started` for thread `hostSessionId`, from `exec resume --json`, parsed like
    `thread.started` at `worker-process.ts:96-118`.
  - Claude: see Q4.
  - Without evidence (the host rejected the session or its authentication, or exited before a
    turn), nothing is written and the ids stay owed. That is registry Failure §1c.
- **This changes registry §7 step 4.** The registry currently receipts once a `process` is recorded.
  Under this spec, `process` recorded is launch, not acceptance.

### Wake (MF8)

`room-mcp/src/wake-reconciler.ts` replaces `HooksBridge.maybeWake/deliver/retryPending` and the
state of `SocketWakeRouter`.

- **Wakeable:** `owed()` ∩ `shouldWakeOnMsg` ∩ not in `wakes.json` ∩ not reserved ∩ not consumed by a
  pending wait (`waitConsumesMessage`) ∩ **not in the session frontier**.
  - The frontier is persisted, so a message that arrived while the MCP was restarting is still
    wakeable afterwards.
  - Messages that were owed before the session existed are left for its first reply or hook.
- **`reconcile()`** runs single-flight and fenced. It is triggered by:
  - a bus change, a `seen:<P>` change or an `outcomes` change;
  - a binding change or a provider reconnect;
  - a `room_wait` finishing or being cancelled;
  - every reservation release or expiry, and every commit;
  - MCP start;
  - a timer that re-arms while anything is wakeable, with backoff 1, 3, 8, 30 s after a failure.
- **Send:** one pointer for all candidates, `[room] N things need you: <from> <kind>; …. Call
  room_state; it shows them.`
  - Codex: `codex queue --thread <boundSession().id>`.
  - Claude: the socket, then the channel if the socket fails and channels are admitted.
  - `sendChannelNotification` (`channel.ts:8`) must reject on failure instead of swallowing it
    (Leave 1).
  - Only a successful send writes `wakes.json`.
- **Presence:** the recipient publishes `inbox: {owed, wokenAt?}` in awareness while fenced.
  `recipientNotice` then says "delivered", "woken <t> ago, not yet read", "offline, owed", or shows
  the outcome.
- **No bound session** (the shared Codex app-server; registry §16 binds a synthetic
  `mcp:<pid>:<startTime>`): wakes are off and the hook cannot find the MCP. Tool replies and
  `room_wait` still deliver.

### Addressing across branches and new kinds

- Messages are addressed to participant names. In a repository room (reporooms), a branch switch
  keeps the room, the cursor and the receipts.
- `MessageKinds` stays the one policy registry (Leave 2). Any kind with `to` is owed, kept in
  `mail`, woken and ended per its own entry.
- Manifest registers `fetch`/`fetch-reply` without file text on the bus.

## Migration

**R6a.** Repository-room docs are born at `schemaVersion: 2`.
- The server and the relay refuse non-schema-2 clients before sync.
- Live legacy connections are closed with 4001 (reporooms §Migration).
- There is no mixed-version window, no numeric receipt reading and no legacy trim leader. MF7's
  rows no longer apply.

Two migrations remain:
1. **Owed addressed messages** are copied from legacy branch-room docs into `mail` by
   `migrateRepo`, once, before any client is admitted (reporooms §Migration step 3; the relay runs
   the same for local rooms).
   - "Owed" means no `seen:<to>[id]` in the legacy doc.
   - Messages hidden only by the old in-memory `markHistorySeenOnJoin` have no receipt, so they are
     replayed. That is the ruling (MF5): uncertain history is replayed.
2. **Local hook records are not receipts (MF5, second pass).**
   - `room-hook-seen.json`'s `seen`/`shown` are **not imported**. The baseline hook persists them
     (`before-edit.mjs:115`) *before* it writes stdout (`:120`), so a kill between the two leaves
     a record of a message that was never handed off. Every such message is replayed from `mail`:
     a duplicate, never a loss.
   - At the first 0.17 start in a checkout, `migrateLocalState`:
     - copies only the non-message dedupe fields (`companyTold`, `near`, `claims`) into the bound
       session's `hook.json`;
     - renames `room-hook-seen.json`, `room-state.json`, `room-session.json`,
       `room-write-intents-*.json`, `room-hook-activity.json` and `*.notice-lock` to
       `*.migrated`.
   - There is no `legacy` value of `Via`.

## Failure and recovery

- **MCP crash or `kill -9` mid-reply.** The batch never committed, so its ids are owed. After
  restart in the same host session, the frontier, `routed` and `wakes.json` persist: the message
  is delivered again once and not woken twice.
- **Crash after the stdout flush, before commit.** A duplicate. That is the R2a trade.
- **Hook killed between print and confirm.** The lease expires; a duplicate.
- **Hook select while the MCP is restarting.** The content-free pending line only.
- **Host crash after a confirmed handoff.** The receipt stands and the model may never have seen
  the message. Room cannot observe this. See [Risks](#risks).
- **Partition, two holders of P (R1a).** Each process checks its fence on every operation. The
  loser stops selecting and committing within one reconcile tick, and its `state.json` stops being
  written, so no stale snapshot delivers. Receipts the loser committed before it noticed describe
  real handoffs to its session.
- **Two trimmers in a partition** converge (invariant 9). Mail moves racing receipts: the next trim
  deletes a receipted entry once its reply window closes.
- **Relay restart in a local room.** The snapshot holds `bus`, `mail`, `outcomes`, `archive` and the
  referenced receipts, all within the bounds.
- **Two sessions in one checkout.**
  - Different participants: separate session directories, endpoints and ledgers.
  - The same participant: refused by the lease.
- **Codex threads under one app-server.** Unbound: wakes and the hook are off, and replies still
  deliver (Q2).
- **Clock skew.** Clocks are used only for TTLs, which are monotone and measured in days.

## Risks

- **Beyond the handoff.** If the host crashes after bytes reached its pipe, a receipt exists that
  the model never acted on. Room cannot observe this. The only mitigation is a later human
  re-send, visible through `room_state`'s delivered-at line.
- **The hook adds up to two loopback round trips per edit while company exists.** The budget is
  700 ms, then the content-free fallback. The relay already runs a loopback server inside the MCP,
  so this is a known pattern, including under Codex.
- **A content-free Codex wake costs one tool call to read.** This is Leave 1.
- **Evicting owed messages under the caps.** An automatic flood can evict addressed notes. Each
  eviction is recorded in `outcomes` and shown to its sender.
- **The archive becomes per-message records** (≤5,000 by about 60 B). The PR ledger's "earlier
  history" counts only what is retained.
