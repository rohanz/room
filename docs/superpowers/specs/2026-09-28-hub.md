# The hub: a narrow authority in the relay and the server (spec `hub`, 2026-09-28)

Status: design only, on `redesign-hub` at 40345d8 (wave 1 merged). Binding: the lead's decision "narrow hub
hybrid" and rulings R-H1–R-H7 (cited where applied); inputs: the Astra and Fable hub reviews ("Astra table",
"Fable table") and the [plan](2026-09-28-redesign-plan.md). Line numbers point into 40345d8 and the installed
`@y/websocket-server` 0.1.1, `y-websocket` 3.1.0 and `y-leveldb` 0.1.2, and drift.

Every room already has a hub holding the whole doc: the local relay (`packages/relay`) or the server
(`packages/server`). This spec makes it the authority for four facts; everything else stays where the specs
put it.

## 1. The line

No persist-before-ack journal (R-H5): message durability stays what the doc gives today (reporooms §B4
"Guarantee"). An unreachable hub means "[room] hub unreachable; coordination paused" (§7), never local
authority. Two set-once writes stay client-side, as specced: a projector's `recipient-retired` outcomes
(registry §12) and the placeholder rewrite in `mail` when an unresolved identity is claimed (reporooms,
Migration).

## 2. Protocol

### 2.1 Transport: a new y-websocket message type

The hub rides the room's existing websocket. y-websocket uses types 0 (sync), 1 (awareness), 2 (auth) and
3 (query awareness) (`y-websocket.js:20-23`). The hub adds **`MSG_HUB = 7`**: `[varUint 7][varString
json]`, one JSON object per frame (`lib0` encoding, as the other types).

- **Server.** The stock `setupWSConnection` registers one `message` listener (`utils.js:256`) whose switch
  handles only 0 and 1 and has no default (`utils.js:174-199`), so a type-7 frame is ignored there. The server
  already wraps `conn.emit` for view keys, identity and the size cap before it emits `connection`
  (`server/src/index.ts:374-407`). A new `bindHub(ws, hub, principal)` in `server/src/hub.ts` is installed
  **first** in that callback, so it is the innermost wrapper: it sees frames after the outer wrappers, which
  pass type 7 untouched (`isWriteMessage` is false for a non-sync type, `readonly.ts:16-25`; `filterAwareness`
  returns a non-awareness buffer as is, `:67`; `DocumentIdentityGuard.accept` says ok for a non-sync frame,
  `:174-176`; `capDocSize` counts only write messages, `:330-342`). `bindHub` consumes type-7 frames (does not
  forward them) and replies with `ws.send`. `principal` is `{login?, readOnly}` from `accept()`.
- **Relay.** `attach()`'s switch (`relay/src/index.ts:79-88`) gains `case MSG_HUB`. Every relay connection
  already presented the clone key (`:250-254`), so the principal is `{local: true}`.
- **Client.** `WebsocketProvider` copies its handler table per provider (`y-websocket.js:358`) and dispatches
  by type (`:118-124`); a handler that writes nothing to the encoder sends no reply (`:231`). The MCP sets
  `provider.messageHandlers[7]` and sends frames with `provider.ws.send` while `provider.wsconnected`.

### 2.2 Frames, request ids, timeouts

```ts
type Req = { v: 1; id: string } & (                   // id: unique per connection, e.g. `r<n>`
  | { op: 'hello'; proto: 1; schema: 2; client: string; sessionId: string }
  | { op: 'acquire'; name: string; holder: HolderIn; supersedes?: number }
  | { op: 'renew'; name: string; epoch: number }
  | { op: 'release'; name: string; epoch: number }
  | { op: 'post'; lease?: { name: string; epoch: number }; msg: PostIn; auto?: boolean }) // lease: required from wave 4
type HolderIn = { sessionId: string; pid: number; startTime: string; executable: string; workerId?: string }
type PostIn = { id: string; type: MsgType; from: string; to?: string; [field: string]: unknown } // no seq, no at
type Reply = { v: 1; re: string } & ({ ok: true; [k: string]: unknown } | { ok: false; reason: Reason; text: string; retryMs?: number })
type Push = { v: 1; push: 'lease-lost'; name: string; epoch: number; reason: 'superseded' | 'expired' | 'expired-participant' | 'not-authority' }
```

The hub answers each request once, on its connection, in arrival order; before `hello` it answers
`hello-first`. No request-id table is kept: every operation is safe to retry. The client times out after 5 s
(local) or 10 s (team); the outcome is then unknown and the caller retries or reports (§7).

### 2.3 Operations

- **hello** → `{ok, proto: 1, incarnation, ttlMs: 45000, renewMs: 15000, authority: true}`. Sent after every
  (re)connect. A changed `incarnation` tells the client the hub restarted (R-H7).
- **acquire** → `{ok, epoch, ttlMs}`. The hub grants `name` when it has no live lease, or when the live lease
  belongs to the same `holder.sessionId` (an MCP restart or reconnect inside one host session; registry §15
  row 2), or when `supersedes` equals the live lease's epoch (a worker taking over the name its lead reserved;
  registry §15 row 3; the lead passes the epoch in the launch env). Every grant takes a new epoch (§3), so a
  superseded grant's in-flight writes are fenced out, and the superseded connection gets `lease-lost`
  (`superseded`). In the local relay only, a live lease whose holder process is `dead` by `liveness()`
  (`room-mcp/src/leases.ts:12-19`) ends at once; the relay shares the machine with every holder. The server
  never judges process liveness. Retrying an acquire from the same session is safe: it supersedes itself.
- **renew** `{name, epoch}` → `{ok, ttlMs}` when `epoch` is the live lease's (or is adopted in the settle
  window, §4.4); the TTL restarts on the hub's clock. Otherwise `stale`. Idempotent.
- **release** `{name, epoch}` → `{ok}`. Releasing an already-ended lease of that epoch is `ok`; another epoch
  is `stale`. Idempotent.
- **post** → `{ok, seq, at}`. The hub checks that `lease` is live (the fence; the poster's own lease, whatever
  `from` says), then looks the id up in `bus ∪ mail`: found → `{ok, seq, at, duplicate: true}` with the
  **original** seq. Found only in `archive` or `outcomes` (body gone) → `{ok, duplicate: true, gone}` with no
  seq. Otherwise: a message over 64 KiB is `too-large`; an addressed post without `auto` goes through
  `admit()` (`shared/src/delivery.ts:199-214`) and is refused `over-cap` with admit's reason text; an `auto`
  post (conflict, `pushed`, completion, copy, relay, idle-claims notice) is never refused, and the trim evicts
  (ledger, Admission). Accepted: `seq` (§3), `at = wall clock`, default `priority`, appended to `bus` in one
  transaction with `HUB_ORIGIN`. `from` is not validated beyond the server's observe-only identity rule (D3).

### 2.4 Rejections

| `reason` | When | Client text or action |
|---|---|---|
| `version` | `proto` unsupported (§10) | "[room] this room's hub speaks protocol N; update Room to 0.M or later" |
| `hello-first` | request before hello | resend hello |
| `not-authority` | relay without the authority lock (§5) | "not the authority; reconnect": drop the socket, rediscover |
| `starting` | hub loading, taking an incarnation, or in the settle window (§4.4) | retry after `retryMs` |
| `held` | name has another live lease; `holder: {sessionId, since}` | next name candidate (registry §15) |
| `not-yours` | server: `ownsName(name, login)` fails (`readonly.ts:58-60`) | refuse the name |
| `stale` | renew, release or post with an epoch that is not the live lease | lease lost (§4.3) |
| `read-only` | view-key connection | none (the web never sends hub frames) |
| `too-large`, `over-cap` | post limits (§2.3) | the text, verbatim, in the tool reply |
| `room-full` | server: doc over `ROOM_DOC_MAX_MB` (`server/src/index.ts:314`) | 4413 text (reporooms §B11) |
| `invalid` | malformed frame or field | a bug; logged on both sides |

### 2.5 Pushes (R-H7)

Accepted messages reach clients through the CRDT `bus`, as today: the hub is the sole appender, sync is the
replay, `seq` orders it; a second delivery channel would bring back the parallel paths Fable 2 removed. The
only push is **`lease-lost`**, to the connection that last acquired or renewed, when the hub supersedes or
expires the lease, expires the participant (defensive), or loses its authority. "Incarnation changed" needs
no push: it only happens with a new process, so clients see it in `hello` after reconnecting. Pushes are
hints; correctness rests on the client's TTL clock (§4.3).

## 3. Counters that never repeat (R-H1)

**Values.** An epoch or a seq is `I · 2^21 + n`: `I` is the hub's **incarnation**, `n` a counter in memory for
that incarnation, one for epochs and one for seqs. With `I < 2^32` the value stays a safe integer
(`(2^32−1)·2^21 + 2^21−1 = 2^53−1`), so the cursor is one integer and values order by `(I, n)`. When `n` would
reach `2^21`, the hub takes a new incarnation first (same procedure; requests meanwhile get `starting`).

**Incarnation.** Each hub start (a relay start or takeover; on the server, each time a room's doc is loaded,
since the stock server destroys a doc when its last connection closes, `utils.js:207-222`) computes

`I = max(D + 1, S + 1, ⌊wall / 1000⌋)` where `D` = the highest incarnation in the durable record, and `S` = the
highest incarnation it can see in the doc: `meta.hubIncarnation`, and `⌊v / 2^21⌋` of every `seq` on `bus` and
`mail` and every `holder.epoch`.

It then writes `D := I` durably and only then serves:
- **Local relay:** `<common>/room/hub/incarnation.json`, `{max: I}`, temp, fsync, rename, fsync-dir (`writeAtomic`,
  `leases.ts:82-86`), under the authority lock (§5).
- **Server:** one `<YPERSISTENCE>/hub/incarnation.json` for the process (without `YPERSISTENCE`,
  `<tmpdir>/room-server-hub-<PORT>/incarnation.json`), the same write. Every per-room
  incarnation (read `D`, compute `I`, fsync-write) runs through one in-process queue, so two rooms loading
  together never pick the same `I`. The meta mirror is then written and awaited with
  `persistence.provider.storeUpdate` (`y-leveldb.js:446-447`). The file is the record because y-leveldb writes
  without `sync` (`levelPut`, `y-leveldb.js:127`), which a VM kill can lose.

**Where the counters live.** In memory within an incarnation (monotonic); mirrored for readers into `meta`
(`hubIncarnation`, `hubEpoch`, `hubSeq`), written in the same transaction as the grant or post that issued
them. `meta` is a snapshot root (`shared/src/memory.ts:9-12`). A Y.Map value is last-writer-wins by client id,
and relay snapshots lag by 2–10 s (`relay/src/memory.ts:84-85`), so the mirror is never trusted as the
source.

**Proof that no value repeats**, even when the last snapshot is lost:
1. Two hubs never serve one room at once: the relay holds the authority lock (§5); the server runs one process
   per volume (§6).
2. Incarnation `I` issues nothing before `D ≥ I` is durable. A later start reads `D ≥ I` and picks `I' > I`. An
   earlier start's `I''` was durable before it served, so this start read `D ≥ I''` and picked `I > I''`. So
   incarnations are distinct and increase with start order.
3. Within one incarnation, `n` increases in memory, so `(I, n)` is unique, and every value issued later is
   larger.
4. The doc is not in the proof: `S` only raises `I`. Losing a snapshot, or a stale replica bringing back an old
   mirror, cannot lower it.

Every hub has a durable record. A server without `YPERSISTENCE` (tests, demos) keeps its record in the temp
directory, keyed by port: its rooms are in memory, but clients' replicas outlive a restart and carry the old
values back. The `⌊wall/1000⌋` term is only a floor, not the uniqueness argument. `I` fits 32 bits until 2106.

## 4. Leases and clocks

### 4.1 The lease record

The hub is the only writer of `participants[${P}\0holder]` (reporooms, flat record):
`{sessionId, epoch, pid, startTime, executable, workerId?, at, ended?: 'released' | 'expired'}`. It is written
at grant and at end, and kept after the end so readers still accept the last holder's facts as offline
(reporooms `acceptedGit`). `machine` is dropped: the epoch replaces it (Fable table row 1). Lease TTL state
(last renew time) is in hub memory only, never in the doc.

**The fence becomes the epoch** (from wave 4, when names are acquired via the hub; until then the session id,
as built). `ParticipantGit.fence`, `ManifestHead.fence`, the manifest incarnation key `${name}\0${fence}`, and
conflict-slot fences carry `String(holder.epoch)`; `acceptedGit` and `versionOf` compare against it;
`liveHolder(view, name)` returns the epoch of an un-ended holder whose session has fresh presence.

### 4.2 TTL and renewal (R-H4)

**TTL 45 s, renew every 15 s.** The worst stall on record is 0.16.33's index build: a synchronous pass of
about 18 s, run twice, so about 36 s with no timers (CHANGELOG 0.16.33). Renewing at TTL/3 survives two missed
renewals and any 30 s stall; a 36 s stall right after a renewal still ends inside the TTL. Indexing now yields
(0.16.33), so these are margins. A longer TTL delays cross-machine takeover after a kill -9 (the relay ends
dead local holders at once, §2.3); a shorter one turns stalls into lost names, the 0.16.33 failure.

### 4.3 The client's clock

The client measures validity from the **send time of its last acknowledged renew** (or acquire): valid while
`max(mono − t₀, wall − w₀) < TTL`, where `t₀`/`w₀` were read just before that request was sent. The hub
restarts its TTL on receipt, later than the send, so the client always considers the lease lost no later than
the hub does. The wall term covers sleep: `process.hrtime` does not advance while macOS or Linux is
suspended, and a laptop asleep past the TTL must not wake up believing it still holds the name (registry
rehearsal "a laptop asleep"). A backward wall step only shortens validity, which is safe.

At TTL, or on `stale` or `lease-lost`, the client drops the lease and pauses (§7). It re-acquires; a new epoch
means its fenced records (manifest key, `git.fence`) are rewritten under that epoch.

### 4.4 The hub's clock and the takeover window (R-H2)

- Lease expiry and participant absence use only the hub's monotonic clock. A lease ends when TTL passes since
  its last renew on that clock; the hub then writes `ended: 'expired'`.
- **A new incarnation never expires anything using time measured before it started.** Every live lease found
  in the doc (a `holder` without `ended`) gets a full TTL from the incarnation's start. Holders renew to the new
  hub on reconnect and keep their epoch.
- **Seeding.** A relay successor seeds its doc from its own replica before serving (§5). The server serves a
  room only after its LevelDB state is loaded (§6).
- **Settle window.** For 5 s after an incarnation starts, an acquire for a name with no live lease gets
  `starting` (`retryMs: 1000`), and an un-ended `holder` that arrives by sync for a name with no live lease is
  **adopted** with a fresh TTL. A grant the dead hub made in its last moments may be missing from the
  successor's replica; the holder's reconnect (relay tick 2 s, `relay/src/index.ts:381`, plus y-websocket's
  backoff) brings it back inside the window. Its sync step 2 is async relative to its `hello` and renew
  frames, so a renew in the window for an epoch with `incarnationOf(epoch) < I`, on a name with no live lease,
  is **adopted** too: granted at that same epoch with a fresh TTL. After the window such a renew is `stale`.
- **Re-assertion.** Hub-owned values (`holder`, `meta.hub*`) can lose a last-writer-wins race to a stale
  replica whose items the hub's doc never saw (the relay rebuilds its doc from a value copy,
  `shared/src/memory.ts:37-38`). Outside the settle window the hub rewrites any hub-owned value that differs
  from its in-memory table (an un-ended `holder` it does not hold live becomes `ended: 'expired'`); the rewrite
  follows both items causally, so it wins. On `bus` it keeps the relay's dedupe by id
  (`relay/src/memory.ts:58-81`) and deletes entries whose id is in `archive` or `outcomes`; a message found only
  in a replica is kept, since the replica refilled what the hub lost.

## 5. The local relay: one authority per clone (R-H3)

**The lock.** `<common>/room/hub/authority.lock`, an `InstanceToken` created with `createExclusive`
(`leases.ts:71-79`), recovered with `recover(file, () => true)` only when its holder is `dead` (`:165-174`),
released with `compareAndRelease` (`:155-163`) when the relay closes. A process takes it **before** it starts a
relay; without it, it never starts one. It then reads `incarnation.json`, takes `I` (§3), and serves.

**Where `leases.ts` goes.** `packages/relay/src/leases.ts`, with the process probe (`probeProcess`,
`pidAlive`, now `room-mcp/src/worker-process.ts:145-206`) in `packages/relay/src/process.ts`. The relay cannot
import room-mcp (room-mcp depends on the relay, `room-mcp/package.json:21`), and hub-core stays free of the
filesystem. `room-mcp/src/leases.ts` and `worker-process.ts` re-export them, so no caller changes.

**Start and the two-racers path.** Today two racers that both find the derived port taken start relays on free
ports, and the later one closes after 150 ms (`relay/src/index.ts:329-352`), so two relays can run for that
window. With the lock, only its holder starts a relay; the other waits for `room-local.json` (the existing
20 × 100 ms loop, `:337`) and joins. As a backstop, a relay re-checks its lock token (nonce included) every
tick and before each hub request; a relay without the lock answers every hub request `not-authority` and
pushes `lease-lost` (`not-authority`) to holders, so it can never grant.

**Takeover.** When the watch tick finds the relay gone (`:358-374`), the survivor takes the lock (the dead
owner's is recovered), starts the relay on the same port with its **own replica as the seed**
(`ensureLocalRelay(..., {seed: () => Y.encodeStateAsUpdate(roomDoc.doc)})`, applied before the first
connection), takes a new incarnation, and serves. If the owner process is alive but its relay does not answer
(an event-loop stall), the lock is not recoverable and nobody takes over: the stalled owner resumes as the
authority, and its clients see a paused hub meanwhile. That is the case the port race could not tell apart.

**Kill -9 of the owner:** within 2 s a survivor recovers the lock and binds; holders reconnect, see the new
incarnation in `hello`, get a fresh 45 s TTL and renew with their epoch; the dead owner's lease ends at once
(§2.3). On Windows an `unknown` holder is kept (registry §Leases), so a reused pid blocks takeover until a
human removes the lock, which `room_state` names.

## 6. The server (R-H6)

- **Loading first.** The stock `bindState` is async and nobody awaits it (`utils.js:36-45`, `:159-168`). The
  server calls `setPersistence` (`utils.js:54`) with the same bind code plus a per-doc `loaded` promise; the hub
  for a room starts after it resolves, then takes its incarnation. Until then hub requests get `starting`.
- **Origin.** Every hub write is `doc.transact(fn, HUB_ORIGIN)`. The identity guard's shadow applies the real
  doc's updates with no login set (`readonly.ts:215-216`), and each check returns early without a login
  (`:222-223`, `:235-236`, `:256-257`, `:270-271`), so hub writes are never reported as a member's. `capDocSize`
  meters only inbound write frames (`:330-342`); hub writes are not frames. The hub refuses posts with
  `room-full` while the room's `DocSizeMeter` is over the cap; lease writes stay allowed (they are tiny).
- **Principal.** `bindHub` passes `{login}` for logged-in connections; acquire requires `ownsName(name, login)`,
  the rule presence already follows (`index.ts:379-385`). View-key connections get `read-only`.
- **One writer.** One server process per `YPERSISTENCE` volume, today's Fly shape (`deploy/fly.toml:20-32`,
  one volume, idle stop). An idle stop is a hub restart (§4.4). `closeRepo` (`index.ts:130-148`) stops a
  room's hub before it deletes the doc.

## 7. "Hub unreachable; coordination paused"

The client (`HubClient`, §9) is **paused** for a room when it holds no valid lease by §4.3's clock, or when
`hello` has not succeeded (the lease condition from wave 4; before it, only posts need the hub):

- **Stops** every write fenced by the name: posts, receipts `seen:<P>` and ledger select/commit (ledger
  invariant 5), manifest and `git` publication, claims and scope writes, conflict slots.
- **Says so** once per tool reply: "[room] hub unreachable; coordination paused. Your files are unaffected;
  messages and claims resume when it is back." `room_send` answers "not sent: hub unreachable". `state.json`
  carries `paused`, so the before-edit hook prints the same line.
- **Keeps working:** editing, local reads, `room_read` of the replica marked "as of <age>", previews marked
  stale, local worker operations (registry), awareness, CRDT sync.
- **Nothing is queued in memory.** Automatic posts are re-derived by their owners on reconnect: conflict
  notices by the slot reconcile (reporooms §B5), `pushed` from `git.pushedPending` (reporooms §B4), completions
  from `report.posted`/`runs[n].posted` (registry §7), idle-claims notices from their journal (registry §18).
  Each is idempotent by id (§2.3).
- **Resumes** by `hello`, re-acquire (same name if free; the O_EXCL file lease is still its own) and a full
  republish under the new epoch. A short outage while the lease is valid (a relay takeover) is not a pause.

## 8. Hub-run trim, bounds, outcomes, archive and expiry

- **Trim.** The hub calls `trim(doc, wall(), {origin: HUB_ORIGIN})` (`delivery.ts:110-191`) every 60 s and after
  a post that takes the bus past `BUS_KEEP`, and `admit` (which trims first) on addressed posts. `trim` stays a
  pure function, for the hub and for tests. Every message's `at` is the hub's wall clock, so `(at, id)` in the
  bounds is one clock.
- **Expiry.** A participant is absent while it has records and no live lease (the hub knows; presence is not
  consulted). `ExpiryTenure` stays in `shared/src/expiry.ts:19-62`; hub-core runs one with `epoch = inc:<I>`
  and passes a view whose `fresh` means "live lease": each incarnation adds only durations it measured (R-H2), so
  time with no hub counts for nothing and a successor restarts its measurement from the value found. At
  `ROOM_STALE_DAYS` it calls `expireParticipant` (`:69-81`) with `HUB_ORIGIN`, and ends any lease on that name
  with `lease-lost` (`expired-participant`). Workers are never measured (their projector retires them).
- **Deleted:** `trimLeader` and `leadsTrim` (`delivery.ts:239-268`); roomd's `trimBusIfLeader`, its timer and
  the client `tenure` (`roomd/src/index.ts:271`, `:478-479`, `:1008-1015`); the client append in `RoomDoc.post`
  (`shared/src/doc.ts:558-576`) once wave 2 routes posts through the hub; the ledger's "two trimmers converge"
  requirement and the reporooms expiry-leader election.

## 9. One module: `packages/hub-core`

Transport-free and filesystem-free: a `Hub` over a `RoomDoc`, a clock and a persistence hook.

```ts
interface HubHost {
  doc: RoomDoc; mono(): number; wall(): number; log(line: string): void
  store: { read(): Promise<number | undefined>; write(max: number): Promise<void> }  // durable incarnation (§3)
  holderDead?(h: HolderIn): boolean; authority?(): boolean     // relay: liveness(), lock token still ours
  owns?(p: Principal, name: string): boolean; full?(): boolean // server: ownsName, DocSizeMeter over the cap
}
function startHub(host: HubHost): Promise<Hub>   // loads, computes I, awaits store.write, then serves
interface Hub { readonly incarnation: number; stop(): void
  handle(conn: object, frame: Req, p: Principal): Reply; closed(conn: object): void
  tick(): void /* leases, trim, expiry; every 1 s */; onPush(fn: (conn: object, push: Push) => void): void }
```

hub-core also holds the codec (`MSG_HUB`, `encodeFrame`/`decodeFrame`), `HUB_ORIGIN`, `encodeSeq(I, n)`/
`incarnationOf(v)` and the contract suite (§12), and depends on `@room/shared` and `yjs` only. Adapters:
`relay/src/hub.ts` (lock, file store, seed, `attach` case), `server/src/hub.ts` (`bindHub`, file store and
awaited meta, `loaded`, principal).

## 10. Version negotiation under the 0.17 cutover (R6)

Hub protocol 1 ships with `schemaVersion: 2` in 0.17; no 0.16 client speaks it (R6 refuses schema-less
clients before sync).
1. **Preflight.** The server's schema-2 preflight reply and the relay's `/health` (`relay/src/index.ts:213-218`)
   gain `hub: 1`. Without it a 0.17 client stops before joining: "[room] this Room server has no 0.17 hub; ask
   its operator to deploy Room 0.17". The server is deployed first (reporooms, Rollout).
2. **hello.** An unsupported `proto` gets `version`: "[room] this room's hub speaks protocol <N>; update Room
   to 0.<M> or later" (or "…; the hub needs updating" when the client is newer). The client stays joined and
   paused (§7), never a silent fallback. A `hello` timeout (a stock server ignores type 7, `utils.js:174-199`)
   gives the paused line with "the hub did not answer".

A later protocol 2 is added by accepting `proto ∈ {1, 2}` for one release, as R6 did for schema.

## 11. The hub step, and what waits for waves 2–5

**The hub step (after wave 1, before wave 2)** builds `packages/hub-core` (codec, counters, lease table,
sequencer, re-assertion, trim and expiry ticks over shared's `ExpiryTenure`); the relay wiring (authority lock,
`leases.ts`/`process.ts` moved, incarnation file, seed, `MSG_HUB`, `/health`); the server wiring (`loaded`,
incarnation file, `bindHub`, principal, `room-full`); §8's deletions except the client append (until wave 4 no
`holder` exists, so hub expiry measures nobody, as `ExpiryTenure` does today); the contract suite over both
adapters; and a **thin** `room-mcp/src/hub-client.ts`: `HubClient` with `hello`, `acquire`, `renew` (own 15 s
loop), `release`, `post`, timeouts, the §4.3 clock and `paused(): string | undefined`, unit-tested with a fake
transport and clocks, **not wired into tools**.

**Later waves:** wave 2 routes `RoomDoc.post` callers through `HubClient.post`, deletes the client append and
says "not sent: hub unreachable"; until wave 4 posts carry no `lease` and the hub skips that check. Wave 3
turns the ledger frontier and the registry's `busFrontier` into a seq. Wave 4 acquires names via the hub (O_EXCL
lease, then hub lease), makes `lease` required on posts, moves fences to the epoch (§4.1), wires `paused` into
replies and hooks, and deletes the 90 s grace and `machine`. Wave 5 ships the preflight `hub` field, the refusal
texts and hub-origin migration writes.

## 13. Risks

- **Latency:** each post and acquire is a round trip; claims stay CRDT, so the before-edit hook is unchanged.
  **A stalled relay owner pauses a local room** for the stall (§5). Fly idle stops restart hubs (§4.4).
- **Durability is unchanged** (R-H5): a message accepted just before a relay dies is lost if no replica got
  it. **Multiple server instances** would be two authorities (§6); they need routing first.
