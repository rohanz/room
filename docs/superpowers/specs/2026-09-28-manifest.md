## 1. Goal

Answer "what of Ben's work is in this room, and is Ben's version of `x` known?" from one record per
participant per room. Decide "may this path's text leave this machine?" from one immutable value per
participant. The three records are:

- **Authorization** (`SharingPolicy`): the level the human asked for, clamped by the server ceiling, plus the
  paths declared for text at `declared`. Built from one local file. The CRDT never holds it as authority.
- **Coordination scope**: what the room is told the participant works on. It is made of `scopes[name]` and,
  for a lead with workers, `coordination[name]`, which the bridge writes. It feeds `near.ts`, claims and
  notices. It never feeds publication.
- **Manifest** (`manifest[name]` + `manifestHead[name]`): the facts tier of the overlap design. For every
  changed path the policy lets the room know about, it holds the change kind and whether the text is in
  the room, plus the blob hash and size only where the policy authorizes the path's text (D1). Excluded
  paths appear only as keyed digests. Every reader uses the manifest.

The manifest is tier 1 of "cost scales with overlap" (roadmap, "The design the gaps point at"). §4.6 says how
it prepares for tier 2 (text only where scopes overlap) and for patches against a base, without doing either.

## 3. Invariants

1. The daemon publishes file text only for paths the current `PublicationInputs` authorizes. It checks once, just before the Y transaction that writes, and re-validates the file with `lstat` at that point.
2. In each room, `manifest[name]` and `manifestHead[name]` have one writer. For a participant that runs a daemon in that room, it is that daemon, while its session holds the name and publisher leases. For a local worker's team-room projection, it is the lead's bridge (R3b). Every write carries the writer's `fence`.
3. A manifest entry and the text it describes (overlay text, base text) are written in the same Y transaction.
4. When `complete` is true, `manifestHead[name].base` equals the participant record's `participants[P].git.base` (reporooms). Both are written in the same transaction at the end of a HEAD transition.
5. A reader certifies "equals base" for `p` only if all of these hold, both when it reads and when it finishes: the head is complete and its `fence` is valid (§6: the record's own holder, or for a projection the lead's *current live* holder); `coverage` is `all`; `p` has no entry; and `digest(roomSalt, p)` is not in `excluded`. Otherwise absence means nothing.
6. `held` means "changed relative to my base, text not in the room". Readers never substitute base text for a held entry.
7. A changed path excluded by `.roomignore`, the default ignores, safety rules, the per-file size cap or the total budget never appears by name, at any level. It appears only as `sha256(roomSalt ‖ path)` in `excluded`.
8. At `intent`, or as a non-publisher, the manifest lists nothing: no entry (not even D), no digest, `coverage: none`. This gate runs before any other rule, and exclusion rules run before D (N1).
9. `SharingPolicy` and `PublicationInputs` are immutable. Every change produces a new value, and a reconcile planned under an older value writes nothing.
10. `PolicyStore` in the session holding the participant's name lease is the only writer of the participant's sharing file. Nothing reads `scopes` or `coordination` to decide publication.
11. The bridge never writes `scopes[lead]`, the lead's policy or sharing file, or the lead's own manifest.
12. A departing declared prefix keeps authorizing text until a full-checkout scan, planned after its departure and run without hot-file deferral, has planned every path under it.
13. Every reader in §6 distinguishes `text`, `deleted`, `base`, `held`, `excluded` and `unknown`. It prints a reason for the last three, and reads one immutable snapshot per participant per operation.
14. A preview, or a run in its scratch tree, that omitted any participant's changed path is reported and recorded as partial, never as verification of the combined work.
15. No Y.Map (or Y.Text) is ever created by two writers at the same key: every nested shared type this spec adds lives under a flat top-level key naming its writer's incarnation (`${name}\u0000${fence}`) and is created only by that writer; `manifestHead[name]` is a plain JSON value, not a nested type.
16. **D1.** An entry carries `hash`, `size` and `baseHash` only where its writer's policy authorizes the path's text (`authorizesText`: level `full`, or `declared` with the path inside `textPrefixes`); a projection needs the lead's policy to authorize it and a source that has the value (§5.5). Every other entry is path, change kind and state (plus `held`, `at` and `fence`). No replicated field holds the size or any hash of such a file's content, and readers treat a hashless `held` entry as a gap: it never resolves exactly.

## 4. Data model

### 4.1 Y.Doc (replicated; R5: authoritative only for replicated facts; schema 2 per R6a)

```ts
// packages/shared/src/types.ts
export type Coverage = { kind: 'all' } | { kind: 'none'; reason: 'intent' | 'not-publisher' | 'starting' | 'unprojectable' }
export interface ManifestHead {
  base: string            // == participant record base (R3a); guards a mid-transition read
  fence: string           // writer's holder sessionId (registry `holder`); a projection carries the lead's
  coverage: Coverage
  projectedBy?: string    // projection only: the lead participant whose live holder must equal `fence`
  level: ShareLevel       // effective level, for display; decisions use entries
  textPrefixes?: string[] // declared: where text is authorized (active + ending + retained); display
  excluded: string[]      // hex sha256(roomSalt ‖ path), sorted, one per excluded changed path; names never
  rev: number             // +1 only when entries (ignoring `at`), text or `excluded` change (content revision; conflict key)
  semRev: number          // +1 on ANY change a reader relies on: rev, coverage, level, complete, base, fence (SF4)
  scannedAt: number       // writer clock of the last full scan (heartbeat); display only (Fable 9)
  complete: boolean       // false during seed, a HEAD transition, or while a projection is being rebuilt
  publisher?: string      // for coverage none/not-publisher: who publishes this checkout
  projectedFrom?: string  // team projection only: the worker ID (registry) it is projected from
}
export interface ManifestEntry {
  change: 'M' | 'A' | 'D'  // relative to head.base
  hash?: string            // git blob id of working content, repo object format; absent for D and outside
                           // the text-authorized area (invariant 16, D1)
  size?: number            // bytes; absent exactly when `hash` is
  baseHash?: string        // blob id at head.base (absent for A, and outside the text-authorized area); §4.6
  state: 'shared' | 'held' // D is always 'shared': the deletion is the whole fact (§4.5)
  held?: 'scope' | 'binary' | 'worker'  // 'scope' entries never carry hash, size or baseHash
  at: number               // writer clock when the working content last changed; display only
  fence: string            // writer's incarnation; always equals the subtree key it lives under (MF11)
}
```

**Hashless entries (D1).** At `declared`, a changed path outside `textPrefixes` is written as `{change,
state: 'held', held: 'scope', at, fence}`, and a deletion there as `{change: 'D', state: 'shared', at,
fence}`. The area check comes first, so an out-of-area binary file is `held: 'scope'`, not `'binary'`.
The daemon still hashes the file locally to decide "changed" (§5.3 step 5) and to know when to move `at`,
but that hash stays in memory. An edit that changes only an out-of-area file's content rewrites `at` and
nothing else: `at` is display only, so it moves neither `rev` nor `semRev` (§5.3). After a restart the
daemon keeps an existing entry's `at`. Entries that do carry a hash: `shared` text, `held: 'binary'` inside
the area or at `full`, and `held: 'worker'` projections where the lead's policy authorizes the path (§5.5).

| Map / field | Key | Writer, per room | Replaces |
|---|---|---|---|
| `manifest` | flat key `` `${name}\u0000${fence}` `` → `Y.Map<path, ManifestEntry>` | the participant's daemon; for a projected worker, the lead's bridge; the map is created, written and deleted only by that fence's writer | `deleted`; "which paths changed" read from `overlays` keys |
| `manifestHead` | participant | same writer as `manifest` | `presence.share` as a fact; `overlayAt` |
| `coordination` | lead participant | the lead's bridge (`Bridge.syncCoordination`) | the union written into `scopes[lead]` (`bridge.ts:196`) |
| `meta.roomSalt` | — | the room creator, once (32 random bytes, hex); schema owned by reporooms | — |
| `overlays` | re-keyed flat: `` `${name}\u0000${fence}` `` → `Y.Map<path, Y.Text>` | same writer as `manifest` (invariant 15) | now only the text store for `shared` entries |
| `basetextFlat` | kept (`person\0sha:path`) | same writer as `manifest` | base text for shared M/D entries, for git-less readers |
| `scopes[name]` | kept | the participant's MCP (`room_scope`, `room_done`) | no longer written by the bridge |

**Publication incarnation (MF11).** Entries live under the flat key `${name}\u0000${fence}` of the writer's
incarnation (its holder session). Two clones racing for one name therefore create two different top-level
keys, never the same nested map (a concurrent create at one key would let one child map win and detach the
other writer's). A loser can neither add to nor delete from the winner's entries: it only touches
`manifest[name\u0000loserFence]`. The current incarnation is `manifest[name\u0000head.fence]`. The holder
deletes other incarnation keys for its own participant on its first write; readers never depend on that.

`deleted`, `overlayAt` and `bases` are not part of schema 2. `base` is in the participant record (reporooms).
None of the new maps join `MEMORY_TYPES` (`shared/src/memory.ts:5`). They are live state that their writers
rebuild on start. `readonly.ts:140` `PARTICIPANT_MAPS` gains `manifest`, `manifestHead` and `coordination`.

### 4.2 Local file (R5: `<git-common-dir>/room/`, temp-and-rename)

`room/sharing/<sha256(room ‖ NUL ‖ participant)>.json`. Its one owner is `PolicyStore` in the session that
holds the participant's name lease (registry `names/`). Within the process, writes are serialized on one
promise chain. Each write replaces the whole record (temp file, `fsync`, `rename`).

```json
{ "v": 1, "room": "github.com/o/r", "participant": "ben", "worktree": "/abs/realpath",
  "requested": "declared",
  "declared": { "active": ["src/app/"], "ending": ["tests/old/"], "retained": ["docs/x.md"] },
  "disclosed": { "level": "declared", "version": 2 }, "updatedAt": 1790000000000 }
```

- The level and the grant are one record, so a level change and the grant clearing it causes are a single
  atomic write. After a crash, the file holds either the old pair or the new pair, never a mix.
- If `worktree` differs from the joining worktree, the grant is reset and `requested` is kept. A grant
  names paths in one checkout.
- It replaces `room-choice.json`'s `share` and `warned`/`warnedLevels` for sharing (`choice.ts:19`,
  `rememberShare` `:60`, `markWarned` `:95`), and `room-retained-declared-<hash>.json`
  (`roomd/src/retained-declared.ts`). `room-choice.json` keeps only its non-sharing fields (registry and
  reporooms).

### 4.3 The values

```ts
// packages/roomd/src/policy.ts (new)
export interface SharingPolicy {
  readonly level: ShareLevel; readonly requested: ShareLevel; readonly ceiling: ShareLevel
  readonly textPrefixes: readonly string[]; readonly ending: readonly string[]
  readonly publisher: boolean   // holds the worktree publisher lease (registry §16)
}
export interface ExclusionRules {  // today spread over roomIgnore, DEFAULT_IGNORED_DIRS, sizeCap, totalBudget
  readonly roomIgnore: RoomIgnore; readonly sizeCap: number; readonly budget: number; readonly id: string
}
export interface PublicationInputs { readonly policy: SharingPolicy; readonly rules: ExclusionRules; readonly head: string }
export function authorizesText(p: SharingPolicy, path: string): boolean
```

`PolicyStore` (`room-mcp/src/policy-store.ts`, one per session) builds `SharingPolicy` from the sharing file
and the ceiling (`CeilingSource`, one per server, from `/auth/config`). The daemon owns `ExclusionRules`
(reloading `.roomignore`, `index.ts:528`, `:1059`) and the applied HEAD. Any change to any of the three
builds a new `PublicationInputs` and calls `daemon.applyInputs(next)`. The standalone `roomd` CLI
(`roomd/src/cli.ts:32`) builds a fixed `SharingPolicy` from `--share` with `policyFromLevel(level)`: no
grant, and `publisher: true`.

### 4.4 Hashes and digests

- `hash`/`baseHash` are git blob ids in the repository's object format, as `git hash-object --no-filters`
  would produce them. Text already read is hashed in-process. Base blobs come from `gitBlobInfoMany`
  (`publisher.ts:250`). Readers hash overlay text the same way before trusting it.
- `digest(p) = sha256(hex-decoded roomSalt ‖ utf8(p))` over the repo-relative path, normalized by
  `normalizeCoordinationPath`. Readers compute it per path they are about to certify. With no `roomSalt`,
  the room refuses to start (R6a; reporooms writes it at creation).

### 4.5 What each level publishes (D1)

| Level | coverage | Entries | Text | `excluded` |
|---|---|---|---|---|
| `intent` | `none` | none | none | empty |
| `declared` | `all` | every non-excluded changed path; `hash`/`size`/`baseHash` only inside `textPrefixes` | where `authorizesText` (non-UTF-8 there: `held: 'binary'` with hash); otherwise `held: 'scope'`, hashless | digests |
| `full` | `all` | every non-excluded changed path, with `hash`/`size`/`baseHash` | all but non-UTF-8 (`held: 'binary'`, with hash) | digests |

D1 chose this over option A (path, size and hash for every changed file), which an admitted member could
use to confirm a guessed content of a small out-of-area file, and over "unknown" outside the area, which
would hide which files changed and so keep coverage from being `all`. The cost: an out-of-area file never
resolves exactly, so a preview or conflict check touching it is partial (§6.1; reporooms §B5).

"Changed" uses git's model relative to `head.base`: worktree and index differences (including commits
between base and HEAD), plus untracked files that are not gitignored. A gitignored untracked file is not
part of the repository, is not changed, and is not digested.

**Deletion (SF5, N1).** When `lstat` says ENOENT, base has the path, and the path passed the intent/publisher
gate and the path exclusion rules (§5.3 order), the result is `change: 'D', state: 'shared'` at `declared`
and `full`, whatever the text authorization. A deletion carries no text to withhold, so the entry is exact, and every
reader resolves it as `deleted`. A path that exists but is unsafe (a symlink, not a regular file, or
leaving the root) is excluded (digested), never D. A hot file (`DiskBatch.deferHot`) keeps its last applied
entry and text until its throttle expires, except in a settling scan (§5.2).

### 4.6 Preparing for tier 2 and for patches (not built now)

- **Tier 2 (text only where scopes overlap):** `plan()` adds `&& nearAnyone(p)` (`near.ts` over `scopes ∪
  coordination` of present participants); other entries become `held: 'far'`, which readers already handle.
  `room_read` of a far path becomes the tier-3 fetch, a request message (ledger, "New message kinds").
  A far entry is inside the text-authorized area, so it keeps its `hash`, `size` and `baseHash` (D1).
- **Patches:** `baseHash` names the blob a later `patch?: string` would apply to; a reader rebuilds text from
  `git cat-file blob <baseHash>` plus the patch and checks `hash`, else `unknown: fetch` (today's `NeedFetch`).
  Only text-authorized entries have a `baseHash`, which is also the only place a patch would be allowed.
- **Split documents:** facts live only in `manifest`, `manifestHead`, `scopes`, `coordination` and claims, so
  they form the roadmap's small index document; `overlays` and `basetextFlat` move to per-participant docs.

## 5. Behaviour per path

### 5.1 Changes to inputs

1. `room_share(level)` (`tools/share.ts:26`) calls `PolicyStore.setRequested(level)`. That write also
   clears `ending` and `retained` when leaving `declared`, in the same record write.
2. `CeilingSource` refreshes on join and reconnect and calls `PolicyStore.setCeiling`. The module-global
   `shareMaxCache`/`shareSessions` fan-out and the `trackServerShare` loop (`session.ts:213-238`) are removed.
3. A `.roomignore` reload, or a change to cap or budget, produces a new `ExclusionRules`.
4. `daemon.applyInputs(next)` replaces `setShare` and `setEffectiveShare` (`index.ts:494-517`). In one
   transaction, and before any await, it re-plans the current entries under `next` without I/O:
   - A `shared` M/A entry, or a `held: 'binary'` entry, that is no longer authorized becomes `held: 'scope'`.
     Its text and base text are deleted, and so are its `hash`, `size` and `baseHash` (D1). A D entry stays
     D (`shared`): narrowing text authorization does not change an exact deletion, but its `baseHash` goes.
   - An entry (D included) now matched by the exclusion rules is deleted, and its digest is added to `excluded`.
   - At `intent`, or for a non-publisher, all entries, text and digests are deleted, and `coverage` becomes `none`.

   It then sets `this.inputs = next` and enqueues a full scan. Widening only enqueues the scan, which adds
   the hash, size, base hash and text of newly authorized paths in one transaction (invariant 3).

### 5.2 Declared grant and settlement

`PolicyStore` holds `declared = {active, ending, retained}` and is its only writer (invariant 10).

- `room_scope(paths)` writes `scopes[name]` (coordination) and calls `PolicyStore.declare(paths)`. That sets
  `ending ∪= active − paths` and `active = paths`, persists, and builds a new value.
- `room_done` calls `declare([])`: every active prefix moves to `ending`. There is no flush and no wait.
- **Settling scan.** A full scan planned under inputs `I` whose `I.policy.ending` is non-empty runs with
  `bypassHot` for every path under an ending prefix. `plan()` reports `unsettled`: paths under an ending
  prefix that it could not plan, because of a failed read, an `lstat` race, or a git error.

  After `apply`, `PolicyStore.settle(I, entries, unsettled)` handles each prefix that is in `I.ending` and
  still in the store's `ending`, and that has no unsettled path. It adds every path under the prefix whose
  entry is `shared` (or D) to `retained`, then removes the prefix. A prefix with unsettled paths stays
  `ending`, persisted, and the next full scan tries again.

  Retained paths with no entry are dropped in the same write: they equal base again, or were excluded.
- `textPrefixes = active ∪ ending ∪ retained`. `authorizesText` is `level === 'full' || (level ===
  'declared' && scopeCovers(textPrefixes, path))`.

Unlike 0.16.17's `retainLeavingScope` (`publisher.ts:89`), which enumerated what the process knew at the
instant of change (Leave 2), the prefix stays authorized until an unthrottled whole-checkout scan planned every
path under it. Kept semantics: a retained file leaves when it equals base, on a level change, or when excluded.

### 5.3 Reconcile (the publisher)

One entry point, `Publisher.reconcile(paths | 'all')`, runs from the work queue on watcher batches,
`pollHead`, the periodic tick, and after `applyInputs`:

```
I = this.inputs                                         // captured once: policy, rules, head
scan = paths === 'all' ? await changedSince(I.head.base) : paths ∪ own published paths
disk = await readDisk(scan, I.rules)                    // lstat, safety, ignore, size, UTF-8, hash, text ≤ cap
base = await gitBlobInfoMany(record base, scan) + base texts for authorized changed paths
desired = plan(I, disk, base, carriedBaseline)          // pure; table-tested; returns entries, excluded, unsettled
if (stopped || this.inputs !== I || !holdsLeases()) { markDirty(); return }
if (!revalidate(desired.textPaths)) { markDirty(); return }  // sync lstat: still a regular, safe, same-size file
roomDoc.transact(() => apply(desired, fence))           // entries, text, base text, excluded; rev++ iff changed
if (paths === 'all') policyStore.settle(I, desired.entries, desired.unsettled)
```

- **Scan input (MF7).** `changedSince(base)` is the union of:
  - `git diff --no-renames --name-only -z <base>`: worktree vs base, covering base..HEAD commits, the index and the worktree; disabling rename detection lists both the deleted source and added destination;
  - `git ls-files --others --exclude-standard -z`;
  - every path in this participant's current `manifest`;
  - every digest owner the daemon can name (it keeps its own `excluded` paths in memory);
  - the `ending` and `retained` paths.

  So a worker that committed `x` after its carried base C, then restarted against an empty document,
  lists `x`. Its base is C, not HEAD.
- **`plan()` per path**, in sorted order (a deterministic budget):
  1. `intent` or non-publisher → nothing: no entry, no D, no digest. (Such a plan is empty and does not
     even read disk.)
  2. Path rules (`.gitignore`d tracked path, `.roomignore`, default ignores, unsafe path name) → excluded
     if changed (ENOENT with base having it, or content differing from base), else nothing. Before D.
  3. `lstat` ENOENT → D (`shared`) if base has the path, else nothing. `baseHash` only if `authorizesText`.
  4. Disk-shape rules (symlink, not a regular file, over cap) → excluded if changed, else nothing.
  5. `hash === baseHash` (both computed locally) → nothing.
  6. Not `authorizesText` → `held: 'scope'`, with no `hash`, `size` or `baseHash` (D1, invariant 16).
  7. Otherwise an entry with `hash`, `size` and `baseHash`: `shared` if UTF-8 and within budget (over
     budget → excluded), else `held: 'binary'`.

  `eligibility(facts)` (`publisher.ts:30`) survives as the per-path core, with `retained`/`inScope`
  replaced by `authorizesText`.
- **Checks.** Staleness is one identity check on `I` after all awaits, plus the synchronous `lstat`
  revalidation (MF6). This replaces `sharingGeneration` and the fifteen `sharingChanged()` calls in
  `publishDiskState` (`publisher.ts:279-432`).
- **Failure handling.** A failure logs once per distinct message and marks the publisher dirty. The
  periodic scan runs every 5 s while dirty and every 60 s otherwise; the 0.16.18 backoff timer goes.
- **Revisions.** `rev` changes only when content changes, so derived conflicts keyed on it do not churn.
  `semRev` also changes with coverage, level, completeness, base and fence. `scannedAt` changes on every
  full scan and is display only (SF4). An entry's `at` is display only too: re-editing a hashless
  out-of-area file rewrites `at` and moves neither `rev` nor `semRev`; its entry otherwise changes only
  when its change kind or state does (D1).

### 5.4 HEAD transition

`base` comes from reporooms' `Roomd.resolveBase()`:
- in a team room, for everyone including a `where: 'here'` carried worker (R3c): the anchor, i.e. the newest
  ancestor of HEAD contained in a remote-tracking ref. Never C^, which may be an unpushed lead commit;
- a local room: HEAD, or the carried commit.
A peer that cannot resolve a participant's `base` answers `unknown: fetch` ("cannot compare"), never base.

So in a team room the manifest also lists committed-but-unpushed files. This is intended: teammates cannot
resolve an unpushed commit, and the §5.3 scan (`git diff <base>`) already covers base..HEAD. A push that
moves `base` is a HEAD transition as below.

`pollHead` (`index.ts:752`) keeps the 0.16.22/0.16.23 order: the applied HEAD advances only after every step
succeeds. It first writes `complete: false`. Its last step is the single transaction reporooms defines
for the HEAD transition (reporooms rev 2, MF4): the participant record's `git` (`rev + 1`), this participant's claim
moves and releases (re-anchoring), any `pushed` notice, the reconciled entries, and a head with the new
`base`, `complete: true` and `rev + 1`. Claim moves are computed before it, so readers never see `complete:
true` with old claim coordinates; a restart reruns the whole transition with prev = the recorded `git.head`. Readers seeing `complete: false`, a different `base`, or a failed fence check (§6) answer
`unknown: updating`.

### 5.5 Workers: their own rooms and the team projection (R3a, R3b; MF3)

- **A worker's own room.** The worker's daemon owns the worker's record, `base` and manifest in every room
  it joins. It builds its policy from the spawn share (`tools/workers.ts:176`) with its own `PolicyStore`,
  and nothing crosses from the lead's policy. In its workers room, `base` is the carried commit C (the
  registry's "carried from C", which the daemon reads from the registry record, not from the CRDT; registry
  N2). A `where: 'here'` worker joins the team room itself: its own daemon writes its team record, `base` is
  its team-room anchor (R3c), and its entries include the carried edits and any unpushed commits since the
  anchor that its exclusion rules and policy allow. The registry pins `base` to C for the life of the
  worktree, so Fable 10's expiry (`Daemon.carried()`, `index.ts:811`) no longer applies.
- **Team projection of a `where: 'local'` worker** (only these; R3b). Its daemon never joins the team room. The lead's bridge is the
  single writer there (registry §13) of the worker's projected participant record (reporooms), its
  `manifestHead` and its `manifest`, fenced with the lead's holder session and `projectedBy` = the lead. The input is
  `WorkerRegistry.projectable(lead)` filtered to `where: 'local'` records, the full non-terminal set. `project(set)` runs on start, on reconnect,
  on every registry `onChange`, and when the lead's team-room `base` moves. It writes the projections in the set and deletes every projection whose
  `projectedFrom` is not in the set, or whose `fence` is this lead's older session.
- **Composing a projected manifest** is pure, from local facts, with no disk read:
  - **Base (R3c):** `base` = the lead's current team-room base B (from the lead's participant record). The
    worker's full tree is diffed against B; the lead–own-worker pair is not evaluated in the team room.
  - **Source 1, the worker's own workers-room manifest (against C):** its entries give the paths the
    worker changed, with their hash and size where the source entry has them (the worker's own policy in
    its workers room decides that, invariant 16).
  - **Source 2, everything between B and C:** `git diff --no-renames --name-only B C` (unpushed lead commits and the
    carried edits) plus the registry's `carriedUntracked`. For such a path the worker did not touch, the
    hash is the blob at C. The carried paths pass
    through the lead daemon's `excludes(path)`, and excluded ones are digested with the team room's salt.
  - **Text:** every projected entry is `held: 'worker'`, except `D`. Today a local worker's text never
    reaches the team room (the bridge relays only scope and claims). This keeps that disclosure and lets
    the team see facts. Text reaches the team only after collection, as the lead's own work.
  - **Hash and size (D1):** a projected entry keeps `hash`, `size` and `baseHash` only where the lead's
    team-room policy `authorizesText(path)` (the lead at `full`, or at `declared` with the path inside
    its `textPrefixes`) and the source supplies them. Otherwise the projected entry is hashless, like the
    lead's own out-of-area files. The team room never learns more about a worker's file than it would
    about the same file as the lead's own work.
  - **Coverage (N2): inherited, never upgraded.** The projection is `all` only if every one holds: the
    lead's level is not `intent`; the source head's coverage is `all`, it is complete, and its `fence` is
    the worker's current holder; the source's `excluded` is empty (local-room digests cannot be re-keyed to
    the team salt without names). Otherwise the projection has `coverage: none` and no entries or digests:
    the reason is the source's own (`intent`, `not-publisher`), `starting` for an incomplete source, or
    `unprojectable` for exclusions or a lead at intent. A source at `intent` or `none` never yields `all`.
- **Stale projections** of a dead or stepped-down lead stay until a new holder's `project()` or the expiry
  authority removes them. Readers reject them meanwhile: a projection is valid only while its `fence`
  equals the *current live* holder of `projectedBy` (§6), checked at read and again at completion (MF3).

### 5.6 Coordination (the bridge)

`Bridge.syncScope` (`bridge.ts:171`) becomes `syncCoordination`. It writes `coordination[lead] = {paths,
workers, at}`, where `paths` is the union of the lead's projectable workers' scope paths and manifest
paths. It deletes the record when there are none. It never reads or writes `scopes[lead]`, the lead's
policy or its daemon (Leave 1). `coordinationPaths` (`near.ts:8`) reads `scopes ∪ coordination` for scope
evidence and `manifest` for changed evidence, `held` entries included (SF1): a participant with held-only
files stays near. Hooks consume this through `room/sessions/<sid>/state.json` (ledger).

### 5.7 Two sessions in one checkout

The registry's durable per-worktree publisher lease (registry §16) replaces `choosePublisher`
(`index.ts:583`). The non-publisher works as follows:
- **Its own manifest.** Its store builds `publisher: false`. Its daemon writes `manifestHead = {coverage:
  {kind: 'none', reason: 'not-publisher'}, publisher: <lease holder>}`, with no entries, text or digests.
- **How readers see it.** Readers resolving it answer `unknown: not-publisher`: "<name> shares this
  checkout with <publisher>; see <publisher>'s changes". `room_state` and `room_share` print the same line
  from one helper, which replaces `secondaryPublishingLine` (`tools/share.ts:8`).
- **No base facts (D5).** It writes no `git` record and posts no `pushed`: only the publisher does
  (reporooms §B2, §B4; registry §16). Its daemon still re-anchors its own claims on a HEAD change.
- **Its scope and grant.** It keeps its own `scopes[name]` and sharing file. On a lease handover the old
  holder first builds `publisher: false`, which withdraws synchronously, and only then releases the lease
  (registry §16).
- **Its own reads.** Reading its own files uses the local-source adapter (§6), as for every session.

## 6. Readers: "not shared" versus "equals base", every one

One resolver replaces `liveText` (`tools/state.ts:122`) and `withheld` (`:98`). It works on an immutable
snapshot (SF4):

```ts
type Version =
  | { kind: 'text'; text: string; entry: ManifestEntry } | { kind: 'deleted'; entry: ManifestEntry }
  | { kind: 'base'; text: string | undefined }             // certified (invariant 5); read at record base
  | { kind: 'held'; entry: ManifestEntry; why: string }
  | { kind: 'excluded' }                                    // digest match: changed, name withheld by rules
  | { kind: 'unknown'; why: 'intent' | 'not-publisher' | 'updating' | 'no-record' | 'fetch' | 'no-base-text'; detail: string }
interface ParticipantSnapshot { name: string; head: ManifestHead; record: ParticipantRecord; entries: ReadonlyMap<string, ManifestEntry>; texts: ReadonlyMap<string, string> }
// entries = manifest[`${name}\u0000${head.fence}`] only, minus any entry whose own `fence` ≠ head.fence (MF11)
snapshot(s: Session, person: string): ParticipantSnapshot | undefined   // copies in one synchronous read
versionOf(snap, path, env: { gitAt?: (sha, path) => Promise<string | undefined>; known?: (hash) => Promise<string | undefined> }): Promise<Version>
```

- **Fence check (MF3).** Own record: `fence === record.holder.sessionId`. Projection (`projectedFrom`
  set): `fence === liveHolder(projectedBy)`, where `liveHolder` (reporooms' participants view) returns the
  lead record's `holder.sessionId` only while that session has fresh presence. A dead or replaced lead
  (S1 → S2, projection not yet rewritten) fails the check even though the projection and its own record
  both still say S1.
- **Order of checks:** no head → `no-record`. Head not complete, or base mismatch, or the fence check
  fails → `updating`. Coverage `none` → its reason. Only entries of the current incarnation
  (`manifest[name\u0000head.fence]`, entry `fence` = `head.fence`) count, for lookup and for absence. Entry `shared` → `text`/`deleted`
  (hash checked; a mismatch → `updating`). Entry `held` with a `hash` → `text` if `known(entry.hash)`
  returns text whose hash equals `entry.hash` (Leave 3), else `held`. Entry `held` without a hash (D1) →
  `held`, always: it is a gap, and no blob the reader holds can stand in for it. Digest in `excluded` →
  `excluded`. Otherwise `base`.
  If `gitAt` is missing, `no-base-text`; if the commit is missing, `fetch`, which is today's `NeedFetch`.
- **Snapshot rule.** An operation that awaits (a preview, a diff, conflict inputs) takes one snapshot per
  participant before its first await. At the end it re-reads each participant's live `head.semRev` and
  re-runs the fence check (including `liveHolder(projectedBy)`). If `semRev` moved or the fence no longer
  holds, it retries once, then reports "Ben's changes moved during the preview; re-run". An intent
  downgrade of an empty manifest changes only coverage; `semRev` catches it (SF4).
- **Local-source adapter (SF1).** Every own-file reader resolves the caller's own version from the caller's
  disk: `room_read` (via `ownUnpublishedCheckout`), `room_claim`'s symbol lookup and digest
  (`claims.ts:40-57`), `room_state path=` (`scope.ts:45`), and the caller side of previews and conflicts.
  It works at `intent` and for a non-publisher.
- **Git-less readers (SF3).** The web view has no `gitAt`. It resolves `base` only from `basetextFlat`,
  which holds base text only for that participant's shared M/D entries. Otherwise it answers `unknown:
  no-base-text` ("base text not in the room"), never `undefined` fed into an empty-string comparison
  (`panels.ts:787-803`). Directory scopes cannot be expanded without git, so the web's coverage block lists
  declared *files* only and says "N declared directories".

### 6.1 Preview coverage, freshness and completeness (Flask finding; MF9)

`buildCombinedTree` returns `gaps: {person, path?, why}[]` and `complete = gaps.length === 0`, in addition to
its current result. Path gaps come from `held`/`excluded`/`unknown` versions of candidate paths. A
hashless `held: 'scope'` entry (D1) is always a path gap, so a preview over such a path is PARTIAL and names
it ("src/app/config.py: changed by ben, outside ben's declared area"), even when the reader holds the same
content.
Participant-level gaps (no `path`; MF9) are added for every participant whose snapshot has a non-empty
`excluded` ("N changed paths excluded, names not shared"), `coverage: none` (its reason), or an incomplete
or unfenced head. So an excluded-only or intent peer, who contributes no candidate path, still makes the
preview partial. Every `room_preview_merge` and the web Merged tab print one block per participant:

```
ben (declared, scanned 40 s ago, rev 57):
  shared: tests/test_app.py (changed 2 min ago), src/app/routes.py (8 min ago)
  in ben's declared area, unchanged so far: src/app/views.py
  changed, text not shared: src/app/config.py (outside declared area), assets/logo.png (binary)
  2 changed paths excluded by ben's rules (names not shared)
```

"Unchanged so far" means a path certified `base` (invariant 5) under one of Ben's declared scope files, or
under a declared directory's files that the reader's git lists at Ben's base. "Scanned N ago" is an age
only. A head with `complete: false` prints "updating after a commit; re-run".

Machine-consumed outcomes (`files.ts:185-219`):
- **The verdict line.** With `!complete`, it reads "PARTIAL preview: N of Ben's changes are not in the room
  (…); the combined code was NOT fully checked".
- **A scratch run.** A run with `run=` still happens. Its verdict says "ran on a partial tree", and
  `lastPreview = {clean, complete: false, testsPassed: false, partialPassed, testsCommand}`.
  `tools/workers.ts:77`'s "combined preview passed" line requires `complete`.
- **The ledger.** The fyi note posted for `room_pr_note` (`files.ts:214`) says "partial preview (…)" and
  is never listed as a passing preview (`prs.ts`).
- **The zero-path early returns (`:185-186`).** With gaps (path or participant-level), they return "no
  mergeable shared changes; not in the room: …", never "none of you has changes".

## 8. Migration and compatibility (R6a)

- **The version boundary.** The manifest is part of doc `schemaVersion: 2` (Room 0.17). The server and the
  relay refuse clients below schema 2 on the new repo-room docs *before sync*. They close existing 0.16
  connections with 4001 (reporooms owns the handshake and the wording). No room mixes versions, so this
  spec has **no dual-write and no legacy read path**. The `legacy` resolver branch is gone. A lead and a
  worker on different installs are refused by the relay.
- **Persisted documents.** 0.16 branch-room documents are not opened by 0.17 (reporooms' migration). A
  schema-2 document starts with no `manifest`; each writer creates its records on seed with `complete:
  false`, then fills them in.
- **Local durable state, migrated once at the first 0.17 start** by `PolicyStore.open`, under the name lease:
  - **Requested level.** If there is no sharing file for (room, participant), `requested` is taken from
    `room-choice.json` `share` (the per-clone value today). `disclosed` is taken from `warnedLevels` for
    this worktree and server. Those fields are then removed from `room-choice.json` with a temp-and-rename
    write, under `room-choice.json`'s existing lock.
  - **Grant.** `room-retained-declared-<hash>.json` and the 0.16.12 legacy `room-retained-declared.json`
    in this worktree's git dir are imported into `declared.retained` when their `{server, room,
    participant}` matches once the old branch-room name is mapped with reporooms' `repoRoomOf(old room)` (looked up once at the first 0.17 start). They are then deleted. A crash before the
    delete re-imports idempotently.
- **The cutover is hard (D2, confirmed by the human 2026-09-28).** Every teammate upgrades at once; old
  branch rooms become reporooms' 30-day read-only archive.
- **Consent (lead condition ii; wording by D1).** `sharingDescription('declared')` (`config.ts:50`) becomes
  "paths of every changed file; text only in your declared area". A session joining at
  `declared` whose sharing file has `disclosed.version < 2` shows it once, then records `{level, version:
  2}`. README, onboarding and the join skill change with it.

## 9. Failure and recovery

- **Crash or kill -9.** Level and grant change in one persisted write before a value takes effect, so a
  restart resumes from a consistent pair; `ending` prefixes survive until an unthrottled full scan settles
  them. The restarted daemon writes `complete: false`, runs `applyInputs` from the persisted value, then a
  full scan (§5.3 input). Nothing is published or withdrawn on the strength of in-memory state that died.
- **A lost lease.** `holdsLeases()` failing at apply writes nothing and builds `publisher: false`. A
  stepped-down holder's late write fails readers' fence check and is overwritten by the new holder.
- **Partition.** Peers see the last manifest with its age; one writer per record per room means reconnect
  needs no conflict resolution; a mistaken peer delete is repaired by a full scan (§5.8).
- **Races.** Inputs change (policy, rules, cap, budget, HEAD) → identity differs, nothing written, and
  narrowing already withdrew synchronously. File swap after the read → `lstat` revalidation fails. Preview
  against a transition, a coverage change or a lead change → `semRev`/fence recheck, one retry, then a report.
- **Git failure.** Logged once, retried on the 5 s tick; entries stay as last applied; unplanned `ending`
  paths keep their prefix `ending`.
- **Two sessions in one checkout:** §5.7. **One participant in two host sessions:** refused by the name
  lease (R1).
- **The lead dies with projected workers.** Projections stay but fail `liveHolder(projectedBy)`, so readers
  answer `unknown`; a new holder's `project()` or the expiry authority (§5.8) replaces or removes them.

## 12. Risks

- **What declared sharing still discloses (D1).** Option A's risk, a hash of a tiny out-of-scope file
  confirming a guessed content, is gone: out-of-area entries carry no hash and no size. What remains
  visible to admitted members (D3: admitted means trusted) is each out-of-area changed path, its change
  kind and when it last changed (`at`). A path whose existence must not be visible needs `.roomignore`
  (a digest) or `intent`. The cost is exactness: a declared participant's out-of-area files are always
  gaps, so previews and conflict checks touching them are partial.
- **An excluded-path digest confirms a guessed path changed (MF1 ruling).** A member who guesses
  `secrets/prod.env` can compute its digest with the room's salt and learn that the path changed. The salt
  stops precomputed tables across rooms, not guesses within the room. The mitigations: only admitted
  members see digests, and only for changed paths. For paths whose existence must not be confirmable, the
  answer is `intent`, or not keeping them in the checkout.
- **A reader is missed.** A reader that still reads `overlays` directly would treat held as base. After
  step 3, `RoomDoc.overlayText`/`text` are private to `versionOf` and the daemon, and a CI grep forbids
  `.overlays` elsewhere.
- **Projection lag.** A worker's team facts are only as fresh as the lead's `project()`: on change,
  reconnect, and the registry's 30 s tick.
- **Doc size.** About 150 bytes per changed path plus 64 per digest; negligible next to overlay text.
