# Local durable state in SQLite

**Revision 2026-11-05.** Resolves [the full spec review](../reviews/2026-11-05-spec-review-sqlite-state.md): **M1** selects the official Node.js 22.22.3 minimum, catchable bootstrap preflight and actual-host launch qualification while keeping hooks dependency-free; **M2** assigns migration to one explicit offline owner with a durable generation, whole-operation admission/drain barrier, lock order and crash recovery; **M3** adds identity reservations, scoped blockers and evidence relations for invalid/quarantined state. Also addresses **S1–S5**: narrows the first release, maps tables to invariants and deletion obligations, bounds maintenance, orders semantic leases/cancellation, corrects citations and hook timing, and describes concurrent best-effort hook observations. These are design requirements, not completed implementation or qualification evidence.

Date: 2026-11-05. Status: proposed; no runtime or storage change is shipped by this document.

## Problem and first shipping scope

Room has built transactional storage from JSON, exclusive creation, guards, fsync, rename, quarantine and reconciliation. The roadmap proposes consolidation (`docs/roadmap.md:37`), but being JSON is not sufficient reason to migrate a domain. Atomic publication already exists: registry temporary files are fsynced, exclusively linked or renamed, and their directory synced (`packages/relay/src/leases.ts:78`, `:93`, `:104`). Hooks, choice tag writes and preview metadata use lighter temporary-file/rename semantics (`plugins/room/hooks/common.mjs:223`; `packages/room-mcp/src/choice.ts:91`; `packages/room-mcp/src/preview-cache.ts:251`). SQLite's intended benefit is atomic updates of related lifecycle facts and constrained queries, not inventing atomic file writes.

Ship **worker lifecycle and collection admission only** in the first storage release: worker identity/reservations, valid worker payloads, runs/reports/exits, operation/run-writer/destination leases, collection review holds and per-room cleanup intent. Keep discard steps and patch metadata inside the versioned worker payload; no separate tables without a query benefit. Include only the migration, blocker and invalidation infrastructure necessary for these domains.

0.17.31's pending collected-worktree cleanup supplies a concrete invariant: a kept checkout must retain its live record; applying output must not be repeated merely to finish cleanup (`CHANGELOG.md:10`; `packages/room-mcp/src/retire.ts:80`). Archive, phase and pending room cleanup need atomic updates (`packages/room-mcp/src/worker-registry.ts:913`, `:921`, `:939`). Tag/capacity/intent admission currently spans separate files (`packages/room-mcp/src/worker-registry.ts:693`). These are reasons to convert related facts together, while retaining the state machines.

Other releases do not establish database fixes: 0.17.26–27 preview reclaim/order, 0.17.30 zombies, and 0.17.32 cwd evidence depend on OS/process/Git checks (`CHANGELOG.md:52`, `:48`, `:22`, `:3`). Credential and hosted-store read failures concern other boundaries (`CHANGELOG.md:27`, `:28`); 0.17.29 changed exports (`CHANGELOG.md:34`). SQLite cannot supply missing host identity, unwitnessed exit codes, sharing error propagation or message delivery evidence. The cleanliness review predates subsequent fixes and is context, not a current failure reproduction (`docs/superpowers/reviews/2026-11-04-cleanliness-room-mcp.md:3`, `:73`). No performance gain is demonstrated yet.

## Runtime and launch contract (M1)

Use `node:sqlite` through one typed `LocalState` API and explicit transactions at `<git-common-dir>/room/state.sqlite`. Verify the canonical common Git directory and HEAD before creating storage (`packages/room-mcp/src/worker-registry.ts:73`). Record random clone ID and canonical location; a copied DB cannot authorize a process on another machine.

The exact minimum supported MCP distribution is the **official nodejs.org Node.js 22.22.3 binary distribution**, with bundled SQLite **3.51.3**, on the native OS/architecture being qualified. [Its release notes](https://nodejs.org/en/blog/release/v22.22.3) record that SQLite update (consulted 2026-11-05). This is a capability floor, not a promise that this historical patch remains security-current: the release must test a currently patched official 22.x at or above this floor. Other vendors, custom builds and other major lines remain unqualified until explicitly tested; version comparison alone does not qualify them. Use the minimum 22.x `DatabaseSync` API. SQLite arrived in [22.5](https://nodejs.org/download/release/v22.14.0/docs/api/sqlite.html), flag-free in [22.13](https://nodejs.org/en/blog/release/v22.13.0); neither is the selected floor. Require SQLite >=3.51.3; this release does not accept backports by version guessing, even though [the WAL advisory](https://sqlite.org/wal.html#walreset) names fixed backports.

Both hosts currently launch an external command named `node`, not the host executable's embedded runtime. Installation instructions for the compatibility release must put the qualified official distribution's bin directory first in the **host launch environment's PATH** (Windows: directory containing `node.exe`), fully stop the host and its persistent MCP-launching parent/daemon, then relaunch from that environment. A GUI host needs its own environment corrected and restarted; upgrading terminal Node alone is insufficient. Do not change frozen hooks or silently download/substitute a runtime. No new host configuration feature is assumed.

## Schema and quarantine constraints (M3)

Use `STRICT` tables, foreign keys enabled on every connection, bound parameters, bounded versioned JSON, positive seq/run checks and explicit phase enums. Indexed identity columns are authoritative and must agree with payload fields. No cascading deletion of history, reservations or evidence.

| First-release tables | Keys, relations and benefit | Required contract tests |
|---|---|---|
| `schema_meta`, `imports` | Singleton schema/min-reader/min-writer, DB/clone ID, migration generation/state and source manifest digest; `(generation, source_path, digest)` import assignments/results. Infrastructure required by conversion. | Stable legacy IDs; crash and duplicate-migrator recovery; version refusal. |
| `worker_reservations`, `workers`, `adoptions` | Reservation PK worker ID, state `valid`, `quarantined`, `missing-reserved` or `retired-tombstone`, nullable evidenced checkout/lead/room; valid payload row PK/FK reservation, phase/seq and lead/room/checkout indexes. | `tag_reservations` | Unique tag → reservation ID FK, incarnation/holder evidence. Tag need not reference a valid worker payload. | Existing quarantined W still reserves tag; malformed tag cannot become free. |

Reservation rows have no synthetic phase, launch, host identity or capability. `workers` exists only for validated payloads. A reservation without a payload cannot launch, resume, report, signal, collect, discard or project as a normal worker. It remains visible as blocked diagnostic state. A retired tombstone remains until tag/checkout reuse is justified by valid retirement/cleanup evidence, not age. Deleting a worker payload never deletes its parent reservation. A transition to reusable and any tag release must assert no relevant blocker, lease, shared link, kept checkout or pending cleanup in the same transaction.

Every admission/cleanup query checks blocker targets for clone, destination/checkout, tag, worker and run as applicable, in the same snapshot/transaction as its decision. Missing payload and blocked state are distinct from absence. Shared-owner cleanup consults all incoming `shared_links`, including borrowers whose own payload is invalid; owner quarantine blocks reuse/deletion of the shared checkout. An existing valid borrower retains its link but cannot use it to authorize effects against a blocked owner. Run writer/operation leases can reference reservations without valid payloads for preservation, but only valid worker/run facts grant new operation authority. Never release a damaged lease based on age or decoding failure.

Capacity uses the existing valid-worker status predicate (`worker-registry.ts:680`): starting/running/unknown/ambiguous consume capacity. Today's quarantine scan is a tag barrier, not a count of valid running workers. Preserve known counts; when damage prevents proving occupancy, add a capacity blocker at the evidenced lead scope, or clone-wide if unknown, and refuse new spawn/resume rather than counting it as zero or inventing a live worker. This deliberately conservative import behavior must be visible to the user. Retirement/cleanup never erase a blocker to free capacity.

Import examples are normative:

- `quarantine/W.json.bad-*` plus `tags/build.json → W` creates reservation W in `quarantined`, the build tag FK and evidence/blockers. A valid borrower referencing W keeps an FK to that reservation. Do not drop the link/tag to satisfy a foreign key.
- A tag reservation with a safe worker ID but no payload creates `missing-reserved`; it cannot become reusable without the same missing-record/dead-holder evidence required today. A malformed tag or adoption preserves bytes and blocks its tag/ownership scope; unknown identity escalates to clone scope.
- A malformed report still at `runs/W/1.report.json` has parent provenance; block W/run 1. An already quarantined `1.report.json.bad-*` has **no reliable worker parent** (`worker-registry.ts:441`). Do not guess from basename or nonce fragments: preserve it with clone-wide run/cleanup/capacity blockers until an explicit human mapping resolves the ambiguity. Do not infer witnessed exit or completion from it.
- Malformed collection holds block the destination identified by the original path hash; if canonical mapping cannot be established, block all collection destinations until resolved. Valid holds never silently disappear. Malformed policies remain in the unchanged file backend and retain conservative publication failure/intent-only behavior (`packages/room-mcp/src/policy-store.ts:28`, `:96`). Migration does not replace them with SQL defaults; retirement requiring policy revocation stays pending on failure.

Evidence preserves raw bytes independently of JSON decoding and valid rows, with digest and original path if known, and explicitly unknown provenance where lost. Human recovery is a stopped-writer, scoped repair: back up evidence, inspect authoritative Git/process/worktree and reservation facts, supply an explicit identity mapping or disposition, validate relations, then audit removal of only the named blocker. Unknown quarantine may require manual inventory of every worker checkout. No “clear all,” force bypass, guessed ownership or automatic evidence expiry. Physical DB corruption requires offline salvage, not row quarantine.

## Concurrency, leases and bounded maintenance

Each MCP owns a connection. `BEGIN IMMEDIATE` serializes short writes; worker updates require matching seq and lease token/generation, increment seq and append change together. No transaction spans awaits, Git, process probes, user writes or network calls. Use `busy_timeout=0` and asynchronous jitter retries of the **whole** transaction, including open/recovery/close BUSY. Normal SQL retry budget is 1 s; destination lane wait is separately 30 s (`docs/reference.md:93`). A zero busy timeout does not bound query execution, fsync or checkpoint time.

A committed lease survives a SQL transaction: it blocks other callers throughout external effects. Acquire in order: operation admission ticket (below), destination lane if needed, shared owner operation lane, borrower/worker operation lane, run-writer lane, short SQL transaction. Multiple destinations/owners at one level use canonical sorted keys; do not acquire an earlier level while holding a later one. Capacity/tag checks and intent allocation occur atomically in SQL after owner/worker lanes. Report writes need only their run-writer lane. Publisher election remains independent in files: establish/verify it before operation admission; never wait for publisher acquisition while holding lifecycle lanes. Losing it prevents publication, not release of recovery evidence.

Preview calls take an admission ticket before any OS preview lock/helper; cleanup taking preview locks does so after its destination/owner/worker lanes, without entering callbacks that acquire those lanes in reverse. An admitted nested call reuses its outer ticket. Discard→stop reuses the same call token/worker lane, returns “already held,” and must not release the outer lane (`worker-registry.ts:755`). Other same-MCP calls get distinct tokens. Release in reverse order, compare token+generation, and retain ownership through intent→effect→acknowledgement. Probe full identity outside SQL before takeover; alive/unreadable is busy. Recheck exact observed generation in a transaction, and authority before each external effect. SQL cannot undo or fence an arbitrary write already in progress.

Cancellation before admission drops queued work; after admission but before effect it rolls back/releases exact leases. After an effect it must persist its outcome or ambiguous recovery intent before releasing admission; never replay an ambiguous apply. An uncertain commit is resolved by operation ID on reopen. A process killed before acknowledgement leaves durable intent and a ticket requiring identity-based recovery; a timeout cannot erase them. Pending collected cleanup, deterministic publication IDs, discard replay and patch hash→fsynced bytes→ack ordering stay intact (`worker-registry.ts:979`; `packages/room-mcp/src/retire.ts:80`, `:131`, `:220`). Network/Y.Doc delivery remains at-least-once with deduplication.

Verify WAL, FULL, foreign keys, `trusted_schema=OFF`, extensions disabled, and `wal_autocheckpoint=0` on every writable connection. WAL requires same-host local filesystem locking; unsupported/unknown remote or synchronized paths refuse activation. The migration owner also serializes election of one maintenance MCP via a dedicated maintenance ownership file, recovered only from verified death. That MCP schedules a passive checkpoint at most once every 30 s or after 16 MiB WAL growth. No automatic checkpoint on a tool's committing connection, no read transaction across awaits, and no unlinking WAL/SHM to relieve pressure. See [WAL checkpoint behavior](https://sqlite.org/wal.html#ckpt) and [PRAGMA definitions](https://sqlite.org/pragma.html).

Retention/budgets for this first release:

- `changes`: retain at most 10,000 entries and at most seven days; persist the low watermark before pruning. A reader behind it does a bounded full snapshot, never assumes no changes. Delete at most 200 rows per transaction/pass.
- `imports`: retain the active generation's source assignments/results and all unresolved evidence indefinitely. Keep the last completed generation plus its manifest and one pre-migration backup for at least 30 days and through upgrade acceptance; explicit offline archive is required before further removal. No duplicate history per polling pass.
- `instances`: keep referenced/live/unknown identities; prune only verified-dead, unreferenced instances after seven days, at most 200 per pass. No observation-history table. Blockers, active holds, pending intents/cleanup and unresolved evidence have no automatic expiry. Worker history remains until explicit archival; storage pressure must not silently delete recovery facts.
- Maintenance prunes at most one 200-row batch per 30 s tick, yields between work, and issues no VACUUM/TRUNCATE checkpoint during live operations. Bound import batches to 200 records/4 MiB decoded bytes, per record 1 MiB; larger legacy metadata refuses with a diagnostic rather than truncation. Raw evidence is streamed under a separate 256 MiB total import budget; exceeding it leaves maintenance pending for explicit inventory/repair.
- Warn at 64 MiB WAL; at 256 MiB stop admitting growth-producing lifecycle mutations and request short readers close/restart. Permit diagnostics and bounded acknowledgement/recovery work, and never discard intent to meet the cap. Log oldest reader/maintenance identity where known, without payloads. Disk failure rejects writes. Caps are pressure thresholds, not guarantees about a single SQLite fsync's duration.

Measure query/commit/checkpoint event-loop delay and hook p50/p95/p99 under contention and a pinned reader before selecting a synchronous adapter for shipping. If synchronous I/O prevents the existing hook service budgets from being met, move DB calls/checkpointing to a bounded worker-thread adapter before release. Do not claim the 1 s retry deadline is a hard fsync deadline.

## Dependency-free hooks (M1, S4, S5)

Hooks never import SQLite, npm dependencies or a database CLI. Preserve frozen `plugins/room/hooks.json` byte-for-byte; change neither manifest for this storage proposal. Both scripts import built-in-only `common.mjs` and use files/authenticated loopback. MCP durable lifecycle state changes do not require hook SQL access.

`openMcp` bounds connect/default request selection timing and reply size (`plugins/room/hooks/common.mjs:239`). Before-edit uses 700 ms at `plugins/room/hooks/before-edit.mjs:78`; SessionStart uses 300 ms at `plugins/room/hooks/session-start.mjs:41`. These are **selection budgets**, not total hook deadlines: explicit `request(body, ms)` overrides the default remaining deadline, and each script allows a separate 1,000 ms confirmation (`before-edit.mjs:168`; `session-start.mjs:62`). The host manifests separately specify five seconds; input reads, process probes and filesystem work also consume time. Preserve select→accepted stdout→confirm ordering (`before-edit.mjs:162`; `common.mjs:304`). Malformed reply, stdout failure or missing confirm leaves messages owed. Execution receipts and wake attempts never prove delivery; shared receipts remain fenced Y.Doc state.

Per-session paths isolate sessions, **not concurrent invocations within a session**. SessionStart and before-edit can both publish `hook.json`; MCP fallback can also publish `session.json` (`packages/room-mcp/src/session.ts:151`). Temp/rename avoids torn files but older observations may win last rename. Keep the existing best-effort bridge; no SQL observation table, durable journal or single-writer claim. Accept lost diagnostic/model/activity updates and duplicate coordination context. Suppression records cannot suppress owed ledger messages or become authority for identity/capabilities.

Readers validate full session binding and current process ancestry independently of timestamps. Within a bound MCP, accept strictly increasing, finite, non-future activity times; equal timestamps cause no new activity and conflicting equal-time metadata remains unknown or the previously validated observation. Lower times cannot regress accepted state. Clock rollback/future timestamps make freshness unknown until a valid current observation arrives; do not infer a new session, delivery, process death or durable activity from them. On restart, file time alone cannot revive prior-session activity; revalidate identity and use current-process startup/binding evidence. Unordered model/suppression metadata may be missed until the next hook; duplicates are preferable to delivery loss. Keep bounded receipts/pruning, stale projection rules and alone fast path without IPC. Hooks never start a helper/MCP per edit, and `state.json` cannot be restored from SQL as live presence.

## Migration and activation protocol (M2)

The first conversion and every later SQL-to-SQL upgrade have **one explicit owner: an offline maintenance command**, invoked deliberately for a canonical common directory. MCP startup never auto-converts or applies DDL. The compatibility release adds the protocol below before storage conversion; exact compatibility build/version IDs must be recorded in its release manifest. Unmodified 0.17.32 has no such fence, so there is no live mixed-version upgrade.

Use two dependency-free durable bootstrap controls outside SQL: the existing `room/registry/migration.lock` for exclusive migration ownership and a new guarded `room/storage-gate.json` for admission/generation/registrations. The lock uses full instance identity, nonce, guarded verified-dead recovery and a 30 s wait as in `worker-registry.ts:1283`; it is not a SQL `BEGIN` or a TTL. Retain these controls after cutover for SQL-to-SQL upgrades. The gate has a monotonically increasing migration generation, phase (`legacy`, `draining`, `staging`, `db-complete`, `active`), owner identity/token, source/target schema and minimum reader/writer build, DB ID, manifest/backup digests, and import checkpoint. Initialize an absent gate under its guard only after checking there is no DB/activation evidence; concurrent initialization cannot overwrite a successor. Publish changes by fsynced temp file, rename and directory sync. Never reset generation on failure. Corrupt/missing gate with other activation/DB evidence refuses operation.

**Registration and whole-operation barrier.** Under the gate's short file guard, every compatibility or SQL MCP registers its process identity/build, checks gate generation/version and records a unique admission ticket before preparing a writable repository. All openers include synchronous snapshots, worker admission, background reconcile/projectors, retirement, report/exit callbacks, idle helpers that consult lifecycle state and preview/maintenance entry points. No constructor bypass. Tickets cover the entire operation from first authority read through Git/process/network/file effects, durable acknowledgement and lease release; checking a marker before a write is insufficient. Nested helpers reuse a ticket; detached tasks/helpers register their own ticket/identity before their parent releases it. Tickets and registrations are private durable records under the same gate guard, linked to generation; the exact file layout may be sharded to bound guard work, but admission and phase transition share one guard.

The offline owner is registered as maintenance, without an ordinary operation ticket; it cannot run normal tools while holding migration ownership. A migrator first owns `migration.lock`, then under the gate guard increments generation and publishes `draining`, atomically closing new admission. Compatibility processes refuse new operations immediately on their next admission check, stop timers/watchers, finish existing tickets, close SQL connections and acknowledge drained generation. Existing ticket holders may complete their operation despite the phase change; the owner cannot scan until all have drained. There is no lease-age shortcut. A dead ticket holder is recovered only after full identity verification and its outstanding intent/effect is reconciled or explicitly marked blocked. A live paused process or unknown identity blocks conversion. A SQL connection with no active ticket must be closed and acknowledged before DDL; no prepared writable repository survives a generation change. Registrations/tickets are capped at 256 processes and 4,096 concurrent operations per clone; reaching the bound refuses admission, never drops an existing ticket. Scan at most 200 records per yielded pass, and retain unknown/dead-but-unreconciled entries until resolved.

**Lock order.** Never wait for drain while holding the gate guard, a SQL transaction, legacy destination/operation/capacity guards or a preview OS lock. Ordinary operations: admission under gate guard (release guard) → destination collection lane → shared-owner → worker operation → run writer/capacity/record guards as needed → preview OS lock/helper if needed, releasing in reverse. No operation may acquire migration ownership while admitted. Compatibility release must route the legacy pre-registry importer through the offline owner, removing independent startup imports; otherwise its existing migration lock could invert this order. Migrator: migration ownership → short gate transition → drain with no lower locks → legacy destination lanes in canonical order → owner/worker/run lanes in stable ID order → capacity/record guards only for bounded synchronous snapshots → preview lock checks if needed → SQL transactions. After drain these lower locks are verification/exclusion against known legacy paths, not a replacement for the barrier. Failure to acquire one stops the migration without stealing it. Preview helpers/check children must finish and release locks before conversion; unknown cwd/process evidence retains quarantine and stops conversion. Preview metadata stays in files, and no surviving helper is silently declared drained.

The explicit owner performs these steps while retaining migration ownership:

1. **Preflight before maintenance:** run the catchable capability/filesystem check above. Then inventory installed/loaded MCP builds, workers, launchers and helpers across every linked worktree, registrations, process identities and legacy operation/collection locks. Finish or stop workers without removing worktrees. Fully stop old host/MCP-launching processes and prevent their automatic relaunch during maintenance. A registration list alone cannot prove absence of unmodified 0.17.32. Require a complete process/host inventory, all affected sessions stopped/restarted into the compatibility build, and explicit operator confirmation that old installations will not be launched. Record this evidence. Unknown inventory or an uninspectable writer refuses conversion; if the environment cannot establish exclusive offline access, leave files authoritative. A marker cannot technically fence an old binary deliberately launched later; that configuration is unsupported and must be stated prominently.
2. **Recheck after ownership:** reread gate, DB/version and completion marker; a losing/stale migrator discards staged manifests and never publishes from a prior generation. If already active and matching, report complete. Otherwise establish draining generation and await every registered process/ticket/helper. Admission/register/drain operations use short guards only. Startup wait is at most 10 s with a maintenance/restart result, keeping below Codex's 30 s startup timeout. Explicit migration gets a 120 s drain and 10-minute bounded import attempt; deadlines leave durable maintenance state, never reopen admission automatically.
3. **Stage only under quiescence:** acquire legacy exclusions as above; finish the old `migration.json` importer with its durable source→worker assignments before converting, or retain incomplete state and stop (`worker-registry.ts:1303`, `:1327`). Back up only converted bookkeeping/evidence plus required provenance, with bounded path/digest manifest; preserve worktrees, Git refs, logs and file-only domains. Stable assignments must survive owner death and a changed staging attempt. Refuse incomplete scans, permission failures or missing required snapshots. Quarantine originals remain private; source bytes are never rewritten as defaults.
4. **Import and validate:** create staging schema with matching generation and importing state; journal bounded batches and deterministic source assignments. Preserve IDs, seq, runs/nonces, immutable report chains, witnessed observations, adoptions/tags, shared links, collectPending, archive, per-room cleanup, discard steps, patch paths/hashes and hold token hashes. Construct M3 reservations and blockers before validating references. No normal opener can use staging tables. Revalidate every source digest under continued drain/exclusions; source changes abort completion. File-only policy/choice/delivery state is neither converted nor dual-written.
5. **Commit and publish:** one transaction applies final constraints, DDL/schema version, min-reader/min-writer, manifest digest and DB-complete generation. Only this owner runs DDL. Close/checkpoint staging connections and durably publish the DB if staged separately; fsync containing directory. Under the gate guard publish the activation marker/gate with the same generation, DB/clone ID, schema, minimum versions and manifest digest, using durable rename. Gate/DB disagreement or incomplete publication leaves maintenance closed. Then transition to active and release exclusions/ownership. New openers under the gate guard check active generation, marker, DB schema and both reader/writer compatibility before preparing statements; ticket admission pins generation until operation completion. No dual write and no automatic JSON fallback.
6. **Verify before resume:** fresh sessions check worker inventory, held checkpoints, blockers, policies and pending delivery/recovery state before consequential operations. Retain source backup read-only; hooks continue the file bridge. Ports remain the single file backend across **all clones**. Any future port conversion requires a separate user-wide owner, registrations/drain/generation and all-clones barrier; this design does not authorize it.

**Crash/reopen rules:** before drain publication, legacy authority remains; after drain but before DB completion, restart stays in maintenance and the next verified owner resumes/revalidates staging using durable assignments. A crash during a backup/batch/DDL transaction leaves prior committed batches intact and rolls back only the uncommitted SQL transaction, not the barrier. After DB-complete but before marker/gate activation, the successor verifies generation, source manifest and DB integrity and republishes the matching marker; it does not reimport stale sources. After marker publication but before active, finish the matching active transition. After active, legacy files are backups only. Missing active DB or marker/DB mismatch is an error, never empty creation. Successor ownership requires the old identity definitively dead; an unknown owner remains blocked. Every irreversible publish/checkpoint rechecks owner token/generation; an old suspended owner cannot complete a newer generation. SQL-to-SQL upgrades use exactly the same registration/drain/connection-close boundary, WAL-aware pre-upgrade backup and transactional version change; older readers and writers refuse incompatible versions rather than probing tables optimistically.

Downgrade needs stopped-world validated export of converted domains. Deleting DB/marker cannot be a rollback: stale files can resurrect retired workers/holds. Restoring old metadata cannot undo applied files, removed worktrees or published text. Keep recovery patches/Git evidence with backups. First-release backup/importer retention is at least 30 days and through acceptance; removal/export is explicit, not a timer-based downgrade promise.

## Addendum 2026-11-05: network filesystems

Codex 0.166.0 forces DELETE journaling for its own SQLite databases on NFS and ships `codex migrate-nfs-db`
(see [host-survey-2026-11-05-codex.md](../../archive/reports/host-survey-2026-11-05-codex.md)). WAL relies on
shared memory that network filesystems do not provide. Room's preflight therefore detects the filesystem type
under the git common dir (statfs on macOS and Linux; Windows UNC and mapped drives) and opens the database with
`journal_mode=DELETE` and `busy_timeout` there, reporting the choice in `room_state(check=true)`; it never
opens WAL on a path it cannot prove local. A clone that moves between a local and a network path is handled by
re-detecting on every open, since journal mode is persistent in the file and a WAL database on NFS must be
converted before use.

## Failure handling and security

Busy, cancellation and unknown commit outcomes resolve by operation ID with bounded retries; no external effect precedes committed intent. Full disk, permissions or I/O failures preserve DB and pending cleanup and refuse new consequential work. Corrupt/newer/missing-after-activation DB refuses writes and publication requiring local authority; preserve DB/WAL/SHM and stop all writers before integrity checking or salvage. Never rename a live DB, silently recreate it or use a JSON fallback. Unknown process identity cannot free a lease, signal a PID or clear preview quarantine. Runtime failure refuses before maintenance. Hook endpoint failure retains bounded startup/activity evidence and owes undelivered messages.

Use SQLite backup support or a closed/checkpointed offline copy, not a lone main-file copy while WAL is live. Native local filesystems need qualification; known network/sync paths and foreign-machine copies refuse writable activation. DB directory, gate/registrations, WAL/SHM, backups and evidence are private (0700 directory/0600 files; validate native Windows ACLs). Reject symlink substitution and unexpected ownership/types. Disable extension loading and unsafe schema execution; no generic SQL RPC or remote paths. A local same-user process can bypass cooperative storage checks; a DB is not a new security boundary. No tokens in choices or payload logs. Diagnostics expose versions, identities, operation IDs/error classes, blocker targets, generation, last commit, busy counts and WAL/DB size, never private tasks/log tails/recovery tokens. Ordinary SQLite deletion does not promise secure erasure. Hold recovery remains scoped and audited (`docs/reference.md:95`).

## Remaining open question

What native OS/filesystem combinations can be release-qualified, and do measured synchronous commit/checkpoint delays require the worker-thread adapter? ## Five-line summary

Ship worker lifecycle, reservations and collection holds together; keep independent domains in files.  
Require official Node.js 22.22.3 or qualified later 22.x, with catchable actual-launch capability checks.  
Keep hooks dependency-free and file/loopback-based, preserving frozen manifests and delivery semantics.  
Use one offline migration owner, durable generations, whole-operation drain and explicit relational blockers.  
Open: qualify native filesystems and measure whether synchronous storage requires a worker-thread adapter.
