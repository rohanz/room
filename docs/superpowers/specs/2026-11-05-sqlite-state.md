# Local durable state in SQLite

**Revision 2026-11-06 — amendments accepted.** Incorporates the maintainer's accepted [slice 2 plan amendments and decisions](../plans/2026-11-06-sqlite-state.md): the daemon is the sole online SQLite owner, using one bounded DB worker thread; an offline command owns migration/DDL and empty-clone initialization; RPC results are durable; first qualification targets local single-host APFS, ext4 and NTFS only. Preserves the [full spec review](../reviews/2026-11-05-spec-review-sqlite-state.md) invariants: **M1** official Node.js 22.22.3 minimum, catchable bootstrap preflight, actual-host launch qualification and dependency-free hooks; **M2** explicit offline ownership, durable generations, whole-operation admission/drain, lock order and crash recovery; **M3** reservations, scoped blockers and evidence relations. **S1–S5** scope, deletion, bounded maintenance, lease/cancellation and hook-delivery requirements remain. These are design requirements, not completed implementation or qualification evidence.

Date: 2026-11-05; amended 2026-11-06. Status: design document with amendments accepted on 2026-11-06; no implementation, native/runtime/filesystem or performance qualification is claimed, and no runtime or storage change is shipped by this document.

## Problem and first shipping scope

Room has built transactional storage from JSON, exclusive creation, guards, fsync, rename, quarantine and reconciliation. The roadmap proposes consolidation (`docs/roadmap.md:45`), but being JSON is not sufficient reason to migrate a domain. Atomic publication already exists: registry temporary files are fsynced, exclusively linked or renamed, and their directory synced (`packages/local-state/src/leases.ts`). Hooks, choice tag writes and preview metadata use lighter temporary-file/rename semantics (`plugins/room/hooks/common.mjs`; `packages/room-mcp/src/choice.ts`; `packages/room-mcp/src/preview-cache.ts`). SQLite's intended benefit is atomic updates of related lifecycle facts and constrained queries, not inventing atomic file writes.

Ship **worker lifecycle and collection admission only** in the first storage release: worker identity/reservations, valid worker payloads, runs/reports/exits, operation/run-writer/destination leases, collection review holds and per-room cleanup intent. Keep discard steps and patch metadata inside the versioned worker payload; no separate tables without a query benefit. Include only the migration, blocker and invalidation infrastructure necessary for these domains.

0.17.31's pending collected-worktree cleanup supplies a concrete invariant: a kept checkout must retain its live record; applying output must not be repeated merely to finish cleanup (`CHANGELOG.md:60`; `packages/room-mcp/src/retire.ts`, `finishPendingCollect`). Archive, phase and pending room cleanup need atomic updates (`packages/room-mcp/src/worker-file-store.ts`, `beginRetirement`; `finishCleanup`). Tag/capacity/intent admission currently spans separate files (`packages/room-mcp/src/worker-file-store.ts`, `writeIntent`). These are reasons to convert related facts together, while retaining the state machines.

Other releases do not establish database fixes: 0.17.26–27 preview reclaim/order, 0.17.30 zombies, and 0.17.32 cwd evidence depend on OS/process/Git checks (`CHANGELOG.md`). Credential and hosted-store read failures concern other boundaries (`CHANGELOG.md`); 0.17.29 changed exports (`CHANGELOG.md`). SQLite cannot supply missing host identity, unwitnessed exit codes, sharing error propagation or message delivery evidence. The cleanliness review predates subsequent fixes and is context, not a current failure reproduction (`docs/superpowers/reviews/2026-11-04-cleanliness-room-mcp.md`). No performance gain is demonstrated yet.

## Current boundary and disposition

All paths below are relative to the canonical Git common directory unless stated otherwise. Linked worktrees share the registry; checkout and host-session identities remain distinct. The user contract is in `docs/reference.md`; checkpoints and retention are in its worker and collection-checkpoint sections.

The per-clone daemon is the sole online SQLite service. MCP registry facades use typed authenticated local RPC, including for asynchronous snapshots, and never open `state.sqlite`. MCPs and independently registered helpers retain ownership of Git/process/file/network effects and their semantic leases; daemon ownership does not transfer those authorities. Team-only sessions attach to clone storage through a control-only connection without joining or publishing a local Y.Doc room or passing team credentials into the daemon. An authenticated storage attachment counts as a writer for the existing five-minute idle clock; viewers neither access storage nor keep it alive. Repository binding alone grants no worker-run authority: nonce/run/checkout admission still requires validation.

## Runtime and launch contract (M1)

Use `node:sqlite` through a typed asynchronous `LocalState` client/daemon boundary and explicit transactions at `<git-common-dir>/room/state.sqlite`. Only the daemon DB worker opens the online repository database; the offline maintenance command alone initializes schemas, migrates and runs DDL, including an empty clone with an empty source manifest. MCPs may open disposable preflight probes only. Keep SQLite-free client/types imports separate from storage primitives in `packages/local-state/`; relay must not depend on room-mcp or own host/Git orchestration. Verify the canonical common Git directory and HEAD before creating storage. Record random clone ID and canonical location; a copied DB cannot authorize a process on another machine. No online initialization, permanent backend selector, dual write or JSON fallback.

The exact minimum supported distribution for MCP preflight, daemon and offline maintenance is the **official nodejs.org Node.js 22.22.3 binary distribution**, with bundled SQLite **3.51.3**, on the native OS/architecture being qualified. [Its release notes](https://nodejs.org/en/blog/release/v22.22.3) record that SQLite update (consulted 2026-11-05). This is a capability floor, not a promise that this historical patch remains security-current: the release must test a currently patched official 22.x at or above this floor. Other vendors, custom builds and other major lines remain unqualified until explicitly tested; version comparison alone does not qualify them. Use the minimum 22.x `DatabaseSync` API. SQLite arrived in [22.5](https://nodejs.org/download/release/v22.14.0/docs/api/sqlite.html), flag-free in [22.13](https://nodejs.org/en/blog/release/v22.13.0); neither is the selected floor. Require SQLite >=3.51.3; this release does not accept backports by version guessing, even though [the WAL advisory](https://sqlite.org/wal.html#walreset) names fixed backports.

Both hosts currently launch an external command named `node`, not the host executable's embedded runtime. Installation instructions for the compatibility release must put the qualified official distribution's bin directory first in the **host launch environment's PATH** (Windows: directory containing `node.exe`), fully stop the host and its persistent MCP-launching parent/daemon, then relaunch from that environment. A GUI host needs its own environment corrected and restarted; upgrading terminal Node alone is insufficient. Do not change frozen hooks or silently download/substitute a runtime. No new host configuration feature is assumed.

Scratch cleanup must touch only this probe's files after closing its connections.

## Schema and quarantine constraints (M3)

Use `STRICT` tables, foreign keys enabled on every connection, bound parameters, bounded versioned JSON, positive seq/run checks and explicit phase enums. Indexed identity columns are authoritative and must agree with payload fields. No cascading deletion of history, reservations or evidence.

|---|---|---|
| `schema_meta`, `imports` | Singleton schema/min-reader/min-writer, DB/clone ID, migration generation/state and source manifest digest; `(generation, source_path, digest)` import assignments/results. RPC response loss is not mutation failure. Resolve the original operation ID before issuing effects or choosing a new call ID: an exact retry returns its durable result, and a reused ID with a different digest refuses. Unacknowledged or ambiguous results never expire. A completed ticket can never execute again; once an acknowledged result has been pruned, lookup returns “result unavailable,” never blind reexecution. Keep external-effect intent in the versioned worker payload; a SQL result does not prove an external effect completed. Unresolved results remain recovery facts under pressure.

Reservation rows have no synthetic phase, launch, host identity or capability. `workers` exists only for validated payloads. A reservation without a payload cannot launch, resume, report, signal, collect, discard or project as a normal worker. It remains visible as blocked diagnostic state. A retired tombstone remains until tag/checkout reuse is justified by valid retirement/cleanup evidence, not age. Deleting a worker payload never deletes its parent reservation. A transition to reusable and any tag release must assert no relevant blocker, lease, shared link, kept checkout or pending cleanup in the same transaction.

Every admission/cleanup query checks blocker targets for clone, destination/checkout, tag, worker and run as applicable, in the same snapshot/transaction as its decision. Missing payload and blocked state are distinct from absence. Shared-owner cleanup consults all incoming `shared_links`, including borrowers whose own payload is invalid; owner quarantine blocks reuse/deletion of the shared checkout. An existing valid borrower retains its link but cannot use it to authorize effects against a blocked owner. Run writer/operation leases can reference reservations without valid payloads for preservation, but only valid worker/run facts grant new operation authority. Never release a damaged lease based on age or decoding failure.

Capacity uses the existing valid-worker status predicate (`worker-file-store.ts`): starting/running/unknown/ambiguous consume capacity. Quarantine evidence is not a count of valid running workers; its blockers must still constrain admission. Preserve known counts; when damage prevents proving occupancy, add a capacity blocker at the evidenced lead scope, or clone-wide if unknown, and refuse new spawn/resume rather than counting it as zero or inventing a live worker. This deliberately conservative import behavior must be visible to the user. Retirement/cleanup never erase a blocker to free capacity.

Import examples are normative:

- `quarantine/W.json.bad-*` plus `tags/build.json → W` creates reservation W in `quarantined`, the build tag FK and evidence/blockers. A valid borrower referencing W keeps an FK to that reservation. Do not drop the link/tag to satisfy a foreign key.
- A tag reservation with a safe worker ID but no payload creates `missing-reserved`; it cannot become reusable without the same missing-record/dead-holder evidence required today. A malformed tag or adoption preserves bytes and blocks its tag/ownership scope; unknown identity escalates to clone scope.
- A malformed report still at `runs/W/1.report.json` has parent provenance; block W/run 1. An already quarantined `1.report.json.bad-*` has **no reliable worker parent** (`worker-file-store.ts`). Do not guess from basename or nonce fragments: preserve it with clone-wide run/cleanup/capacity blockers until an explicit human mapping resolves the ambiguity. Do not infer witnessed exit or completion from it.
- Malformed collection holds block the destination identified by the original path hash; if canonical mapping cannot be established, block all collection destinations until resolved. Valid holds never silently disappear. Malformed policies remain in the unchanged file backend and retain conservative publication failure/intent-only behavior (`packages/room-mcp/src/policy-store.ts`). Migration does not replace them with SQL defaults; retirement requiring policy revocation stays pending on failure.

Evidence preserves raw bytes independently of JSON decoding and valid rows, with digest and original path if known, and explicitly unknown provenance where lost. Human recovery is a stopped-writer, scoped repair: back up evidence, inspect authoritative Git/process/worktree and reservation facts, supply an explicit identity mapping or disposition, validate relations, then audit removal of only the named blocker. Unknown quarantine may require manual inventory of every worker checkout. No “clear all,” force bypass, guessed ownership or automatic evidence expiry. Physical DB corruption requires offline salvage, not row quarantine.

## Concurrency, leases and bounded maintenance

The per-clone daemon owns one bounded DB worker thread with a data connection and a separate explicit maintenance connection; neither escapes the adapter. No MCP owns production connections or prepared statements. `BEGIN IMMEDIATE` serializes short writes; worker updates require matching seq and lease token/generation, increment seq and append change together with the durable operation result. No transaction spans awaits, Git, process probes, user writes or network calls; close every read snapshot before awaiting. Use `busy_timeout=0` in local WAL mode and asynchronous jitter retries of the **whole** transaction, including open/recovery/close BUSY. Future qualified DELETE mode uses an explicitly bounded busy timeout, initially zero, with the same retry policy. Normal SQL retry budget is 1 s; destination lane wait is separately 30 s. A zero busy timeout does not bound query execution, fsync or checkpoint time.

Authenticated typed RPC carries protocol/schema version, clone/DB ID, daemon nonce, generation, authenticated instance, admission ticket and per-call token. Mutations also carry operation ID, input digest, expected seq and required lease token/generation. Return a revision and durable result or typed refusal (`maintenance`, `incompatible`, `capacity`, `unavailable`, `blocked`, `busy`, `pressure`, `uncertain`). No arbitrary SQL, filesystem path or callback RPC. Bound the initial queue to 128 commands, paginated reads to 200 records/4 MiB and each payload to 1 MiB; overflow refuses before effects. Reserve a bounded control/acknowledgement path so saturation cannot prevent drain completion. Async snapshots return consistent worker/run/report/exit/reservation/blocker facts and a revision; every consequential command revalidates fresh authoritative rows, expected seq, blockers and lanes. Display snapshots/caches never grant effect authority. Use DB ID/generation/entity revision for freshness, with `changes(after)` low-watermark/gap refresh on reconnect; socket delivery alone is not invalidation. Callbacks that cannot await consume an explicitly supplied snapshot and remain conservative on unknown state.

A committed lease survives a SQL transaction: it blocks other callers throughout external effects. Its holder is the actual effect-owning MCP/helper identity, never the daemon; socket loss or daemon restart cannot free a live caller's lane or ticket. Acquire in order: operation admission ticket (below), destination lane if needed, shared owner operation lane, borrower/worker operation lane, run-writer lane, short SQL transaction. Multiple destinations/owners at one level use canonical sorted keys; do not acquire an earlier level while holding a later one. Capacity/tag checks and intent allocation occur atomically in SQL after owner/worker lanes. Report writes need only their run-writer lane. Publisher election remains independent in files: establish/verify it before operation admission; never wait for publisher acquisition while holding lifecycle lanes. Losing it prevents publication, not release of recovery evidence.

Preview calls take an admission ticket before any OS preview lock/helper; cleanup taking preview locks does so after its destination/owner/worker lanes, without entering callbacks that acquire those lanes in reverse. An admitted nested call reuses its outer ticket. Discard→stop reuses the same call token/worker lane, returns “already held,” and must not release the outer lane (`worker-file-store.ts`). Other same-MCP calls get distinct tokens. Release in reverse order, compare token+generation, and retain ownership through intent→effect→acknowledgement. Probe full identity outside SQL before takeover; alive/unreadable is busy. Recheck exact observed generation in a transaction, and authority before each external effect. SQL cannot undo or fence an arbitrary write already in progress.

Cancellation before admission drops queued work; after admission but before effect it rolls back/releases exact leases. After an effect it must persist its outcome or ambiguous recovery intent before releasing admission; never replay an ambiguous apply. An uncertain commit is resolved by operation ID on reopen. A process killed before acknowledgement leaves durable intent and a ticket requiring identity-based recovery; a timeout cannot erase them. Pending collected cleanup, deterministic publication IDs, discard replay and patch hash→fsynced bytes→ack ordering stay intact (`worker-file-store.ts`; `packages/room-mcp/src/retire.ts`). Network/Y.Doc delivery remains at-least-once with deduplication.

Verify the selected journal mode, FULL, foreign keys, `trusted_schema=OFF` and extensions disabled on every writable connection; WAL connections also require `wal_autocheckpoint=0`. First-release qualification is local single-host APFS, ext4 and NTFS with WAL; network, synchronized and unknown filesystems refuse until tested. Future network DELETE support requires the qualification and relocation rules in the addendum. The daemon alone owns maintenance and schedules a passive checkpoint on its maintenance connection at most once every 30 s or after 16 MiB WAL growth. There is no elected maintenance MCP, maintenance ownership file or separate storage-owner election. No automatic checkpoint on the data connection, no read transaction across awaits, and no unlinking WAL/SHM to relieve pressure. See [WAL checkpoint behavior](https://sqlite.org/wal.html#ckpt) and [PRAGMA definitions](https://sqlite.org/pragma.html).

Retention/budgets for this first release:

- `changes`: retain at most 10,000 entries and at most seven days; persist the low watermark before pruning. A reader behind it does a bounded full snapshot, never assumes no changes. Delete at most 200 rows per transaction/pass.
- `imports`: retain the active generation's source assignments/results and all unresolved evidence indefinitely. Keep the last completed generation plus its manifest and one pre-migration backup for at least 30 days and through upgrade acceptance; explicit offline archive is required before further removal. No duplicate history per polling pass.
- `operation_results`: retain unacknowledged/ambiguous results without expiry. After explicit acknowledgement, prune in bounded batches when seven days old or the 10,000 acknowledged-entry limit is reached. Unresolved-result pressure refuses growth rather than deleting results; pruning cannot authorize a completed ticket to execute again.
- `instances`: keep referenced/live/unknown identities; prune only verified-dead, unreferenced instances after seven days, at most 200 per pass. No observation-history table. Blockers, active holds, pending intents/cleanup and unresolved evidence have no automatic expiry. Worker history remains until explicit archival; storage pressure must not silently delete recovery facts.
- Maintenance prunes at most one 200-row batch per 30 s tick, yields between work, and issues no VACUUM/TRUNCATE checkpoint during live operations. Bound import batches to 200 records/4 MiB decoded bytes, per record 1 MiB; larger legacy metadata refuses with a diagnostic rather than truncation. Raw evidence is streamed under a separate 256 MiB total import budget; exceeding it leaves maintenance pending for explicit inventory/repair.
- Warn at 64 MiB WAL; at 256 MiB stop admitting growth-producing lifecycle mutations and request short readers close/restart. Permit diagnostics and bounded acknowledgement/recovery work, and never discard intent to meet the cap. Log oldest reader/maintenance identity where known, without payloads. Disk failure rejects writes. Disk/I/O/queue pressure checks also apply to any future qualified DELETE mode. Caps are pressure thresholds, not guarantees about a single SQLite fsync's duration.

The bounded worker-thread adapter is selected from the outset to protect daemon transport/health from synchronous SQL. A stalled thread refuses further growth rather than spawning an unbounded pool; do not terminate it merely because a write timed out. On thread failure retain relay memory, refuse storage-dependent effects and resolve committed operation IDs before reopening authority. Reconnect discards cached authority and revalidates daemon nonce, generation and results. Authenticated storage attachments, including control-only team sessions, count as writers for the five-minute idle clock; viewers do not. Measure queue, query/commit/checkpoint and event-loop delay plus hook p50/p95/p99 under contention and pinned readers. Hooks must be no slower than the measured baseline; worker lifecycle and other operations may be at most 20% slower than baseline. The purpose is concurrency correctness, not a speed claim. The 1 s retry deadline is not a hard fsync deadline.

## Dependency-free hooks (M1, S4, S5)

Hooks never import SQLite, npm dependencies or a database CLI. Preserve frozen `plugins/room/hooks.json` byte-for-byte; change neither manifest for this storage proposal. Both scripts import built-in-only `common.mjs` and use files/authenticated loopback. Daemon-owned durable lifecycle state changes do not require hook SQL access.

`openMcp` bounds connect/default request selection timing and reply size (`plugins/room/hooks/common.mjs`). Before-edit uses 700 ms at `plugins/room/hooks/before-edit.mjs:63`; SessionStart uses 300 ms at `plugins/room/hooks/session-start.mjs:41`. These are **selection budgets**, not total hook deadlines: explicit `request(body, ms)` overrides the default remaining deadline, and each script allows a separate 1,000 ms confirmation (`plugins/room/hooks/before-edit.mjs:152`; `plugins/room/hooks/session-start.mjs:62`). The host manifests separately specify five seconds; input reads, process probes and filesystem work also consume time. Preserve select→accepted stdout→confirm ordering (`before-edit.mjs`; `common.mjs`). Malformed reply, stdout failure or missing confirm leaves messages owed. Execution receipts and wake attempts never prove delivery; shared receipts remain fenced Y.Doc state.

Per-session paths isolate sessions, **not concurrent invocations within a session**. SessionStart and before-edit can both publish `hook.json`; MCP fallback can also publish `session.json` (`packages/room-mcp/src/session.ts`). Temp/rename avoids torn files but older observations may win last rename. Keep the existing best-effort bridge; no SQL observation table, durable journal or single-writer claim. Accept lost diagnostic/model/activity updates and duplicate coordination context. Suppression records cannot suppress owed ledger messages or become authority for identity/capabilities.

Readers validate full session binding and current process ancestry independently of timestamps. Within a bound MCP, accept strictly increasing, finite, non-future activity times; equal timestamps cause no new activity and conflicting equal-time metadata remains unknown or the previously validated observation. Lower times cannot regress accepted state. Clock rollback/future timestamps make freshness unknown until a valid current observation arrives; do not infer a new session, delivery, process death or durable activity from them. On restart, file time alone cannot revive prior-session activity; revalidate identity and use current-process startup/binding evidence. Unordered model/suppression metadata may be missed until the next hook; duplicates are preferable to delivery loss. Keep bounded receipts/pruning, stale projection rules and alone fast path without IPC. Hooks never start a helper/MCP per edit, and `state.json` cannot be restored from SQL as live presence.

## Migration and activation protocol (M2)

The first conversion, empty-clone initialization and every later SQL-to-SQL upgrade have **one explicit owner: an offline maintenance command**, invoked deliberately for a canonical common directory. Neither MCP nor daemon startup auto-converts, initializes SQL or applies DDL. An empty clone follows the same maintenance ownership/publication protocol with an empty source manifest. The compatibility release adds the protocol below before storage conversion; exact compatibility build/version IDs must be recorded in its release manifest. Slices 1–3 keep legacy files authoritative and cannot activate SQLite; slice 4 switches the complete lifecycle/hold/lease domain together. The operator activation window is deferred until slice 4 exists and requires the human's operational authorization. Unmodified 0.17.32 has no such fence, so there is no live mixed-version upgrade.

Use two dependency-free durable bootstrap controls outside SQL: the existing `room/registry/migration.lock` for exclusive migration ownership and a new guarded `room/storage-gate.json` for admission/generation/registrations. The lock uses full instance identity, nonce, guarded verified-dead recovery and a 30 s wait as in `worker-file-store.ts`; it is not a SQL `BEGIN` or a TTL. Retain these controls after cutover for SQL-to-SQL upgrades. The gate has a monotonically increasing migration generation, phase (`legacy`, `draining`, `staging`, `db-complete`, `active`), owner identity/token, source/target schema and minimum reader/writer build, DB ID, manifest/backup digests, and import checkpoint. Initialize an absent gate under its guard only after checking there is no DB/activation evidence; concurrent initialization cannot overwrite a successor. Publish changes by fsynced temp file, rename and directory sync. Never reset generation on failure. Corrupt/missing gate with other activation/DB evidence refuses operation.

**Registration and whole-operation barrier.** `StorageGate.register/admit/finish/drain/status` validates canonical common-dir/HEAD, private instance identity, build ranges and generation. Under the gate's short file guard, every compatibility or SQL MCP registers its process identity/build, checks gate generation/version and records a unique admission ticket before preparing a writable repository. The barrier covers snapshots, worker admission, background reconcile/projectors, retirement, report/exit callbacks, idle helpers that consult lifecycle state and preview/maintenance entry points. No constructor, snapshot or timer bypass. Tickets cover the entire consequential operation from first authority read through Git/process/network/file effects, durable acknowledgement and lease release; checking a marker before a write is insufficient. Nested helpers reuse a ticket; detached tasks/helpers register their own ticket/identity before their parent releases it. Tickets are private atomic live-process records, while registrations and recovery evidence are durable, all linked to generation in the layout below; phase transitions take the gate guard, and admission is checked against them lock-free as described below. Display-only snapshots outside an operation use the compatibility release's `ReadValidation` contract below instead of creating a ticket; they cannot authorize effects.

The offline owner is registered as maintenance, without an ordinary operation ticket; it cannot run normal tools while holding migration ownership. A migrator first owns `migration.lock`, then under the gate guard increments generation and publishes `draining`, atomically closing new admission. The draining successor records `drainingFrom` as the previous generation: live predecessor tickets may finish and admit parented children while draining; new unparented admission refuses. Generation change cannot invalidate predecessor acknowledgement paths, and parented children must finish independently. Compatibility processes refuse new operations at their next admission check, stop timers/watchers, finish admitted effects through final acknowledgement and lease release, then unregister. The daemon continues admitted acknowledgement/result lookup and diagnostics while draining; a closed socket does not manufacture completion. Existing ticket holders may complete despite the phase change; the owner cannot scan until all have drained. There is no lease-age shortcut. A dead ticket holder is recovered only after full identity verification and its outstanding intent/effect is reconciled or explicitly marked blocked; only the `migration.lock` owner may remove that ticket through audited `resolveDead`. A live paused process or unknown identity blocks conversion. Registrations/tickets are capped at 256 processes and 4,096 concurrent operations per clone; reaching the bound refuses admission, never drops an existing ticket. Scan at most 200 records per yielded pass, and retain unknown/dead-but-unreconciled entries until resolved.

**Compatibility-release details accepted for slice 2 (2026-11-06).** These contracts were marked “decided, not in spec” in the lead's `packages/local-state/src/protocol.ts`; this amendment records their exact names. They implement the legacy barrier without enabling SQL:

Per-call tickets coordinate live processes on one machine: complete temporary-file publication by link/rename supplies visibility, without fsync on ticket create/remove or guard acquire/release. Registrations, the gate record, every generation/phase transition and `resolveDead` audits remain fsync-durable. Before its first ticket is published, a registration durably records `hasHeldTickets: true` once; capacity pruning never discards this evidence. After tickets finish, a marked registration must unregister to acknowledge the holder is drained. If an unsynced ticket vanishes, a marked ticketless registration still appears in drain/status ticket listings as `registration:<nonce>` with kind `reconcile`: live/paused and unknown holders block, and verified-dead holders block until the maintenance owner reconciles **all** that holder's lifecycle intent/effect records under `room/registry` and explicitly calls `resolveDead` on the synthetic ID. The gate cannot interpret those lease records and never infers their reconciliation from ticket absence. Resolve surviving tickets first, then audit and remove the registration evidence; a crash between audit and removal leaves conservative evidence that can be audited again. Normal `finish` stays cheap; clean unregister and first-admission registration marking carry durability costs once per process registration. This also conservatively blocks a live holder in a simulated ticket-loss test, without relying on the fact that a real machine power loss terminates that holder. `closeStorageGates(): Promise<void>` drains accepted worker RPCs before joining the worker; racing new RPCs refuse while it closes, and a later call may lazily restart it. Callers finish operations and unregister before closing.

Admission itself takes no gate guard (compatibility-release detail, 2026-11-07). An admitter reads the gate, publishes its ticket atomically, then reads the gate again; if the generation or phase changed in between it withdraws the ticket and refuses (a parented child is re-checked against the new state instead). A drain publishes its successor generation under the guard before it scans tickets, so every ticket either is seen by that scan or is withdrawn by its admitter before anything acts on it. The guard still serializes initialization, registration and every phase or generation transition. Capacity is re-checked after publication so concurrent admitters cannot persistently exceed the bound.

A preview helper (lock helper, setup Git or check) holds a parented ticket carrying its own process identity, admitted before it receives GO. When its cleanup misses the grace deadline, the MCP keeps that ticket after replying and releases it only once the helper's process group is definitively gone (only `ESRCH` proves absence) and no process has its working directory inside the preview tree that attempt worked in; an unreadable or partial process listing keeps it (compatibility-release detail, 2026-11-07). Until then the drain lists it. A descendant that leaves both its group and the tree is beyond this evidence, as it is for the tree's quarantine.

- `STORAGE_PATHS` fixes `room/storage-gate.json`, guarded by `room/storage-gate.json.guard`; private registrations are `room/storage-gate/registrations/<nonce>.json`, tickets `room/storage-gate/tickets/<holder nonce>.<ticket id>.json` (each carrying the holder's process identity, so drain can verify liveness even when a registration is damaged), and dead-ticket audit records live under `room/storage-gate/resolutions`. `room/state.sqlite` or `room/state.active.json` is activation evidence; either without a readable gate refuses. `migration.lock` and `migration.json` remain under `room/registry/`. Slice 2 creates neither SQL activation file.
- `STORAGE_BUILD=1` identifies the compatibility capability independently of wire/Y.Doc compatibility or the diagnostic release string. A newly initialized legacy gate starts at generation 1 with `minReader=minWriter=1`. A build below either minimum, an `active` SQL gate for build 1, a foreign `cloneId` or a different canonical common directory refuses `incompatible`; exact release IDs remain required in the release manifest.
- Gate refusals throw `StorageRefused(reason, detail, remedy)`. Slice 2 uses `maintenance`, `incompatible`, `capacity` and `unavailable`, plus `busy` only when `StorageGate.unregister(registration)` still has outstanding tickets; slice 3 adds `blocked`, `pressure` and `uncertain` for the storage client. Bound `detail` to 512 characters without task text, tokens or file contents; `remedy` names the operator command when provided. `GATE_LIMITS.guardWaitMs=2_000` bounds short-guard acquisition before `unavailable`. Caps refuse `capacity` without evicting existing registrations/tickets; unreadable/corrupt gate, activation evidence without a gate and I/O failure refuse `unavailable`.
- A `Ticket.id` is a 128-bit random hex ID and the lifecycle-lane call token. Unrelated calls in the same MCP get distinct tickets/tokens; only a genuinely nested discard→stop reuses the outer ID and cannot release its lane. `AdmitOptions.parent` permits a detached child only while its parent remains a live predecessor ticket (`generation <= drainingFrom`); a finished parent cannot admit children. Finish/acknowledgement remains permitted for predecessor tickets during drain.
- `StorageGate.resolveDead(owner, ticketId, note)` is explicit migration-owner recovery after verified death and intent/effect reconciliation, with an audit entry recorded before removal; unknown holders block. `StorageGate.reopen(owner)` allows `draining → legacy` after legacy-only maintenance, such as the offline pre-registry import, without changing generation. It is never automatic, never a timeout recovery, and never a rollback from SQL activation. `StorageGate.takeOver(owner)` lets a successor that recovered `migration.lock` from a verified-dead holder adopt its draining generation by publishing generation+1, so the suspended owner's token is stale. A gate is opened for one canonical common directory (`openStorageGate(commonDir)`); `StorageGate.status()` is read-only, initializes nothing, takes no guard and writes nothing, and reports `migration.json` as `done`, `pending`, `absent` or `unreadable` without deciding whether a pre-registry import is needed (the room-mcp legacy-evidence predicate owns that). `StorageGate.observe()` returns the current `ReadValidation` without a guard.
- `ReadValidation { generation, phase }` applies to display snapshots outside an admitted operation: take no ticket, read the gate before and after the snapshot without a guard, and retain the result only if both reads show `legacy` with the same generation; otherwise refuse `maintenance`. Inside an admitted operation snapshots use its ticket. The migrator publishes its new generation before changing lifecycle files, preventing acceptance of an import-spanning snapshot. This read-only exception creates no effect authority and no SQL opener; after activation snapshots use the daemon service and active-generation validation.
- Every `PreflightFailure` refuses its `PreflightSurface` (`mcp`, `daemon` or `offline`) before registration or touching Room state, apart from isolated disposable probe scratch. `PreflightResult` reports an unqualified filesystem as `storage: 'unqualified'` without refusing legacy file operation in the compatibility release; it still refuses SQL activation later. Probe WAL only on a qualified filesystem. This compatibility behavior does not qualify network, synchronized, unknown or other unqualified local filesystems for SQLite.
- The daemon does not register with the gate in slice 2 because it opens no storage. Later daemon storage ownership uses `StorageCloseAck { generation, daemon, daemonNonce, at }` to acknowledge both SQL connections closed for that generation and no reopen without an active gate. Slice 2 has no SQL close acknowledgement; the transport stop and verified authority handoff still apply to offline maintenance as needed.

**Daemon close and authority handoff.** After every ticket and registered helper is reconciled, close both daemon SQL connections and acknowledge closure, including idle connections with no active ticket. Disconnect writers, save transport snapshots, request authenticated nonce-specific daemon stop and verify its birth-identity exit. Failed snapshot save leaves the storage gate closed even if transport repair admission reopens. The offline owner then acquires the same existing `AuthorityLock` in maintenance mode, without serving a relay; no second storage ownership file/election is introduced. A racing daemon starter checks the gate under that authority before opening storage, refuses maintenance and releases authority. Only the verified offline owner can then open the repository/staging DB. No prepared writable repository survives the handoff. Existing transport drain or `daemon-cutover.json` alone proves neither whole-operation drain, SQL closure nor exclusion of old binaries.

**Lock order.** Never wait for drain while holding the gate guard, a SQL transaction, legacy destination/operation/capacity guards or a preview OS lock. Ordinary operations: admission under gate guard (release guard) → destination collection lane → shared-owner → worker operation → run writer/capacity/record guards as needed → preview OS lock/helper if needed, releasing in reverse. No operation may acquire migration ownership while admitted. Compatibility release must route the legacy pre-registry importer through the offline owner, removing independent startup imports; otherwise its existing migration lock could invert this order. Migrator: migration ownership → short gate transition → drain/daemon close and stop with no lower locks → maintenance `AuthorityLock` → legacy destination lanes in canonical order → owner/worker/run lanes in stable ID order → capacity/record guards only for bounded synchronous snapshots → preview lock checks if needed → bounded SQL transactions. After drain these lower locks are verification/exclusion against known legacy paths, not a replacement for the barrier. Failure to acquire one stops the migration without stealing it. Preview helpers/check children must finish and release locks before conversion; unknown cwd/process evidence retains quarantine and stops conversion. Preview metadata stays in files, and no surviving helper is silently declared drained.

The explicit owner performs these steps while retaining migration ownership:

1. **Preflight before maintenance:** run the catchable capability/filesystem check above. Then inventory installed/loaded MCP builds, workers, launchers and helpers across every linked worktree, registrations, process identities and legacy operation/collection locks. Finish or stop workers without removing worktrees. Fully stop old host/MCP-launching processes and prevent their automatic relaunch during maintenance. A registration list alone cannot prove absence of unmodified 0.17.32. Require a complete process/host inventory, all affected sessions stopped/restarted into the compatibility build, and explicit operator confirmation that old installations will not be launched. Record this evidence. Unknown inventory or an uninspectable writer refuses conversion; if the environment cannot establish exclusive offline access, leave files authoritative. A marker cannot technically fence an old binary deliberately launched later; that configuration is unsupported and must be stated prominently.
2. **Recheck after ownership:** reread gate and completion marker and obtain current DB/version agreement through the authenticated daemon when it is online; the offline command must not open the repository DB before authority handoff. If an active daemon proves matching identity/version, report complete; otherwise validate the DB only after handoff. A losing/stale migrator discards staged manifests and never publishes from a prior generation. Establish a draining generation when maintenance is required and await every registered process/ticket/helper. Admission/register/drain operations use short guards only. Startup wait is at most 10 s with a maintenance/restart result, keeping below Codex's 30 s startup timeout. Explicit migration gets a 120 s drain and 10-minute bounded import attempt; deadlines leave durable maintenance state, never reopen admission automatically.
3. **Stage only under quiescence:** complete daemon connection closure, snapshot save, verified stop and maintenance `AuthorityLock` handoff, then acquire legacy exclusions as above; finish the old `migration.json` importer with its durable source→worker assignments before converting, or retain incomplete state and stop. Back up only converted bookkeeping/evidence plus required provenance, with bounded path/digest manifest; preserve worktrees, Git refs, logs and file-only domains. Stable assignments must survive owner death and a changed staging attempt. Refuse incomplete scans, permission failures or missing required snapshots. Quarantine originals remain private; source bytes are never rewritten as defaults.
4. **Import and validate:** create staging schema with matching generation and importing state; journal bounded batches and deterministic source assignments. Preserve IDs, seq, runs/nonces, immutable report chains, witnessed observations, adoptions/tags, shared links, collectPending, archive, per-room cleanup, discard steps, patch paths/hashes and hold token hashes. Construct M3 reservations and blockers before validating references. No normal opener can use staging tables. Revalidate every source digest under continued drain/exclusions; source changes abort completion. File-only policy/choice/delivery state is neither converted nor dual-written.
5. **Commit and publish:** one transaction applies final constraints, DDL/schema version, min-reader/min-writer, manifest digest and DB-complete generation. Only this owner runs DDL. Close/checkpoint staging connections and durably publish the DB if staged separately; fsync containing directory. Under the gate guard publish the activation marker/gate with the same generation, DB/clone ID, schema, minimum versions and manifest digest, using durable rename. Gate/DB disagreement or incomplete publication leaves maintenance closed. Then transition to active and release exclusions, maintenance authority and migration ownership. The next bound client starts the daemon; under authority it validates active gate/marker/DB agreement and both reader/writer compatibility before preparing statements, without DDL. MCP clients validate the service identity and admission generation, never open the DB. Ticket admission pins generation through operation completion. No dual write and no automatic JSON fallback.
6. **Verify before resume:** fresh sessions check worker inventory, held checkpoints, blockers, policies and pending delivery/recovery state before consequential operations. Retain source backup read-only; hooks continue the file bridge. Ports remain the single file backend across **all clones**. Any future port conversion requires a separate user-wide owner, registrations/drain/generation and all-clones barrier; this design does not authorize it.

**Crash/reopen rules:** before drain publication, legacy authority remains; after drain but before DB completion, restart stays in maintenance and the next verified owner resumes/revalidates staging using durable assignments. Interrupted daemon close/stop/authority handoff also stays closed: recover by verified process identity, reconcile tickets/effects, prove both connections closed and daemon exit, and acquire maintenance authority. A racing daemon in the exit-to-acquisition interval cannot reopen storage under a maintenance gate. A crash during a backup/batch/DDL transaction leaves prior committed batches intact and rolls back only the uncommitted SQL transaction, not the barrier. After DB-complete but before marker/gate activation, the successor verifies generation, source manifest and DB integrity and republishes the matching marker; it does not reimport stale sources. After marker publication but before active, finish the matching active transition. After active, legacy files are backups only. Missing active DB or marker/DB mismatch is an error, never empty creation. Successor ownership requires the old identity definitively dead; an unknown owner remains blocked. Every irreversible publish/checkpoint rechecks owner token/generation; an old suspended owner cannot complete a newer generation. SQL-to-SQL upgrades use exactly the same registration/drain/daemon-close/stop/authority handoff, WAL-aware pre-upgrade backup and transactional version change; older readers and writers refuse incompatible versions rather than probing tables optimistically. Timeouts never reopen admission automatically.

Downgrade needs stopped-world validated export of converted domains. Deleting DB/marker cannot be a rollback: stale files can resurrect retired workers/holds. Restoring old metadata cannot undo applied files, removed worktrees or published text. Keep recovery patches/Git evidence with backups. First-release backup/importer retention is at least 30 days and through acceptance; removal/export is explicit, not a timer-based downgrade promise.

## Addendum 2026-11-05: network filesystems

The [2026-11-05 host survey](../../archive/reports/host-survey-2026-11-05-codex.md) records Codex 0.166.0's NFS DELETE-mode policy and migration command; that is context, not Room qualification. Room's accepted policy is **qualified DELETE or refuse**, with the 2026-11-06 maintainer decision narrowing the first release to **local single-host APFS, ext4 and NTFS only**. Network DELETE mode is **not qualified in the first release**: network, synchronized and unknown paths refuse until tested. Selecting these local filesystems as qualification targets does not claim they have passed implementation tests.

Detect the filesystem on every repository open using macOS/Linux statfs plus mount information and Windows UNC/mapped-drive resolution. Use WAL only on proven, qualified native local paths; never open WAL on a path that cannot be proven local. A future network DELETE configuration requires explicit locking, durability, privacy and single-host ownership qualification before support. DELETE alone cannot fence another machine; multi-host access and foreign-machine DB copies remain refused. Diagnostics report the detected filesystem and selected mode or refusal without opening an unsafe repository DB.

For future qualified network use, verify `journal_mode=DELETE`, FULL and foreign keys and use an explicit bounded `busy_timeout`, initially zero, with the same one-second asynchronous whole-transaction retry budget. Probe DELETE semantics in private scratch rather than requiring network WAL. Journal mode persists in the file: moving a WAL DB requires drain and conversion with all connections closed at a provably safe location **before** network use. Never open WAL on NFS to discover conversion is needed; if safe conversion cannot be proved, refuse with relocation/recovery guidance. No automatic online journal-mode conversion. First-release SQL refusal satisfies the DELETE-or-refuse policy; the compatibility-only legacy-file exception in M2 does not permit SQLite activation.

## Failure handling and security

Busy, cancellation, lost RPC replies and unknown commit outcomes resolve by the original operation ID/input digest with bounded retries and durable result lookup; no external effect precedes committed intent. Do not silently generate a new call ID after uncertainty, and never replay a completed ticket whose acknowledged result was pruned. Daemon/DB-thread failure retains relay memory, refuses storage-dependent effects and preserves live caller leases/tickets and unresolved results until verified recovery. Full disk, permissions or I/O failures preserve DB and pending cleanup and refuse new consequential work. Corrupt/newer/missing-after-activation DB refuses writes and publication requiring local authority; preserve DB/WAL/SHM and stop all writers before integrity checking or salvage. Never rename a live DB, silently recreate it or use a JSON fallback. Unknown process identity cannot free a lease, signal a PID or clear preview quarantine. Runtime failure refuses before maintenance. Hook endpoint failure retains bounded startup/activity evidence and owes undelivered messages.

Use SQLite backup support or a closed/checkpointed offline copy, not a lone main-file copy while WAL is live. First qualification is local single-host APFS, ext4 and NTFS; network/sync/unknown paths refuse until tested, and foreign-machine copies cannot authorize operation. Any later network support must satisfy the addendum's qualified DELETE-or-refuse and offline relocation policy. DB directory, gate/registrations, WAL/SHM, backups and evidence are private (0700 directory/0600 files; validate native Windows ACLs). Reject symlink/junction substitution and unexpected ownership/types. Disable extension loading and unsafe schema execution; no generic SQL RPC or remote paths. A local same-user process can bypass cooperative storage checks; a DB is not a new security boundary. No tokens in choices or payload logs. Diagnostics expose versions, identities, operation IDs/error classes, blocker targets, generation, last commit, busy counts and WAL/DB size, never private tasks/log tails/recovery tokens. Ordinary SQLite deletion does not promise secure erasure. Hold recovery remains scoped and audited (`docs/reference.md`).
