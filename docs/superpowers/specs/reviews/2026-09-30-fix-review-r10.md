## Findings

### X1 — should-fix: trimming the expanded attributes pathname hashes a different file

**Location:** `packages/room-mcp/src/tools/files.ts:724–726`.

`git config --path --get` preserves whitespace belonging to the configured filename, then adds its output delimiter. `.trim()` removes filename bytes as well as that delimiter. The fingerprint still includes the original config value, but subsequent changes to the actual file's contents are invisible because `optionalAttributeFile` reads the trimmed pathname and treats its absence as empty attributes.

**Concrete sequence:** `node --import tsx /tmp/astra-review-r10/path-probes.mts trailing` (also reproduced with `newline`):

1. Commit `x = base\n`, create an empty external file whose pathname ends in a literal space, and set `core.attributesFile` to that exact absolute pathname using an argv value.
2. Warm the cache; the check rejecting CRLF passes.
3. Write `x text eol=crlf\n` to that same external file, without changing the configuration string, ancestor, or source `x`.
4. Source `git check-attr` reports `eol: crlf`. The next preview keeps the same slot and fingerprint, reports `cached base`, reads `base\n`, and **passes**.
5. `materializeGitTree` reads `base\r\n`; the identical check **fails**, exit 1. Source `x` remains unchanged.

Logs: `/tmp/astra-review-r10-path-trailing.log` and `/tmp/astra-review-r10-path-newline.log`. These use real Git, with no filesystem or Git-result mocking. `~/` and `~user/` expansion work in separate probes; the defect is the destructive trimming after Git expands the path. Git's pathname expansion rules are documented in [git-config](https://git-scm.com/docs/git-config#Documentation/git-config.txt-pathname).

**Suggested change:** request NUL-terminated config output (`git config --null --path --get core.attributesFile`) and remove exactly its terminating NUL. Preserve every pathname byte. Apply the same delimiter-only principle to other Git pathname outputs rather than general whitespace trimming. Add content-change regressions for a trailing-space filename and a filename ending in newline.

**Impact:** incorrect **check results** and possible false passing-preview evidence under a valid, albeit uncommon, pathname. No source/index/other-checkout mutation observed. This is not a caching-efficiency or disk-space issue.

### X2 — should-fix: failed system-path discovery accepts guessed paths as a complete policy

**Location:** `packages/room-mcp/src/tools/files.ts:696–701`, consumed at `:733–741`.

Any failure of `git var GIT_ATTR_SYSTEM` falls back to two paths derived from `--exec-path`. Those are not a conservative superset of Git installations' effective system attributes. Missing guesses hash as empty, so caching proceeds even though the real system policy was never fingerprinted. This affects the explicitly implemented older-Git compatibility path and also masks other query failures. Git added these path variables in [2.42.0](https://git-scm.com/docs/git-var/2.42.0); the returned path, when available, is authoritative.

**Concrete sequence and evidence:** `/tmp/astra-review-r10/system-fallback.mts`, log `/tmp/astra-review-r10-system-fallback.log`, runs real Apple Git 2.50.1 but injects an unsupported-variable failure **only** for `var GIT_ATTR_SYSTEM`. All other Git operations remain real. Read instrumentation records paths without replacing file contents.

1. Apple Git reports `--exec-path=/Library/Developer/CommandLineTools/usr/libexec/git-core` and effective system attributes `/etc/gitattributes`.
2. With only the path query forced to fail, warm and repeat a preview. It creates and reuses a slot (`cached base`).
3. The fingerprint reads `/Library/Developer/CommandLineTools/usr/etc/gitattributes` and `/Library/Developer/CommandLineTools/etc/gitattributes`; it never reads `/etc/gitattributes`.
4. On such a layout with an effective system attribute file, warming with an empty file and then adding `x text eol=crlf` leaves the fingerprint unchanged while fresh checkout conversion changes. **This last check-result consequence is inferred from the demonstrated omitted input and Git's attribute behavior; I did not write `/etc/gitattributes`, or claim an old Git binary or an actual system-file content-change run.**

The same mismatch is visible in this machine's Homebrew layout: its reported system path is `/opt/homebrew/etc/gitattributes`, while fallback guesses are `/opt/homebrew/opt/git/etc/gitattributes` and `/opt/homebrew/opt/etc/gitattributes`.

**Suggested change:** when effective system-path discovery is unavailable and system attributes are enabled, throw/return an uncertain policy so the existing caller uses fresh materialization. Do not substitute guessed paths for proof. An explicitly disabled system policy can safely return no paths; parse Git's boolean semantics or use a Git-backed boolean query. Add a discovery-failure fixture that proves caching is bypassed, without editing the real system file.

**Impact:** potentially stale **check results**, not just extra cache misses. No other-checkout writes. This is narrower than X1: the shipped query-success path works on both tested Git installations. I asked rohanz whether an older-Git support floor excludes this path; three `room_wait` calls timed out. **Assumption:** the compatibility path is supported because the code explicitly implements it and the repository states no >=2.42 floor. Even with a newer floor, propagating unexpected discovery failures is safer than accepting an incomplete policy.
