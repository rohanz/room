## New must-fix

### N1 — Temporary graph provenance lag creates a duplicate contract episode

**Owner area:** sharing / contract reconciliation. **Introduced by:** `67c73d1`. **Locations:** `packages/room-mcp/src/conflict-set.ts:77–80`, `:95`, `:102–104`; caller at `:208–218` and `:447–451`.

After A is notified that B changed `call(a)` to `call(a, b)`, B's manifest revision advances without changing that signature—for example, a README-only edit. Until B's graph stamps the new revision, `withdrawContractDetails()` or `contracts()` redacts the existing slot. When the same observation becomes current again, the new restoration code unconditionally reconstructs its predecessor with `settled: 'none'` and `factId: ''`. `changedFact` consequently becomes true, increments the epoch and posts the identical contract fact under a new ID. Hub deduplication cannot suppress it because the ID changed.

**Proof:** a disposable production-ConflictSet probe used coherent manifest/graph revisions and a deduplicating post adapter. The only contract observation was unchanged throughout. Expected accepted IDs for that symbol: `[cf:<call-slot-hash>:1]`; HEAD produced `[cf:<call-slot-hash>:1, cf:<call-slot-hash>:2]`. The same probe passed using `0a5003d`'s ConflictSet with the current dependencies, isolating the regression to this change. Separately, a real temporary Git repository with a running GraphIndex and a started ConflictSet reproduced epoch **1 → 2** after a head-only revision and automatic graph provenance catch-up; no graph snapshot was injected in that probe. The synchronous observer redacts even when catch-up finishes before the normal reconcile debounce.

**Why must-fix:** reporooms §B5 and its test-plan item 7 explicitly require conflict→unknown→the same conflict to be silent. This duplicates logical notices during ordinary editing, rather than only when privacy permissions actually change. Repeated unrelated revisions can keep producing new notices for the same incompatibility.

**Fix direction:** distinguish a temporary freshness gap from an actual withdrawal of content authorization, or retain durable private/keyed equality evidence and opaque episode identity sufficient to recognize the same fact on restoration. Preserve both the D1 redaction guarantee and the newly repaired monotonic history. Do not restore the old unsalted signature hashes to replicated redacted slots. Add unchanged-fact provenance-lag coverage through the running graph/watcher pipeline and across an MCP restart, alongside the changed-signature and clean/subset restoration cases.
