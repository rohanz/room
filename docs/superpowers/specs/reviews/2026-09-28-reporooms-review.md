## Must-fix

1. **Committed branch changes disappear from conflict detection and default previews.** Spec: `reporooms:278`, `:339`. Code: `packages/room-mcp/src/conflicts.ts:299`, `:371`; `packages/room-mcp/src/tools/combined-tree.ts:99`. A and B change the same line on different branches; A pushes, so its base advances and its manifest entry disappears. The manifest intersection is now empty: the conflict is removed as “merge cleanly again”, although the branch trees still conflict. Default preview also excludes A before its ancestor-to-base path collection can help. Derive candidate paths from each pair's ancestor-to-base changes plus manifest changes; retain unknown coverage when paths/text cannot be established. Absence of a candidate is not proof of a clean merge.

2. **The conflict fingerprint cannot invalidate all inputs, and the specified IDs omit R4's revisions.** Spec: `reporooms:120`, `:123`, `:126`, `:281`, `:290`. Code: `packages/room-mcp/src/conflicts.ts:375`–`:379`; `packages/shared/src/doc.ts:436`. A held entry becomes shared with identical content, or a claim moves under the same ID: git revs, content hashes and claim IDs stay equal, so the stored unknown/conflict is reused forever. A timed-out check has the same problem on the 60-second tick. Include manifest availability/completeness revision, claim geometry/version and resolved base identities; retry unknown results independently of content changes. Distinguish a stable pair slot from the required `(a,b,path,aHash,bHash,mergeBase)` fact identity, and define deterministic notification/recurrence IDs rather than referring to today's random-ID posts. Test held→shared, timeout→success, same-ID reanchor and conflict→clean→same conflict.

3. **`carried^` is not necessarily a remotely resolvable base; base resolution also has an unhandled no-ancestor case.** Spec: `reporooms:50`, `:216`–`:221`, `:245`. Code: `packages/roomd/src/index.ts:817`; `packages/room-mcp/src/tools/state.ts:109`; `packages/room-mcp/src/worker-git.ts:197`. Lead commits U without pushing, then spawns from carried commit C: C^ is U, which no teammate can fetch. Also, an upstream on another remote can contain HEAD while the prescribed fetch only tries origin. An orphan/reset upstream can make `merge-base(HEAD,refs[0])` return no result and stall publication despite R3. Select and publish a genuinely resolvable anchor, include all changes since that anchor, and specify the unavailable/unrelated-history fallback without throwing from the daemon. Remote-tracking refs are stale observations, not proof that the server still serves the object.

4. **The advertised complete HEAD revision precedes claim reconciliation.** Spec: `reporooms:193`–`:203`, `:551`, `:612`. Code: `packages/roomd/src/index.ts:765`–`:781`, `:893`. A branch switch publishes new git/manifest state at step 5, then dies before step 6. Readers see `complete:true` with old claim coordinates; the restart's special validation covers only anchorless migrated claims. Preserve a durable/reconstructible unfinished claim transition, or include reanchored claims in the complete boundary. Define which previous HEAD/base survives restart and retry all unfinished work, not just migrated claims. The manifest sibling's final transaction (`2026-09-28-manifest.md:266`) must have the same boundary.

5. **The proposed 410 preflight contradicts the promised old-client 403 behavior.** Spec: `reporooms:429`, `:440`, `:516`. Code: `packages/room-mcp/src/session.ts:587`–`:599`, `:476`, `:512`. A fresh 0.16 client preflights an old branch name through `/view-token`; `410 {movedTo}` is treated as success, so it proceeds to a refused WebSocket and reports a sync timeout. `watchClosed` is installed only after daemon startup, so accepting and immediately closing 4001 is not a reliable substitute for this join path. Give schema-less preflights 403 text; reserve redirects for schema-2 callers, and test an actual old client rather than only endpoint status codes.

6. **Rewriting branch view tokens widens a bearer capability.** Spec: `reporooms:440`–`:442`, `:416`. Code: `packages/server/src/index.ts:241`–`:251`, `:409`–`:413`. A developer gives an outsider a view link for `main`; that outsider has no GitHub push access. Rebinding its token to the repo room exposes feature/release branch content. Repo-level authorization of the person who minted the token does not authorize its eventual holder. Revoke old tokens and require a newly authorized repo-view token, or preserve a genuinely restricted archive endpoint. A removable UI branch filter is not access control. Also specify live-cutover token handling: rewriting only on server load does not fix existing links immediately after migration.

7. **Migration's completion marker is not atomic with document persistence, and its lock omits competing lifecycle operations.** Spec: `reporooms:154`, `:523`–`:549`, `:632`. Code: `packages/server/src/store.ts:1`–`:6`, `:155`; `packages/server/src/index.ts:99`–`:101`, `:130`–`:145`, `:416`. Documents live in LevelDB; File/Pg store only registry/session/audit data. Copying into a Y.Doc and then setting `migratedAt` can persist the marker before the copied document, losing owed mail after a crash. Define awaited source loading/flushing, target durability, then durable completion; exercise crashes at each boundary. Require successful admission **before** starting migration, and serialize close/expiry/open with the same lock: otherwise an unauthorized schema-2 request can trigger cutover, or a close racing the copy can resurrect the supposedly closed doc.

8. **Old participant names are not unique across source rooms.** Spec: `reporooms:467`–`:473`, `:529`–`:536`. Code: `packages/room-mcp/src/session.ts:312`–`:315`; `packages/shared/src/doc.ts:381`. Two clones were both `ben`, one in main and one in feature, each with claims and owed questions. Copying by bare name merges their scopes and sends both mail streams to whichever clone next acquires `ben`; the second is renamed, with no mapping for its old mail or claims. A newest-scope timestamp cannot choose the correct identity. Define a deterministic source-room/name→new-identity mapping and rewrite all references, or preserve ambiguous records in an explicitly unresolved archive until ownership is established. Do not validate both clones' claims against the first returning clone's disk.

9. **A legacy document can already occupy the destination key; case folding also needs registry migration.** Spec: `reporooms:69`, `:526`, `:541`, `:557`. Code: `packages/server/src/names.ts:26`; `packages/server/src/index.ts:236`–`:238`, `:374`; `packages/roomd/src/git.ts:68`. 0.16 accepts an explicitly named `github.com/o/r` doc. The proposed legacy union includes that same key: migration either retains old overlays/meta in the new doc or later purges the active repo doc as “legacy”. Separately, an existing registry key `github.com/O/R` is not found by `rooms.has('github.com/o/r')`. Inventory aliases, canonicalize/coalesce registry keys, and move a schema-1 destination to a distinct archive key before creating schema 2. Test pre-existing branchless docs and differently cased aliases together.

10. **The local mixed-version plan assumes the relay itself upgraded.** Spec: `reporooms:560`–`:596`. Code: `packages/relay/src/index.ts:165`–`:168`, `:314`–`:327`, `:246`; `packages/shared/src/memory.ts:5`. A 0.16 lead keeps its relay alive; a new ordinary session adopts it because health checks only clone/key, creates `local/x`, and stamps schema 2. The old relay still admits schema-less clients and serves old web assets. Add relay protocol/epoch negotiation before adopting it and define refusal or coordinated replacement of a live old relay. Old-worker HTTP 426 also does not stop its reconnect loop; a generic ten-minute note plus a live/unjoined PID cannot prove that this particular worker uses the wrong version. Align this lifecycle with registry M4 (`2026-09-28-registry.md:559`), which currently assumes refusal makes the run exit.

11. **The nested participant-map safety claim contradicts the registry's cross-clone race model.** Spec: `reporooms:97`–`:106`. Sibling: `2026-09-28-registry.md:403`–`:414`, `:636`. Code: `packages/room-mcp/src/session.ts:312`; `packages/shared/src/doc.ts:175`. Two separate clones sync an empty room, each passes its local lease/check, then each inserts a different nested `Y.Map` at `participants['ben']`. Yjs selects one entire map; the losing daemon can keep writing a detached map while manifests under the same name survive. An in-memory reproduction confirmed that later writes to the losing child do not reach the visible participant. Define a race-safe flat record/field layout, holder fencing and rebinding/reconciliation. A read once after sync is not distributed exclusion, so “never created concurrently” cannot be an invariant supplied by the current registry design.

12. **The neighbourhood filter removes the PR coordination feature it is supposed to retain.** Spec: `reporooms:356`–`:363`, `:377`–`:383`. Code: `packages/shared/src/near.ts:10`; `packages/room-mcp/src/prs.ts:52`–`:71`; `packages/server/src/github.ts:78`–`:85`. `pr#7` touches the file I am about to claim, but `neighbours` excludes every `pr#*` and `coordinationPaths` now filters through it: no PR proximity/claim warning remains. Separate message recipients/evaluators from coordination evidence so mirrored scopes remain visible. Also specify both base and head queries plus deduplication: one current `/github/prs?branch=feat` request returns only PRs **targeting** feat, not feat's PR into main.

13. **Projected workers have no evaluator for their outbound team conflicts.** Spec: `reporooms:105`–`:106`, `:278`–`:292`. Code: `packages/room-mcp/src/conflicts.ts:296`, `:307`–`:352`; `packages/room-mcp/src/bridge.ts:171`. Worker W runs only in the local room, while its lead projects W into the team room. W edits inside teammate B's claim. W's local ConflictSet cannot see B; the lead's team ConflictSet evaluates only `me=lead`, so no `W→B` edit-in-claim fact or warning is produced. B's evaluator checks B's edits, not W's. Assign projected conflict evaluation to the projector, with its fence and deterministic worker-owned keys, and route the resulting notice back to W; explicitly resolve the “evaluator is a” rule for this case.

14. **The promised legacy export has no admitted read path.** Spec: `reporooms:433`, `:440`, `:547`. Code: `packages/server/src/index.ts:244`–`:249`, `:409`–`:413`; `packages/room-mcp/src/prs.ts:111`. `room_export room=<legacy>` needs a token bound to that exact archived doc; token minting returns 410, old tokens are rebound, and legacy joins are refused. Specify an authenticated archive/export endpoint or an explicit schema-2 read-only archive capability, separate from normal repo-room admission. Keep the archive immutable and test exporting an offline persisted branch doc, not merely an already loaded one.

## Should-fix

1. **Keep unjoined administrative close.** Spec: `reporooms:459`. Code: `packages/room-mcp/src/tools/join.ts:252`–`:269`; `deploy/DEPLOYING.md:91`. Removing base lockout does not guarantee joining: an oversized/corrupt room can fail sync while authenticated DELETE still works. Deleting the 0.16.29 escape hatch makes the user start a daemon and publish state merely to delete a broken room. Keep the existing confirmed, authenticated unjoined path and update its repo-name parsing.

2. **Fix the push predicate and qualify exactly-once claims.** Spec: `reporooms:254`–`:258`. Code: `packages/roomd/src/index.ts:752`; `packages/relay/src/memory.ts:83`. After a force reset, `next.base` can move backwards to an ancestor of `prev.head`, satisfying the predicate without this participant pushing. Require a forward ancestry relation and distinguish an observed upstream advance from attribution of who pushed. A Yjs transaction is also not a durable commit: a relay crash before its deferred snapshot loses both the record and notice. State the recovery/delivery guarantee in those terms.

3. **Contract-notice IDs omit the change being reported.** Spec: `reporooms:311`–`:315`. Code: `packages/room-mcp/src/conflicts.ts:273`–`:286`. B changes a signature twice without committing: `bRev` is unchanged, so the second incompatible signature has the same proposed ID and is suppressed. Key by the observed before/after signature or manifest/graph revision. If the doc check searches only bounded bus history, trimming also re-enables old notices after restart; define the durable/current-state check.

4. **Name normalization cannot infer whether a suffix is an explicit room or a branch.** Spec: `reporooms:72`–`:81`, `:160`, `:588`. Code: `packages/room-mcp/src/choice.ts:19`, `:52`; `packages/room-mcp/src/session.ts:517`; `packages/roomd/src/git.ts:69`–`:70`. A remembered explicit `local/x/special` is indistinguishable from the alleged derived default and gets dropped. A legacy `git/h/repo/main` without `isOpen` is indistinguishable from a branchless grouped repo; the browser lacks `rooms.has`. Record provenance or use server-supplied canonical aliases instead of guessing. Define creation behavior before a non-GitHub repo is in the open-repo registry.

5. **The participants-view dependency and “only change neighbours later” claim need a narrower contract.** Spec: `reporooms:305`, `:377`, `:391`–`:398`, `:763`. Code: `packages/shared/src/views.ts:133`–`:172`; `packages/shared/src/near.ts:8`; `packages/room-mcp/src/tools/state.ts:86`. An offline record remains in `participants`, so the stated union still returns it after the unspecified expiry rule; conflict removal has no defined authority. Assign freshness/retirement/view ownership before implementation and keep hiding distinct from destructive deletion. Later splitting also needs provider/subscription lifecycle, reconnect reconciliation, cross-document transactions and message routing; these cannot follow solely from changing a synchronous function body. Describe neighbours as the consumer-selection seam, not the whole transport change.

6. **State the member trust model and the cap failure behavior explicitly.** Spec: `reporooms:107`, `:127`, `:446`, `:736`. Code: `packages/server/src/index.ts:50`–`:55`, `:400`–`:405`; `packages/server/src/readonly.ts:240`, `:310`, `:330`. An admitted buggy client can overwrite/delete another participant despite the claimed owner-only map guard; at the larger repo-wide cap a daemon can report successful complete revisions that the server silently drops. Adding root names to the observe-only guard establishes neither enforcement nor single-writer authority. Choose the audit's trusted-member model or an explicit validated-write boundary, and specify a visible rejected/unsynced state at the cap. The 50% warning alone does not address either failure.

7. **Cut repetition, not missing contracts.** Spec: `reporooms:28`–`:43`, `:485`–`:506`, `:610`–`:635`, `:696`–`:751`, `:755`–`:774`. An implementer currently finds the same base/refusal/deletion rule in several sections; revisions can leave conflicting copies. Keep one behavior/site checklist and the normative migration protocol. Remove the problems table (~16 lines), fold the deletion table into that checklist (~22), merge repeated recovery prose into tests (~25), move rollout estimates and rehearsal scripts to an implementation plan (~40), and combine risks/open questions into a short unresolved-decisions list (~35). Shorten repeated rationale in B1–B14 by ~35 lines to reach roughly 600. Preserve the concrete refusal matrix and migration crash tests.
