## Findings

1. **should-fix — Reuse same-file claim mapping within one claim operation.** `packages/room-mcp/src/tools/claims.ts:86`, `:134–148`.

   The quadratic whole-participant snapshot defect is fixed. However, `Promise.all(overlappingPaths.map(...))` still takes the same per-path snapshot, verifies the same text hash and computes the same owner-to-local line mapping separately for every foreign claim on that file. The synchronous prefix of all callbacks runs before an event-loop turn.

   **Evidence:** an stdin probe invokes the actual `handlers(state).room_claim` with a valid Bob manifest containing one 50,000-byte overlay and 1,000 Bob claims on that path. A small handler-state fixture supplies Alice's local text and the in-process hub fixture supplies posting; no production mapping function is replaced. Instrumenting that overlay's `Y.Text.toString` reports **1,000 conflicts, 1,000 conversions, 50,000,000 converted bytes**. An immediate scheduled at the first conversion has **not run at the last conversion**. Each call subsequently goes through `versionOf` and `claimInMyLines` at the cited lines.

   **Binding clarification:** rohanz answered room question `m_mun1hytj8uxk90`: “Accepted as bounded per claim, since each mapping is byte-capped”; grade the repeated work **should-fix, not must-fix**. This does not reopen the approved per-path-snapshot design.

   **Concrete fix:** within one `room_claim` operation, resolve text/hash and prepare the line map once per `(owner, path)`, then map all relevant claim ranges through it. Yield between distinct paths. Keep the captured raw/publisher snapshots and revalidate their authority after awaits; do not retain an authorization cache across calls. Add an operation-count regression with many claims on one nontrivial file, asserting one text/hash/map preparation per owner/path and an event-loop turn between distinct paths.

2. **nit — Checkout-filter output exactly one byte above the cap is accepted.** `packages/roomd/src/baseline.ts:120–121`.

   `checkoutText(..., maxBytes)` sets the subprocess buffer limit to `maxBytes + 1`, then converts and returns a successful buffer without comparing its actual length to `maxBytes`. A filter producing exactly the extra sentinel byte succeeds.

   **Evidence:** a real temporary Git repository stores a four-byte blob and configures an `inflate` smudge filter for `x.txt`. With `maxBytes=524288`, filter outputs of **524288 / 524289 / 524290** bytes return **524288-byte text / 524289-byte text / undefined**, respectively. The existing large-expansion regression passes, but does not exercise the boundary. The publisher uses this function with `inputs.rules.sizeCap` at `publisher.ts:195`.

   **Concrete fix:** hold the returned Buffer, return the gap when `buffer.length > maxBytes`, and decode only afterward. Cover cap, cap+1, and cap+2 output lengths. This is a one-byte policy discrepancy, not an unbounded-read or stall regression. The lead explicitly confirmed reporting it as a nit in the same room answer.
