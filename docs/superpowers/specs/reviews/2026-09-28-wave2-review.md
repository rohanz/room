## Must-fix

- **M1 — `packages/roomd/src/disk-scan.ts:42`, `:43`; `packages/roomd/src/policy.ts:82`: exclusion rules do not consistently precede publication/deletion. Owner: policy.** A tracked file matched by `.gitignore` is read and published because `readDisk` never supplies `ignored`, and the daemon's `isSafeRoomPath` does not check Git ignore rules. Separately, ENOENT returns before `safe(p)`, so deleting a tracked default-ignored `.env` produces a named D entry, including `baseHash` at full sharing. A real-Git `readDisk` → `plan` probe returned the modified `private.txt` text and a `.env` D/base hash, with no exclusion digests. The latter remains true even when the supplied safety predicate explicitly rejects `.env`. This violates manifest §5.3's path-rules-before-D order and invariants 7/16; the tracked-ignore case is a failure to implement the specified new rule, rather than a claim that Git itself ignores tracked files. Compute path exclusions, including tracked paths matched by Git ignore rules, independently of disk shape; apply them before ENOENT and before reading text. Test changed and deleted paths for `.gitignore`, default ignores and `.roomignore` separately.

- **M2 — `packages/room-mcp/src/session.ts:540`, `:548`; `packages/room-mcp/src/policy-store.ts:126`: production wiring makes every changed-policy settling scan stale. Owner: policy.** `onChange` gives the daemon `{...policy, publisher: ...}`, but `settle` requires reference equality with the store's original `policy`. After `room_scope`/`room_done`, no scan using that cloned object can settle. A real daemon wired exactly like the session callback produced `samePolicy:false`, `ending:['src/']`, `retained:[]` after a successful full scan. The departed directory keeps authorizing subsequently created files until another event such as restart repairs it, rather than retaining only the files proven changed by the settling scan. Preserve one authorization identity through store and daemon, or carry and validate an explicit immutable policy revision while changing publisher inputs separately. Add an integration test through the session callback; the current retained-done/store tests pass the store's own object directly and miss this bug.

- **M3 — `packages/roomd/src/policy.ts:77`; `packages/roomd/src/publisher.ts:155`, `:199`; `packages/room-mcp/src/policy-store.ts:128`: a failed file read becomes certified equality and can revoke retention. Owner: policy.** A `DiskFact` error goes only into `unsettled`; it produces neither entry nor exclusion. `apply` still replaces the whole manifest with `complete:true`/`coverage:all`, removing the previous entry and overlay. Injecting EACCES while scanning a genuinely changed `src/x` yielded an empty manifest with complete/all coverage. A manifest reader therefore certifies base for content the writer could not read. Once M2 is fixed, settlement also drops an already-retained path absent from `entries`, even if that path is in `unsettled`, permanently withdrawing its grant after a transient failure. Keep failed scans incomplete/unknown, retain unresolved grants, log and schedule the dirty retry, and only certify equality or remove retention after a successful observation. Test existing shared and retained files, plus failure during a HEAD transition.

- **M4 — `packages/roomd/src/publisher.ts:90`, `:94`, `:175`: narrowing authorization leaves a deleted file's base text shared. Owner: policy.** Publish a deletion at full sharing, then switch to declared sharing with no prefix covering that path. The manifest loses `baseHash`, but the legacy D marker remains; `reconcileBaseTexts` retains base text for every `changedPaths` entry, including that marker. A real daemon retained `Ben\0<base>:x = 'private base text'` both synchronously after narrowing and after the subsequent full scan. Manifest §5.1 requires withdrawal of unauthorized base text as well as overlay text and hashes. Reconcile base-text ownership against the text-authorized publication set, explicitly removing the base text for an unauthorized D while retaining the exact deletion fact. Cover full → declared and prefix settlement; checking only M/A overlays misses this path.

- **M5 — `packages/room-mcp/src/tools/index.ts:102`, `:112`, `:150`: an error reply can receipt inbox content it never contains. Owner: ledger.** The inbox reserves messages, then disclosure preparation and other reply-building operations can throw. The inner catch substitutes an error string but leaves the selected batch attached; the outer call hands it to the transport, which commits all selections after writing that error. A probe made `markDisclosed` throw after selection: the complete reply was `error: probe disk full`, yet the addressed message's `seen` receipt became true. Release/discard selections whenever their rendered content is removed, or preserve that content in the error response; only attach a batch representing the final response bytes. Merely calling `release` before later committing the same batch is insufficient because the ledger deliberately accepts late commits. Add a transport-level failure-after-selection test, not just an EPIPE test.

- **M6 — `packages/room-mcp/src/tools/join.ts:59`, `:61`: sharing disclosure is durably consumed before handoff. Owner: ledger/policy.** `prepareTeamSharingDisclosure` persists `disclosed` while merely preparing the pending sentence. Kill the MCP or fail the transport before stdout confirmation, then reopen the same sharing store: the new session treats that level as already disclosed and offers nothing, despite no notice receipt. A real-store probe released the first reply batch without committing it; the second session printed no disclosure while the persisted record already said full/version 1. This is ledger MF10's specifically prohibited claimant-dies loss. Advance the durable disclosed marker only after confirmed delivery, with an idempotent recovery path from the actual notice receipt. Reopening after an unconfirmed tool reply and an unconfirmed hook selection must re-offer the sentence.

- **M7 — `packages/roomd/src/index.ts:743`, `:760`, `:779`; `packages/room-mcp/src/session.ts:547`: the HEAD transition loses an owed pushed notice on refusal or crash. Owner: lead/ledger.** The transaction commits the advanced git record without `pushedPending`, then sends a fire-and-forget post whose result the session wrapper discards. If the hub is unreachable, the next poll returns early on unchanged HEAD/refs; after restart the surviving advanced record also lacks the old range. A real checkout with a simulated upstream-ref advance and a refusing poster made exactly one `pushed` attempt across repeated polls, with no pending marker in git rev 3. A crash between the transaction and post has the same loss. Reporooms §B2 steps 5–6/§B4 and manifest §5.4 explicitly require this marker; it is part of the wave-2 transition obligation. Record the pending range in the transaction, retry it by deterministic ID on startup/reconnect/poll, and clear it only after hub acceptance, without overwriting a newer pending transition. Test refusal and a surviving-document restart at the transaction/post boundary.

- **M8 — `packages/room-mcp/src/worker-launch.ts:82`, `:95`; `packages/room-mcp/src/tools/workers.ts:227`; `packages/room-mcp/src/registry.ts:332`: failure writing the launch fact can abandon a live child. Owner: writes.** `spawn()` has returned, but `delivered` and the handle are not set until after the awaited `onLaunched` write and `proc.started`. If the write throws, the catch does not stop the child and releases its port. Fresh spawn may then call `abandonPreparation` and remove the live child's checkout; resume records `launch:'never'` although the child may already be processing the prompt. A fake-child probe with an already-resolved `started` and a failing launch write returned `delivered:false`, zero kill calls and zero registered handles after spawning. Preserve child ownership immediately on return from spawn. Observe the actual start/error outcome even if persistence fails; retain an ambiguous/launched record or stop and confirm exit before any rollback. Never classify a persistence failure as proof the process never started. Test both fresh and resume launch-write failures.

- **M9 — `packages/room-mcp/src/worker-registry.ts:675`, `:701`: discard recovery cannot signal a surviving worker. Owner: writes.** Replay runs only in phase `discarding`. `statusOf` consequently returns `collecting` without a run, and `realStateInput(record, status)` strips the process identity. The subsequent `signalWorker(..., own, ...)` therefore fails its ownership check even when the persisted launch token matches a demonstrably live worker. A direct adapter/ownership probe returned `pid:0`, no `processStartTime`, and `canSignal:false` with an otherwise matching probe. Kill the lead after persisting the discard plan but before stopping its long-running child: every reconcile returns at this same check, so the recorded operation cannot finish. Build stop authority directly from the current durable run/admitted chain, independently of display status, and use the normal verified TERM/wait/KILL handling. Test actual `replayDiscard` from a plan with a live child; the patch-publication tests do not exercise this step.

## Should-fix

- **S1 — `packages/room-mcp/src/relevance.ts:22`, `:24`: positive ancestry is cached across reset/checkout. Owner: ledger.** The cache is keyed by directory and advertised SHA, and a positive result never expires. Check a pushed notice while HEAD includes B, then reset to A before B: the same relevance function still returns false forever, while a new instance correctly returns true. The real-Git probe reproduced this. Relevance is supposed to follow the reader's current HEAD without writing a receipt. Key the result by observed HEAD or invalidate it on every HEAD transition, including backwards moves and branch switches; test both directions.

- **S2 — `packages/room-mcp/src/policy-store.ts:112`: changing the level clears active scope authorization too. Owner: policy.** Declare `src/`, switch to full, then back to declared without changing scope. The store returns no text prefixes although the coordination scope still says `src/`; even setting full while already full clears a grant. A store probe reproduced `[]`. Manifest §5.1 requires clearing ending/retained when leaving declared, while active remains the current declaration. Preserve active paths, and make same-level requests idempotent; test declared → full → declared and full → full after a scope call.

- **S3 — `packages/room-mcp/src/worker-registry.ts:98`, `:99`; `packages/room-mcp/src/tools/workers.ts:150`: the advertised existing/outside-directory spawn cannot join its registry. Owner: writes.** Spawn with `dir` in another checkout and `allowOutside:true` writes the record in the lead's registry and passes that root as `ROOM_REGISTRY`. Admission instead opens the child's common-dir registry, requires the supplied root to equal it, and refuses before consulting the intended record. A two-repository probe reproduced “collected, discarded or superseded” solely from this mismatch. The normal `trusted()` path also requires an owned Room worktree, so the retained external-directory feature needs distinct capability handling. Either support admission and signal/resume using the explicit registry record with canonical-dir and nonce checks while keeping disk/delete capabilities restricted, or reject this unsupported mode before writing intent/spawning. Do not report a successful worker launch which can never join or report done.
