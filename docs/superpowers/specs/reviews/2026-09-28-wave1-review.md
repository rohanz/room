Even a previous manifest entry for `old` cannot rescue this: line 111 discards paths absent from the current diff/untracked sets. Publishing this as complete coverage certifies `old` as unchanged at base, and a future preview retains the deleted file. Disable rename detection for this path enumeration, or expand both sides of rename records. Test staged and committed renames, including a source that already had a manifest entry. This also exposes an omission in the spec's illustrative diff command; the all-changed-paths and exact-deletion contracts take precedence.

- **S2 — `packages/room-mcp/src/worker-registry.ts:321`: a done report can never acquire its durable `posted` marker. Owner: store.** Registry §7 requires the worker to persist its done report, post the deterministic completion, then set `report.posted`. Calling `writeReport(done)` followed by `writeReport({...done, posted:'wk:w_1:1'})` leaves `posted` undefined because the second write returns immediately. The inline probe reproduced this. A projector consequently cannot distinguish this successfully posted completion from an unposted report through that field. Preserve the existing done payload while allowing the monotonic posted update. Also retain the original `chain` and `hostSessionId`: before done, the current spread overwrites those set-once fields, contrary to §4. Test the full done → post → posted sequence and a restarted writer's identity fields.

- **S3 — `packages/room-mcp/src/worker-status.ts:58`: two consecutive failed resume launches erase the prior completed status. Owner: store.** Run 1 has a done report; resume runs 2 and 3 both have `launch:{outcome:'never'}`. The implementation skips run 3 once, then classifies run 2 as `failed: never started`, rather than preserving run 1's done result with “follow-up not delivered.” The probe reproduced `failed` on run 2. This breaks the recursive meaning of “status of n−1” after multiple rejected follow-ups. Walk past all non-started resume attempts, preserving the failure-to-deliver note, and test two or more failures after a done run.

- **S4 — `packages/room-mcp/src/worker-registry.ts:226`, `:399`: structurally corrupt JSON bypasses quarantine and aborts registry open. Owner: store.** The record validator checks only version, ID and whether runs is an array. A file containing `{v:1,id:'w_1',phase:'prepared',runs:[{n:1}]}` passes it; `reconcile()` calls `liveness(undefined)` for the absent launcher. Apply equivalent checks to report/exit/lease inputs as appropriate. The current corrupt-record test only supplies syntactically invalid JSON, which exercises a different failure path.

- **S5 — `packages/roomd/src/manifest-publish.ts:120`: text-budget exclusion runs before text authorization. Owner: facts.** With a four-byte text budget, shared in-area file `a='1234'` consumes it; out-of-area file `z='12345'`, below the per-file cap, then becomes a digest-only exclusion. The real-checkout probe returned `{path:'z', excluded:true}` instead of a hashless `held:'scope'` fact. Move that budget decision to the authorized-text branch and test scope/binary cases after authorized text fills the budget. No out-of-area hash leaked in this probe, but the promised path-level coverage was lost.

This is a remaining contract gap, not a newly introduced regression in the old oversize behavior. Establish/enforce the aggregate assumptions or define an explicit supported overflow contract; retain a test that includes newly owed mail when protected data alone exceeds the limit. The current shedding success test proves only the case where enough expendable data exists.
