### New Should-fix

- **S8 — `packages/room-mcp/src/worker-registry.ts:51–73`, `:219`, `:230`, `:382`, `:499`: guard contention synchronously freezes the caller's entire event loop. Owner: store.** A child process holds the capacity guard for about 1.1 seconds; the MCP-side process schedules a 10 ms timer and calls `writeIntent()`. The repeated `Atomics.wait` returns only after **1,260 ms**, with the timer still unrun; yielding afterward lets it fire. The same helper allows up to 30 seconds per acquisition, and reconcile can encounter multiple records. This blocks stdio/cancellation and any relay/presence/heartbeat timers in that process, not just the contested operation. It is not acceptable as the general live-call retry strategy: these call sites include watcher/poll reconciliation, H1, report/exit writes and worker mutations, rather than only a separate startup utility. However, this additive `WorkerRegistry` currently has **no production callers** outside its own module; today's worker adapter still uses the existing implementation. Thus this is Should-fix before runtime integration, not a claim that the currently shipped MCP already hangs on these new paths. Keep guarded mutation bodies synchronous, but yield while waiting for acquisition (with the monotonic deadline and cancellation), or defer background reconciliation on contention. The full-suite contention fix establishes eventual acquisition, not event-loop responsiveness; add a timer-responsiveness contention test. A startup-only synchronous wait would need isolation or a clearly bounded startup allowance and does not justify applying it to every mutation.
