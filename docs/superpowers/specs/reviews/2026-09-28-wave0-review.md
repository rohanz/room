## Must-fix

- **M1 — `packages/room-mcp/src/leases.ts:121`: guarded release cannot release a bare instance token.** `holder()` accepts both `{holder: token}` and a bare token, but `compareAndRelease()` only checks `current.holder.nonce`. Registry §4 explicitly creates `runs/<id>/<n>.writer` with `createExclusive(file, myToken)`. Concrete reproduction: create with an `InstanceToken`, then release with that exact token: creation returns `true`, release returns `false`, and the file remains. A live MCP finishing its report-writer role cannot relinquish it; a successor remains blocked until the old process dies or another path rewrites it. Normalize the token shape consistently in release/recovery, or make one required envelope explicit throughout the API and spec. Add release/successor tests for the run-writer representation.

- **M2 — `packages/room-mcp/src/session.ts:183`: the app-server early return also rejects explicitly identified workers.** The worker branch is below the parent-mode refusal. With `workerId: 'w_1'`, a matching durable worker session record and `appServer: true`, `boundSession()` returns `undefined`; the registry's pre-generated Claude ID is also bypassed. Registry §17 makes only an unidentified **lead** under a shared app-server unbound. Once the ledger consumes this primitive, such an identified worker cannot bind to its session for receipts/hook arbitration despite having the required evidence. Resolve verified worker identity before applying the app-server lead rule, and test both worker hosts. The lead confirmed this interpretation in answer to `m_mul0bch0ypb1r4` during this review.

- **M3 — `packages/room-mcp/src/session.ts:168` and `:183`: failure to identify the parent command fails open into thread binding.** `parentCommandLine()` converts a failed/timed-out `ps` into `''`; the app-server test treats that as a non-app-server. If process identity was readable but this separate command lookup fails, records from multiple threads whose hook chains contain the same app-server parent are eligible, and line 192 picks the newest one. Reproduction with two records sharing a parent: `parentArgs: ''` binds `thread-b`, while `parentArgs: 'codex app-server'` correctly returns `undefined`. A call originating from thread A can consequently use B's session identity for ledger arbitration/receipts. Preserve an unknown parent-mode result and leave Codex leads unbound unless the parent is positively identified as a supported dedicated host; keep the explicit-worker exception from M2. Existing `workspace.ts:18` already treats unknown shared-Codex ancestry conservatively.

## Should-fix

- **S1 — `packages/room-mcp/test/leases.test.ts:17`, `:27`; `packages/shared/src/participant-record.test.ts:61`: the tests overstate concurrency and ownership enforcement.** Both `createExclusive()` calls are synchronous callbacks on one event loop, so the `Promise.all` test is two sequential creates. The release test also runs replacement and release sequentially; no test kills a guard owner or exercises recursive guard recovery. The CRDT test genuinely merges competing fields, but its losing writer stops because a test-local `tick()` implements that behavior, not because a production writer does. A broken recovery/release interleaving or a future writer that ignores holder loss can pass all these tests. Add separate-process contention plus kill/recovery tests for the foundation now; label the CRDT test as a fencing-contract simulation and require an actual daemon/lease ownership-loss test when wave 4 wires it. Do not count it as the plan's end-to-end two-clone rehearsal.

- **S2 — `packages/room-mcp/src/leases.ts:102`: `withGuard<T>` accepts async callbacks but releases before their work completes.** Returning a Promise executes the `finally` immediately. A direct probe using `withGuard(file, async () => { await Promise.resolve(); ... })` admitted a second guard holder before the first callback finished. A later registry operation that awaits between its occupancy check and intent write could silently lose exclusion even though TypeScript accepts the call. Current internal callers are synchronous, so this is not a regression in today's rooms. Make the synchronous-only contract explicit and reject promise-returning callbacks in the type API, or provide an awaited variant that retains the guard through completion.

- **S3 — `packages/room-mcp/src/leases.ts:30`, `:45`, `:53`: first-use directory creation is outside the durability barrier.** Recursive `mkdirSync` can create `room/registry/...` or `room/sessions/<sid>`, but only the immediate directory containing the final record is fsynced. Its newly created entry in its parent (and higher newly created ancestors) is not explicitly made durable. On a filesystem requiring parent-directory fsync for durable directory creation, a power loss after a successful first intent/session write can lose that directory subtree even though the file and leaf directory were synced. This undermines the durable-record-before-side-effect contract when registry writes adopt the helper. Durably initialize the directory hierarchy, or fsync each newly created directory's parent before reporting a durable write. This concerns power-loss durability, not ordinary process SIGKILL.

- **S4 — `packages/room-mcp/src/leases.ts:31` and `:47`: crash-created temporary files have no recovery cleanup.** Normal exceptions clean up, but SIGKILL after `openSync`/file fsync, or after linking and before the `finally`, leaves a uniquely named `.tmp` forever. A later acquisition creates another UUID temp and never examines the previous one; repeated interrupted registry/session writes accumulate stale copies, including possibly large records. Add conservative orphan-temp cleanup tied to provably dead writer identity (or a safe maintenance phase), without removing a live writer's temporary file. Also account for the temp unlink being after the directory fsync if cleanup itself is meant to survive power loss.
