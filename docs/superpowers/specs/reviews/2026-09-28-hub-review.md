# Hub implementation review — 2026-09-28

Reviewed `40345d8..cedd54e` against the full hub spec and the redesign plan's Hub core section. Code is unchanged. Validation: `npx vitest run packages/hub-core packages/room-mcp/test/hub-client.test.ts --maxWorkers=1` passed **29/29 tests across 3 files**. Additional socket-free, inline probes reproduced M1, M3, M4, M5, S1, S2 and S3 below. M2 is a filesystem durability finding from inspection. Socket/process rehearsals were not run in this sandbox. The two explicitly excluded, already-assigned issues are omitted.

**Must-fix**

- **M1 — A server without YPERSISTENCE repeats counters even within the spec's stated forward-clock exception.** `packages/server/src/hub.ts:34`, `packages/hub-core/src/hub.ts:163`.
  **Scenario:** At wall second 1000, load rooms A, B and C: their incarnations are 1000, 1001 and 1002 because the shared store advances for each room. C posts its first message. Restart the process two seconds later, with no clock rollback; load C first, before a surviving replica syncs. Its new in-memory store chooses incarnation 1002 again, and its first post repeats C's previous seq. The probe produced **2101346304 twice**. Thus even “restarts are over a second apart and the clock does not step back” (§3) does not establish uniqueness: concurrent room loads, reloads and rollover advance the counter ahead of wall time. More allocations can expose epochs to the same problem.
  **Suggested fix:** Give incarnation allocation a durable record independently of whether documents use LevelDB, or refuse to offer the never-repeat hub contract without that record. Do not rely on a timestamp floor as a uniqueness mechanism. Add a multi-room, fresh-store restart test; merely restarting hubs against one surviving in-memory store misses this.

- **M2 — The server's incarnation file is not fully durable on initial directory creation, and real directory-fsync errors are swallowed.** `packages/server/src/hub.ts:13`, `packages/server/src/hub.ts:19`.
  **Scenario:** The first startup creates `<YPERSISTENCE>/hub`, writes/renames `incarnation.json`, fsyncs `hub`, and starts issuing counters. It never fsyncs the parent directory containing the new `hub` entry. A machine/filesystem crash can lose that directory entry along with the supposedly durable counter; the allowed loss of recent LevelDB updates then leaves no high-water mark. A later restart can reissue an incarnation. Independently, `syncDir` suppresses every sync error, including I/O failures, and therefore can acknowledge an incarnation whose final durability step failed.
  **Suggested fix:** Use a durable-directory creation procedure that fsyncs newly created directory entries in their parents, as the relay's `ensureDurableDirectory` already does. Ignore only explicitly unsupported directory-fsync errors; fail startup/rollover on durability failures. Keep the incarnation write before serving. Test the required fsync ordering and failure propagation; the in-memory “killed” test does not validate filesystem persistence.

- **M3 — The authority forgets ended holders, allowing stale replicas to roll back fences and settlement renews to resurrect released epochs.** `packages/hub-core/src/hub.ts:216`, `packages/hub-core/src/hub.ts:322`, `packages/hub-core/src/hub.ts:404`.
  **Scenario A:** Grant epoch E1, supersede with E2, release E2. A stale replica then wins the holder key with E1. `end()` removed the only authoritative in-memory record, so `reassert()` merely marks E1 expired instead of restoring E2. The probe left `holder.epoch = E1`; retrying the acknowledged release of E2 returned `stale`. Once epoch fences are wired, the last owner's E2 facts also fail the offline holder fence. **Scenario B:** Restart with a carried lease, release it during the five-second settle window, then receive an already-in-flight renew for that epoch. `renew()` ignores the record's `ended` flag, adopts the released epoch, and the next reassertion removes `ended`. This was also reproduced.
  **Suggested fix:** Retain authoritative holder records/high-water marks, including terminal state, separately from live TTL entries. Reassert the latest ended holder as well as live holders. Settlement must not adopt an epoch this incarnation has already ended or superseded. Add tests for stale sync after release/expiry and delayed renew after an acknowledged release, alongside the existing live-holder reassertion test.

- **M4 — Automatic post retries bypass the client's TTL fence.** `packages/room-mcp/src/hub-client.ts:171`, `packages/room-mcp/src/hub-client.ts:227`.
  **Scenario:** Acquire at t=0; begin a fenced post at t=44.999 s. A recovering/loading hub answers `starting`. Retry after t=45 s. `post()` checked `paused()` and the epoch only before entering `request()`; unlike `renew()`, it supplies no per-send validation. The retry sends the expired epoch. A successor that gave the inherited lease a fresh TTL can accept it. The probe sent a second post at t=46 s and returned success, while an immediate `paused()` reported the expired lease. A `lease-lost` received during the retry delay has the same missing check.
  **Suggested fix:** Recheck hello/pause state and the exact current, valid lease immediately before **every** post transmission, including `starting` and `hello-first` retries. Abort with the paused/not-sent result after lease expiry or loss. Add a test that crosses TTL between the initial send and retry, with a successor still willing to accept the old epoch.

- **M5 — Hub-driven participant expiry appends unsequenced messages.** `packages/hub-core/src/hub.ts:438`; call chain: `packages/shared/src/expiry.ts:77`, `packages/shared/src/doc.ts:199`, `packages/shared/src/doc.ts:560`.
  **Scenario:** A participant has a claim, releases its lease and reaches the stale threshold. Hub maintenance calls `ExpiryTenure.observe` → `expireParticipant` → `clearWorkerCoordination` → legacy `RoomDoc.post`. That appends a `release` message directly, without going through `issue('seq')` or updating `meta.hubSeq`. The probe produced a release message with `seq: undefined`. This is a new hub-owned write path, distinct from the intentionally retained client append until wave 2; it breaks the sole sequencer contract and cannot participate in the planned integer frontier.
  **Suggested fix:** Route internally generated expiry notices through the hub's sequenced append primitive, sharing allocation, timestamp and trim behavior with RPC posts. Let expiry return notices or accept an appropriate callback rather than calling the legacy client writer. Test expiry with an actual claim and assert that its release has a unique seq and advances the meta mirror.

**Should-fix**

- **S1 — Closing HubClient does not cancel requests sleeping between retries.** `packages/room-mcp/src/hub-client.ts:94`, `packages/room-mcp/src/hub-client.ts:237`, `packages/room-mcp/src/hub-client.ts:249`.
  **Scenario:** A request receives `starting`, leaves `pending`, and sleeps for `retryMs`; the session then calls `close()`. Only pending reply timers and the renewal interval are cleared. The retry sleep wakes and sends again through a transport whose listeners were removed. The probe observed two sends although `close()` ran after the first. An acquire/post can therefore mutate the room after the owning session closed, and then hold a timeout waiting for a reply it cannot receive.
  **Suggested fix:** Add a terminal closed flag and cancellable retry waits. Reject every active operation on close and check closure before any send or retry. Include repeated close and close-during-starting-delay tests. This also prevents new direct API calls from using an already-closed client.

- **S2 — Loaded counter mirrors have no reassertion baseline until the first new grant/post.** `packages/hub-core/src/hub.ts:127`, `packages/hub-core/src/hub.ts:152`, `packages/hub-core/src/hub.ts:416`.
  **Scenario:** Restart with `hubSeq=123` and `hubEpoch=124`. Before issuing anything new, a stale value-copy replica overwrites them with 1 and 2. `lastSeq` and `lastEpoch` are undefined, so even after settlement/tick the hub leaves those older values in place. Reproduced. Allocation itself remains protected by the durable incarnation, but the promised authoritative reader mirrors regress.
  **Suggested fix:** Initialize authoritative mirror baselines from the loaded state and define how late settlement state raises them. Reassert those values even before the first issue in the new incarnation. Extend the existing reassertion test to restart first instead of always issuing fresh counters before injecting stale state.

- **S3 — A short return does not reset a participant's accumulated absence.** `packages/hub-core/src/hub.ts:304`, `packages/hub-core/src/hub.ts:389`, `packages/hub-core/src/hub.ts:438`.
  **Scenario:** A released participant is almost at `ROOM_STALE_MS`. Between two 60-second maintenance passes it acquires a lease, publishes a new scope, then releases after ten seconds. At the next maintenance pass it has no live lease again; `ExpiryTenure` never observed the live interval and adds the whole gap to the old absence. The probe deleted the returned participant and its new scope after only **20 seconds** of renewed absence.
  **Suggested fix:** Reset that participant's absence segment and persisted expiry counter whenever the hub establishes/adopts a live lease, not only when a periodic sample happens to see one. Add a return-and-release-between-ticks test. The current expiry test's final renew follows a jump of the entire stale period, is actually stale, and its unchecked return value does not prove that the “here” participant stayed live.

- **S4 — Some integration tests promise stronger evidence than their fixtures provide.** `packages/relay/test/hub.test.ts:52`, `packages/relay/test/hub.test.ts:115`, `packages/server/test/hub.test.ts:146`.
  **Scenario:** A regression in dead-owner lock recovery could leave the relay tests green: the racers are calls in one process, and the survivor test uses graceful `owner.stop()`, which releases the lock before takeover. It does not exercise recovery after kill -9 or a stalled live owner. Likewise, the test named “in observe or enforce mode” never installs/runs either wrapper mode; its hub post is authored by the same login (`ada`) as the guard, so incorrect attribution can still pass. Those green results can be mistaken for proof of the requested crash and hub-origin invariants.
  **Suggested fix:** Run separate-process contenders behind a start barrier, then kill the actual authority without cleanup; separately stall a live authority and assert that no replacement grants. Exercise the real identity wrapper in both modes with hub writes that would be foreign if attributed to the caller. Preserve the current shared contract tests—they test useful behavior—but add the process rehearsals and missing assertions before calling the acceptance properties proven.

**Leave**

- **L1 — Keep the authority lock and conservative liveness design.** `packages/relay/src/hub.ts:24`, `packages/relay/src/leases.ts:165`, `packages/relay/src/index.ts:406`, `packages/hub-core/src/hub.ts:189`.
  **Scenario checked:** Two joiners find the derived port occupied; or an existing owner stalls while its PID/birth identity remains live. Starting two granting relays would be wrong. The normal path takes the exclusive lock before starting, refuses recovery unless the recorded process is demonstrably dead, and checks its nonce before requests and ticks. PID reuse is checked against process birth identity; unknown identity conservatively blocks recovery. **Suggested action:** Keep this design and substantiate it with S4's real-process tests. Do not replace the lock with a health-timeout takeover heuristic.

- **L2 — Keep the shared engine, serialized incarnation allocator, and server wrapper order.** `packages/hub-core/src/hub.ts:28`, `packages/server/src/index.ts:390`, `packages/server/src/hub.ts:144`, `packages/hub-core/src/hub.ts:350`.
  **Scenario checked:** Two rooms load concurrently; a view-key holder sends a hub frame; a post is retried after archival; or the doc is over its cap. Wrong outcomes would be duplicate allocations within the running process, a view-key mutation, re-appending an archived ID, or accepting a fresh post despite `full()`. The shared allocator serializes allocations, the inner hub wrapper receives type 7 after the outer guards and refuses view keys, duplicate lookup precedes limits, and `full()` gates new posts while lease operations stay available. The meter's `size()` still increments its write counter on hub calls, so this is not an entirely unmetered growth path. **Suggested action:** Preserve these choices; address M1/M2 without adding a second engine or a persist-before-ack message journal.

- **L3 — Keep the explicit staged cutover boundary.** `docs/superpowers/specs/2026-09-28-hub.md:345`, `packages/hub-core/src/hub.ts:346`, `packages/room-mcp/src/hub-client.ts:104`.
  **Scenario checked:** On this intermediate branch, clients still call the legacy append, posts may omit a lease, and hello does not yet enforce schema-2 admission. Shipping that state as completed 0.17 would be wrong, but §11 explicitly assigns client post routing, required epoch fences, paused tool/hook wiring, and admission refusal to waves 2–5. **Suggested action:** Keep those tracked as release gates rather than treating their absence as regressions in this hub step. M5 is separate because the newly introduced hub maintenance path itself bypasses its own sequencer. The admitted-user trust model also deliberately does not turn every renew/release into a new authorization layer.

New findings / additional cases:

- **Must-fix N1 — A late terminal record cannot end an already-adopted epoch.** `packages/hub-core/src/hub.ts:278`, `packages/hub-core/src/hub.ts:378`. **Scenario:** The successor receives a delayed renew for old epoch E before its holder record syncs and adopts it.
