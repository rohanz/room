### Wrong, incomplete or unproven claims

1. **P1: a producer fence on a record does not fence a destructive outcome (D:91,94,97–99).** The design acknowledges the ownership change, but does not supply the mechanism. `Hub.post` validates a private live lease and connection/session at `packages/hub-core/src/hub.ts:672–684`; `outcomes` has no writer epoch (`packages/shared/src/types.ts:255`). `owed` suppresses any matching key at `delivery.ts:89`; it never checks the ending writer. `ParticipantLease.fence()` (`packages/room-mcp/src/names.ts:296–303`) is local knowledge, not a compare-and-set at the hub. A delayed old-holder outcome can suppress an id the new holder adopted unchanged. Keying the outbox by incarnation does not repair an already-published exact-id outcome. A capable hub must authorize the terminal transition; old hubs must not execute it.

2. **P1: “register before posting” and a Yjs transaction do not establish durable registration before posting (D:93–94,98).** Current slot writes and posts are separate (`conflict-set.ts:161–167`); `createPost` yields for lease lookup and then makes an independent hub request (`post.ts:58–68`). Relay snapshots are debounced 2 s with a 10 s deadline (`relay/src/memory.ts:180–185`). `Hub.post` appends and returns without awaiting a save (`hub.ts:707–709`). Even adding the root to snapshots permits the hub to retain the message while the independently transmitted registration is lost. State the failure model: producer-process crash with surviving hub differs from relay crash, all replicas lost, IO failure and power loss. No persist-before-ack journal currently exists (also explicitly deferred by the hub spec, `docs/superpowers/specs/2026-09-28-hub.md:23`).

3. **P1: not every current `drop` is positive semantic-ending evidence (D:76,94–95,111).** In particular `withdrawUnauthorizedContracts` calls raw `slots.drop` at `conflict-set.ts:573–574`; `contractPathAuthorized` returns false for absent/unfenced snapshots, absent head or salt at `:584–591`. An updating/missing publication can therefore take the same removal path as actual grant revocation. The design says missing manifests never write endings, so blindly extending `drop` would contradict it. `claims` also drops finished own-worker slots at `:1125–1128` based on a registry observation. Audit each reason, revalidate exact worker/run/name facts, and split `withdraw-authority`, `evaluated-clean`, `retired-incarnation` and `unavailable` transitions. A full evaluation is not one transaction today: it yields and settles slots incrementally (`:644–653,736–789,925–943`). Batch peer/group terminal decisions after the final valid pass; an interrupted partial scan must not end the remainder.

4. **P1: durable endings need an atomic/retryable terminal operation, not “atomically … when possible” (D:94,97–98).** If code marks ended/deletes the inventory and crashes before writing the outcome, replay cannot enumerate the ids. If it writes the outcome first and loses the state transition, a recreated current record can try to replay the now-terminal id. Within one hub, transition state and exact outcomes must commit in one transaction. Across rooms, retain an immutable terminal source intent until destination acknowledgement or a defined safe deadline; never use an acknowledged successful post as the ending acknowledgement.

5. **P1: outcomes are suppressors with bounded retention, not permanent deduplication (D:50 and the replay promises at D:94,97–98).** `delivery.ts:23–25,197–209` keeps at most 2,000 outcomes/256 KiB/30 days. Archive is also bounded (`:20–22,192–196`). `hub.ts:689–694` deduplicates only while a message/archive/outcome exists. An indefinitely “current” stored-body retry can resurrect an expired/receipted message after these suppressors disappear; it receives a fresh hub timestamp. This can defeat the 14-day policy. The outbox needs a publication/retry deadline and a durable terminal state/GC rule, and must honor `expired`, `over-cap`, receipts and `gone` results. Natural TTL of an ongoing conflict does not itself authorize minting a new id to circumvent caps/TTL.

6. **P2: snapshotting the inventory alone does not preserve receipts needed by replay (D:91,97).** `memory.ts:66–84` retains receipts referenced by bus/mail/outcomes, not by new roots; orphan receipts are discarded regardless of available byte budget. `RoomDoc.retireWorker` also clears name receipts at `doc.ts:239`. If current replay records outlive ledger references, a restart can forget a receipt. Either stop production before that point, extend the receipt reference/retention rule with strict bounds, or retain no replay body after successful publication. The ledger remains the sole receipt authority in all variants; copying “shown” into an outbox would duplicate it.

7. **P2: bounds are a requirement, not a design yet (D:93,97,103).** No entry, id-set, per-producer, per-recipient, per-room or serialized-byte limit or admission behavior is specified. “Never silently evict current” leaves overflow unresolved. Protected roots may exceed the 5 MiB target (`memory.ts:50–54`); above 64 MiB `relay/src/memory.ts:117–121` skips the save and preserves an older snapshot. Duplication of up-to-64-KiB bodies makes this material. Define admission before publication, explicit diagnostics and safe TTL fallback for records not admitted. Terminal GC must not leave a live retry or permit id reuse. Count/bytes, not a 6–10-module estimate, determine the storage guarantee. The effort estimate at D:103 is not implementation evidence.

8. **P2: retirement's name guard is not a universal guard on ending old worker dependencies (D:95).** `workerOwnsName` (`doc.ts:212–216`) protects deleting *current name-owned state*. If old worker w1 is retired after w2 takes the same tag, w1's explicitly registered obligations can still be ended by w1's lifecycle authority; a current-name guard would unnecessarily strand them. End only exact dependency w1/producer-incarnation ids. Never delete w2's current slots, receipts or records. Conversely, `workerViews` is display state (`doc.ts:172–189`), not permission to identify a missing worker or infer an ending. The current cursor already filters old addressed mail for a new worker (`ledger.ts:319–330,392–402`); the broad D:80 claim that every successor reads earlier addressed mail omits this exception. Ordinary takeover and replayed new-seq mail remain relevant cases.

9. **P2: old-hub behavior and discovery need a real capability plan (D:89,99–101,116).** I checked the pinned `v0.17.0`: `shared/src/delivery.ts:89` and `hub-core/src/hub.ts:689` honor outcomes; its `shared/src/memory.ts:14–29` omits arbitrary new roots. This supports the baseline mechanical claim, not all intermediate-version integration. Existing baseline capabilities explicitly promise no stronger durability (`packages/hub-core/src/negotiation.ts:43–56`). Nothing there currently advertises notice inventory, authorized endings or replay. Add an optional registered capability with those precise semantics, select through the existing bootstrap, and use the fixed legacy adapter for 0.17.0–0.17.32. Do not infer support from release strings, root presence, sync readiness or a client-published marker. Do not send a new op/field to an old hub. Optional unknown offers can be ignored; making the capability a room requirement would reject old writers and violate the requested rollout.

10. **P2: destination durability and fencing across two rooms are only sketched (D:98–99).** Current `Bridge.projectOnce` guards team authority (`bridge.ts:285–304`) but no durable handoff record or destination validation exists. The destination hub cannot validate a remote team epoch using its own name lease. Source/destination room generations, worker id, lead identity, producer incarnation, exact id, transition revision and source authority evidence/authorized bridge adoption must be specified. A source ending accepted before takeover is different from an uncommitted old-holder proposal arriving afterward. “Republish durable local/source intent” through an old relay (D:99) is an alternative only if that source actually survives and is reachable; no such local store is supplied. Without it, TTL fallback is the only proved option.

11. **P2: “clear obligation before ending” preserves neither delivery order nor urgency by itself (D:94,96).** Registering an unposted fyi does not deliver a clear to someone previously told the conflict. Ending notify before an equally urgent replacement is accepted can lose the only owed notification while conflict remains open. Commit replacement publication and supersession together at the capable hub, or keep predecessors until the replacement is accepted; failed/refused posts cannot consume them. On partial clear retain the prior highest-urgency notify and latest fyi. The two retained tiers suffice under current `messages.ts:60–66`; storing every historical predecessor body is unnecessary. On full clean end old conflict obligations only after the coherent clean transition, and preserve the clearing delivery attempt under the explicitly chosen crash guarantee.

The nine gate tests support current-state observations, not the new outbox claims. The grouped case deliberately uses legacy multi-slot keys; current edit-in-claim production is stable per path. The routing case constructs the exact constructor wiring but does not run bridge shutdown/restart. There is no crash, mixed-version, outcome-GC, takeover-in-flight, admission or projection-handoff implementation in those tests. The design candidly states several of these limits; they remain implementation gates, not reasons to discard the whole direction.

### Exact id reuse and what breaks

**Unchanged takeover/renewal:** `conflict-set.ts:137–145` increments epoch only on changed settled fact, and retains an existing `episode`; `:254,266–270` reuses its id. At a new fence the same fact is re-fenced without a new identity. If an old writer adds `outcomes[id] = expired` between takeover and replay, `owed` excludes it (`delivery.ts:89`) and the real hub returns duplicate/gone (`hub.ts:694`) once no message copy remains. Removing the bad root record or fixing the slot cannot undo the outcome. This is why an exact registered id still requires a valid ending authority.

**Drop all merge slots, reopen:** settle A/B/x conflict -> `epoch=1`, `peerEpisode=1`; `peerNoticeId(A,B,1,[[x,1]],[])` is produced at `:206`. Drop the last slot (`:115`), end its old id, then settle identical A/B/x again: `prev` and pair are empty, so `:139,183–189` return the same counters and `:75–78` produces the identical id. The active new slot exists but its message is terminal. Our first skipped characterization exercises this exact trace, including a post attempt with the old id.

**Other reset paths:** grouped `possible` counter restarts at 1 when the group is empty (`:232–239`), and its `:266–267` id ignores the per-slot random `episode`; adding a UUID only to `ConflictSlot.episode` does not fix it. Non-contract clear ids (`:268–269`) also ignore that UUID. Claim-pair keys/counters (`:61–64,139`) can reuse an id if the same subjects are restored after deletion. Allocate a group/peer/clear lifecycle token, not just a contract/edit token. Preserve `cf:<pair>:peer:` grouping or explicitly replace its supersession implementation; otherwise current old readers lose their grouping behavior.

**After suppressor GC:** an outcome is not eternal. Once archive/message/outcome references are gone, the same old id can be accepted again. That does not justify reusing it: a restored delayed publisher could resurrect an ended episode or repeatedly reset TTL. Managed requests need a bounded retry horizon and generation/epoch checks independent of the presence of an outcome.

## 3. Smallest sound design

### Separate ending correctness from exact publication replay

For the stale-delivery task, keep **one authoritative lifecycle inventory at the delivery hub**, not a second delivery ledger or a permanent body queue. Producers still decide conflict semantics from completed coherent evaluations; readers only use existing outcomes/receipts/routing. The hub arbitrates whether that producer is allowed to commit its decision. Its code does not infer a subject from a message, decode a hash, or derive a lifecycle from missing slots.

An inventory record needs: source/destination room identity and generation; producer identity and semantic incarnation (worker id when applicable, distinct from lease epoch); episode/group token; monotonic accepted revision; current authority name/epoch; exact message ids with recipient/from and urgency role; explicit dependency worker ids/episode members or authority references needed for lifecycle termination; and a finite publication/retry horizon. A same-room record omits redundant cross-room fields. Keep at most the current message and retained higher-urgency predecessor per peer episode under today's priority rules, plus distinct owner/holder ids and pending terminal transitions. No full bodies or historical claim strings are needed merely to enumerate endings.

The inventory is authoritative for **which managed delivery ids belong to which lifecycle**, not whether a user saw them or whether disk changes merge. Slots are producer derivations, not deletion authority. `seen:<recipient>` stays authoritative for receipts. The hub alone commits managed inventory revisions and their terminal outcomes; producers submit proposals, worker retirement submits an exact-incarnation lifecycle proposal, and hub expiry uses its existing tenure. State is not authoritative merely because a client sync wrote a new root. As with existing hub mirrors, canonical authority state needs protection/reassertion against stale replica writes (`hub.ts:774–812` is the existing pattern); independently owned per-producer keys avoid overwriting unrelated records.

### What a capable hub must verify

Implement an optional notice-lifecycle capability through `hub-core/src/negotiation.ts`; extend a gated operation/intent path, leaving baseline posts and message vocabulary unchanged. Do not smuggle an ending into a `note` body. A replicated intent may be a proposal mailbox, but its arrival alone is not authorization: consume it under authenticated, current authority or require a current-session request to adopt it. A gated request is simpler than trusting arbitrary replicated proposal authorship.

Before accepting any ending, in the same non-yielding decision/commit:

1. Confirm the connection negotiated the capability, belongs to the current room/generation, is writable, and the hub is the active authority. Validate bounded intent shape, ids/count/bytes and permitted operation.
2. Validate the requester's **private live lease**, epoch, principal and host session exactly as `Hub.post` does. A replicated `holder` or a producer-supplied epoch alone is insufficient. For projection also validate its authorized source/bridge mapping; destination-local epoch is not proof of a team lease.
3. Match the exact accepted inventory key, producer incarnation, expected revision and episode token. All ended ids must be registered under it with the recorded recipient/from. A new worker at the same tag cannot adopt the old worker identity. Lifecycle authority for retirement may end dependencies of that exact retired worker across producer inventories; it cannot end other dependencies just because their names match.
4. Validate the producer transition's captured input revisions against the authority's accepted relevant state (manifest/policy/claim and worker lifecycle revisions, as applicable); reject moved/unknown evidence. Preserve existing producer snapshot/registry guards. The hub verifies authority and version matching, not the merge algorithm itself; a legitimate producer must still supply a coherent semantic decision. Scope the invariant to authoritative published state, not unseen remote disk writes.
5. For a replacement, require its publication to be accepted in the same transition, or leave the old urgent obligation active until it is. Partial-clear fyi cannot terminate the retained notify; complete clean and explicit lifecycle withdrawal are different reasons. Record the new generation/token before any reopened id is used.
6. Atomically advance the inventory revision/terminal state and insert set-once exact outcomes with the existing valid shape. Never overwrite an existing terminal result or touch `seen` as a substitute for delivery. Commit/ack distinguishes registration, publication and ending; post success/duplicate alone is not an ending ack.

Retry is keyed by producer incarnation + operation/revision + exact ids. Repeating a committed transition returns its committed result without a new revision, timestamp or post; a contradictory operation at that revision is rejected. A retry of a committed ending remains terminal even if an outcome was later pruned. An uncommitted old-epoch request after adoption is rejected. Takeover transfers only open inventory under a fresh accepted revision, revalidates current evidence and retains semantic ids; it must not replay old uncommitted terminal proposals under the new lease automatically. Terminal records never reopen; a real new episode gets a new random token.

For **registration then posting**, a capable hub can register the ids and append the supplied message in one authority transaction. The body is transient input and remains stored once in the existing ledger. Crash before commit produces neither; crash after commit leaves inventory + message together; lost reply retries the same accepted id. Where a producer uses a separate register operation, crash before post leaves an enumerable but unposted id and may safely wait for fresh evaluation; no exact body replay is claimed. Admission failure must be explicit before calling a publication managed. If registration is declined, baseline untracked posting is an explicit TTL fallback, not a partially managed guarantee.

### What persistence and bounds must mean

Protect the inventory with the same snapshot/recovery generation as its delivery ledger. Persist inventory + outcomes together in the relay's fresh-value snapshot. Add the root to `MEMORY_TYPES`, validate schema/version and sizes, and include it in diagnostics. Retain only ids until the ledger's own receipt/outcome and allowed retry horizon let them retire; do not add “shown” flags. If no stored-body replay exists, an orphan receipt does not create production work and need not be retained forever.

Concrete starting budget for the implementation to measure: 2,000 registered ids and 512 KiB serialized inventory per room, with a 200-id/64-KiB per-producer share and a bounded batch (e.g. 64 ids/64 KiB). These are **proposed admission limits**, not measured sufficient capacities. Include terminal/pending-intent overhead in the budget; reserve capacity for endings of already admitted ids. Refuse new managed registrations at saturation and report TTL fallback; never delete a current id to make room or pretend it ended. Coalesce replaceable fyi/notify state before admission. Do not promise every automatic notice fits. Test cleanup progress while at capacity.

Define a finite maximum managed publication/retry lifetime no longer than its delivery TTL unless a distinct user-approved policy changes it. GC only after no authorized publisher can retry the old generation/id, all required destination acknowledgements are committed, and no remaining ledger reference needs the suppression record. Recheck private epoch/generation/deadline on every retry so old replicas cannot extend the horizon by resyncing old records. Active conflicts may stay in slots longer; this does not create perpetual notification debt. Late source intents outside the supported horizon fall back to existing TTL rather than claim a fresh guaranteed ending. Outcome caps/TTL remain in force; inventory retention must close the late managed replay route separately.

This establishes atomic persisted snapshots and the repository's existing acknowledged-but-unsaved loss limits. If “durable” means survive **all replicas and relay crashing immediately after ack**, a persist-before-ack barrier/journal is additionally required in both relay and server adapters. Neither an inventory nor a full outbox can manufacture that guarantee from today's debounce. Do not promise it in stage 2 without implementing and testing it.

### When a body really is necessary

If the required guarantee is “after registration is durably accepted, the exact unposted notice will be published even if its process, slots, manifests and source disappear,” an id inventory cannot recover the payload. The body or equivalent complete deterministic rendering inputs must be persisted somewhere before that acknowledgement. An **immutable pending-publication record only** can do that; do not copy every already-posted message permanently. Retire pending payloads under explicit publication/terminal acknowledgement and the chosen save-before-ack contract, not merely a locally observed successful `PostResult` (`post.ts:69–72` does not expose `gone` distinctly). Preserve diagnostics for cap/size/refusal failures and bound payload admission separately.

The same tradeoff applies to a clearing fyi lost before publication. The smaller design fixes stale owed delivery and supports fresh reevaluation; it does not promise exact crash replay of that event. That difference must be an explicit release promise. The lead's preference for less state is consistent with solving the reported stale-delivery bug first.

### Projection extension

Keep source semantic authority in team, holder obligations in team and owner-delivery inventory in workers. Persist a minimal source transition containing destination room/generation, authorized lead/worker incarnation, exact ids, accepted source revision and terminal token. Persist destination registration before treating a projected post as managed; destination commit atomically registers/appends. Persist source terminal intent before handoff, then destination validates/adopts the authorized bridge and applies the same idempotent terminal transition. Acknowledge exact terminal revision; source retains it through the bounded retry period until that ack. New bridge takeover must explicitly adopt committed source state under both authorities. An older bridge must not overwrite a later destination terminal state or terminate a successor's ids.

There is no two-room atomic commit. Destination may temporarily owe the last committed notice while bridge/lead is absent. If a room is old or authority unavailable, do not copy raw team slots or infer a clear; use TTL. Exact remote authority verification/adoption is stage 3 design work and must be reviewed before claiming end-to-end projection support. A client-supplied team epoch compared to a local workers-room holder is not an implementation of it.

### Authority and lifecycle

- `hub-core/src/notice-lifecycle.ts` owns bounded canonical inventory in private hub memory and publishes a cloned diagnostic mirror (`noticeInventory`, schema version 1). It never restores authority from that mirror. Producer records carry the hub generation, authority name/session/principal/epoch, worker incarnation, revision, exact IDs, group/episode tokens, urgency, private worker dependencies and finite deadlines. No message body or receipt is stored there.
- `Hub.handle` gates the optional `notice-lifecycle` operation on the adapter’s authenticated selection. It checks current authority, room generation, writable connection, private live lease, epoch/principal/session, canonical participant mirrors and captured published manifest/claim/worker/contract-graph inputs. Inventory matching additionally checks producer incarnation, expected revision, exact IDs and episode tokens. Replicated records and client-supplied worker identity cannot authorize endings.
- Publication calls the existing ordered post path and commits its registration plus permitted predecessor endings in one Y transaction. Refusal changes neither inventory nor predecessor outcomes. Partial fyi retains notify; a complete clean publishes its clearing attempt before atomically ending registered predecessors. Explicit withdrawal remains silent. Direct `evaluated-clean` endings without the accepted clearing publication are refused.
- Requests are idempotent by operation digest/revision. Contradictory retries fail; exact accepted retries do not append, refresh timestamps or overwrite terminal outcomes. Open takeover explicitly transfers open entries; terminal IDs remain under their closed source and are never reopened. Registration cannot claim an existing untracked body or another producer’s ID. Accepted IDs cannot be resurrected through baseline post after ledger suppressor GC.
- `room-mcp/src/notice-lifecycle.ts` is the serialized proposer. Hub acknowledgements provide bounded inventory/delta inputs so the next proposal need not assume the Yjs mirror arrived first. This local cache is not a shared writer or receipt authority. Capability loss uses baseline TTL behavior; moved/unknown evidence never authorizes a terminal outcome.
- Conflict producers allocate random tokens for new slot, peer, possible-group and clear lifecycles, preserving legacy ids when no new managed episode exists. A changed worker ID creates a new subject episode even if bytes and conflict geometry match; unknown evidence retains the previous subject until evaluation completes. This prevents w1 retirement from consuming a same-tag w2 notice. Ordinary unchanged holder takeover preserves semantic identity.
- Managed group/peer publication and queued withdrawals run from guarded replay after a completed pass. Withdrawal proposals retain their captured input revision and episode. Missing contract publications preserve an unknown slot and its identity; explicit text-grant revocation is a separate positive transition. Missing neighbours, finished-but-resumable workers and legacy consolidation do not become retirement evidence.
- `worker-projector` invokes retirement only through the registry’s existing `ended()` rule (`retired` or `abandoned`), rechecking the registry revision, worker ID, sequence and originating instance before proposing. The hub captures worker IDs/principals from private reservation/acquire state at notice registration. A retirement proposal can affect only exact registered dependencies of that principal’s worker, even after a successor holds the name or the notice producer stops. Kept, stopped and resumed active records do not qualify.

### Bounds, failure model and rollout

The implemented admission ceilings are 2,000 IDs / 512 KiB per room, 200 IDs / 64 KiB per logical producer/worker incarnation, and 64 ending IDs / 64 KiB per request. Serialized accounting includes operation/terminal state, bounded key overhead and a 256-byte ending reserve for every admitted open ID. Reservations are consumed by endings; empty or already-ended fresh operations cannot grow history. Terminal metadata stays bounded for the hub’s lifetime. Registration may therefore fall back until restart. Explicit admission/batch-size fallback logs `notice lifecycle TTL fallback` and uses the unchanged baseline post; it does not consume managed predecessors.
