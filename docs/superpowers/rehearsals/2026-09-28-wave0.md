## 4. D5 binding check: a Codex thread in clone X binds to X's room — FAIL on 0.16.34 (open for wave 4)

The check used a `codex:codex-rescue` thread through the Codex plugin's shared app-server broker
(`app-server-broker.mjs`, codex plugin 1.0.6). The thread's cwd was `/tmp/room-w0-a`, and it called
`room_state` / `room_join where=local`. The app-server (pid 57133) had been started by the broker with
cwd `/tmp/room-redesign`, the lead's checkout. Its Room MCP child (pid 57270, bundle 0.16.34) logged:

```
08:52:19.022Z pid 57270: local room local/room-redesign/redesign-wave0: joined relay on 127.0.0.1:49146 (pid 95145)
08:52:19.099Z pid 57270: joined as rohanz+codex (remembered name rohanz is in use by another session)
08:52:19.383Z pid 57270: rohanz+codex joined local/room-redesign/redesign-wave0 (clone /private/tmp/room-redesign)
```

The thread printed `pwd` = `/private/tmp/room-w0-a`, yet it joined the lead's room with the lead's clone. So the
2026-09-26/27 incident is not explained by pre-0.16.24 bundles alone: on 0.16.34 the MCP binds to the
app-server's cwd, not the thread's. The MCP process was still alive after the thread finished, which
reproduces D5's lingering process too. This answers registry open question 4 (negative), and wave 4 must fix it.
`boundSession()` (wave 0) is not wired into join yet, so this wave cannot change the result.
