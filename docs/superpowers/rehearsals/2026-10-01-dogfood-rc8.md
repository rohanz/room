## New findings

1. **medium (process) — a doc summary invented the host feature the brief relied on.** The lead read
   the Claude Code env-var page through a summarising fetch. It reported a
   `CLAUDE_CODE_SUBPROCESS_ENV_KEEP` allowlist "since 2.1.283" and said `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` applies only to Bash.
   Neither is true: there is no KEEP, and SCRUB strips only credentials, from Bash, hooks and MCP
   servers alike. The envfix worker caught it with an end-to-end `claude -p` probe and a string
   search of the 2.1.286 binary, then asked before building on it. Read host docs raw (`curl … .md |
   grep`), and have a worker prove a host feature end to end before designing on it.
2. **low — the migrated room's recent bus is 0.16 history.** Seven of room_state's ten recent lines
   were 2026-09-28 messages carried over from the 0.16 rooms (`registry-review`, `reporooms-review`,
   "moved the base to 422c74e1a5"). They were stale before the batch began and pushed out the
   current batch's lines.
3. **low — room_state repeats "nothing owed for an unresolved name (rohanz on redesign): ask them to
   rejoin"** and a second such line for `room on redesign-wave0`, on every call. Nothing is owed and
   there is no one to ask.
4. **low — a false "not in this worktree" warning.** The envfix spawn reply warned `.room/workers
   named in the task is not in this worktree (untracked or ignored in the lead clone)`. The task only
   described where worker worktrees live.
5. **low — duplicate possible-conflict notices.** Collecting bgexit and lowfix into the lead tree
   while envfix held a claim on `workers.test.ts` gave two identical "POSSIBLE conflict on
   packages/room-mcp/test/workers.test.ts" notices with different ids. One "cleared" notice
   followed after envfix finished.
6. **good — what worked.** Three parallel workers, one real design question answered in-thread
   (envfix: the briefed host variable does not exist; here is a verified alternative), claims
   without prompting, one clean combined preview, and one collect per worker cleaned up its worktree,
   branch and logs. The workers' own end-to-end probes (real `claude -p` and `codex exec` with a probe
   MCP server) are the evidence for fix 2.
7. **process — the lead edited source while its own full suite ran.** The round-2 fix was made
   while the round-1 suite was running (3,247 passed, but on a half-changed tree), so the suite was
   run again on the final commit. The rc6 lesson still applies to the lead itself.

## Outcome

Astra: 2, 1, 0 must-fix (SHIP at round 3). Round 1: the worker env file could be redirected through a
linked `.room` or `.room/workers`; a follow-up to a worker that had reported once got no
background-work warning. Round 2: the log was found by `dirname(worktree)`, which is wrong for a
worker whose checkout is outside `.room/workers` (the existing log tail already read
"(log unavailable)" there); records now carry their log path. Each fix has a test that fails without it.
Typecheck, knip and build:plugin clean. A full suite on the final commit had one failure under load
(average about 10): `workers.test.ts` "keeps ports distinct across independent lead registries",
where one of two concurrent spawns produced no launch. It passed 5/5 alone and in two whole-file
runs (147/147), and a fresh full suite on the final commit passed: 289 files / 3,248 tests.

The rc6 and rc7 fixes held in use: room choice, notices, worker linking, the carry note, claim
summaries, preview output and settle. Two did not, both diagnosed and fixed here: workers still could
not trust the repo's suite, and collect did not wait for an exiting worker. The rc8 fixes themselves
(the foreground rule and its detection, the clean worker shell, session-scoped status, activity
labels, the collect wait) are covered by tests; the clean worker shell was also proved end to end on
both hosts by the envfix worker. The next batch, led on rc8, is the first that can feel them.
