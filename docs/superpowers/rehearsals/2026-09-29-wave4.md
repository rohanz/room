## 1. Two sessions in one checkout — FAIL (wording)

`s1` and `s2` both join `/private/tmp/rh4-s12` with `ROOM_NAME=ann`. `s2` becomes `ann+claude` ("remembered name ann is
in use by another session").

**Exactly one publisher.** The publisher lease file lists only `s1`:

```
publishers/1a7f40d6….json: {"worktree":"/private/tmp/rh4-s12","holder":{"pid":65397,…,"sessionId":"rh4-s12-rh4-s12-1",…},
  "attachments":{"local/rh4-s12/main":"ann"}}
ann:        manifestHead={…,"fence":"3755275519524864","coverage":{"kind":"all"},…}
ann+claude: manifestHead={…,"fence":"3755275519524865","coverage":{"kind":"none","reason":"not-publisher"},…,"publisher":"ann"}
```

**`room_state` does not say why.** The non-publisher's `room_state` gives no reason. The only trace is the
participant line:

```
s2: room_state →
    local: nothing leaves this machine
    …
    participants (2 active):
      - ann's agent · claude: another session in this checkout · working
      - ann+claude · agent of ann · claude (you): no upstream, no task declared · working
```

The team room is the same. Its first line, "team room: sharing the full text of files you change with 0 people",
reads as if this session publishes its own files. The reason appears only in these places:
- the one-time team disclosure on the first reply: "note for your human: This checkout's file text is published by ann
  and follows ann's sharing settings (full). …";
- `room_share`: "sharing: This checkout's file text is published by ann and follows ann's sharing settings (full).";
- `room_done` and `room_join`.

**Cause:** `room_state` builds its header without `publisherLine(s)`. See `packages/room-mcp/src/tools/scope.ts:106`,
and `:156-158` for the per-participant line. `publisherLine` (`tools/share.ts:13`) is used only by `share.ts`,
`workers.ts:98` (`room_done`) and `join.ts:44`.

The first run gave the same shape (rev 1→2→3, one `pushed:ann:c132ca46…:d0e09055…`).

In both rooms:
- every `git` write is from the publisher, under its epoch;
- `ann+claude…-4` never get a `git` key;
- the team room has exactly one `pushed`.

**A note on the count.** A commit plus its push gives one rev bump per git fact:
- the commit moves `head` (rev 5);
- the push moves `base` and writes `pushedPending` (rev 6);
- a third, same-rev write clears `pushedPending` once the hub accepts the post (§B2 step 6, `roomd/src/index.ts:797-802`).

That is one writer and one notice, not the literal "one `git` update" of the plan's sentence.

## 4. Name leases — PASS

**Team room** (`s4.mts`): clones `t4a` and `t4b`, the same login `ann` and the same explicit tag, so the hub arbitrates
across clones. The whole sequence ran twice, with tags `x` and `y`, with the same result. The run below is tag `y`.

**4a. kill -9 the holder.** A second session keeps trying the same name about every 4.4 s:

```

B#1:  +0.4 s  error: not in a room. Room could not join: ann+y is held by another session; use room_join.

B#11: +44.5 s  you: ann+y · agent of ann · y · claude in local/origin/main
HOLDER: {"sessionId":"rh4-s4-B","pid":3709,…,"epoch":3755275676811278}
```

The server log reads: `lease 3755275676811277 on ann+y expired` → `granted ann+y to rh4-s4-B at epoch
3755275676811278`. Tag `x` gave 45.0 s and epoch …274 → …275.

**4b. A late writer.**
- B (the holder now) gets SIGSTOP. C takes the name after 44.4 s, at epoch …279.
- While B is stopped, `api/models.py` in B's clone is changed, so B's watcher fires as soon as B runs again.
- Then B gets SIGCONT, and B calls `room_scope`, `room_send`, `room_state` and later `room_claim`.
- The observer records every write to the `participants`, `manifestHead`, `manifest` and `scopes` keys of `ann+y`.

```
B: room_scope → [room] another session now holds ann+y; rejoin to take a new name. Coordination is paused; your files are unaffected.
                not done: room_scope writes under your name, and coordination is paused; retry once it resumes.
B: room_send  → [room] another session now holds ann+y; … not sent: hub unreachable
B: room_state (+25, +35, +45 s) → [room] another session now holds ann+y; rejoin to take a new name. …
B: room_claim → … not done: room_claim writes under your name, and coordination is paused; …
DOC: writes under ann+y since SIGCONT (0)
DOC: end: git.fence=3755275676811279 head.fence=3755275676811279 snapshot fenceValid=true; scope undefined; late note on the bus: false
```

In the tag-`x` run, the first reply 1.5 s after SIGCONT read "[room] the name lease on ann+x lapsed; coordination
paused while it is re-acquired. …" instead, which is also a paused state.

The old holder's late writes were not rejected by readers. They were never attempted: zero doc writes, and only
C's epoch appears in `git`, `manifestHead` and the manifest keys.

**Wording nit.** While the name is taken, `room_send` says "not sent: hub unreachable", but the hub is reachable. The
constant comes from `room-mcp/src/post.ts:10` (and `hub-client.ts:53`).

**Local room** (`s4local.mts`):
- While A (`ann+x`) lives, a worktree session asking for `ann+x` gets "ann+x is held by another session in this clone
  (pid 11780). Room tries again on the next Room tool call …".
- After `kill -9` of A, which was also the relay owner, a new session got `ann+x` 7.2 s later. The epoch went
  …025536 → …802752: a new relay incarnation, so a higher `I`.
- No TTL wait here. The relay ends a dead local holder at once (hub §2.3); the 7.2 s is relay takeover and the 5 s
  settle window.

## 5. Resume acceptance (D4) — PASS

`s5.mts` drives the real paths. The lead (Claude env, local room) runs `room_spawn tag=rw host=claude carry=false`,
and the fake `claude` gets `--session-id 89dd91e7-…`.
- In mode `first`, the fake starts the bundle as its MCP, calls `room_done`, and prints `system/*`, `assistant` and
  `result`.
- Each follow-up is a real `room_send type=question to=lead+rw`, which resumes the worker (`claude -p --resume
  89dd91e7-… …`). The fake's mode is then `a`, `b` or `c`.

```
after first run: rw (claude, done, 0m) … · rh4 first run: nothing to change
(a) system/hook_started, system/hook_response, system/init; exit 0
    run 2 mode=resume promptMsgIds=["m_mum62s5w4yvvtb"]  → status failed, note "exited without room_done"
    seen:lead+rw = {}                                       (no receipt)
(b) system/init, assistant{session_id: 89dd91e7-…}, result success; exit 0
    run 3 mode=resume promptMsgIds=["m_mum62s5w4yvvtb","m_mum62upohsakhj"]   ← (a)'s message was still owed
    seen:lead+rw = {"m_mum62s5w4yvvtb":{"s":"89dd91e7-…","via":"prompt"},"m_mum62upohsakhj":{"s":"89dd91e7-…","via":"prompt"}}
    status failed, note "exited without room_done"          (a clean resumed exit without room_done is not done)
(c) stderr "No conversation found with session ID: 89dd91e7-…", result error_during_execution is_error num_turns 0; exit 1
    run 4 mode=resume promptMsgIds=["m_mum62x8o5klmx4"]
    workerView note: "its retained conversation 89dd91e7-… no longer exists; the message stays owed"
    lead's room_wait: "worker rw failed: its retained conversation 89dd91e7-… no longer exists; the message stays owed"
    receipt for m_mum62x8o5klmx4: null
```

**Side finding: the failure text quotes the previous run.** After (a), the lead was told:

"worker rw failed: exited without room_done; Done. marked done; released 0 claim(s), scope cleared. … room-mcp:
stopping: stdin closed …"

That is run 1's `room_done` text. `postObservedFailure` takes `workerLogTail(logFile)` over the last 64 KiB of the
whole shared log, not from `run.logStart` (`room-mcp/src/worker-registry.ts:712`; `worker-process.ts:110`). The note
is correct; the appended tail tells the lead the worker reported done.

## Other finding: `room_state` shows a frozen base

Every `room_state` "you: … (base X)" line reads `meta.base` (`tools/scope.ts:120`). R3 says `meta.base` is deleted.

In the team room, `meta.base` stayed `c132ca46c0…`, the base at the first join, after two commits and pushes had
moved every `git.base` to `5b61d67967`. Every session, publisher included, kept showing `base c132ca46c0`. The local
room showed the same stale value after the commit.
