# 0.17.1 local reproductions (2026-10-03)

Standalone clone, Node 22.14.0. These are synthetic, socket-free measurements, not a repeat of the overnight Codex rehearsal. All commands ran in the foreground.

## X1: graph parsing

`graph-responsiveness.test.ts` generates and commits 3,000 Rust files (40 functions per file), uses warm immutable baseline reads to isolate parsing, probes the real claim handler every 10 ms, calls the real impact handler during indexing, and awaits completion. Before the fix it failed its 100 ms lag bound: indexing 3,415 ms, max lag 255 ms, impact 3,127 ms. The claim itself did no coordination work because the session was alone; timer lag measures how long a queued request could be blocked.

Root cause: `runRefresh` parsed both private and public versions synchronously on the MCP thread (and parsed baseline contract signatures there too). Eight async refreshes could resume together. Existing 50 ms yields happened after parsing, so they could not bound a single parse or the group of resumed refreshes. `room_impact` additionally awaited the entire build.

After: indexing 1,834 ms, max lag 2 ms, impact <1 ms, 181 claim probes completed, all 3,000 files indexed. Equal text versions are parsed once within each worker job. Graph mutation and snapshot publication remain on the MCP thread with 20 ms yields. `parse-worker.test.ts` checks Rust/Python grammar loading and cancellation. Existing graph tests pass. A temporary esbuild bundle using the plugin's exact banner and grammar layout also parsed Rust successfully; no plugin assets were rebuilt.

Worker threads are cleaner than smaller slices here: slices cannot interrupt one expensive tree-sitter query. One lazily started thread per index owns its runtime; stop terminates it and rejects outstanding requests. The existing eight-file queue bounds requests. No host features were changed.

Lead index inheritance is deferred: room graph snapshots contain capped edges, not complete per-file definitions/references/signatures. Reusing them would lose import resolution and contract baselines; a safe cross-process cache needs immutable blob keys, coverage/fence rules, bounded storage and invalidation. That is larger than this fix.

## X2: conflict reconcile fan-out and retries

Two failing regressions in `conflict-set.test.ts` prove the cause. Six participants, each publishing only its own disjoint file, produced 53 full runs across ten publication rounds (9/9/9/8/9/9 per participant). A check repeatedly receiving triggers ran nine times before `flush` returned, despite the nominal two-attempt limit.

Root cause: broad observers treated status, publication clocks and graph timestamps/edges as conflict changes, then traversed every comparable pair. The guard compared all room claims and a serialized full peer graph during each pair check. The `rerun` path recursively invoked another two-attempt reconcile, so the two-attempt bound was not an actual bound. Derived conflict writes themselves were not directly observed; input publication and graph-provenance churn supplied the triggers.

Change: coalesce meaningful triggers once per event-loop turn and through one debounce timer, and ignore clocks and unrelated edits. Check at most twice, then schedule one later pass for continued changes; the periodic pass rearms only after a pass completes. An earlier version also cached checked pairs; review found its invalidation repeatedly wrong, and measurement showed coalescing alone keeps idle work at zero (ten disjoint bursts: 0 reconciles, 0 comparisons), so the cache was removed. Unknown evidence keeps its retry deadline. Revocations remain synchronous.

After: zero runs for all six participants across ten disjoint publication rounds; adding a real overlap schedules the affected participants while the other four remain idle, and counts stay flat afterward. `flush` returns after two checks under sustained triggers. All 76 conflict tests pass, including coverage loss, grant revocation, carried-baseline degradation, overlap transitions and graph provenance. Typecheck and knip pass. Iteration counts are the local CPU proxy; the six-process live CPU measurement is not reproduced here.

## X5: synchronous watcher scan on rejoin

`rejoin-responsiveness.test.ts` commits 8,375 files under nested crate-shaped folders, starts and stops roomd, then starts it again with a fresh in-memory provider and the same checkout/name. No graph is started. It counts synchronous lstat/realpath/stat calls and samples a 10 ms heartbeat. Git auto-GC is disabled in the fixture so maintenance cannot race cleanup or leave background processes. Native watching failed with EMFILE in this environment; the large-tree measurements use Chokidar polling.

The original watcher failed the regression: first join 10,166 ms, second join 10,128 ms, maximum lag 477 ms, 463,893/463,891 synchronous filesystem calls. These are instrumented measurements (the spies themselves add overhead). Root cause: Chokidar's synchronous ignore predicate called `isSafeRoomPath` multiple times per path, re-lstatting and re-realpathing every ancestor, then startup synchronously re-statted the whole watched set to count files. It was the full re-watch, independently of graph parsing or Yjs history replay.

The predicate now uses lexical containment, existing ignore rules and Chokidar's supplied stat. `followSymlinks: false` prevents traversal through links; change handling and disk publication retain their filesystem containment checks. Counting during the existing scan removes the extra whole-tree stat pass, so the scan uses Chokidar's asynchronous traversal rather than Room's synchronous per-path probes.

After, with the same instrumented fixture: first join 655 ms, second join 596 ms, maximum lag 28 ms, seven/five synchronous filesystem calls. The regression and seven related roomd suites pass (96 tests), including symlink refusal, ignored trees, startup errors and publication races. The full tool suite passes (118 tests). Final typecheck and knip pass.
