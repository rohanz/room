# Dogfood: leading the rc7 batch on Room 0.17.0-rc6 (2026-10-01)

The rc7 batch (fixes for the rc6 dogfood findings) was led the same way as rc6
([2026-10-01-dogfood-rc6.md](2026-10-01-dogfood-rc6.md)): a Claude Code session loading Room from
this checkout (`--plugin-dir plugins/room`, 0.17.0-rc6) in the clone's local room, with five Claude
workers (claude-opus-5-5, effort high, `carry=false`). Reviews ran outside Room (direct read-only
`codex exec`). Same severity scale as rc6.

## Findings

1. **confirms rc6 #1 — still in the 0.16 branch room.** room_state at the start of the batch:
   `room: local/room-redesign/redesign-wave0`. rc6 itself did not migrate the remembered choice, so
   this batch, which fixes it, ran in the old room.
2. **confirms rc6 #4 — five `carry=false` spawns, five identical "3 uncommitted changes ... not in
   this worktree" notes.**
3. **confirms rc6 #9 — the first room_state of the session was dominated by the rc6 workers'
   `finished:` reports** (three of ten recent lines, each 600–1,100 characters).
4. **low — the lead's own line shows a stale task from an earlier session.** room_state lists
   "rohanz's agent (you): done: 0.17.0-rc2 fix batch finished at d841e19 ... (15:17)", which is the
   status of a lead session from the previous day, carried by the same participant name. A new
   session should start with no task declared, or mark an inherited status as earlier.
5. **low — worker activity often reads "running env".** Claude workers run tests as
   `env -u ROOM_TAG ... npx vitest`; rc6's safe activity labels reduce any env-prefixed command
   to "env", which says nothing. The command after the `env` assignments/flags would help.
6. **confirms rc6 #6 — claim summary still collapses** (`rohanz+migchoice: 3 claim(s) · packages/room-mcp/`).
7. **medium — a Claude worker ended its turn waiting on its own background tests.** The preview
   worker started its suites as a background Bash task, wrote "I'll be notified when the suites
   finish", and ended its turn; in `claude -p` that ends the process, so it "finished: ended without
   a report" with the work untested. A `room_send` resumed it. The worker brief (or the worker
   launch) should say that a headless worker must run tests in the foreground, or Room could keep a
   worker alive while it has background tasks running.
8. **medium — workers cannot trust the repo's own suites in their environment.** Two workers
   reported 17–25 failures in `workers.test.ts`/`tools.test.ts` that a clean HEAD worktree shows
   too ("this worker run was collected", host detected as codex), so each compared against HEAD by
   hand. A worker inherits Room's worker variables beyond the three the repo's test command
   unsets (`ROOM_TAG`, `ROOM_OWNER`, `ROOM_SERVER`), and identity-sensitive tests read them. The test
   setup should clear every `ROOM_*` worker variable, not rely on the caller.
9. **low — "room_collect waits up to 15 s" was not true for one worker.** The completion said
   "its process is still exiting (room_collect waits up to 15 s for it)"; collect a few seconds
   later answered "skipped preview: running", and worked after a further 20 s wait.
10. **good, and the real story behind rc6 #8.** The first preview after five workers finished again
   said all five "moved during the preview". The rc6 message names every participant in the
   preview, not the ones that moved; the one that moved was the worker resumed for a follow-up,
   whose exit ended its name lease during the preview. A finished worker read from its trusted
   worktree now never counts as moving (its exit changes only its overlay), the message names only
   the movers, and a bounded 12 s settle covers running ones.
11. **verified — fix 1 on this repo.** A fresh worktree of this checkout, linked by the new step,
   took 38 ms: 241 entries, `@room/shared` and `@room/roomd` resolve to the worktree's packages,
   `yjs` and `vitest` to the lead's install, and removing the worktree left the lead's install intact.
   The leading session itself ran the rc6 bundle, so this batch's workers still had no links.
12. **process — review.** Astra round 1 found three must-fix items (a workspace missing from the
   worktree linked back to the lead; a discovery failure with no names gave no warning; a finished
   worker resumed during a preview stayed exempt from its freshness check), round 2 one (workspace
   globs with braces silently matched nothing). All four were "the fail-safe path is silent" or
   "the exemption outlives its premise": brief fail-safe work with "every path that does not link
   must warn" up front.
13. **low — waiting is awkward for a headless lead.** Between worker reports the lead's only bounded
   wait is `room_wait` (at most 100 s), which also served as the timer for the full suite and the
   reviews: foreground `sleep` is refused, and a Monitor `until` loop needs an approval a headless
   session cannot give. That works, but room_wait reporting "nothing new" 20 times is noise.

## Outcome

Astra: 3, 1, 0 must-fix (SHIP at round 3). Full suite 288 files / 3,222 tests; typecheck, knip and
build:plugin clean. Did the fixes make leading smoother? This session ran the rc6 bundle, so it met
every rc6 finding again (the branch room, the repeated carry note, the collapsed claims, the long
recent lines, the "moved" preview). The fixes are verified by tests and, for worker linking, on a
real worktree of this repo; the next batch, led on rc7, is the first that can confirm them in use.
