# Room 0.17.5 release-readiness review

**No blocking code defects found in the review-hold feature, but 0.17.5 should not be published yet.** The release record is still open, and there is no full-suite or CI evidence for the release commit. I executed no tests; this is source and record inspection only.

## Findings, in priority order

### 1. Release gate: the 0.17.5 record is incomplete (blocks publishing, not the code)

- `docs/superpowers/rehearsals/2026-10-05-0175-release.md:3` says "packaging and installed-plugin verification in progress". README:84 already links to it as the release record.
- The only evidence for the release commit is typecheck, build and 271 targeted tests across six files (`0175-release.md:13`). Full CI is claimed only for base `b454fb7f` (`:5`).
- The `packages/server/test/hub.test.ts` teardown change ships in this diff, but no server suite is among those six files. Whether base CI covered it is not stated.
- 0.17.4 set the bar: release-commit CI plus an installed-plugin smoke (`0174-release.md:27-35`). The 0.17.5 record needs the same, plus the installed-bundle hash check on both hosts.
- I could not verify the bundle hash `26178267…` or the hooks.json hash; I have no hashing tool.

### 2. Discard now takes the collection lease, contradicting "Ordinary collection is unchanged" (medium)

- Previously `if (a.discard) return roomCollect(a)` bypassed the lease (diff line 151). Now every call goes through `withCollectLease` (`collect.ts:774`).
- That lease waits 30 s and then fails with "another collection is in progress" (`worker-registry.ts:203, 738-747`).
- An apply can hold the lease for a long time: each worker can wait up to 15 s twice (`collect.ts:455, 501`).
- **Reproduction:** eight workers, several still exiting. Session A runs `room_collect()`. Session B in the same checkout runs `room_collect(tag=x, discard=true)`. B previously proceeded; it now errors after 30 s.
- A long discard (stop escalation) likewise blocks applies.
- This is needed to gate discard, and it is safe, but it is an undocumented behaviour change. I found no test for a discard contending for the lease. Fix the CHANGELOG wording at minimum.

### 3. A hold from the wrong checkout succeeds silently (medium, usability)

- The hold is keyed on `realpath(session.dir)` (`collection-review.ts:13`, `collect.ts:776`).
- The success text says only "for this checkout" (`collection-review.ts:46`). `status()` prints no path either.
- **Reproduction:** a reviewer running as a Room worker, or any session in another worktree, calls `checkpoint="hold"` and gets "hold active". The lead's `room_collect()` in the real destination is not blocked.
- The skill and `reference.md:67` warn about this, but the tool reply gives no way to detect the mistake. This is the exact failure the feature exists to prevent.
- Suggested fix: print the canonical destination path in the hold and status replies.

### 4. A stuck hold has no documented recovery (medium-low)

- Ownership is the bound host session ID, re-evaluated on each use (`binding.ts:2, 51`).
- After a Claude `/clear`, or for any unbound session (synthetic `mcp:<pid>:<startTime>`), an MCP restart changes the owner.
- The token is printed once. A repeat `hold` returns "already active" without it (`collection-review.ts:41`). Holds never expire.
- **Reproduction:** reviewer holds, the context compacts or the session is cleared, and the token is lost. Every apply, copy and discard for that checkout is blocked indefinitely.
- The only exit is deleting `<registry>/collection-reviews/<hash>.json` by hand. Normal status does not print that path; only the corrupt-state error does (`:20, :26`). `reference.md:69` does not describe this.
- Corrupt state has the same problem: it fails closed, including for `release`, with no tool path out.
- Suggested fix: document manual removal as the human's escape hatch.

### 5. Unbound sessions sharing one MCP process share an owner (low, unverified)

- With no binding, the owner is the process's synthetic ID (`binding.ts:51`, `collect.ts:779`).
- If one Codex app-server MCP process serves both a reviewer thread and a lead thread, the lead's plain `checkpoint="release"` would match the reviewer's hold.
- I did not confirm whether the app-server shares an MCP process across threads. Worth one check before relying on holds under the Codex daemon.

### 6. Minor

- A multi-line `reason` can fake extra reviewer lines in `status()` (`collection-review.ts:32`); cosmetic.
- Moving or renaming the checkout silently drops the hold, because the key is the path's hash.
- Retired-worker cleanup (`retire.ts:78`) and resumed-discard recovery (`worker-registry.ts:1057-1075`) run without the gate. This matches the documented limits (`reference.md:69`).
- A local agent can delete the hold file; this is documented as "not a security boundary".

## What held up

- **Force bypass:** `assertClear()` runs before `roomCollect` for every non-checkpoint call (`collect.ts:784`). Nested discards recurse inside the lease.
- **Argument validation:** unknown keys, mixed checkpoint and collection arguments, and token format are rejected before the lease is taken (`:765-771`).
- **Token privacy:** only the token's hash is stored, and status omits it.
- **Concurrency:** read-modify-write happens under the cross-process lease with an atomic rename.
- **Aliasing:** symlinked paths resolve through realpath, the same key the lease uses.
- **Version consistency:** both manifests, the marketplace entry, `HOOKS_VERSION`, the doctor fixture and the bundled server all say 0.17.5, and the bundle contains the hold code.

## 0.17.4 records

# Follow-up: test corrections and documentation

**No remaining code blockers.** Both test changes model the real APIs rather than hiding a defect, and the documentation addresses the findings I marked as needing text. Full CI on the release commit is still the publication gate; I ran nothing, this is source inspection only.

## Test change 1: abandoned-discard replay fixture

This is a correct fixture fix.

- Discard replay deliberately bypasses the injected liveness probe for a launch that has only a PID and no verified process identity. It calls the real `pidAlive(launch.pid)` and keeps the worktree if that PID exists (`worker-registry.ts:1027-1030`).
- The old fixture used bare `pid: 201`, so the outcome depended on whether the runner happened to have a PID 201. That matches the reproduced failure.
- With a `process` identity supplied, the host goes through `this.alive(identity)`, which is the injected `'dead'` probe (`:1023, :1031-1044`, `:363`). Using `process.pid` proves the fixture no longer depends on real PID state.
- The assertions are unchanged: all five discard steps, worktree removed, patch published (`worker-write-paths.test.ts:211-214`).

One optional gap: the keep-the-worktree guard for a live PID-only launch now has no explicit test in this file. The reproduction shows it works, but a small test asserting retention would pin it down. The neighbouring collect test still uses bare `pid: 201` (`:221`). I did not see collect recovery consult the launch PID (`:1182`), so it is probably not flaky, but I did not trace it fully.

## Test change 2: contract re-entry

This correctly models `reconcile()`, with one caveat.

- `reconcile()` returns early by awaiting an in-flight pass if one is running (`conflict-set.ts:461`). It caps itself at two attempts, then schedules a debounced follow-up after returning (`:466-477`). An input change during a pass only sets `rerun` (`:326`).
- So "the notice exists the moment `reconcile('re-entry')` resolves" was never guaranteed. The test's own mutations at lines 1393-1397 can start a pass that the explicit call merely joins.
- The new `vi.waitFor` keeps the same assertions: conflict status and epoch, exactly two accepted notices, two distinct IDs, and the changed signature text.

The caveat: `toHaveLength(2)` inside `waitFor` passes as soon as the count reaches two, so a late third duplicate notice could be missed. Nothing in the source suggests one occurs, and the old test had the same blind spot for anything arriving after return. A short settle followed by a re-assert would close it; not a blocker.
