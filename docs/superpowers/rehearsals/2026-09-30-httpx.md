## Findings

- **H1 (high).** `room_preview_merge(people=["ana's agent","ana+issue2","ana+issue3"], run=…)`: the lead named
  itself by display name. `files.ts:261` maps names only through `fullName`, which resolves worker tags, not
  "X's agent", so "ana's agent" became a separate participant with no manifest record. `combined-tree.ts:218-229`
  then deletes each path whose version is unknown for *any* participant, so every path left the tree: "final
  combined tree: 0 path(s) applied … ran … passed". The check ran on the base and reported a pass. Fix both: resolve
  display names (and refuse unknown names) as `room_send` does, and drop only the unknown participant's side of a
  path, not the path; do not run or report a check on an empty combined tree.
- **H2 (medium; partly this setup).** `worker-config.ts:113-116` starts Claude workers as `claude -p …` with no
  `--plugin-dir`, so they load whatever Room is installed for Claude Code, not the lead's. A lead on a newer plugin
  gets workers the room refuses. Pass the lead's plugin root (or refuse to spawn on a version mismatch with a
  plain message).
- **H3 (medium).** Resume is undiscoverable. Neither `room_send`'s description ("Ask an agent (to), answer
  (inReplyTo), or post a note") nor the room-workers skill says that a message to a finished, uncollected worker
  resumes it. The lead worked around collect (plain `git apply`) to keep a worker, then started a new one.
- **H4 (medium).** A lead that applies worker output outside `room_collect` keeps drawing conflict notices and
  `[interrupt]`s against its own finished workers (11 in 2.5 min). Room could treat a lead's workers' stale
  claims as the lead's, or drop claims when a worker reports done.
- **H5 (low).** Two workers sharing one worktree (`room_spawn dir=`): discarding one removes the worktree, the
  other's registry entry then says it has uncommitted changes and cannot be discarded.
- **H6 (low, wording).** ben's agent read ana's scope + one claim as "a claim on all of httpx/".
