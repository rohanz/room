# Soak test: Room 0.17.0-rc3 on staging, 2026-10-01

Three hours of eight simulated participants against the staging server, with one machine restart at minute 90.
Harness: [`scripts/soak.mts`](../../../scripts/soak.mts) (rerunnable: `npx tsx scripts/soak.mts run`, then
`npx tsx scripts/soak.mts report`). Start 2026-09-30 22:36:15Z, restart 00:06:26Z, end 01:36:15Z, post-soak idle
samples to 01:42Z.

## Setup

- **Code.** `redesign` at `970e37a` (rc3), clients run from source (`joinSession` + `createTools` from
  `packages/room-mcp/src`, through `npx tsx`), one process per participant.
- **Server.** `room-rohanz-staging` (machine `82de15a703de48`, sin, shared-cpu-1x, 512 MB), image `rc3`,
  `NODE_ENV=staging`, `GITHUB_CLIENT_ID=fake`, `ROOM_TRUST_PROXY=true`, fresh volume. Synthetic data only.
- **Participants.** Fake logins `soak-a` … `soak-h` (plus `soak-observer`, which syncs both rooms read-only for
  the metrics and never joins). Rooms `github.com/soak/alpha` (a, b, c on `main`; d, e on `feature-x`) and
  `github.com/soak/beta` (f, g, h on `main`): local repos whose origin URLs carry those names and never fetch.
- **Load per participant, with jitter.** One message every 30–90 s (50% addressed questions, 30% addressed notes,
  20% broadcast notes), each question answered after 3–30 s. Deterministic ids: a refused post retries the same
  id every 5 s for up to 5 min. 10% of posts are sent a second time under their id. Claims on line ranges of a
  file shared with a neighbour every 1–3 min, held 30–120 s while the range is edited, then released. A file
  edit every 20–60 s, 8% of them a 100–500 KB file. A disconnect every 10–20 min lasting 5–75 s. One
  leave-and-rejoin under the same name. The inbox is drained through the session's ledger every 5–15 s, and
  every committed batch is logged as a delivery.
- **Metrics.** Every 10 min over `flyctl ssh console` (read-only): the server process's VmRSS/VmHWM and CPU
  ticks from `/proc`, `du /data` and MemAvailable. From the observer: room document size, live leases,
  presence, bus and mail. Plus `/health` every 10 s and `flyctl logs --no-tail` (every 10 min, and every 60 s
  from 22:48Z, since one fetch returns only the last 100 lines). The admin inventory answered
  `403 soak-observer is not in ROOM_ADMINS`; secrets were left alone and `du` used instead.

## Findings

1. **CPU throttling on shared-cpu-1x (blocks a busy trial on the current VM size).** Server CPU rose steadily
   with the bus, from 1.9% of a core (bus 250) to ~10% (bus 2,000–2,650), and stayed there after the restart
   reloaded the same bus. shared-cpu-1x guarantees only a small baseline share and lends burst credit above it.
   After about 2.5 h of 8–11% the credit ran out. `/proc/stat` steal time since the restart was 1,899 s of
   5,870 s (32%); the stall window lasted about 2,040 s, so the guest got almost no CPU in it. With CPU
   withheld, health checks timed out, renew replies were late enough that short disconnects lost their epoch,
   expiries ran up to 60 s, and reconnects took up to 310 s. Correctness held: no message lost, no counter
   reused. `deploy/fly.toml:36` uses the same size in production. Candidate costs, not isolated:
   - `admit()` runs a full `trim()` on every addressed post (`packages/shared/src/delivery.ts:215`): 5.1 ms at
     2,000 bus entries on an M-series core (1.3 ms at 250).
   - The hub's 1 s tick re-scans the whole bus whenever any member update has arrived
     (`packages/hub-core/src/hub.ts:714`, `:749`).
   - The identity guard applies every member update to a shadow doc.
   This harness is chattier than real agents, so take it as an upper bound, but the slope matters: CPU grows
   with bus length up to `BUS_KEEP` 2,000 per room. Options: a larger VM (shared-cpu-2x or performance), or make
   trim and the re-assertion scan incremental.
2. **Native memory growth (risk on 512 MB).** On Linux the growth is anonymous memory: RssAnon 207 MB,
   RssFile 57 MB at minute ~165. A local rc3 under the same load with LevelDB, with a GC forced every minute,
   held 21–37 MB of heap and 4–15 MB external while RSS reached 300–350 MB (macOS). There, `vmmap` showed
   ~6 MB of live malloc allocations next to ~75 MB of freed small-malloc pages still resident. So freed native
   memory is being retained, not live objects. On Linux the likely culprit is glibc arena fragmentation under
   LevelDB's threadpool I/O. Not confirmed: Docker was not available, and changing staging's environment was
   out of scope. Suggested next steps: a staging run with `MALLOC_ARENA_MAX=2` (or jemalloc) and a 12–24 h soak
   to see whether it plateaus. Separately, `Dockerfile:26` runs the server under the `tsx` CLI, which keeps a
   48 MB wrapper and a 16.5 MB esbuild process resident. Running `node --import tsx` directly, or compiled JS,
   saves about 64 MB of the 512 MB.
3. **Idle RSS and the startup stored-inventory scan (the known note).**
   - **Staging.** Untouched before the soak (empty volume, hours idle), the server process idled at 100 MB
     VmRSS (HWM 109). The machine's node processes totalled ~165 MB with the wrapper (48 MB) and esbuild
     (16.5 MB). The 149 MB figure matches server plus wrapper.
   - **Local, rc2 vs rc3.** Both idle at 97–98 MB on an empty volume. With 39 MB stored, rc3 idles at 162 MB
     against rc2's 97 MB, and with 78 MB stored at 207 MB. The extra memory is native (heap ~9 MB and external
     ~4 MB in both versions) and does not drop over minutes. Skipping the startup scan
     (`packages/server/src/index.ts:274`) brings rc3 back to 98.6 MB.
   - **Cause.** The scan reads every stored value to sum sizes (`packages/server/src/stored.ts:156`), and that
     memory stays resident: about 1.4× the stored bytes. `fillCache: false` made no difference.
   - **Release impact.** Not blocking for small volumes. On a large production volume, idle memory would
     approach the 512 MB limit. Production's `/data` size was not checked (production was out of scope). Fix:
     size documents from table metadata or `approximateSize` instead of reading values, or run the scan in a
     short-lived child process.
   - **During the soak.** The 203 MB right after the restart was not idle (8 clients reconnecting, 5 MB stored),
     and after the soak the server stayed at ~205 MB rather than dropping back (see 2).
4. **Bug: a server without `YPERSISTENCE` logs everyone out within 60 s (should fix; does not affect Fly).**
   `FileStore.loadSessions()` with no sessions file replaces the in-memory sessions with `{}`
   (`packages/server/src/store.ts:112-114`). The 60 s `reconcileSessions()` (`packages/server/src/auth.ts:327`,
   called from `packages/server/src/index.ts:92`) then treats every session as revoked and closes its sockets
   with 4401. Reproduced: a fake login answers `/auth/me` and then "not logged in" 70 s later. This breaks
   `scripts/demo.sh` and volume-less self-hosting (and it invalidated an in-memory comparison run here).
5. **Minor: in-flight hub requests are not failed when the socket closes** (`packages/room-mcp/src/hub-client.ts:310`).
   A post sent just before a disconnect or restart waits the full 10 s timeout and then reports "not sent: hub
   unreachable", even when the hub is back within 2 s. Background posts are re-derived, but a `room_release`
   notice in that window was reported as not sent and is not retried. Not blocking.

Not a finding: posts and claims during a pause were refused as specified ("not done: … coordination is paused").
The client always lapsed its own lease before the hub did (about 43 s against the hub's 45 s).
