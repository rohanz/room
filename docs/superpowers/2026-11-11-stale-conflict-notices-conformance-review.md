## Findings

### 1. P2: coherent contract clean leaves the old notify owed

**Locations:** `packages/room-mcp/src/conflict-set.ts:377–388`; `packages/room-mcp/src/notice-lifecycle.ts:101–110`; `packages/hub-core/src/notice-lifecycle.ts:151–157`.

Contract publication's existing message shape has no `clearedFrom` field. The producer constructs the clearing contract with `priority: fyi`, but the new lifecycle helper decides completeness solely with `'clearedFrom' in body`. It therefore excludes the preceding notify from `end`. The hub accepts/registers the clearing fyi and leaves the original managed notify open and owed. Contract messages are not covered by per-peer merge supersession, so the stale notify is still deliverable.

**Failing test:** `a coherent contract clean ends its prior notify` (new evidence file, line 52). It proves the original was managed, settles clean, verifies the actual fyi contract was appended, then fails because the original has no outcome. The existing contract test (`room-mcp/test/notice-lifecycle.test.ts:241`) exercises explicit grant withdrawal, not evaluated clean. Existing full conflict-set controls do not enable this capability for all their fixtures.

**Smallest correction:** carry the semantic completion reason in the negotiated lifecycle intent, separately from the unchanged contract message shape, and let the hub authorize a complete-clean replacement with that explicit reason. Do not parse the text, add an unnegotiated message field, weaken partial-fyi urgency checks globally or label clean as grant withdrawal. Add real producer and hub checks for that contract-specific operation.

### 2. P2: changing edit evidence from exact to possible loses the association with earlier obligations

**Locations:** `conflict-set.ts:90–94,313–320,345–356,386–403`; `room-mcp/src/notice-lifecycle.ts:103–104,127–137`.

An exact edit-in-claim notice is registered under the slot-key group. A possible result changes `noticeGroup` to owner/other/path/possible; the subsequent clean retains that possible group via `clearedFrom`. Replacement/withdrawal scans only the selected group. The final clean ends the possible notice, but neither the prior exact owner's id nor its `:holder` id is enumerated. Holder cleanup also uses the possible group's holder variant, rather than the group under which the exact holder notice was registered. No reader should reconstruct this relationship: the producer must retain the episode-to-group obligations it actually opened.

**Failing test:** `exact edit overlap followed by possible and clean ends all owner and holder obligations` (line 64). The initial owner/holder notices are both real managed publications. Soft assertions independently show both old ids lack outcomes and both remain owed after clean. This is the production stable per-path key, not a legacy two-claim grouping construction.

**Smallest correction:** retain exact and aggregate episode relationships at the producer/inventory boundary. On complete clean or positive final withdrawal, enumerate every obligation ended by that completed evaluation, including the holder copy, while preserving a possible group if another member is still possible. A stable group alone is not automatically enough for legacy multi-member groups; test both directions of exact/possible transition and a surviving grouped member. Do not infer endings from a representative claim's disappearance.

### 3. P2: cached producer authority survives lease reacquisition and blocks all later transitions for that pair

**Locations:** `room-mcp/src/notice-lifecycle.ts:38–42,69–82,96–110`; `hub-core/src/notice-lifecycle.ts:107–123`.

`producer()` returns its cached pair id before comparing the record's authority to the current lease. The cache is cleared on a hub incarnation change, but not on a participant lease epoch/session change in the same hub. After reacquisition, publication supplies the new live epoch with the old producer id. The hub correctly refuses it with `adopt open notice inventory before changing it`. The helper catches this as a failed publication and retains the same cache. Replays encounter the same failure until the Session/helper is replaced; existing open ids remain owed and new notices/clears for that pair cannot be published through this path.

**Failing test:** `a session with a reacquired lease adopts its existing producer before a clean transition` (line 78). The same authenticated Session acquires a fresh private hub epoch, retaining semantic work and current generation. The run logs the actual adoption-required refusal before failing its clean/outcome assertions. This is a valid hub grant, not a fabricated replicated holder. The test does not require that refusal after a future fix; it asserts successful clean/outcome behavior.

**Smallest correction:** invalidate/revalidate the pair cache on authority change, explicitly adopt open records once under the new live lease, and handle already-transferred records without recopying terminal entries. Preserve the unchanged semantic ids. Add same-session lapse/reacquisition plus separate-session takeover tests through the lifecycle helper; the current raw-hub adoption test alone cannot catch this client failure.

## Stage boundaries and future persistence

The implementation honestly limits capability semantics (`hub-core/src/negotiation.ts:49`) and maintained reference text (`docs/reference.md:41–47`) to the current same-room authoritative hub. It stores no bodies, adds no save-before-ack barrier, does not restore inventory and does not enable managed projected conflicts: `ConflictSet` passes a session only when `team.room === notices.room && owner === team.me.name` (`conflict-set.ts:522–523`). Worker retirement runs for the joined role only (`worker-projector.ts:140`). `:landed`/`:degraded` remain baseline. No unauthorized historical purge or stage-2/3 implementation was found.

The new inventory mirror is diagnostic; private canonical state is a process-local `Map` (`hub-core/lifecycle:67–75`). No root was added to `shared/src/memory.ts`, and `Hub.start` does not restore it. H `lost stage-1 inventory is unknown after a hub restart` (221) checks a second hub against the existing doc and keeps old mail untracked/owed. This is a restart fallback test, not durable replay.

**Can stage 2 persist this state without reshaping?** The record already has a version, exact ids, producer/worker incarnation, accepted revisions/operation digests, urgency/dependencies/deadlines and explicit terminal markers. It can be serialized without stored bodies or redefining subject semantics. However, simply snapshotting/restoring `noticeInventory` is unsound: clients can write the diagnostic mirror; records bind to the old hub generation/epoch/session; adopted records currently spread that old generation; and client `records()` discards generations that do not match the current authority. Stage 2 needs authenticated private export/load, durable authority linkage and an explicit restore/adopt generation transition, protected snapshot integration, validation/bounds, and receipt/outcome/retry-horizon treatment. These require algorithm/authority changes, although no wholesale semantic record reshape is forced by the current same-room fields. Stage 3 will additionally need explicit source/destination room identities/generations and handoff acknowledgements; they are not present here and are not claimed.

Admission has explicit fallback and reserves ending space (`hub-core/lifecycle:163–164,215–222`). Terminal metadata is retained for the hub's lifetime, so registrations can eventually stay on fallback until restart; the reference discloses this. The tested synthetic capacities (112 producer / 913 room ids) are lower than count caps because of bytes/reserve. This is a disclosed stage-1 availability tradeoff, not durable GC or production performance evidence.

### Root correction and transition audit

The producer now states `update` or `complete` in the optional lifecycle intent. Neither the proposer nor hub reads `clearedFrom`, message type or message text to decide completion. Contracts, direct slot notices and peer aggregates use the same explicit transition. The hub permits a complete replacement only with an accepted fyi publication, the exact registered group/episode/ids and the existing private lease, generation, principal, producer, input-revision and expected-revision checks. Owner and holder obligations of that episode end in that publication's transaction; a second holder-withdrawal request is no longer needed. Refused publications have no ending effect. Ordinary update coalescing still uses the actual published urgency, recipient and member; a partial fyi cannot consume notify/interrupt debt.

An edit path has one random semantic episode shared by its members across exact and approximate evidence. Individual exact owner/holder updates and the aggregate possible presentation have separate coalescing members within that episode. A complete evaluation requires every member of that episode to be positively clean. Unknown members, including members whose publication disappears, remain unresolved. A managed `drop(..., 'unavailable')` retains unknown membership instead of deleting it; explicit authority withdrawal remains distinct. Repeated unavailable drops do not rewrite the same unknown marker. Different worker incarnations still get different episodes. Updating an equally urgent notice may supersede the older presentation for that member, as before; completion selects only the exact semantic episode.

The audit also found two related transitions outside the three reported failures. A formerly clean but now unknown slot could replay its old clearing body and authorize an ending after the original clearing post had been refused. An unknown or partially completed aggregate can also share a presentation id with a later complete evaluation. Managed clearing replay now requires current clean evidence; aggregate completion checks all members. A managed complete publication has a distinct deterministic `:complete` id within the random episode, so a prior partial presentation cannot suppress its later completion. This changes managed id values, not the baseline message vocabulary or body fields. Four byte-comparison controls cover merge, edit-in-claim, claims and contract conflict/clean bodies against baseline producers. Partial peer fyi continues to retain the earlier unreceipted notify plus the latest fyi.

Producer cache hits now validate the current lease epoch/session and transferred-record state. Same-Session reacquisition and a genuinely separate Session's takeover explicitly adopt only open inventory under the new private grant. Semantic ids stay unchanged, and terminal entries stay with the closed source. This does not implement inventory restoration after a hub restart.
