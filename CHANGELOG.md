# Changelog

## 0.17.0

Room now has **one room per repository across branches**. Each participant reports their own branch and base, and conflicts are compared at each pair's merge base. The hub grants participant names and orders messages. At-least-once delivery applies to messages retained in a surviving replica's ledger; an acknowledged post can be lost if every replica holding it disappears before persistence. Expiry and caps can remove retained messages. Idle-session wakes contain a pointer, not the message text.

The sharing manifest now describes `declared` as paths of eligible changed files, with text only in your declared area. Ignored, unsafe, oversized and budget-excluded paths remain digest-only. Declared changed files remain shared while they differ from their base, including after `room_done` and daemon restart. The durable worker registry keeps worker ownership and recovery state. The team server and the local relay enforce the same live document cap. `room_close` closes the repository room for every branch.

**Upgrade:** 0.16 and 0.17 cannot share a room. Deploy the 0.17 server, update every plugin, and restart or reconnect sessions together. See [the upgrade guide](docs/upgrading.md), including archived branch-room exports.

**Known limits:** Codex `/quit` can leave a participant name reserved until its lease expires. Everyone admitted to a team room is trusted; finer server permissions remain [future work](docs/roadmap.md). Claims are advisory and inferred contract impact still needs tests.

**0.17.0-rc12** fixes the four medium and high findings of the [all-Codex Werkzeug rehearsal](docs/superpowers/rehearsals/2026-10-02-codex-all.md) (eight Codex workers in a team room; [rc12 dogfood notes](docs/superpowers/rehearsals/2026-10-02-dogfood-rc12.md)).

- **Previews and collect include a worker's commits.** Workers that committed before `room_done` stayed at "updating after a commit; re-run" until they exited, so the lead's eight-way preview applied nothing and ran the tests on the lead's own tree. A worker's branch (`room/<tag>`) has no remote ref, and in a `--single-branch` clone there is no `<remote>/HEAD` either: the worker had no anchor, its base fell back to its HEAD, its manifest never completed, and each commit emptied its published changes. A team-room worker now anchors to its registry-pinned spawn base when teammates can fetch it, else to the newest remote commit under it (an unpushed lead commit or Room's carry commit is on no remote), whenever that is newer than the remote anchor; with neither, to the spawn base, comparable on this machine only. The lead's preview reads its own workers from their worktrees in any room (collect already did), so a worker's committed and uncommitted work is previewed, tested and collected while it is still running or after it exits. When a participant really has no anchor, the preview says so instead of "updating after a commit".
- **Claims on separate lines are not a conflict.** Line ranges were mapped across copies with a quadratic table that gave up past a million cells (a 2,829-line CHANGES.rst), and an unknown owner text mapped to the whole file; `room_claim` then printed `CONFLICT … (approximate lines)` and the before-edit hook `holds CHANGES.rst:1-2829 (approximate whole-file warning)` for regions that did not touch: 19 needless questions. Mapping now strips the common prefix and suffix and diffs only the changed middle (bounded Myers, then the old table; past both bounds, a claim in that middle keeps its holder's numbers, marked approximate). Lines Room cannot map are a plain note in the holder's own numbers ("also holds CHANGES.rst:6-6 in their copy; their lines may have shifted relative to yours"), shown only when those lines are near yours. A whole-file range appears only for a whole-file or folder claim.
- **A failed worker's notice names the host's error.** Two workers died on "Selected model is at capacity" and the lead read `failed: exit 1; Reading additional input from stdin...` (Codex's stderr banner). The notice, `room_state` and collect now quote the host's own error: Codex `turn.failed` (else its last `error` event) or Claude's `is_error` result (else its API error message), falling back to the log tail. A transient model-capacity or rate-limit error says so and how to retry (`room_send` it to resume, or respawn it with `dir=` its worktree when it has no host session).
- **Room tools stay fast with many workers.** With eight workers, `room_spawn` took up to 26.8 s and `room_state` 13.9 s. The lead's Room server was blocked, not busy: every status read probed every worker with three synchronous processes on macOS (`ps`, `sysctl`, `ps`), and status is read on each room change; in a reproduction the lead spent 120 of 316 s in those probes and its own graph index took 75 s. A live process's identity is now read at most once per 2 s (250 ms while it is younger than 5 s and may still `exec` into its host), a dead one is answered by `kill(pid, 0)`, and the boot time is read once a minute. Because a cached read could describe a predecessor on a reused pid, signalling a worker and recording a launch read its identity afresh, and a "dead" or "not ours" verdict on a live pid is confirmed by a fresh read; a confirmed mismatch is kept for that record alone (a process that was gone stays gone), so a host recorded before it exec'd costs one read a minute, not one per status read. The first spawn no longer runs `codex --version` synchronously, a commit's file is read from Git once while cached (claim and conflict reconciles re-read the same base files), and a preview reads each base file once instead of once per participant. `scripts/load-repro.mts` reproduces the rehearsal's load with fake `codex` hosts; on this machine, eight workers went from `room_spawn` max 14.1–17.9 s, `room_state` max 13.8–17.4 s (p50 0.65 s), event-loop stalls up to 4.9 s and 3 of 8 workers reported after 316 s, to `room_spawn` max 2.2 s, `room_state` max 1.9 s (p50 0.25 s), no stalls and all 8 reported in 40 s.

**Unreleased (after rc10): room documents are compacted when the server starts** ([spec](docs/superpowers/specs/2026-10-02-doc-history.md)). The 12-hour soak of rc5 found that a room document keeps its whole Yjs history: about 16 structs per post, so server memory and CPU grew with total traffic, and a restart reloaded all of it.

- **The server compacts a room at its first load after a start.** Past `ROOM_COMPACT_MIN_DELETED` deleted structs (default 10,000, about 3 MB of heap; `0` or `off` disables), it rebuilds the room from its current values under a new `meta.generation` and stores the copy in one atomic write before any client syncs. A failed or interrupted write keeps the old document. Leases, counters and seqs are untouched.
- **Clients state their replica's generation, and a stale replica is refused.** Every Room connection sends `gen` (`fresh` until the replica holds server data) and turns BroadcastChannel off. A replica of an earlier generation is closed with 4409 before any data is exchanged, so old history and duplicated values never come back. room-mcp then rejoins as a host rebind does: same name and session id, its claims and scope kept, the workers room re-attached, retried by the startup join. The web view reloads; `roomagent` exits with code 75 to be restarted.
- **rc clients fail safe.** A client that states no generation keeps working until its room is first compacted, then gets 4403 "update Room to 0.17.0 or later": rc room-mcp stops reconnecting and the rc web view shows the reason.
- **What a compacting restart loses** is what a client restart loses: document writes made between the server stopping and the rejoin, such as a receipt (its message is delivered again) or a tool write already in flight.

**0.17.0-rc10** fixes two findings from leading the rc9 batch, and the two places its own dogfood found those fixes did not reach ([rc10 dogfood notes](docs/superpowers/rehearsals/2026-10-02-dogfood-rc10.md)).

- **Every `room_done` reaches the lead.** A message to a worker that has reported done but whose process is still exiting reaches it in the same run, not as a resume. Its next `room_done` was recorded as already posted and never reached the lead, although the worker was told it had. Each report in a run now has its own completion message (`wk:<worker>:<run>:<n>` from the second on), posted once; a retried `room_done` whose post was refused replaces the unposted report rather than adding one, and a worker's `room_done` calls record and post one at a time. Resumed and `refresh=true` runs already got their own message, and tests now cover all three.
- **A clean overlap is not a CONFLICT.** An edit inside another participant's claim was announced as `CONFLICT` even when the two versions merged cleanly. Room now three-way merges them first: if they merge, both sides get `overlap on <path>: … overlaps <name>'s new claim …; merges cleanly`, and later `overlap cleared`. `CONFLICT` is kept for versions that do not merge, and an overlap that stops merging is announced again as a `CONFLICT` (and as an overlap if it merges again), including for your own running worker's burst of edits.
- **`room_done` says whether the lead was told.** It said "Your lead has been told" without checking. When the run's outcome was already posted (for example as an observed failure), it now says the lead was not sent this report and reads the summary with `room_state`; when the post is refused, it says the report is saved and is posted on the next `room_done`, or by the lead's session when the worker exits.
- **The web view draws a clean overlap as an overlap.** The timeline card, code-line tag, hover and detail said "conflict" / "Unresolved conflict" for every edit-in-claim notice. A span whose editors' latest notices all merge cleanly now reads `overlap` ("Overlap: merges cleanly", in amber); one editor's clean overlap does not hide another's conflict in the same claim.

**0.17.0-rc9** fixes what a single-developer C++/JUCE project (on 0.16.40 and rc8) and the rc8 batch found, and brings the user docs up to date with rc1–rc8 ([rc9 dogfood notes](docs/superpowers/rehearsals/2026-10-01-dogfood-rc9.md)).

- **A room is quiet while you are alone.** A branch note woke an idle solo session and cost it a turn. With no company (your own workers count only for their own notices; your human's messages always pass), nothing wakes the session or reaches its hook inbox. Waiting items appear in `room_state` and the next Room tool reply.
- **Gitignored folders are not walked.** A worker beside a gitignored vendored JUCE tree logged "skipped N file(s)" every 10 s, 95 times, with N varying: the watcher descended every ignored file and counted new ones per window. roomd now asks Git for ignored folders (`ls-files --others --ignored --exclude-standard --directory`, on start, on `.gitignore` changes and every 60 s), does not watch them, and logs one stable summary once per change (`skipped 1 gitignored folder, not watched: libs/JUCE/`). Folders holding tracked files are still descended. On a 3,000-file ignored tree, daemon start went from 7.3 s to 0.2 s and a 300-file build burst there from 24.7 s of reconciles to none. The hot-path throttle now counts only real text changes; before, edits to one file could defer another file's next edit by 30 s.
- **Previews scale with the work, not the checkout.** A preview took 9 s, all of it "merge". Carried untracked files went through the merge even when a worker never touched them, at about 12 Git processes each. They are now left out, carried base reads are cached once per preview, and carried files are hashed in one `git hash-object --stdin-paths`. On a JUCE-shaped fixture with 400 carried files, 58.3 s became 0.65–0.86 s. The slow-tool log shows `merge Nms (git N calls Xms)`.
- **Build logs are worker scratch, not conflicts.** Two workers' `build_before.log` made a hard conflict that blocked the preview's test run and collect. An untracked, never-committed, uncarried `*.log`, `*.tmp`, temp, swap or OS file in a worker is scratch: the preview names it in one line, collect does not bring it in and saves each worker's copy to `.room/scratch/<tag>/` (5 MB per file, 50 MB in all; anything not saved is named). Two workers creating the same new file differently is reported as such, not as a line-range conflict.
- **A stopped worker can take your later commits.** `room_send(to=worker, refresh=true)` rebases the worker's branch onto your HEAD before resuming it, keeping its uncommitted edits, and tells it which commits came in. A conflict changes nothing. Running workers, `dir=` workers, branches with a merge commit, and ignored files where the rebase would write (compared case-insensitively) are refused before any change, with guidance.
- **A long macOS session keeps its Room tools.** The lead's Room server stopped itself with "host session ended" while the lead was alive: a clock correction moved macOS's derived boot time by a second, and Room's process identity (`darwin:<boot>:<start>`) was compared exactly. macOS start times now compare by the process's absolute start, with the boot part allowed to drift by up to a minute, for host liveness, session binding, worker ownership and the local migration.
- **Smaller fixes.** A new worker that reuses a tag is not owed messages addressed to the earlier worker of that name. room_state leaves migrated 0.16 history out of its recent messages (`all=true` shows it), and prints no "nothing owed for an unresolved name" lines. A possible conflict is announced once per teammate and file, naming all their claimed ranges, with one "cleared". Brief-path warnings skip `.room/`, `.git/`, absolute, `~` and URL paths.
- **Docs.** README, the reference, upgrade guide, roadmap, AGENTS.md, deploy guides and skills now cover worker dependency linking, the clean worker shell, background work at exit, the activity line, the relay document cap, export without a stored document, migrated placeholders, the local room migration, Linux process naming and the `full` default.

**0.17.0-rc8** fixes the two medium findings and three low ones from leading the rc7 batch, and is the first batch led on a build with the rc6 and rc7 fixes ([rc8 dogfood notes](docs/superpowers/rehearsals/2026-10-01-dogfood-rc8.md), which confirm or refute each of them in use).

One worker started its suites in the background, ended its turn, and "finished without a report", untested. The worker brief and the room-workers and room-etiquette skills now say: run tests and builds in the foreground and wait for them, then finish with `room_done`. When a Claude worker exits without `room_done`, Room reads its `stream-json` log. Backgrounded `local_bash` tasks with no `task_notification` or terminal `task_updated` before the run's last `result` were still running at exit. The status and the lead's notice then say `ended without a report — background work was still running (N background task(s) killed at exit)`; a follow-up that ends that way says so too. Normal exits, foreground commands, background tasks that finished or were stopped in time, subagents and monitors do not count, and no command text is shown. The worker's `ROOM_WORKER_*` variables, the real `~/.codex` (with Room 0.16.40) and `CLAUDE_PLUGIN_ROOT` then reached the tests. Every package now has a `vitest.config.ts` that reuses the root settings (`vitest.shared.ts`). The setup (`isolateTestEnv`) also clears inherited `CLAUDE_*`, `CODEX_*`, `OIDC_*`, git location, worker launch (`PORT`, `VIRTUAL_ENV`, thread caps) and server variables. Inside a worker, those two suites went from 19 failures to 261/261 from the package directory and from the root.
- **Room's coordination variables stay out of a worker's shell.** The variables Room gives a worker (`ROOM_WORKER_ID`, `ROOM_TOKEN`, `ROOM_REGISTRY` and the rest) are for its Room MCP server. A worker's commands no longer see them; `PORT` and the thread caps stay.
  - Claude workers get a `CLAUDE_ENV_FILE` (`.room/workers/<tag>.env.sh`, 0600, never written through a link). It first runs the lead's own `CLAUDE_ENV_FILE`, if any, then unsets every `ROOM_*` variable before each Bash command. MCP servers and hooks do not run it.
  - Codex workers run with `shell_environment_policy.filters={"ROOM_*"="exclude"}` (Codex 0.146+). Their MCP server still receives its `env_vars` list.
  - Both were checked end to end on Claude Code 2.1.286 and codex-cli 0.159.2 with a probe MCP server.
  - The spawn reply warns where the scrub cannot apply: an env file it could not write, Claude's PowerShell tool on Windows, or Codex older than 0.146.
  - `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` cannot do this: it strips only credentials, and from MCP servers and hooks as well.
- **Smaller fixes.**
  - A new session no longer shows the previous session's `done:` note as its status: sessions publish when they joined, and older notes are ignored.
  - Worker activity labels `env -u … NAME=value prog …` by its program (`running npx vitest`, names and values never shown). Trivial probes (`env`, `pwd`, `ls`, `echo`, …) keep the previous activity instead of reading "running env".
  - `room_collect` now waits up to the promised 15 s for a worker that has reported done but whose process is still exiting. Before, it skipped the worker as running.

**0.17.0-rc7** fixes what leading the rc6 batch on rc5 found ([rc6 dogfood notes](docs/superpowers/rehearsals/2026-10-01-dogfood-rc6.md); this batch's own notes are in [rc7](docs/superpowers/rehearsals/2026-10-01-dogfood-rc7.md)).

- **A worker's tests run the worker's code.** A worker worktree had no `node_modules`, so Node resolved workspace packages through the lead's install to the lead's sources, and a worker's cross-package tests could pass on a change they never ran. At spawn, when the lead has `node_modules`, a lockfile (npm, yarn or pnpm) and Git ignores `node_modules`, the worktree gets its own `node_modules`: links to the lead's installed packages, except that workspace packages (from `workspaces` or `pnpm-workspace.yaml`) link to the worktree's own package directories, and nested per-package `node_modules` are rebuilt the same way. Nothing is installed or copied. It takes 3 s at most. When it cannot link (no lockfile, a workspace pattern it does not expand, a workspace missing from the worktree, a failure or the time limit), it removes what it made, and the spawn reply and the worker's brief say that cross-package tests in the worktree would run the lead's code, and name the packages. For Python, a `VIRTUAL_ENV` in the lead checkout is repointed at the worktree's `.venv`, and editable installs of the lead's sources produce the same warning, with `uv sync` as the fix.
- **An upgraded clone joins the repository room.** A local room choice remembered by 0.16 (`local/<repo>/<branch>`) kept an upgraded clone in that branch room. The first 0.17 join now rewrites it to the repository room and says so once. Custom local names, team choices and choices written by 0.17 are left alone ([upgrade guide](docs/upgrading.md)).
- **0.16 branch notices are never replayed.** The local migration imported 0.16's "you switched to B; the room is for R" notices (13 identical copies arrived on one first command). Migration now drops them and imports identical Room notices once, and delivery never shows one already in a room's bus.
- **Linux names a native Claude correctly.** The native installer runs Claude from a version-named file (`~/.local/share/claude/versions/2.1.286`), and Room named Linux processes by that file, so a live Claude worker was "not ours" and never stopped. Both the relay's process probe and the hook scripts now name a process by `/proc/<pid>/comm`, then `argv[0]` when `comm` is missing or truncated, then the executable, which counts as `claude` under `claude/versions/`.
- **Quieter output.** A `carry=false` spawn mentions the uncommitted changes it left behind once per lead session. room_state's claim summary names the most specific files or directories with counts (`3 claims · packages/room-mcp/src/tools/ (2), packages/shared/src/views.ts (1)`), and its recent messages are cut to one line of up to 160 characters (`room_state all=true` shows them in full). The merge preview reports ignored regenerable build output as one line with a count.
- **A preview right after workers finish is checked.** A finished worker's exit (its last publish and its ended name lease) made the preview report it as moving, and the message named every participant. A finished worker read from its trusted local worktree no longer counts as moving. For running participants the preview waits, at most 12 s, for their changes to stop moving before it reports a move, and it names only those who moved.

**0.17.0-rc6** fixes six things found while running rc5 (a batch led on rc5 itself; [dogfood notes](docs/superpowers/rehearsals/2026-10-01-dogfood-rc6.md)).

- **room_state says what each live worker is doing.** A third worker line such as `editing api/tax.py · 20s ago` comes from the latest tool or file event in the worker's log (Claude `stream-json` tool calls, Codex `--json` items). Labels carry no message text, tool output or arguments and stop at 80 characters; only bytes added since the last read are parsed, at most 512 KB per poll. Both hosts already wrote their logs as they ran; a test now guards that.
- **Spawning with untracked files is fast.** Carry hashed each untracked file with its own `git hash-object` and staged each with its own `update-index`; it now runs one `hash-object --stdin-paths` and one `update-index -z --index-info`, with the same hashes, filters and timeout scaling. With 203 untracked files, preparing the worktree went from about 9 s to 1.2 s; a test checks that the number of git processes does not grow with the file count.
- **Migration resolves names that belong to one person.** A 0.16 name used on several branches became a `?<hash>` placeholder. When the server's audit log shows one GitHub login behind every copy, the name now migrates as itself. A placeholder remains whenever the evidence is incomplete: different logins; any writable join to that branch room without a GitHub identity (open server, shared token, OIDC); or an audit log that is in memory only, malformed, or over its entry or byte bound. room_state lists what is left in plain words: `2 messages and 1 claim for an unresolved name (ben on main or ben on feature/x): ask them to rejoin`.
- **Exporting an archive with no stored document says so.** `/archive/export` used to return 200 with an empty body for a registered branch that was never stored. It now returns 404 `no stored document for <room>`, and `room_export` reports `nothing to export from <room>: …` without writing a file. An empty body from an older server gets the same treatment.
- **The local relay enforces the room size cap.** The server's cap check now lives in one shared rule (`hub-core/src/doc-cap.ts`). The relay uses it for writes to a local room over `ROOM_DOC_MAX_BYTES`: they are closed with 4413 and the server's reason, and reads keep working. Unlike the server, the relay still accepts an over-cap update that inserts nothing, such as a newcomer's empty sync reply or a deletion, so a local room without an operator can shrink. Local sessions now pause and retry after a 4413, as team sessions do (y-websocket treats 44xx closes as final). A 4413 that arrives while a session is still starting is kept and acted on once the session is up; before, it was lost and the session stayed offline.
- **CI and Linux.** CI already ran only on `ubuntu-latest`, but this branch had been tested only on macOS. The job's timeout rises from 20 to 45 minutes. A test that used pid 999999 as a dead process now uses one above Linux's pid limit. Known Linux gaps are in the [rc6 notes](docs/superpowers/rehearsals/2026-10-01-dogfood-rc6.md#linux-readiness-fix-6); the main one is that a natively installed Claude is named by its versioned binary.

**0.17.0-rc4** fixes what a 3-hour staging soak of rc3 found ([soak notes](docs/superpowers/rehearsals/2026-10-01-soak.md)). Correctness held there; resource use did not: CPU grew with the message bus until Fly's shared CPU throttled the server, and resident memory grew.

- **Ledger cost no longer grows with the bus.** The hub keeps running indexes of the bus (ids, bytes, malformed entries) and of owed messages per recipient, updated from each transaction's changed items, local or remote. Admission of an addressed post answers from them, without a trim; the bus is trimmed in batches past a 10% count or byte high-water mark, plus the full pass once a minute; the 1 s re-assertion looks only at ids changed since the last tick, and duplicate lookup is an index hit. States the index cannot decide cheaply (malformed or aliased member entries, duplicates under retention, caps or TTLs at their limits) fall back to the old trim and scan until the next minute's maintenance clears them, and that pass also checks the index against a full recompute and rebuilds it on any drift. Outcomes are unchanged: property tests compare both paths with the old algorithm on random and adversarial documents. Operation counts at 100 / 1,000 / 10,000 bus entries: per post 580 / 5,080 / 27,396 before, 35.9 / 35.5 / 35.4 after (amortised, trims included); per tick 122 / 1,022 / 2,002 before, 2 / 2 / 2 after.
- **Other per-update work no longer grows with the room.** Writes queued behind an in-flight write were stored as a full document snapshot each time, so under steady load every write cost O(document); they are now appended as one merged update, with a snapshot only past the existing size threshold or 128 appended records. In observe mode (the default), the identity guard no longer rebuilds its shadow document from the whole room after every flagged packet; the packet is applied to the room anyway, so the shadow is already in step. A CPU profile of the soak load showed both, and the full-document encode was its largest growing cost.
- **No stored-document scan at startup.** The rc3 startup inventory read every stored value and left about 1.4× the stored bytes resident. It is gone: loads are size-checked lazily as before, and `GET /admin/inventory` sizes documents on request from LevelDB table metadata only. A document is flagged "possibly over" when its tables' bytes, times snappy's best-case ratio plus memtable slack, could exceed the load budget; `updates` is reported as 0 (uncounted). `scripts/room-inventory.mts` still measures exactly. With 60 MB stored, idle RSS falls from 143 MB (rc3) to 62 MB.
- **The image runs compiled JavaScript under plain `node`.** `npm run build:server` bundles the server with esbuild (pinned 0.28.2) in a build stage; the runtime image has neither tsx nor esbuild (about 64 MB of resident processes on staging) and sets `MALLOC_ARENA_MAX=2` against glibc arena fragmentation under LevelDB's threadpool I/O: in a 45-minute A/B soak of one image (512 MB, one core), RSS levelled off at 107–123 MB with it and kept climbing to 211 MB without it. Server CPU stayed at 0.9–1.4% of a core throughout ([mini-soak notes](docs/superpowers/rehearsals/2026-10-01-rc4-mini-soak.md)). `npm run server` now needs `npm run build:server` first; `npm run server:dev` runs the source.
- **A server without `YPERSISTENCE` keeps its logins.** The 60 s session reconciliation treated an in-memory store as empty and logged everyone out (it broke `scripts/demo.sh`).
- **A post in flight when the socket drops is resent, not timed out.** Pending hub requests fail as soon as the socket closes; a post is resent under its id after the reconnect and hello within its original deadline (the hub dedupes by id). Lease operations fail at once, so their callers' recovery runs.
- **Docs:** `GET /admin/inventory` needs the caller in `ROOM_ADMINS`; the offline `scripts/room-inventory.mts` does not.

**0.17.0-rc3** fixes a release blocker found by a migration dry run on a copy of production data: one repository's cutover out-of-memory-killed the whole server (512 MB VM) on every retry, taking every room down with it.

- **Stored snapshots stay bounded.** Cold joins and coalesced writes replace older stored updates with one snapshot in a single atomic write, as does legacy-archive expiry; incremental writes compact after appending more than half the last snapshot or 1 MiB, whichever is larger. Storage failures retain the complete live state for retry.
- **Nothing is decoded before its stored size is known.** Migration, archive listing, idle expiry and websocket joins first check LevelDB's table metadata and refuse a document whose read could touch an oversized table, then sum its stored update bytes with an early exit. Migration never decodes a document above `ROOM_LOAD_MAX_MB` (default 32 MB stored); other cold loads and joins use the larger of that and twice `ROOM_DOC_MAX_MB` (507 `room document too large to load`). A 128 MB-heap regression migrates a production-shaped fixture (a 160 MB never-served key and an oversized branch room) that kills rc2's migration within half a second. A small document sorting just before an oversized level-0 table can be flagged until LevelDB compacts it.
- **Migration takes exactly what 0.16.40 could serve.** 0.16.40 admitted a literal `github.com/<owner>/<repo>` name, bare or followed by `/` and any suffix (including empty), with case aliases matched to the registry, so such keys are migrated and exportable by their exact stored name, `%` escapes included (`feature%2Fx`). Keys with an encoded repository prefix (`github.com%2F…`) were unreachable: they are not migration sources, archives or exports, stay in place, are never loaded or purged automatically, and are listed with size and reason in `migration quarantine:` log lines and the registry entry's `quarantined` list. A migration stuck on such a key in rc2 completes on replay.
- **Oversized rooms stay exportable.** A served branch room over the load budget is left unread (its records counted as skipped) and kept as an archive; an oversized legacy canonical room is copied to its archive record by record. `/archive/export` streams stored updates as length-prefixed frames (`application/vnd.room.updates`) without building a document, and refuses with 507 before any headers when its largest record cannot fit the output budget; `room_export` reads both forms. The client frame ceiling is configurable through `ROOM_EXPORT_MAX_FRAME_MB` (default 64 MB; positive finite values). Stored snapshots are not bound by the websocket message cap, so copy and export allocate up to the largest stored record.
- **Operators see problems before the cutover.** `scripts/room-inventory.mts` is a read-only pre-flight over a stopped or snapshot `YPERSISTENCE` directory: every repository's documents with stored sizes, flagging never-served, unregistered and over-budget documents and oversized LevelDB tables (exit 2). Do not deploy onto a volume with a table over budget as-is. The server logs the same flags at startup; `GET /admin/inventory` returns them to `ROOM_ADMINS`, and `POST /admin/purge` removes one never-served or unregistered document on explicit confirmation. See [the upgrade guide](docs/upgrading.md) and [the runbook](deploy/DEPLOYING.md#purging-quarantined-documents).

**0.17.0-rc2** (the manifests stay at `0.17.0`: the stale-version check reads three-part versions). Two reviews of rc1, security and whole-release, said not to ship; rc2 fixes every must-fix and should-fix, and carries what the unreleased 0.16.41 hotfix fixed.

- **A parent room name can no longer absorb other repositories.** Room names are parsed per namespace before admission: `github.com/<owner>/<repo>`, `git/<host>/<path>`, `local/<name>`. `github.com`, `github.com/<owner>`, `archive:` keys and unknown namespaces get 400. GitHub permission and storage use the same exact `owner/repo`; migration takes only the sources the registry recorded and exact GitHub identities, never an open prefix; closing and archive export stay inside one repository; a registry entry under an invalid name is quarantined at startup.
- **Hub leases belong to their holder.** Renew, release and post need the principal and the session that acquired the lease; knowing the epoch is not enough. The principal is the provider-qualified identity (`github:<login>`, `oidc:<issuer-host>:<sub>`), so two OIDC users with one display name cannot take each other's names. After a restart the hub resumes only the leases it stored itself (its own file per room); a holder record in a room document is never a source of ownership, and a holder the hub did not store reacquires its name.
- **A forged document cannot poison the shared counter or crash the server.** Replica-visible counters are checked against what the durable record could have issued before anything is written; a bad room is quarantined while others start, and a record poisoned by rc1 is repaired. Posts are validated per message type; trim, ledger and expiry skip malformed records; one room's failure is caught per request and per room.
- **Requests are bounded.** Malformed request targets get 400 on the server and the relay, before the relay's key check. Bodies are limited while streaming (64 KiB, 413; 4 MiB for a PR note from a live session), with a deadline and a concurrency bound; PR notes summarise their oldest entries to fit. Holder fields, hub frames, names per login and per room, posts per second, rooms, connections and pending logins all have limits (see [self-hosting](deploy/self-hosting.md)); lease grants and other hub writes count against the document cap. Login, poll, upgrade and ticket endpoints are rate-limited and the GitHub device-flow interval is enforced. Upgrade sockets get an error listener before anything can refuse them. Presence has byte, rate and ID budgets; queued output is budgeted per socket and for the whole process before every send, archive exports included; archive and pull-request calls hold a slot per identity until their work has finished; state requests are limited per connection; view keys are reused, capped and rate-limited; room and connection quotas are reserved before any waiting.
- **Upgrading never widens sharing.** A 0.16 clone's `intent` or `declared` choice is kept as a floor for every participant of that clone (other tags, linked worktrees, workers spawned later), including when Room picks a new tag; an unreadable old choice becomes `intent`, never `full`. An explicit `github.com/<owner>/<repo>/<branch>` room setting from 0.16 joins the repository room with a notice.
- **0.16 clients cannot grow a 0.17 server.** They keep using the rooms 0.16 recorded until the repository is cut over, but cannot open a repository or add a branch; a 0.16 client that sends `ROOM_TOKEN` in the URL is refused at once with the upgrade text; the cutover reads a bounded number of branch rooms and leaves the rest in the archive.
- **Disk-full is a state, not a crash.** A failed document write marks the room failing: new coordination writes are refused (`unavailable`, websocket close 4507, `"storage":"failing"` in `/health`), held names stay held, and the full state is retried with backoff until it is stored; nothing is skipped. Registry and view-key saves retry too.
- **Credentials leave URLs.** On GET requests and websocket upgrades, sessions travel in `Authorization: Bearer` and the shared token in `X-Room-Token`; credentials in a query string are refused. POST and DELETE requests may still carry them in the JSON body. Browser links carry their view key in the URL fragment, which browsers never send to a server, and trade it for a single-use 60-second websocket ticket; responses carry `Referrer-Policy: no-referrer`. Team view links in the old query form still open; a local link from an older build does not (its key is no longer a websocket credential): ask your agent for a new one.
- **The local relay's secret never crosses the network, and its connections are encrypted.** Each websocket to the relay starts with a handshake in which the relay proves possession of the secret, and everything after it is encrypted with keys derived from the secret for that connection; a process that takes over the relay's old port, or holds a connection open across a takeover, learns nothing and can alter nothing. Local browser links carry a read-only, room-scoped key derived from the secret, not the secret, and open a self-contained viewer file installed with the plugin (`file://…/viewer.html#…`): the relay's port serves no page or script any more, so a link in the old `http://127.0.0.1:<port>/…` form no longer opens.
- **Revoked access ends live connections.** Logout and session expiry close that session's sockets (4401), including a connection still being admitted; an expired or revoked view key closes its sockets (4403); push permission is rechecked every 10 minutes (`ROOM_REVALIDATE_MINUTES`); a GitHub rate limit during a recheck is treated as unavailable and keeps the connection.
- **Also:** static files are contained by real path; OIDC admins are matched by `oidc:<issuer-host>:<sub>` only; the image installs `tsx` from the lockfile; the disk scan keeps text only up to the publication budget; the local snapshot is fsynced before migration progress is recorded; `room doctor` verifies the saved credential with the server and checks the server's schema and hub protocol.
- **An older Room session holding the relay port is named, not called “something else”.** When the room's usual port answers as a Room relay of any version (an idle 0.16 session, or one with another key), the join reply, `room_state` and `room doctor` say “an older Room session (pid N, started …) still holds this room's relay on 127.0.0.1:<port>; quit it or reconnect Room there”, for as long as this session runs its relay on another port.
- **The skip summary is logged when it changes.** “skipped N file(s) (…)” appears when the set of skipped paths or their reasons changes, and at most hourly after that, not on every reconcile.
- **The standalone `roomd` command is gone.** A daemon started on its own holds no hub name, so 0.17 readers rejected what it published. roomd runs inside a session: the plugin, or `roomagent`.
- **Rollback is a volume restore.** A 0.16 server cannot serve a volume 0.17 has migrated: take a volume snapshot before deploying. [The upgrade guide](docs/upgrading.md) has the commands.
- **Operators:** set `ROOM_TRUST_PROXY=true` behind a reverse proxy (`deploy/fly.toml` does), or every user shares one rate-limit bucket.

## 0.6.0 — 2026-09-15

The day after the hackathon. Everything below was built, reviewed (four passes, alternating Fable and Codex) and live-tested.

**Rooms**
- Local rooms by default: no server, no account. A relay next to the clone; the browser view is served from it on a same-machine link.
- Rooms by instruction: "join the team room" / "work locally", remembered per clone. The hosted server is opt-in (`ROOM_SERVER=hosted`).
- Repos are opened once (`room_create`), then every branch has a room. Repos idle for 30 days close themselves; `room_close` for now.
- Folder-scoped areas from CODEOWNERS; room state and the inbox are filtered to your areas.
- Sharing levels: `intent`, `declared`, `full`; a server ceiling; the bridge never widens what a lead publishes.

**Workers**
- `room_spawn` / `room_dismiss`: a lead dispatches Claude Code or Codex workers into worktrees, coordinated through the room; `room_done` wakes the lead.
- A lead in a team room can keep its workers in a local room (the bridge): the team sees one participant.

**Identity and access**
- GitHub device login; the server holds the token, clients keep an opaque session. Push access required; public repos are not open rooms.
- Principals: `{name, kind: human|agent|bot|ci, owner, label}`; names bound to the verified login; one person can run several agents (`ROOM_TAG`).
- OIDC login, audit log, Postgres option, self-hosting guide. Forwarded GitHub tokens are refused everywhere.

**Coordination**
- Automatic conflict notices: editing inside someone's claim, or a file that no longer merges cleanly, posts an interrupt.
- Reliable wake-ups: retries, freshness checks, Claude Code channel.
- Pull requests appear as participants; `room_pr_note` posts the room's story to the PR.

**Server hardening**
- Read-only view links, message and document size caps, graph snapshot throttling, idle expiry. Runbook in `deploy/DEPLOYING.md`.

**Internals**
- Session registry (a process can hold several rooms), stable worker ids, tools split by concern, message kinds registry, shared views for browser and agent, one config resolver, the relay in its own package.
